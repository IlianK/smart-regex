\section{Syntax}
\label{sec:regex-syntax}

Let $\Sigma$ be an alphabet. Regular expressions over $\Sigma$ are
defined inductively by the grammar
\begin{equation}\label{eq:regex-grammar}
r,s ::= x \mid \varepsilon \mid \emptyset
      \mid r+s \mid r\cdot s \mid r^*
\qquad (x\in\Sigma).
\end{equation}

Here, $x$ denotes a literal symbol, $\varepsilon$ the expression matching
only the empty word, and $\emptyset$ the expression matching no word.
The operators $+$, $\cdot$, and $^*$ denote alternation, concatenation,
and Kleene star, respectively. Concatenation is often written implicitly,
so $rs$ denotes $r\cdot s$.

Unless parentheses are shown explicitly, Kleene star binds most tightly,
followed by concatenation, followed by alternation. Thus, for example,
$ab^*c$ is parsed as $(a\cdot(b^*))\cdot c$, while $a+bc^*$ is parsed as
$a+(b\cdot(c^*))$.

At the language level, $+$ and $\cdot$ are associative: different
groupings denote the same language. For example,
$L((r+s)+t)=L(r+(s+t))$ and
$L((r\cdot s)\cdot t)=L(r\cdot(s\cdot t))$. The grouping determines the
\emph{syntax tree} on which the algorithms operate. We therefore use left
association for both operators: $r+s+t$ means $(r+s)+t$, while $rst$
means $(rs)t$.

The grammar omits operators such as one-or-more, optional, and bounded
repetition ($r^+$, $r?$, and $r^{\{m,n\}}$). These operators can be
expressed using the six core constructs. For example,
$r^+=r\cdot r^*$ and $r?=r+\varepsilon$. Bounded repetition can be
expanded as

\[
r^{\{m,n\}} =
\underbrace{r\cdot\ldots\cdot r}_{m\text{ times}}
\cdot
\underbrace{(r+\varepsilon)\cdot\ldots\cdot(r+\varepsilon)}
           _{n-m\text{ times}}.
\]

Thus, these convenience operators do not add expressive power to the
core syntax. In the implementation, expressions using such operators
are translated into the six core constructs before they are processed
by the parsing algorithms; the translation from external regular
expression syntax to this internal representation is described in
Chapter~\ref{sec:frontend}.

As a running example, consider the regular expression for binary strings
ending in \texttt{"01"}. Over $\Sigma=\{0,1\}$, let
\begin{equation}\label{eq:r01-def}
r_{01} = (0+1)^*\cdot0\cdot1.
\end{equation}

The expression consists of a Kleene star applied to the alternation
$0+1$, followed by the literals $0$ and $1$. By the precedence and
left-association rules, its syntax tree is
$((0+1)^*\cdot0)\cdot1$. The algorithms operate on this syntax tree, with
each node corresponding to one of the constructs in the grammar.

\section{Semantics}
\label{sec:regex-semantics}

The syntax above describes the \emph{shape} of a regular expression,
while its semantics determines the language it denotes. A \emph{word}
over $\Sigma$ is a finite sequence of symbols from $\Sigma$. The set of
all words over $\Sigma$, including the empty word $\varepsilon$, is
denoted by $\Sigma^*$.

For a regular expression $r$, write $L(r)$ for the language denoted by
$r$, where $L(r)\subseteq\Sigma^*$. The semantics is defined by structural
recursion on $r$:

\begin{equation}\label{eq:semantics}
\begin{aligned}
L(x) &= \{x\}, \\
L(\varepsilon) &= \{\varepsilon\}, \\
L(\emptyset) &= \emptyset, \\
L(r+s) &= L(r)\cup L(s), \\
L(r\cdot s) &= \{vw \mid v\in L(r),\ w\in L(s)\}, \\
L(r^*) &= \{\varepsilon\}
          \cup
          \{w_1\cdots w_n
            \mid n\geq 1,\ w_1,\ldots,w_n\in L(r)\}.
\end{aligned}
\end{equation}

Some simple examples are shown in Table~\ref{tab:lang-examples}.

\begin{table}[ht]
\centering
\begin{tabular}{cc}
\hline
Expression & Language \\
\hline
$a$ & $\{a\}$ \\
$\varepsilon$ & $\{\varepsilon\}$ \\
$\emptyset$ & $\emptyset$ \\
$a+b$ & $\{a,b\}$ \\
$ab$ & $\{ab\}$ \\
$a^*$ & $\{\varepsilon,a,aa,aaa,\ldots\}$ \\
\hline
\end{tabular}
\caption{Examples of regular expressions and their denoted languages.}
\label{tab:lang-examples}
\end{table}

A word $w$ \emph{matches} a regular expression $r$ when
$w\in L(r)$. Determining whether this holds is the \emph{membership
problem}.

For the running example, $L(0+1)=\{0,1\}$, so
$L((0+1)^*)=\{0,1\}^*$. Concatenating this language with
$L(0)=\{0\}$ and $L(1)=\{1\}$ gives

\begin{equation}\label{eq:r01-language}
L(r_{01}) = \{\, w\cdot0\cdot1 \mid w\in\{0,1\}^* \,\}.
\end{equation}

Thus, $L(r_{01})$ is exactly the set of binary strings ending in
\texttt{"01"}, including \texttt{"01"}, \texttt{"001"}, and
\texttt{"1101"}. The empty string is not in $L(r_{01})$, since every
word in the language ends with the two symbols $0$ and $1$.

An expression therefore has both a syntactic structure and a meaning:
the syntax determines how the expression is constructed, while its
semantics determines the language it denotes. Different syntax trees may
denote the same language. This distinction is important for the
algorithms developed later: the algorithms manipulate regular
expressions and their syntax trees, while $L(r)$ gives the set of words
represented by the expression.

\section{Rust Implementation}
\label{sec:regex-rust-implementation}

The grammar above is represented directly as a Rust enum
\citep{rust-book-enums,rust-reference-enum}, with one variant for each
syntactic construct:

\begin{verbatim}
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub enum Regex {
    Phi,
    Eps,
    Lit(char),
    Seq(Box<Regex>, Box<Regex>),
    Alt(Box<Regex>, Box<Regex>),
    Star(Box<Regex>),
}
\end{verbatim}

The variants correspond directly to the grammar: \texttt{Phi},
\texttt{Eps}, and \texttt{Lit} represent $\emptyset$, $\varepsilon$,
and literals, while \texttt{Seq}, \texttt{Alt}, and \texttt{Star}
represent concatenation, alternation, and Kleene star.

For example, the running example
$r_{01}=(0+1)^*\cdot0\cdot1$ is represented by an expression tree whose
root is the concatenation of $(0+1)^*\cdot0$ and $1$, following the
left-associated grouping from Section~\ref{sec:regex-syntax}. Its
structure is:

\begin{equation}\label{eq:r01-tree}
\operatorname{Seq}\bigl(
    \operatorname{Seq}(
        \operatorname{Star}(
            \operatorname{Alt}(0,1)
        ),
        0
    ),
    1
\bigr).
\end{equation}

The same structure is represented in Rust by nested enum values. The
outermost \texttt{Seq} represents the final concatenation with $1$, and
its left child represents $(0+1)^*\cdot0$. Thus, the Rust value stores
the parsed structure of the expression directly, rather than only its
textual notation such as $(0+1)^*\cdot0\cdot1$. Since a regular
expression can contain other regular expressions, these nested values
allow functions on \texttt{Regex} to be defined recursively as well.

The recursive variants use \texttt{Box<Regex>} because Rust requires
recursive types to have a finite size. A definition such as
\texttt{Seq(Regex, Regex)} would have no finite size, since each
\texttt{Regex} could contain another recursively. \texttt{Box<Regex>}
provides the required indirection by storing the recursive value
separately \citep{rust-book-box,rust-reference-recursive-types}.

This explicit indirection differs from the Haskell specification on
which the implementation is based. Haskell allows recursive algebraic
data types without an explicit \texttt{Box}-like constructor, whereas
Rust requires the indirection because enum sizes must be known at
compile time. The Rust representation therefore makes the heap-based
structure of recursive expressions explicit, which is relevant to
memory behaviour.

The Rust representation also derives several standard traits.
\texttt{Debug} supports inspection, \texttt{Clone} allows duplication,
and \texttt{Eq} and \texttt{Hash} allow \texttt{Regex} to be used as a
\texttt{HashSet} key. The latter are required by the partial-derivative
implementation, which stores sets of residual expressions
\citep{rust-book-derivable-traits,rust-hashmap,rust-hash}.

Rust's \texttt{match} expressions are checked for exhaustiveness by the
compiler \citep{rust-book-match,rust-reference-match}. Thus, a function
defined by matching on \texttt{Regex} must account for every syntactic
construct of the grammar. This makes the Rust implementation closely
follow the mathematical definition: each case of the grammar has a
corresponding case in the implementation.
