\section{Syntax}
\label{sec:regex-syntax}

Let $\Sigma$ be an alphabet. Regular expressions over $\Sigma$ are
defined inductively by the grammar:
\begin{equation}\label{eq:regex-grammar}
r,s ::= x \mid \varepsilon \mid \emptyset
      \mid r+s \mid r\cdot s \mid r^*
\qquad (x\in\Sigma).
\end{equation}

In the grammar, $r$ and $s$ range over regular expressions, while $x$
ranges over the alphabet $\Sigma$ and denotes an arbitrary symbol, for example
$a$, $b$, or $c$. The expression $\varepsilon$ matches only the empty
word, while $\emptyset$ matches no words. The operators $+$, $\cdot$,
and $^*$ denote alternation, concatenation, and Kleene star,
respectively. 

Concatenation is written implicitly, so $rs$ denotes $r \cdot s$.
Given this notation, we adopt the usual precedence and associativity
conventions. Unless parentheses are shown explicitly, Kleene star binds
most tightly, followed by concatenation, followed by alternation. Thus
$ab^*c$ is parsed as $(a\cdot(b^*))\cdot c$, while $a+bc^*$ is parsed
as $a+(b\cdot(c^*))$. For repeated operators we use left association, so
$a+b+c$ means $(a+b)+c$, and $abc$ means $(ab)c$.

The grammar above is the core syntax.
It omits the convenience operators found in most regular
expression libraries, such as one-or-more, optional, and bounded
repetition ($r^+$, $r?$, and $r^{\{m,n\}}$). These operators do not add
expressive power, since each can be expressed using the constructs of
Equation~\eqref{eq:regex-grammar}. For example, $r^+=r\cdot r^*$ and
$r?=r+\varepsilon$. Bounded repetition expands to:
\[
r^{\{m,n\}} =
\underbrace{r\cdot\ldots\cdot r}_{m\text{ times}}
\cdot
\underbrace{(r+\varepsilon)\cdot\ldots\cdot(r+\varepsilon)}
           _{n-m\text{ times}}
\qquad (m\le n).
\]

In the implementation, expressions using such operators are translated
into the core constructs before they reach the parsing algorithms. The
translation from external regular expression syntax to this internal
representation is described in Chapter~\ref{sec:frontend}.

As a running example, consider the regular expression over
$\Sigma=\{0,1\}$
\begin{equation}\label{eq:r01-def}
r_{01} = (0+1)^*\cdot0\cdot1.
\end{equation}
By the conventions above, its syntax tree is
$((0+1)^*\cdot0)\cdot1$. This tree captures how the expression is
constructed: a Kleene star applied to the alternation $0+1$, followed by
the concatenation with the literals $0$ and $1$.

To determine what the expression means, its syntactic structure must be
given a semantic interpretation. The interpretation assigns a language
to each part of the expression, with the meaning of a larger expression
determined from the meanings of its subexpressions.

\section{Semantics}
\label{sec:regex-semantics}

The syntax above describes the shape of a regular expression. A
\emph{word} over $\Sigma$ is a finite sequence of symbols from
$\Sigma$. The set of all words over $\Sigma$, including the empty word
$\varepsilon$, is denoted by $\Sigma^*$. A \emph{language} over
$\Sigma$ is a subset of $\Sigma^*$.

The \emph{semantics} of a regular expression assigns to its syntactic
structure a language. For a regular expression $r$, we write $L(r)$ for
the language denoted by $r$, where $L(r)\subseteq\Sigma^*$. The
assignment follows the structure of the syntax tree by
\emph{structural recursion} on $r$.

\begin{equation}\label{eq:semantics}
\begin{aligned}
L(x) &= \{x\}, \\
L(\varepsilon) &= \{\varepsilon\}, \\
L(\emptyset) &= \emptyset, \\
L(r+s) &= L(r)\cup L(s), \\
L(r\cdot s) &= \{vw \mid v\in L(r),\ w\in L(s)\}, \\
L(r^*) &= \{\varepsilon\}
          \cup
          \{w_1\cdots w_n
            \mid n\geq 1,\ w_1,\ldots,w_n\in L(r)\}.
\end{aligned}
\end{equation}

Because $L(r+s)=L(r)\cup L(s)$ and set union is associative, the
groupings $a+(b+c)$ and $(a+b)+c$ denote the same language, even though
they correspond to different syntax trees. The same holds for $\cdot$,
since concatenation of languages is associative.

\begin{table}[ht]
\centering
\begin{tabular}{cc}
\hline
Expression & Language \\
\hline
$a$ & $\{a\}$ \\
$\varepsilon$ & $\{\varepsilon\}$ \\
$\emptyset$ & $\emptyset$ \\
$a+b$ & $\{a,b\}$ \\
$ab$ & $\{ab\}$ \\
$a^*$ & $\{\varepsilon,a,aa,aaa,\ldots\}$ \\
\hline
\end{tabular}
\caption{Languages denoted by basic expressions; $L(\emptyset)$ is 
the empty language, while $L(\varepsilon)$ contains the empty word.}
\label{tab:lang-examples}
\end{table}

A word $w$ \emph{matches} a regular expression $r$ if $w\in L(r)$.
Determining whether this holds is the \emph{membership problem}.

For the running example, $L(0+1)={0,1}$, and hence
$L((0+1)^*)={0,1}^*$. Concatenating this language with
$L(0)={0}$ and $L(1)={1}$ gives
\begin{equation}\label{eq:r01-language}
L(r_{01}) = {, w\cdot0\cdot1 \mid w\in{0,1}^* ,}.
\end{equation}
Thus, $L(r_{01})$ is exactly the set of binary strings ending in
\texttt{"01"}, including \texttt{"01"}, \texttt{"001"}, and
\texttt{"1101"}, but not the empty string.

\paragraph{In Rust.}
\label{sec:regex-rust-implementation}
The grammar above is represented directly as a Rust enum
\citep{rust-book-enums,rust-reference-enum}, shown in
Figure~\ref{fig:regex-enum}, with one variant for each syntactic
construct.

\begin{figure}[ht]
\begin{verbatim}
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub enum Regex {
    Phi,                          // empty language
    Eps,                          // empty word
    Lit(char),                    // literal x
    Seq(Box<Regex>, Box<Regex>),  // r . s
    Alt(Box<Regex>, Box<Regex>),  // r + s
    Star(Box<Regex>),             // r*
}
\end{verbatim}
\caption{The internal regular-expression type, with one variant for
each construct of Equation~\eqref{eq:regex-grammar}. This is the
representation every algorithm in this thesis operates on.}
\label{fig:regex-enum}
\end{figure}

The derived traits also support the operations used by the later
algorithms. \texttt{Clone} allows expressions to be duplicated when a
derivative needs to retain an existing subexpression, while
\texttt{PartialEq} and \texttt{Eq} provide structural equality for
comparing expression trees. \texttt{Hash} makes the same structural
representation usable as a key in a \texttt{HashSet}, which is required
by the partial-derivative matcher.

The variants correspond one to one with the grammar: \texttt{Phi},
\texttt{Eps} and \texttt{Lit} represent $\emptyset$, $\varepsilon$ and
literals, while \texttt{Seq}, \texttt{Alt} and \texttt{Star} represent
concatenation, alternation and Kleene star. The type carries no
operator precedence and no associativity, because both were already
resolved when the syntax tree was built: a \texttt{Seq} node holds two
children and says nothing about how the original notation grouped them.

For example, the running example
$r_{01}=(0+1)^*\cdot0\cdot1$ is represented by an expression tree whose
root is the concatenation of $(0+1)^*\cdot0$ and $1$, following the
left-associated grouping from Section~\ref{sec:regex-syntax}. Its
structure is:

\begin{equation}\label{eq:r01-tree}
\operatorname{Seq}\bigl(
    \operatorname{Seq}(
        \operatorname{Star}(
            \operatorname{Alt}(0,1)
        ),
        0
    ),
    1
\bigr).
\end{equation}

The same structure is represented in Rust by nested enum values. The
outermost \texttt{Seq} represents the final concatenation with $1$, and
its left child represents $(0+1)^*\cdot0$. Thus, the Rust value stores
the parsed structure of the expression directly, rather than only its
textual notation such as $(0+1)^*\cdot0\cdot1$. Since a regular
expression can contain other regular expressions, these nested values
allow functions on \texttt{Regex} to be defined recursively as well.

The recursive variants use \texttt{Box<Regex>} because Rust requires
recursive types to have a finite size. A definition such as
\texttt{Seq(Regex, Regex)} would have no finite size, since each
\texttt{Regex} could contain another recursively. \texttt{Box<Regex>}
provides the required indirection by storing the recursive value
separately \citep{rust-book-box,rust-reference-recursive-types}.

This explicit indirection differs from the Haskell specification on
which the implementation is based. Haskell allows recursive algebraic
data types without an explicit \texttt{Box}-like constructor, whereas
Rust requires the indirection because enum sizes must be known at
compile time. The Rust representation therefore makes the heap-based
structure of recursive expressions explicit, which is relevant to
memory behaviour.

\paragraph{Constructors.}

Constructing recursive expressions directly requires explicit
\texttt{Box::new} calls, so the implementation provides four constructors
that encapsulate the boxing, shown in Figure~\ref{fig:regex-constructors}.
All subsequent implementations in Chapter~\ref{sec:derivatives} use them
to construct regular expressions.

\begin{figure}[ht]
\begin{verbatim}
impl Regex {

    pub fn seq(r: Regex, s: Regex) -> Regex {
        Regex::Seq(Box::new(r), Box::new(s))
    }

    pub fn alt(r: Regex, s: Regex) -> Regex {
        Regex::Alt(Box::new(r), Box::new(s))
    }

    pub fn star(r: Regex) -> Regex {
        Regex::Star(Box::new(r))
    }

    pub fn lit(c: char) -> Regex {
        Regex::Lit(c)
    }

}
\end{verbatim}
\caption{The four constructors. Each builds the corresponding
\texttt{Regex} variant and performs the boxing required by the recursive
representation.}
\label{fig:regex-constructors}
\end{figure}

The constructors are structural: they perform no simplification or
semantic transformation. For example,
\texttt{Regex::seq(Regex::Eps, r)} constructs a \texttt{Seq} node with
an \texttt{Eps} left child rather than simplifying to $r$. This differs
from the \emph{*smart*} constructor introduced later, which can inspect
its operands and avoid redundant expressions.

The constructors take their arguments by value, so building an expression
bottom-up moves its subexpressions into the boxes rather than copying
them. The running example is constructed as follows:

\begin{verbatim}
Regex::seq(
    Regex::seq(
        Regex::star(Regex::alt(Regex::lit('0'), Regex::lit('1'))),
        Regex::lit('0'),
    ),
    Regex::lit('1'),
)
\end{verbatim}

This value has the structure of Equation~\eqref{eq:r01-tree} and is
produced by the frontend of Chapter~\ref{sec:frontend} for the surface
pattern \texttt{"(0|1)*01"}.
