\chapter{Regular Expressions}
\label{sec:regular-expressions}


\section{Syntax}
\label{sec:regex-syntax}

Over an alphabet $\Sigma$, regular expressions are defined inductively
by the grammar
\begin{equation}\label{eq:regex-grammar}
r,s ::= x \mid \varepsilon \mid \emptyset
      \mid r+s \mid r\cdot s \mid r^*
\qquad (x\in\Sigma).
\end{equation}

Here $x$ denotes a literal symbol, $\varepsilon$ the expression matching
only the empty word, and $\emptyset$ the expression matching no word.
The operators $+$, $\cdot$, and $^*$ denote alternation, concatenation,
and Kleene star, respectively. Concatenation is often written implicitly,
so $rs$ denotes $r\cdot s$.

Unless parentheses are shown explicitly, Kleene star binds most tightly,
followed by concatenation, followed by alternation. Thus, for example,
$ab^{*}c$ is parsed as $(a \cdot (b^{*})) \cdot c$, and $a + bc^{*}$ is
parsed as $a + (b \cdot (c^{*}))$, not $(a+b) \cdot (c^{*})$.

Both $+$ and $\cdot$ are associative at the language level, meaning that
different groupings denote the same language. For example,
$L((r+s)+t)=L(r+(s+t))$ and
$L((r\cdot s)\cdot t)=L(r\cdot(s\cdot t))$. The grouping
determines the \emph{syntax tree} on which the algorithms operate.
Therefore, both operators associate to the \emph{left}:
$r+s+t$ means $(r+s)+t$, while $rst$ means $(rs)t$.

The grammar deliberately omits convenience operators such as one-or-more,
optional, and bounded repetition ($r^+$, $r\,?$, $r^{\{m,n\}}$). These
can be expressed using the six core constructs. For example,
$r^+=r\cdot r^*$, $r\,?=r+\varepsilon$, and
\[
r^{\{m,n\}} =
\underbrace{r\cdot\ldots\cdot r}_{m\text{ times}}
\cdot
\underbrace{(r+\varepsilon)\cdot\ldots\cdot(r+\varepsilon)}_{n-m\text{ times}}.
\]
Thus, the omission does not restrict the expressiveness of the core
syntax. Chapter~\ref{sec:frontend} (Section~\ref{sec:frontend-translate})
goes into detail of the complete desugarings.


As a running example, consider the problem of recognizing binary strings
that end in \texttt{"01"}. Over $\Sigma=\{0,1\}$, this language is
described by
\begin{equation}\label{eq:r01-def}
r_{01} = (0+1)^*\cdot0\cdot1.
\end{equation}

Here $(0+1)$ is an alternation of the two literals $0$ and $1$, and
$(0+1)^*$ permits any finite sequence of binary symbols. The expression
then concatenates this sequence with $0$ and $1$, so the final two symbols
must be \texttt{"01"}. For example, it matches \texttt{"01"},
\texttt{"001"}, and \texttt{"1101"}, but not \texttt{"0"} or
\texttt{"110"}. By the precedence and left-associativity rules above, its
syntax tree is structured as $((0+1)^*\cdot0)\cdot1$. This tree, rather
than the expression's textual representation, is the structure operated
on by the algorithms.

\section{Semantics}
\label{sec:regex-semantics}

The syntax above describes the \emph{shape} of an expression; the
semantics assigns each expression the \emph{language} it denotes. For a
regular expression $r$, write $L(r)$ for the set of words it matches.
The semantics is defined by structural recursion on $r$:

\begin{equation}\label{eq:semantics}
\begin{aligned}
L(x) &= \{x\} \\
L(\varepsilon) &= \{\varepsilon\} \\
L(\emptyset) &= \{\} \\
L(r + s) &= L(r) \cup L(s) \\
L(r \cdot s) &= \{v w \mid v \in L(r),\ w \in L(s)\} \\
L(r^{*}) &= \{\varepsilon\} \cup \{w_1 \cdots w_n \mid w_1, \ldots, w_n \in L(r),\ n \geq 1\}
\end{aligned}
\end{equation}

Table~\ref{tab:lang-examples} illustrates the distinction between an
expression and the language it denotes, applying
Equation~\eqref{eq:semantics} to six small cases.

\begin{table}[ht]
\centering
\begin{tabular}{cc}
\hline
Expression & Language \\
\hline
$a$ & $\{a\}$ \\
$\varepsilon$ & $\{\varepsilon\}$ \\
$\emptyset$ & $\emptyset$ \\
$a+b$ & $\{a,b\}$ \\
$ab$ & $\{ab\}$ \\
$a^{*}$ & $\{\varepsilon,a,aa,aaa,\ldots\}$ \\
\hline
\end{tabular}
\caption{Six expressions and the languages Equation~\eqref{eq:semantics}
assigns them. Different expressions may denote related or identical sets
of words, while the semantics assigns a precise language to each.}
\label{tab:lang-examples}
\end{table}

The distinction between an expression and its denoted language is
important for the algorithms developed later. Derivative operations are
defined syntactically over regular expressions, while their correctness
is understood in terms of the languages those expressions denote.

A word $w$ \emph{matches} $r$ exactly when $w \in L(r)$. This is the
membership problem.

Unwinding the semantics for the running example, $L(0+1) = \{0,1\}$, so
$L((0+1)^{*})$ is the set of all finite binary strings, including the
empty string. Concatenating with $L(0) = \{0\}$ and then $L(1) = \{1\}$
restricts this to

\begin{equation}\label{eq:r01-language}
L(r_{01}) = \{\, w \cdot 0 \cdot 1 \mid w \in \{0,1\}^{*} \,\},
\end{equation}

i.e.\ exactly the binary strings ending in \texttt{"01"} like \texttt{"01"},
\texttt{"001"}, \texttt{"1101"}, and so on. In particular, the empty
string is not matched, since every word in $L(r_{01})$ contains the final
literal $0$ followed by the literal $1$.


So an expression has both a syntactic structure and a meaning:
the syntax determines how the expression is constructed, while its
semantics, determines the language it
denotes. Different syntax trees may therefore describe the same language.
The distinction between an expression and its denoted language is
important for the algorithms developed later. The derivative algorithms
transform regular expressions themselves, rather than their denoted
languages. For example, consuming $a$ from the expression $ab$ produces
the residual expression $b$, whose language is $\{b\}$. Thus, the
algorithms operate on expressions, while $L(r)$ describes the language
represented by each resulting expression.



\section{Rust Implementation}
\label{sec:regex-rust-implementation}

The grammar above is represented directly as a Rust enum, mirroring each
syntactic construct one to one. Rust enums define a type by enumerating
its possible variants, and are commonly used together with pattern
matching to distinguish between those variants
\citep{rust-book-enums,rust-reference-enum}.

\begin{verbatim}
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub enum Regex {
    Phi,
    Eps,
    Lit(char),
    Seq(Box<Regex>, Box<Regex>),
    Alt(Box<Regex>, Box<Regex>),
    Star(Box<Regex>),
}
\end{verbatim}


In this representation, each production of the grammar corresponds to
one enum variant. For example, \texttt{Phi} represents $\emptyset$,
\texttt{Eps} represents $\varepsilon$, \texttt{Lit} represents a literal
symbol, and the remaining variants represent the three recursive
constructs. 

For example, the running example $r_{01} = (0+1)^{*} \cdot 0 \cdot 1$
is represented structurally by an expression tree whose root is a
concatenation, with $(0+1)^{*} \cdot 0$ and $1$ as its subexpressions,
the same left-associated grouping fixed in
Section~\ref{sec:regex-syntax}. Its structure is
Equation~\eqref{eq:r01-tree}:

\begin{equation}\label{eq:r01-tree}
\operatorname{Seq}\bigl(
    \operatorname{Seq}(
        \operatorname{Star}(
            \operatorname{Alt}(0,1)
        ),
        0
    ),
    1
\bigr).
\end{equation}

Thus, the Rust value is not merely a string representation of the regular
expression; it is a tree that directly represents its syntactic
structure. This structural representation allows operations to be
defined recursively over the expression.

Rust's \texttt{match} expressions are checked for exhaustiveness by the
compiler, meaning that every possible pattern must be covered either
explicitly or through a wildcard pattern
\citep{rust-book-match,rust-reference-match}. This mirrors the structural
guarantee provided by the inductive definition of $r$ in
Section~\ref{sec:regex-syntax}: a function defined by cases on $r$ must
account for every possible form of $r$.

The derived traits support operations used throughout the implementation.
The \texttt{derive} attribute generates implementations of supported
traits for the annotated type
\citep{rust-book-derivable-traits}. In particular, \texttt{Debug}
facilitates inspection of expressions, \texttt{Clone} allows expressions
to be duplicated when required, and \texttt{PartialEq}, \texttt{Eq}, and
\texttt{Hash} allow expressions to be compared and used as keys in
hash-based collections. Rust's \texttt{HashMap}, for example, requires
its key type to implement both \texttt{Eq} and \texttt{Hash}
\citep{rust-hashmap,rust-hash}.
The variants \texttt{Phi} and \texttt{Eps} carry no data, corresponding
directly to $\emptyset$ and $\varepsilon$, while \texttt{Lit} stores the
literal symbol $x$. In the implementation, literal symbols are
represented using Rust's \texttt{char} type and therefore correspond to
Unicode scalar values \citep{rust-char}.

The recursive constructs, \texttt{Seq}, \texttt{Alt}, and
\texttt{Star} require explicit indirection in Rust. A recursive type
must have a finite size, so a definition such as
\texttt{Seq(Regex, Regex)} would not have a finite size: each
\texttt{Regex} would contain another \texttt{Regex}, and so on.
\texttt{Box<Regex>} provides the necessary indirection by storing the
recursive value separately and keeping a fixed-size pointer-like value
within the enum \citep{rust-book-box,rust-reference-recursive-types}.

The use of \texttt{Box} is therefore one of the practical differences
between this Rust representation and the Haskell reference
implementation. It introduces explicit indirection and heap-based
storage for recursive subexpressions, aspects that are relevant when
considering the memory behaviour of the implementation. These
implementation differences are revisited more generally in
Section~\ref{sec:rust-vs-haskell}.

With this representation established, operations on regular expressions
can be defined structurally over the expression tree.
