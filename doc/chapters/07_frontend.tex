\chapter{Frontend: Parsing External Regular Expression Syntax}
\label{sec:frontend}

Every example so far in this thesis has been written directly in
\texttt{Regex} terms, the six-constructor core algebra of
Section~\ref{sec:regex-rust-implementation} that
\texttt{deriv} and \texttt{pderiv} operate on. No real
regular-expression user writes that way. A Snort rule, a SpamAssassin
filter, or an ordinary call to \texttt{cargo run -- match} arrives as an
ordinary PCRE-style pattern \emph{string},
\texttt{"[a-c]+\textbackslash{}d\{2\}"} rather than
\texttt{Seq(Star(...), ...)}. \texttt{src/frontend/} is the module that
closes this gap: it parses that string into its own surface-syntax AST,
then lowers that AST into the \texttt{Regex} every parser in
Chapters~\ref{sec:derivative-parser}
and~\ref{sec:partial-derivative-parser} already understands.

It is modeled throughout on the \texttt{ExtPattern}, \texttt{Parse}
and \texttt{Translate} modules of
\texttt{Text.\allowbreak Regex.\allowbreak PDeriv}, from
\texttt{luzhuomi/\allowbreak regex-pderiv}, Kenny Lu's own reference
implementation
of \citet{sulzmannlu2012}'s partial-derivative submatching. That is a
second, independent reference alongside \citet{sulzmannlu2014}'s own
teaching-page material
(Section~\ref{sec:haskell-language-characteristics}), used here
specifically because the flops14-extended paper itself has nothing to
say about surface syntax: POSIX parsing is defined directly over the
same six-constructor \texttt{Regex} algebra this thesis's core inherits,
with no PCRE-facing frontend of its own.

Section~\ref{sec:dataset-preparation}'s real-world corpus depends on
everything described here, surface-syntax parsing, desugaring, and the
substring-search padding scheme, to turn raw Suricata, SpamAssassin and
RegexLib rule text into \texttt{Regex} values in the first place. The
chapter closes (Section~\ref{sec:frontend-cost}) with the price that
translation charges: how large a \texttt{Regex} an ordinary-looking
pattern actually becomes, which is what the four parsers then have to
walk once per input character.

\section{Two ASTs, One Lowering Step}
\label{sec:frontend-two-asts}

\texttt{src/frontend/} is built around a deliberate separation into two
abstract syntax trees connected by a single function, rather than
parsing pattern text directly into \texttt{Regex}.
Figure~\ref{fig:frontend-pipeline} gives the whole module in one view:
a common path that every entry point follows, and two optional stages
that only some of them switch on.

\texttt{ExtPat} (\texttt{ext\_pattern.rs}) is the \emph{external},
surface-syntax AST: marking and non-marking groups, \texttt{\{m,n\}}
bounds,
\texttt{\textbackslash{}d}/\texttt{\textbackslash{}w}/\texttt{\textbackslash{}s}
shorthands, \texttt{\^{}}/\texttt{\$} anchors, and a
\texttt{greedy: bool} flag on every quantifier (\texttt{a*} against
\texttt{a*?}). It holds everything a PCRE-style string can express,
kept exactly as written, with nothing desugared yet. \texttt{Regex}
(Section~\ref{sec:regex-rust-implementation}) is the \emph{internal},
six-constructor core every parser derives or partial-derives directly:
\texttt{Phi | Eps | Lit | Seq | Alt | Star}, with no groups, no bounds,
no anchors and no laziness flag. Anything \texttt{ExtPat} can say that
\texttt{Regex} cannot represent is desugared away by \texttt{translate}
(Section~\ref{sec:frontend-translate}) or, for \texttt{\^{}} and
\texttt{\$} specifically, erased into \texttt{Eps} and handled one level
up instead (Section~\ref{sec:frontend-substring-search}).

Keeping \texttt{ExtPat} as an honest AST in its own right, rather than
routing straight from the parser into \texttt{Regex} in a single pass,
is what makes \texttt{translate} independently testable. The unit tests
in \texttt{translate.rs} construct \texttt{ExtPat} values by hand and
check their \texttt{Regex} output directly, with no dependency on the
recursive-descent logic in \texttt{parse.rs} at all. It is the same
separation-of-concerns argument that
Section~\ref{sec:parsetree-and-flatten} makes for keeping
\texttt{ParseTree} construction separate from \texttt{flatten} and
\texttt{decode}, applied one layer further out, at the point where a
PCRE-style string first becomes structured data at all.

The separation earns its keep a second time at the entry points.
\texttt{mod.rs} exposes three of them, all sharing one parser and one
\texttt{translate}, and differing only in what they do to the
\texttt{ExtPat} in between:

\begin{center}
\begin{tabular}{ll}
\hline
Entry point & Behaviour \\
\hline
\texttt{parse\_pattern} & \texttt{translate} alone: full-string match \\
\texttt{parse\_dataset\_pattern} & plus anchor-aware padding (Section~\ref{sec:frontend-substring-search}) \\
\texttt{parse\_pcre\_rule} & plus \texttt{/.../i} delimiter stripping and case folding \\
\hline
\end{tabular}
\end{center}

Every example in Chapters~\ref{sec:derivative-parser}
and~\ref{sec:partial-derivative-parser}, and every invocation of
\texttt{cargo run -- parse}, goes through \texttt{parse\_pattern}, which
is why \texttt{"(a|ab)(b|)"} against \texttt{"ab"} means the whole
input and not a substring of it. The corpus of
Section~\ref{sec:dataset-preparation} goes through the other two, which
is where real rule text is handled.

\section{Parsing Surface Syntax}
\label{sec:frontend-parsing}

\texttt{frontend/parse.rs} is an ordinary recursive-descent parser over
a \texttt{Chars} iterator, structured directly after the grammar of
\texttt{Text.Regex.PDeriv.Parse}. Its productions correspond one for
one, each handling exactly the surface-syntax layer its reference
counterpart does:

\begin{center}
\begin{tabular}{lll}
\hline
Reference & This frontend & Layer handled \\
\hline
\texttt{p\_ere} & \texttt{parse\_or} & alternation \\
\texttt{p\_branch} & \texttt{parse\_concat} & concatenation \\
\texttt{p\_exp} & \texttt{parse\_postfixed} & postfix quantifiers \\
\texttt{p\_atom} & \texttt{parse\_atom} & a single atom \\
\texttt{p\_group} & \texttt{parse\_group} & \texttt{( ... )} forms \\
\texttt{p\_charclass} & \texttt{parse\_charclass} & \texttt{[ ... ]} \\
\texttt{p\_enum} & \texttt{parse\_class\_enum} & class members \\
\texttt{p\_bound} & \texttt{parse\_bound} & \texttt{\{m,n\}} \\
\hline
\end{tabular}
\end{center}

The table is a list of names; Figure~\ref{fig:precedence-ladder} is
what those names mean operationally. Each production consumes exactly
one syntactic layer and then calls the next one down, so the order of
the calls \emph{is} the precedence order, and the single back-edge from
\texttt{parse\_group} is what makes the grammar recursive at all.

Four deliberate departures from the reference:

\begin{itemize}
  \item \textbf{Class shorthands are PCRE character classes, not literal
  escapes.} The reference's \texttt{Translate.hs} reads a bare
  \texttt{EEscape c} as the literal character \texttt{c} always; this
  frontend special-cases
  \texttt{d}/\texttt{D}/\texttt{w}/\texttt{W}/\texttt{s}/\texttt{S} into
  character classes (Section~\ref{sec:frontend-translate}'s
  \texttt{alphabet.rs}) instead, since real datasets use them that way
  throughout.

  \item \textbf{Backreferences and lookaround are rejected outright.}
  The backreferences \texttt{\textbackslash{}1} to
  \texttt{\textbackslash{}9}, and the four lookaround openers
  \texttt{(?=}, \texttt{(?!}, \texttt{(?<=} and \texttt{(?<!}, all
  produce a descriptive parse error rather than the reference's literal-digit or
  three-digit octal-ASCII escape reading. Both describe languages that
  are not regular in the formal sense this thesis's entire construction
  depends on, so silently mis-parsing them into \emph{some}
  \texttt{Regex} would be a worse outcome than refusing them, and
  Section~\ref{sec:dataset-preparation}'s extraction pipeline depends on
  this refusal being loud and categorized rather than silent.

  \item \textbf{Named groups are accepted.} \texttt{(?<name>...)} and
  \texttt{(?P<name>...)} parse successfully, and the name is dropped
  during \texttt{translate}. A name carries no meaning once lowered to
  \texttt{Regex}, since this project has no capture-group semantics at
  all, but rejecting a construct this common in real Suricata and
  RegexLib rules purely because the reference parser predates it would
  reject working patterns for no benefit. \texttt{(?P=name)}, a named
  \emph{backreference}, is rejected along with the numeric ones.

  \item \textbf{\texttt{\textbackslash{}xHH} hex escapes are accepted},
  another addition absent from the reference, for the same reason.
\end{itemize}

Two small extensions exist for this thesis's own sake rather than for
the datasets. A literal $\varepsilon$ character in the pattern text
parses to \texttt{ExtPat::Eps}, and a literal $\emptyset$ to
\texttt{ExtPat::Never}, so that
Section~\ref{sec:regex-syntax}'s own notation for $\varepsilon$ and
$\emptyset$ can be written directly on the command line. PCRE syntax has
no way to spell either, and the alternative used throughout
Chapters~\ref{sec:derivative-parser}
and~\ref{sec:partial-derivative-parser} is an empty alternative:
\texttt{(b|)} is $b + \varepsilon$, because
\texttt{parse\_concat} returns \texttt{ExtPat::Empty} when a branch is
empty rather than failing.

\paragraph{Bounds are parsed speculatively.} \texttt{parse\_bound} is
the one place where the parser backtracks. A \texttt{\{} in a pattern is
only sometimes the start of a repetition bound, so \texttt{parse\_bound}
clones the iterator, tries to read a complete \texttt{\{m\}},
\texttt{\{m,\}} or \texttt{\{m,n\}} specification from the clone, and
commits the clone back only on success. On failure the \texttt{\{} is
left unconsumed, and since \texttt{\{} is in the parser's
\texttt{SPECIALS} set, the next \texttt{parse\_atom} call reports it as
unexpected.

This has a consequence worth recording, because it makes one check in
\texttt{translate} unreachable. An inverted bound such as
\texttt{a\{4,2\}} is rejected by \texttt{try\_parse\_bound\_spec}, which
returns \texttt{None} when the upper bound is below the lower one, so
the error the user sees comes from the \emph{atom} parser:
\begin{verbatim}
$ cargo run -- parse "a{4,2}" "aa"
Regex parse error: unexpected special character '{' here
\end{verbatim}
rather than from \texttt{desugar\_bound}'s own
"upper bound is less than lower bound" message, which no input reaching
it through \texttt{parse\_pattern} can trigger. The message is less
specific than the one that exists for the condition, which is worth
knowing when reading extraction-failure categories in
Section~\ref{sec:dataset-preparation}.

\texttt{parse\_bound} additionally accepts a lazy-quantifier marker
(\texttt{a*?}, \texttt{a+?}, \texttt{a\{2,4\}?}) and records it as
\texttt{ExtPat}'s \texttt{greedy: bool} flag: correctly read, but, as
Section~\ref{sec:frontend-translate} explains, not honored by
\texttt{translate}. Grouping, alternation and concatenation otherwise
follow the reference's precedence exactly: alternation binds loosest,
then concatenation, then postfix quantifiers, then a single atom, which
may be a literal, an escape, a character class, a group or an anchor.

\section{Translating \texttt{ExtPat} into \texttt{Regex}}
\label{sec:frontend-translate}

\texttt{translate} (\texttt{frontend/translate.rs}) is a single
structural recursion over \texttt{ExtPat}, one match arm per
constructor, each either a direct one-to-one mapping or an explicit
desugaring:

\begin{center}
\begin{tabular}{ll}
\hline
\texttt{ExtPat} & \texttt{Regex} \\
\hline
\texttt{Empty}, \texttt{Eps} & \texttt{Eps} \\
\texttt{Never} & \texttt{Phi} \\
\texttt{Char(c)} & \texttt{Lit(c)} \\
\texttt{Group}/\texttt{GroupNonMarking(r)} & \texttt{translate(r)} (grouping is precedence-only) \\
\texttt{Or([r1, ..., rn])} & left-folded \texttt{Alt} chain \\
\texttt{Concat([r1, ..., rn])} & left-folded \texttt{Seq} chain \\
\texttt{Opt(r)} & \texttt{Alt(translate(r), Eps)} \\
\texttt{Plus(r)} & \texttt{Seq(translate(r), Star(translate(r)))} \\
\texttt{Star(r)} & \texttt{Star(translate(r))} \\
\texttt{Carat}, \texttt{Dollar} & \texttt{Eps} (see Section~\ref{sec:frontend-substring-search}) \\
\texttt{Dot}, \texttt{Any(cs)}, \texttt{NoneOf(cs)} & sorted, deduplicated \texttt{Alt} of \texttt{Lit} \\
\texttt{Escape(c)} & class shorthand, or \texttt{Lit(c)} \\
\texttt{Bound(r, lo, hi)} & unrolled exact/optional repetition, below \\
\hline
\end{tabular}
\end{center}

The left-folding of \texttt{Or} and \texttt{Concat} is what makes the
associativity convention of Section~\ref{sec:regex-syntax} concrete:
\texttt{abc} becomes \texttt{Seq(Seq(a, b), c)}, and it is that tree,
not the string, that every derivative in this thesis is taken of.

\paragraph{Character classes are ordinary alternation, not a primitive.}
\texttt{Any}, \texttt{NoneOf}, \texttt{Dot} and the class-shorthand
escapes all route through \texttt{alt\_of\_chars}, which sorts and
deduplicates the character set and left-folds it into a plain
\texttt{Alt} chain of \texttt{Lit} nodes. \texttt{alphabet.rs} supplies
the underlying sets: \texttt{alphabet()}, which is 98 characters
(printable ASCII plus tab, newline and carriage return),
\texttt{digit\_chars}/\texttt{word\_chars}/\texttt{space\_chars} for
\texttt{\textbackslash{}d}/\texttt{\textbackslash{}w}/\texttt{\textbackslash{}s},
and \texttt{complement} (the alphabet minus a given set) for their
negated and uppercase counterparts and for \texttt{[\^{}...]}.

There is no dedicated character-class \texttt{Regex} variant anywhere in
this project, and Section~\ref{sec:char-class-optimization} returns to
this as an unexploited optimization. Every one of the four parsers only
ever needs to understand \texttt{Regex}'s original six constructors, at
the cost of a \texttt{\textbackslash{}d} inside a real pattern becoming
a ten-way \texttt{Alt} that the parser walks one branch at a time on
every character. Section~\ref{sec:frontend-cost} measures how large
that cost actually is.

Two consequences of drawing the alphabet this way are worth stating,
since both are departures from PCRE that a rule author would not expect.
The alphabet is ASCII only, so a negated class \texttt{[\^{}a]} denotes
97 specific characters rather than "every character except
\texttt{a}", and a non-ASCII input character matches no class at all.
And \texttt{alphabet()} \emph{includes} newline, so \texttt{.} here
matches a newline where PCRE's \texttt{.} by default does not.

\paragraph{Bounds unroll literally, capped against blowup.}
\texttt{desugar\_bound} builds \texttt{r} repeated exactly \texttt{lo}
times, via \texttt{repeat\_exact}, a left-folded \texttt{Seq} chain
seeded with \texttt{Eps}, then appends either \texttt{Star(r)} for an
unbounded upper end (\texttt{r\{2,\}}) or \texttt{hi - lo} further
nested optional copies for a bounded one (\texttt{r\{2,4\}}), each layer
of \texttt{optional\_extra} being \texttt{Alt(Eps, Seq(r, ...))}. An
exact bound \texttt{r\{2\}} takes a third path, returning
\texttt{repeat\_exact} alone with nothing appended. The \texttt{Eps}
seed stays in the result rather than being smart-constructed away, so
\texttt{a\{2\}} lowers to \texttt{Seq(Seq(Eps, Lit('a')), Lit('a'))}
rather than \texttt{Seq(Lit('a'), Lit('a'))}. That costs one node and
one nullable-test per derivative step, and it keeps
\texttt{repeat\_exact} a single unconditional fold with \texttt{Eps} as
the natural identity for \texttt{lo == 0}.

Unlike every other desugaring in this table, this one can make a pattern
arbitrarily large from a short piece of source text.
\texttt{r\{1586,\}}, which is Section~\ref{sec:dataset-preparation}'s
own example of a rejected real-world bound, would otherwise unroll into
1586 nested \texttt{Seq} nodes before the \texttt{Star} even starts.
\texttt{MAX\_BOUND}, at 1000 repetitions, is this project's own safety
limit rather than something carried over from the reference, and
\texttt{translate} refuses any bound past it with a descriptive error
rather than silently building an oversized \texttt{Regex}:
\begin{verbatim}
$ cargo run -- parse "a{1586,}" "aa"
Regex parse error: bound {1586,} exceeds this frontend's cap of
1000 repetitions (literal unrolling would blow up the regex size)
\end{verbatim}

\paragraph{Greedy and lazy quantifier syntax is parsed but not honored.}
Every \texttt{Opt}, \texttt{Plus}, \texttt{Star} and \texttt{Bound}
match arm above ignores the \texttt{greedy} flag that
\texttt{parse\_bound} (Section~\ref{sec:frontend-parsing}) recorded,
because \texttt{Regex} has no per-operator laziness concept at all.
POSIX-versus-Greedy disambiguation in this thesis is a whole-parser
policy, \texttt{deriv\_std}/\texttt{deriv\_bc} against
\texttt{pderiv\_std}/\texttt{pderiv\_bc}
(Section~\ref{sec:disambiguation-problem}), rather than a per-quantifier
one. \texttt{a*} and \texttt{a*?} therefore produce identical
\texttt{Regex} values.

A pattern mixing lazy and greedy quantifiers, expecting the per-operator
control PCRE engines provide, will parse successfully but not behave as
its author intended. This is a genuine expressiveness gap between the
surface syntax this frontend accepts and what \texttt{Regex} can
distinguish, noted here rather than left to be discovered. The flag is
nonetheless carried on \texttt{ExtPat} rather than discarded at parse
time, so that the information survives to the one layer that could act
on it if per-quantifier policy were ever added.

\paragraph{Case folding.} \texttt{parse\_pcre\_rule} handles a
\texttt{/PATTERN/FLAGS} wrapper, the form Suricata and SpamAssassin
rules are written in. \texttt{strip\_pcre\_delimiters} splits the body
from the flags, passing a pattern through unchanged if it is not
\texttt{/}-delimited, and the \texttt{i} flag triggers
\texttt{case\_fold} on the \texttt{ExtPat} before \texttt{translate}
runs. \texttt{case\_fold} rewrites each literal letter into a two-way
\texttt{Any}, so \texttt{a} becomes \texttt{[aA]}, and leaves digits,
punctuation and class shorthands untouched, since those are already
case-agnostic. Folding at the \texttt{ExtPat} layer rather than after
lowering is what keeps this to a single recursion: at the
\texttt{Regex} layer the same change would have to distinguish literals
that came from a class from literals that came from source text, a
distinction \texttt{translate} has by then already erased.

\section{Substring Search}
\label{sec:frontend-substring-search}

No parser in Chapters~\ref{sec:derivative-parser}
and~\ref{sec:partial-derivative-parser} answers any question but "does
this entire input derive to nullable". There is no
"found somewhere inside a longer string" mode anywhere below the
frontend, and neither \citet{sulzmannlu2014} nor Sulzmann's
teaching-page material defines one: POSIX and Antimirov derivatives are
inherently full-match operations. Real rules, though, are \emph{written}
as search patterns. A Suricata rule fires on seeing its pattern anywhere
in a packet payload, not on the payload being exactly that pattern.

\texttt{frontend/mod.rs} therefore implements substring search entirely
at this layer, before a \texttt{Regex} ever reaches a parser, by padding
the translated core with \texttt{wildcard\_run()}, a \texttt{Star} over
a 98-way \texttt{Alt} of the full alphabet meaning "any run of
characters at all", on whichever side lacks an explicit anchor.
Figure~\ref{fig:padding} gives the four cases, with the size of each
lowered result alongside.

\texttt{starts\_with\_carat} and \texttt{ends\_with\_dollar}
(\texttt{ext\_pattern.rs}) decide which sides need padding by walking
into \texttt{Concat} and \texttt{Group} to find a leading \texttt{\^{}}
or trailing \texttt{\$} even when nested, before \texttt{Carat} and
\texttt{Dollar} are themselves translated away to \texttt{Eps}. Under
the search-oriented entry points \texttt{parse\_dataset\_pattern} and
\texttt{parse\_pcre\_rule}, as against \texttt{parse\_pattern}'s plain
full-string equality used everywhere else in this thesis's own examples,
deciding which side of this padding is skipped is the anchors' only real
effect.

Because the anchors are recognized structurally rather than
positionally, a \texttt{\^{}} that is not at the start, as in
\texttt{a\^{}b}, is not an anchor at all. It still parses to
\texttt{Carat} and still translates to \texttt{Eps}, so it contributes a
node to the lowered expression but nothing to the language:
\begin{verbatim}
$ cargo run -- parse "a^b" "ab" --diag 1
Regex:  a^b
Input:  "ab"
Match:  true
Tree:   ((a, ()), b)
\end{verbatim}
The \texttt{()} in the middle of that tree is the erased anchor. PCRE
would treat the same pattern as unmatchable outside multiline mode. This
is a silent difference rather than an error, and it is the one place in
the frontend where a mis-written pattern is neither rejected nor
faithfully represented.

\paragraph{Edge case.} An unanchored pattern already nullable on empty
input, with \texttt{"a*"} the simplest example, gets padded on both
sides regardless of its own content. The padding's own empty match,
combined with either \texttt{Star}, is then enough by itself to match
\emph{any} string at all, not just runs of \texttt{a}. This is correct
substring-search semantics, since "some substring matches" is satisfied
by the empty substring that every string contains, and
\texttt{mod.rs}'s own test
\texttt{unanchored\_nullable\_pattern\_matches\_anything} asserts
exactly this behaviour rather than treating it as a defect. It is worth
flagging nonetheless, because such a pattern carries no information in a
corpus: it matches every input and so contributes nothing to
Section~\ref{sec:dataset-preparation}'s measurements beyond its own
parse cost.

\section{The Cost of Translation}
\label{sec:frontend-cost}

Every desugaring in this chapter is exact, and several of them are
expensive. Since the object that reaches
Chapters~\ref{sec:derivative-parser}
and~\ref{sec:partial-derivative-parser} is the lowered \texttt{Regex}
rather than the pattern string, the size of that object, and not the
length of the pattern, is what the parsers' per-character work scales
with. Counting nodes in the lowered result for a few patterns makes the
translation's real price visible:

The purely structural desugarings stay small, and their shapes are worth
seeing written out, since each is exactly what
Section~\ref{sec:frontend-translate}'s table prescribes:

\begin{center}
\begin{tabular}{llr}
\hline
Pattern & Lowers to & Nodes \\
\hline
\texttt{a*} & \texttt{Star(Lit)} & 2 \\
\texttt{a?} & \texttt{Alt(Lit, Eps)} & 3 \\
\texttt{a+} & \texttt{Seq(Lit, Star(Lit))} & 4 \\
\texttt{a\{2\}} & \texttt{Seq(Seq(Eps, Lit), Lit)} & 5 \\
\texttt{a\{2,\}} & exact copies then \texttt{Star} & 8 \\
\texttt{a\{2,4\}} & exact copies then nested options & 15 \\
\hline
\end{tabular}
\end{center}

Character classes and search padding are what change the order of
magnitude. A \texttt{\textbackslash{}d} is a 10-way \texttt{Alt} chain
at 19 nodes, \texttt{\textbackslash{}w} a 63-way one at 125,
\texttt{[\^{}a]} a 97-way one at 193, and \texttt{.} a 98-way one at
195. An unanchored search for the three-character literal
\texttt{abc} reaches 399.

That last figure is the one that matters most for
Section~\ref{sec:dataset-preparation}. Searching for a three-character
literal builds a 399-node expression, because each
\texttt{wildcard\_run()} is a 195-node alternation under a \texttt{Star}
and two of them are needed. Every derivative step then walks that
structure.

Figure~\ref{fig:lowered-size} puts these on one logarithmic axis,
together with two patterns closer to what the corpus actually contains.
The span is the point: the same six constructors carry expressions
differing by more than two orders of magnitude, and nothing about the
pattern's source length predicts where in that range it lands.

implementation from an engine with a native character-class
representation, and it applies to the corpus patterns uniformly, since
essentially all of them are unanchored searches containing at least one
class shorthand.

The expansion is also visible in the diagnostics, in a way that is
unhelpful rather than merely large. Because the expected-set reported on
a failure (Section~\ref{sec:diagnostics-design}) is read off the
first-literal set of the expression at the point of failure, and a
lowered class \emph{is} that set, a single mismatched character against
\texttt{.} reports all 98 alternatives individually:
\begin{verbatim}
$ cargo run -- parse "." "ä" --diag 1
Regex:  .
Input:  "ä"
Match:  false
Error:  position 1: found 'ä', expected '\t', '\n', '\r', ' ',
        '!', '"', '#', '$', '%', '&', ... , '}', or '~'
\end{verbatim}
(abbreviated here; the tool prints the full list). The message is
accurate, and it is exactly what the pattern denotes after lowering, but
it no longer resembles the pattern the user wrote. A native class
representation would let the diagnostics layer report
\texttt{expected: any character} instead, which is one more argument for
Section~\ref{sec:char-class-optimization} beyond the performance one,
and Section~\ref{sec:diagnostics-scope-limits} treats it as an instance
of the general limit on what a tracing layer can recover once an
abstraction has been compiled away.

The effect compounds rather than merely adding, which is why the chart
climbs faster than the patterns lengthen.
\texttt{\textbackslash{}d\{2\}} lowers to two copies of the 19-node
digit chain, reaching 41 nodes, and \texttt{\textbackslash{}w+} to a
63-way alternation appearing twice, once for the required copy and once
inside the \texttt{Star}, reaching 252. Stacking both effects,
\texttt{[a-c]+\textbackslash{}d\{2\}} is 54 nodes as a full-string
pattern and 448 once padded for search, from twelve characters of source
text.

Case folding is the one remaining multiplier, and it is comparatively
cheap: \texttt{case\_fold} turns each literal \emph{letter} into a
two-way \texttt{Alt} and leaves everything else alone, so
\texttt{/abc/i} lowers to 405 nodes against \texttt{/abc/}'s 399, six
more for three folded letters. Unlike the class expansion, this one
scales with the number of letters in the pattern rather than with the
size of the alphabet.

None of this changes which language is denoted, and none
of it changes which parse tree any of the four parsers selects. It
changes only how much structure each of them traverses per input
character, which is exactly the quantity
Section~\ref{sec:performance-analysis} measures and
Section~\ref{sec:char-class-optimization} proposes to reduce.
