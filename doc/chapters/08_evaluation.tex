\chapter{Evaluation}
\label{sec:evaluation}

This chapter evaluates the derivative and partial-derivative parsers developed in
Chapters~\ref{sec:derivative-parser} and~\ref{sec:partial-derivative-parser}.
Using two datasets and a common set of criteria, it compares the candidates in
terms of execution time, memory consumption, and translation cost.
It also assesses their agreement on membership decisions and parse-tree shape.

All measurements were taken on an AMD Ryzen~5~5600 six-core processor with
16\,GB of RAM, running Pop!\_OS 24.04 LTS on an AMD B550 chipset.

%
%
%


\section{Candidates}
\label{sec:eval-candidates}

A candidate is a parser $p$ that takes a translated \texttt{Regex} $r$
and an input \texttt{String} $w$, 
and returns either a \texttt{ParseTree} $pt$ or no match.
Such an input pair $(r, w)$ is called an \emph{entry}.
All candidates share the same interface:
\[
p :: (\mathit{Regex}, \mathit{String}) \to
     \mathit{Option\langle ParseTree\rangle}.
\]

Candidates are classified into
two families by their disambiguation strategy.


\textbf{POSIX family.}
\begin{itemize}
  \item \texttt{deriv\_std\_rec}, the recursive standard derivative parser
        (Section~\ref{sec:deriv-std-parser}).
  \item \texttt{deriv\_std\_loop}, the iterative standard derivative parser
  \item \texttt{deriv\_bc}, the bit-coded derivative parser
        (Section~\ref{sec:deriv-bc-driver}).
\end{itemize}

\textbf{Non-POSIX family.} 
\begin{itemize}
  \item \texttt{pderiv\_std}, the standard partial-derivative parser
        (Section~\ref{sec:pderiv-std-parser}).
  \item \texttt{pderiv\_bc}, the bit-coded partial-derivative parser
        (Section~\ref{sec:pderiv-bc-parser}).
\end{itemize}

All five parsers are expected to agree on membership,
so given an entry, they must either all accept it or all reject it.
They are also expected to agree on parse-tree shape \emph{within}
each family, because the parsers of one family share the same
disambiguation policy and differ only in how they compute and
reconstruct the tree. 

For the POSIX family this means the parsers must return the same POSIX parse tree
and the non-POSIX family parsers must return the same leftmost parse tree. 

Across families, agreement is
not required. Since the two families implement different
disambiguation policies, they may select different parse trees for
the same entry even when they agree on membership, as
Chapter~\ref{sec:matching-vs-parsing} shows.

%

\section{Evaluation Criteria}
\label{sec:eval-criteria}

The evaluation considers two aspects of the candidates. The first is
\emph{performance}, measured in terms of execution time, memory consumption,
and translation cost. The second is \emph{correctness}, assessed by comparing
membership and parse-tree selection.

%
%
%

\subsection{Measurement Setup}
\label{sec:eval-criteria-setup}

Each entry runs in its own worker subprocess for timing, memory,
stack-depth, and parse-agreement measurements. Stable Rust has no safe
way to forcibly terminate a thread~\citep{rust-thread-joinhandle}, so one
that has not returned, e.g. from exponential derivation or from
allocating towards the memory cap, cannot be stopped. A
subprocess, by contrast, can be killed unconditionally, and the operating
system reclaims its memory.

\begin{itemize}
  \item \emph{Measured}: the worker exited zero and reported a result line.
  \item \emph{Timed out}: the worker exceeded the default per-entry timeout
        (2\,s) and was killed.
  \item \emph{Crashed}: the worker exited non-zero or was killed by a
        signal, including stack overflows and out-of-memory kills
        when the memory ceiling is enabled.
\end{itemize}

For timing, memory, and parse-agreement measurements, each worker runs on
a custom 256\,MiB stack: all candidates recurse over the pattern
structure, and on deeply nested patterns the default stack would overflow
before the measured input sizes are reached. This stack is a fixed
allowance and not part of the measured footprint.

A timing and memory run produces two outputs per candidate and dataset: (1) a summary
table of aggregate measurements; (2) a per-entry file
to compare individual entries.

%
%
%

\subsection{Timing}
\label{sec:eval-criteria-timing}

Each entry $(r, w)$ is timed once, without warm-up run or repeated
measurements. Translation is measured separately, so the wall-clock
time covers only the parser call $p(r, w)$.
For \texttt{deriv\_std\_rec}, \texttt{deriv\_std\_loop}, and
\texttt{pderiv\_std}, the entire parser call is reported as \emph{Derive}.
For \texttt{deriv\_bc} and \texttt{pderiv\_bc}, the call is split into
three: \emph{Encode} constructs the initial annotated state before
any character of $w$ is consumed, \emph{Derive} processes the input one
character at a time and \emph{Decode} converts the final bit-string into a
parse tree.

Timing results show four statistics, aggregated differently for the two datasets:

\begin{itemize}
  \item \emph{Mean} is a macro-average over patterns of the real corpus, so
        a pattern with 10 entries and one with 2 contribute equally,
        a flat mean is used for the synthetic set.
\item \emph{Median}, \emph{99th percentile}, and \emph{maximum} are pooled
      over individual entries rather than averaged per pattern. The median
      describes a typical entry, the 99th percentile the tail of the entry
      distribution, and the maximum the single worst entry.
\end{itemize}

All four statistics represent lower bounds on the corresponding
execution times, since timed-out and crashed entries are excluded
rather than counted at their timeout values.
A separate \emph{wall} column measures the benchmark's entire loop over one
source pattern. It therefore exceeds $\mathit{entries} \times \mathit{mean}$ by
the per-entry process-spawn and pipe-round-trip overhead excluded from the
individual timings. It captures the total cost of reproducing a pattern's
results, harness included, but is not suitable for comparisons between
candidates.

%
%

\subsection{Memory}
\label{sec:eval-criteria-memory}

Memory is measured with a counting allocator in each worker, baselined
immediately before the parser call so that only allocations made during
$p(r, w)$ are counted. The allocator tracks a running sum of requested
bytes and a running count of live bytes:

\begin{itemize}
  \item \emph{Max live peak}: the highest value of the live-byte counter
        within a call. It bounds the heap a single call requires, and is
        the measure that determines whether a parser can run at a given
        input length within a fixed memory budget.
  \item \emph{Total allocated}: the sum of requested bytes over the call,
        including memory later freed. It is not a footprint, but a proxy
        for allocator pressure and a secondary explanation of timing, since
        a parser that allocates and frees frequently pays a cost even when
        its peak stays low.
\end{itemize}

Total allocation counts memory freed during the call, so it is always at
least as large as peak. Because peak grows with
the input a run processes and total with the work it performs, each is
compared only where those are comparable: peak across rows that reached
comparable input lengths, 
total across rows that completed comparable work.

The allocator sees heap allocations only, not the worker stack
(Section~\ref{sec:eval-criteria-setup}), so a parser that uses substantial
stack but few heap allocations may appear inexpensive in these
measurements. Stack depth is evaluated separately for the two standard
derivative parsers.

%
%
%

\subsection{Translation}
\label{sec:eval-criteria-translation}

Translation depends only on the source pattern and is independent of the
input, so each distinct pattern is translated once rather than once per
entry. Translation runs in the main process because the frontend enforces
the three following resource limits:

\begin{itemize}
  \item \emph{Bound cap}: bounds the numeric value of any repetition bound.
  \item \emph{Depth cap}: bounds the estimated depth of the translated
        pattern.
  \item \emph{Node cap}: bounds the node count of the result.
\end{itemize}

The caps reject a pattern before translation would recurse too deeply or
unroll too large a result, so translation itself is always bounded in
time and memory. A parser call has no such protection. It can run until
the timeout or the memory cap kills it, which is why the caps are checked
at translation and the timeout is enforced per entry.

Translation cost is measured using four quantities:

\begin{itemize}
  \item \emph{Time}: the wall-clock duration of the translation call.
  \item \emph{Total bytes}: the total amount of memory allocated during
        translation.
  \item \emph{Peak bytes}: the highest number of live allocated bytes during
        the call.
  \item \emph{Nodes}: the number of nodes in the resulting \texttt{Regex}.
\end{itemize}

The counting allocator is reset before each translation and read immediately
after the call returns. This excludes subsequent node counting and debug
rendering from the measurement. Mean, median, 99th percentile, and maximum
are calculated directly over patterns. Since each pattern contributes one
measurement, no macro-averaging is needed. Rejected patterns
produce no measurement, so the reported statistics are lower bounds.

%
%

\subsection{Stack Depth}
\label{sec:eval-criteria-stack-depth}

\texttt{deriv\_std\_rec} and \texttt{deriv\_std\_loop} compute identical
results but store the residual sequence differently. The recursive
implementation uses one call-stack frame per input character, the
iterative one a \texttt{Vec}. Stack depth is measured to establish which
of the two exhausts the stack first, and at what input length. Both use
the operating system's default thread stack, which is 8\,MiB on Linux.

The maximum surviving input length is estimated using a doubling search.
Starting from a small input, the length is doubled after each successful
probe until the worker fails to complete. The timeout for each probe is
increased from the default $2\,\mathrm{s}$ to $15\,\mathrm{s}$, to give
slow derivatives time to exhaust the stack and cause a stack overflow.
A worker can also be killed by an
out-of-memory condition when a heap cap is set, as described in
Section~\ref{sec:eval-criteria-setup},
but for this measurement no heap cap is applied, so a
signal kill is more likely to be a stack overflow than an out-of-memory
kill.

The search brackets the last length that completed against the first
that did not. A crash means stack exhaustion limited the input, a timeout
means derivation became too expensive first. The timeouts are kept as
negative controls for patterns where derivation cost, not stack depth,
is limiting.

The same doubling search is used to check the two translation caps, the
\emph{bound cap} and the \emph{depth cap}. For the bound cap, the bound
value is doubled until translation of the bound exhausts the stack. 
For the depth cap, the nesting depth of \texttt{(?:...)} groups is doubled
until translation exhausts the stack. Bound unrolling recurses once for
each unit in a bound's open part, while syntactic nesting recurses once
for each level of grouping.

%

\subsection{Parse Agreement}
\label{sec:eval-criteria-agreement}

Parse agreement is evaluated on entries with a known expected membership
result. Each entry is written as $(r, w, e)$, where $r$ is the translated
\texttt{Regex}, $w$ is the input string, and
$e \in \{\mathit{true}, \mathit{false}\}$ is the expected match result.
No expected parse tree is provided.

Each candidate processes the same entry, and records:
\begin{itemize}
  \item \emph{Timeout or crash}: if the candidate exceeded the timeout
         or was killed by a signal.
  \item \emph{Membership}: a candidate's decision on ($e = \mathit{true}$)  
        or no-match ($e = \mathit{false}$)
  \item \emph{Parse tree}: the parse tree a candidate returned, when $e = \mathit{true}$.
\end{itemize}

A timeout or crash removes the candidate from the comparison for that
entry. Membership is compared across all candidates. 
Any disagreement with $e$ is a bug. 
Parse trees are compared only when $e = \mathit{true}$
and all candidates returned one. 
Agreement is required within each family, 
whose parsers share a disambiguation policy.
Across families it
is reported but not required, since the two policies may differ.

Thus the summary reports how many entries were evaluated and, for each
dataset, how many timed out or crashed, how many every candidate
classified correctly (\emph{match agreement}), and of those, how many
the two families parsed to the same tree (\emph{shape agree}) or to
different trees (\emph{shape disagree}).

\subsection{S2ELab}
\label{sec:eval-s2elab}

The dataset by \citet{s2elab-regexeval-dataset} contains 762 human-authored
patterns. Each pattern has a natural-language description and labeled
matching and non-matching inputs.

The source patterns conventionally use \texttt{\textasciicircum} and
\texttt{\textdollar} as beginning- and end-of-input anchors. A pattern
surrounded by these anchors requires a full-string match, whereas a pattern
without them can match a substring. As described in
Section~\ref{sec:frontend-rejected}, the frontend does not support anchors.
However, fully anchored patterns can still be used by stripping the anchors.
Since the parsers perform full-string matching, the stripped pattern accepts
exactly the inputs intended by the original anchored pattern.

Thus the benchmarks only use the 463 fully anchored patterns 
after stripping their anchors and the 115 unanchored patterns are excluded.
177 patterns are rejected by the frontend with their rejection

\paragraph{Pipeline.} A date pattern like
\texttt{\textasciicircum(0[1-9]|1[0-2])\textbackslash/...\textdollar} is
processed the following:
\begin{enumerate}
  \item \textbf{Extract.} The pattern is kept with the match
        and non-match lists.
  \item \textbf{Deduplicate.} The pattern is byte-distinct and no input string
        appears double.
  \item \textbf{Translate.} The anchors are stripped and the remainder is
        checked to translate.
  \item \textbf{Check labels.} Each input string is checked against the translated
        pattern. The input string \texttt{"11/31/2002"} is accepted because the day group allows
        \texttt{31} regardless of month, validating the pattern's semantics,
        not real-world correctness.
  \item \textbf{Write.} The surviving pairs are written to the corpus.
\end{enumerate}

\subsection{Stack Depth}
\label{sec:eval-stack-depth}

The recursive and iterative forms run on the operating system's default
stack of 8\,MB, without a memory cap, using the doubling search described in
Section~\ref{sec:eval-criteria-stack-depth}. Both rows use \texttt{a}
repeated $n$ times, with $n$ increasing across the sweep.

    & \texttt{rec}  & 16          & timeout & 15.906\,s \\

\hline

\emph{Derivative step} categorizes the pattern's

\emph{Outcome} reports what stopped the sweep: \emph{timeout} at the

\label{tab:stack-depth}

Here, P01 and P30 are used as negative controls, 
since on both the derivative step is
expensive enough that the 15\,s timeout fires before the stack is
reached, at $n=16$ and $n=64$ respectively. P01 fails first because its
nested quantifier makes each derivative step near-exponential. 
P30 fails later because ten adjacent \texttt{(\textbackslash w+)} 
groups produce a product of stars whose cost grows polynomially rather than
exponentially. In both cases the timeout, not the stack, ends the sweep.
Whatever the stack could hold, the input never grows far enough to fill
it. Stack exhaustion is therefore observable only when derivation stays
cheap enough for input length to outgrow derivation cost.

E51 shows this case. The pattern is a single literal, and every entry
mismatches on its first character, so the residual stays tiny and never
grows with the input. The derivative step is constant-cost, and the only
thing that grows is the number of steps, which is the input length. The
recursive form keeps one call frame per character for the whole input, so
its depth grows with $n$ until it crashes between $32\,768$ and $65\,536$
characters. The iterative form stores the same sequence in a \texttt{Vec},
so its depth stays constant regardless of $n$, and reaches the
$2\,000\,000$ sweep cap without failing. 

The iterative form is therefore preferable even with a cheap derivative
step. Both forms compute identical results and differ only in where the
residual sequence is stored, so any difference in outcome is attributable
to stack depth alone. The recursive form fails at tens of thousands of
characters, a length a single realistic match can easily reach. The
iterative form completes every length the sweep covers, and would have
continued past the cap.

intended. \texttt{deriv\_bc} and the partial-derivative variants have

entries. This is consistent with shape-based simplification and
per-step deduplication limiting the redundant states accumulated by
the standard construction. Category F provides the contrast.
Here, \texttt{deriv\_bc} times out on 40\% of entries, while both
partial-derivative variants remain below 4\%.
This shows that the F-family mechanism can defeat bit-coding.

the rates differ from 18\% to 57\%. This is consistent with bound

nesting them. This shape may explain why bit-coded derivatives
outperform the partial-derivative variants in this category.

less memory on short inputs.

Measuring syntactic nesting exposed a gap in the depth estimate.
Previously, groups did not contribute to the count, so deeply nested

per group. This does not change the real-corpus results. Running
\texttt{dataset\_prepare} on S2ELab still gives 578 accepted patterns,

(Section~\ref{sec:eval-agreement}).

The caps are deliberately set below the measured crash points. The
crash test uses one bound with a trivial one-node body, whereas real
patterns can nest bounds and unroll multi-node subtrees. This increases
both recursion depth and frame size. The measurements therefore give
a safety reference, not a safe operating limit, and the caps remain
well below it.

Real patterns remain well below the caps. Of the 762 authored patterns,
714 pass the frontend grammar check alone, before deduplication,
anchor-shape checks, translation, or cap checks. This is an earlier
filter than the 578 accepted patterns in Table~\ref{tab:dataset-summary},
not a directly comparable count. Of the 714 patterns, 442 contain a
bounded repetition. The largest bound is 67, with a median of 2 and
a 99th percentile of 16.

The node cap is set by coverage rather than a recursion threshold.
The largest real-corpus pattern translates to 18\,707 nodes, so the
20\,000-node cap covers every pattern in this evaluation.

\section{Discussion of Results}
\label{sec:eval-discussion}

%
%
%

\subsection{Cost of the standard construction}

The two standard derivative parsers are consistently the slowest and
use the most memory. Their two-pass structure stores every intermediate
expression until the backward pass completes. On \texttt{a\*} input,
their state grows linearly with $n$, while the other three variants
remain bounded in the measured range.

On the full corpus, the standard variants have similar mean times
(7.534\,ms and 7.388\,ms), but their matching totals differ.
\texttt{deriv\_std\_loop} takes 70.510\,s, compared with 72.829\,s
for \texttt{deriv\_std\_rec}. Their non-match totals are almost
identical, suggesting that iteration mainly reduces the cost of
matching. On the representative rows, both variants reach the
memory cap at the same input lengths and have similar allocation
figures. This points to their shared retention of intermediate
derivatives rather than recursion depth. The separate stack-depth
test isolates the other failure mode. Without a memory cap,
\texttt{deriv\_std\_loop} survives 32 times further than the
recursive form. Thus, the limiting factor depends on whether
derivation cost or stack depth grows first.

%
%
%

\subsection{Cost of bit-coding}
\label{sec:eval-cost-bit-coding}

For the standard-derivative family, bit-coding performs better on
the measured corpus. \texttt{deriv\_bc} has a mean time of
1.688\,ms, roughly $4$--$4.5\times$ below the standard variants,
and a peak allocation of 5.1\,MB, about $114$--$144\times$ lower.
Its forward pass retains information needed for single-pass
reconstruction rather than simplifying every redundant branch.
The decode step adds little time, with a mean well below
0.1\,ms.

The representative sweeps extend this result. \texttt{deriv\_bc}
completes six of the eight rows, while both standard variants crash
on all eight. It reaches ten million characters on P60 and P20.
Cumulative allocation can still be high, reaching 271\,GB on P20,
although peak allocation is 3.40\,GB. This distinction between
cumulative allocation and peak live bytes is why both are reported
(Section~\ref{sec:eval-criteria-memory}).

%
%
%

\subsection{Cost of partial derivatives}
\label{sec:eval-cost-partial-derivatives}

The partial-derivative parsers are the fastest and use the least
memory on the S2ELab corpus. They represent the residual as a set
of states rather than one combined expression, limiting the
alternation growth seen in the standard derivative parser.

Within the pair, bit-coding does not consistently help or hurt.
On the full corpus, \texttt{pderiv\_bc} is marginally faster
(0.625 against \texttt{pderiv\_std}'s 0.699\,ms mean) and has
lower total allocation (4.80 against \texttt{pderiv\_std}'s
5.52\,GB), though \texttt{pderiv\_std} still has the lower peak
(2.5 against 3.8\,MB). The ranking changes again on the representative rows.
\texttt{pderiv\_std} is faster on P60, while \texttt{pderiv\_bc} is
faster on P61 and P20. On P20, it also has the lower peak allocation
(3.27 against 4.97\,GB). The results suggest that the relative
cost of bit-coding depends on the pattern and input, not only
on input length.

Both partial-derivative variants produce non-POSIX trees. This is
a difference in parsing policy, not a correctness defect, and is
why the two families are compared separately in
Section~\ref{sec:eval-agreement}.

%
%
%

\subsection{Threats to validity}

\textbf{Corpus scope.} S2ELab represents one domain and its
conventions. Other corpora may have different acceptance rates and
timing profiles. Timing, Memory, and Parse Agreement use the
463-pattern default scope (Section~\ref{sec:eval-s2elab}).
Including the remaining 115 patterns with
\texttt{BENCH\_MATCH\_INTENT=both} could change the absolute
results and potentially the ranking of candidates.

\textbf{The synthetic set.} Its 113 rows isolate individual
complexity mechanisms at controlled scales rather than representing
patterns written by typical users. Most categories vary one parameter
at a time, so combinations of stress mechanisms are not directly tested.

\textbf{Agreement subset.} The \emph{Compared} subset includes
expected matches completed by every candidate, with both families
internally consistent. It excludes 71 of 5\,869 S2ELab matches
(about 1\%) and 237 of 444 synthetic matches (about 53\%).
The synthetic result is therefore based on a much smaller subset.
For alternation-heavy categories, the excluded cases may also contain
more ambiguity because shared prefixes can increase both derivation
cost and the number of possible parses. This need not apply to
categories such as I, where timeouts arise from input length alone.

\textbf{Measurement model.} The memory benchmarks measure heap
allocations, not total process memory. Timing results are specific
to the machine used and may vary with its CPU and cache. A recorded
\emph{crash} means that the process was killed by a signal, not
that stack overflow was confirmed
(Section~\ref{sec:eval-criteria-setup}). The separate stack-depth
test removes the memory cap and provides direct evidence of stack
overflow. The representative-row crashes are instead consistent
with the memory costs of retaining intermediate derivatives.
