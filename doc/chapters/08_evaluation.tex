\chapter{Evaluation}
\label{sec:evaluation}

This chapter evaluates four parser candidates  implemented in
Chapters~\ref{sec:derivative-parser} and
\ref{sec:partial-derivative-parser}:

\begin{itemize}
  \item \texttt{deriv\_std\_rec}, the standard derivative parser in
        its recursive form.
  \item \texttt{deriv\_std\_loop}, the standard derivative parser in
        its iterative form.
  \item \texttt{deriv\_bc}, the bit-coded derivative parser.
  \item \texttt{pderiv\_std}, the standard partial-derivative parser.
  \item \texttt{pderiv\_bc}, the bit-coded partial-derivative parser.
\end{itemize}

Section~\ref{sec:eval-dataset}
describes the two data sources. Section~\ref{sec:eval-agreement}
checks how often the POSIX and non-POSIX parser families agree on
parse-tree shape. Section~\ref{sec:eval-performance} compares the
candidates on execution time and memory.
Section~\ref{sec:eval-discussion} interprets the results.

All measurements were taken on an AMD Ryzen~5~5600
six-core processor with 16\,GB of RAM, running Pop!\_OS 24.04 LTS on
an AMD B550 chipset.

\section{Dataset Preparation}
\label{sec:eval-dataset}

The evaluation uses two pattern sources, chosen for complementary
roles.

\textbf{S2ELab} \citep{s2elab-regexeval-dataset} comprises 762
patterns, each accompanied by a natural-language description and the
author's labeled \texttt{matches} and \texttt{non\_matches}. It
provides measurements on human-authored regular expressions with
author-supplied positive and negative examples, reflecting the kinds
of patterns encountered in practice.

\textbf{The pathological stress set} contains 113 hand-curated
patterns, grouped by the specific complexity mechanism each one
triggers. Within a category, each row defines a pattern and an input
as functions of one or both of two sweep parameters, the input length
$n$ and the pattern size $p$. A category's sweep is a set of values
for these parameters, applied uniformly across its rows and chosen so
that the measured cost moves from microseconds to failure as the
sweep progresses.

%
%

\subsection{S2ELab}
\label{sec:eval-s2elab}

A benchmark corpus for a membership-deciding parser needs, for each
pattern, both a matching string and a non-matching string. A source
that does not ship such pairs forces the corpus builder to manufacture
them, and a manufactured input reflects the sampler's bias. S2ELab
ships both lists with every pattern, so no generation step is needed.

\subsubsection{Anchor stripping and corpus acceptance}
\label{sec:eval-anchors}

The frontend of Chapter~\ref{sec:frontend} rejects every anchor. A
pattern containing \texttt{\textasciicircum} or \texttt{\textdollar}
anywhere reaches \texttt{translate} and is rejected there.

Before calling the frontend, however, the pipeline applies one
transformation of its own. A pattern whose top level is a single
\texttt{\textasciicircum...\textdollar} wrap around the whole pattern
has that wrap stripped by \texttt{strip\_full\_anchors} in
\texttt{src/data/prepare.rs}, before \texttt{translate} runs. Under
full-string matching the wrap is provably redundant: consuming the
whole input already requires both endpoints, so stripping it changes
nothing about what the pattern denotes. The pipeline records the strip
as part of the pattern's \texttt{MatchIntent} tag
(\texttt{ExplicitFullMatch}), and passes the anchor-free pattern to
the frontend.

\textbf{What strips.} \texttt{strip\_full\_anchors} first unwraps any
top-level \texttt{(...)} or \texttt{(?:...)} shell. It then checks
whether the result is a \texttt{Concat} whose first element is
\texttt{Carat} and last element is \texttt{Dollar}, and removes that
pair. Both \texttt{\textasciicircum abc\textdollar} and
\texttt{(\textasciicircum abc\textdollar)} strip to the same
\texttt{ExtPat}. \texttt{\textasciicircum\textdollar} alone strips to
\texttt{Eps}.

\textbf{What still rejects.} Every other anchor placement reaches
\texttt{translate} and is rejected. Four shapes appear.

\begin{itemize}
  \item Start-only, \texttt{\textasciicircum abc}.
  \item End-only, \texttt{abc\textdollar}.
  \item Nested, \texttt{(a\textasciicircum |b)c} or
        \texttt{(a\textasciicircum b)*c}. After shell unwrapping the
        top level is not a strippable \texttt{Concat}, so nothing
        strips.
  \item Multiple pairs, \texttt{\textasciicircum a\textdollar
        b\textdollar}. The outermost pair strips, the inner
        \texttt{Dollar} remains, and \texttt{translate} rejects it.
\end{itemize}

\texttt{parse\_pattern} and \texttt{parse\_pcre\_rule} strip no
anchors at all. Both reject every anchor they encounter, the strippable
wrap included. Stripping is a pipeline-side step, run before either
frontend function.

\textbf{Match intent groups.} Every accepted S2ELab pattern falls into
one of two groups. 463 carry the top-level wrap and have it stripped,
landing on the engine's native full-match reading. 115 carry no anchor
and are translated unchanged, still matched under full-string
semantics but with no way to tell whether the author meant a full
match or a search this project does not implement. Both groups are
written to the corpus.

Every benchmark in this chapter defaults to the 463 stripped patterns
only. Reporting a number for the remaining 115 would assume a reading
of the pattern its own author never committed to. Both groups remain
available on opt-in via \texttt{BENCH\_MATCH\_INTENT=both}.

\subsubsection{The pipeline}
\label{sec:eval-pipeline}

\texttt{run\_pipeline} turns the raw S2ELab JSON into the benchmark
corpus in seven steps.

\begin{enumerate}
  \item \textbf{Extract.} Each entry's pattern and its author's own
        \texttt{matches}/\texttt{non\_matches} become one
        \texttt{ExtractedRule}.
  \item \textbf{Deduplicate.} A pattern byte-identical to one already
        seen this run is skipped.
  \item \textbf{Translate.} \texttt{core\_regex\_tagged} parses and
        translates, applying the anchor strip of
        Section~\ref{sec:eval-anchors}. A rejected pattern stops here.
  \item \textbf{Deduplicate examples.} A string appearing in both
        \texttt{matches} and \texttt{non\_matches} is kept once, as a
        positive.
  \item \textbf{Check labels.} Every surviving example is re-checked
        against the translated \texttt{Regex}. A disagreement is
        dropped, not corrected.
  \item \textbf{Balance per pattern.} Described in
        Section~\ref{sec:eval-balance}.
  \item \textbf{Write.} Each surviving pair becomes one line of
        \texttt{prepared.jsonl}, tagged with its \texttt{MatchIntent}.
\end{enumerate}

\subsubsection{Example: S2ELab entry 100}
\label{sec:eval-worked-pipeline}

  "matches": ["12/31/2003", "01/01/1900", "11/31/2002", ...],

\caption{S2ELab entry 100, fields trimmed.}
\label{fig:s2elab-entry-100}
\end{figure}

\paragraph{Extract.} One \texttt{ExtractedRule} carrying the raw
expression and the two input lists.

\paragraph{Translate.} The top level is a single \texttt{Concat}
opening with \texttt{\textasciicircum} and closing with
\texttt{\textdollar}, so the strip of Section~\ref{sec:eval-anchors}
applies. Both anchors are removed before translation, and the entry is
tagged as a full-match pattern.

\paragraph{Check labels.} Every given example is run through the
translated \texttt{Regex}. The check is against the pattern's own
semantics, not real-world correctness. The given string
\texttt{"11/31/2002"} is listed as a match and is one under the
translated pattern, since the day group accepts \texttt{31} regardless
of month. The pattern silently accepts a November 31st the calendar
does not have, and the check keeps it because the author's claim and
the pattern's own language agree. Whether the pattern encodes a real
calendar is a question the check does not answer.

\paragraph{Balance.} Truncate the entry's matches and non-matches to
the shorter side's count.

\paragraph{Write.} The surviving pairs are appended to
\texttt{prepared.jsonl}.

\subsubsection{Per-pattern balance and macro-averaging}
\label{sec:eval-balance}

For each pattern, the longer list is truncated to the shorter list's
length, keeping the first examples in their original order. A pattern
with 40 matches and 2 non-matches therefore contributes 2 of each. A
pattern is kept only if it has at least one example on each side.
Truncation is applied only within a pattern. A pattern with 50
surviving examples on each side contributes all 50, even when another
pattern in the same corpus contributes only one. Reducing every
pattern to the corpus-wide minimum would discard most of the corpus
to equalize against a single outlier.

The resulting cross-pattern imbalance is corrected at averaging time.
Sections~\ref{sec:eval-timing} and~\ref{sec:eval-memory} compute a
mean per pattern and then average the per-pattern means unweighted,
giving a macro-average in which every pattern contributes once
regardless of its example count. Median, 99th percentile, and maximum
remain computed over individual inputs, since they describe the cost
of the single worst input rather than of a typical pattern.

\subsection{The pathological stress set}
\label{sec:eval-pathological}

The pathological stress set is a second, hand-curated dataset whose
purpose is controlled measurement of asymptotic behaviour. S2ELab
supplies realistic patterns and realistic inputs, but its entries do
not stress any single cost mechanism at scale. The pathological set
does.

Each row specifies one regular expression plus a substitution rule
that maps a swept parameter (input length $n$, pattern size $p$, or
both) to a concrete (pattern, input) pair. Most rows hold the pattern
fixed and sweep $n$ as repeated characters. A smaller number sweep
$p$ by substituting a parameter into the pattern template before
parsing.

Every pattern in the set is authored directly against the engine's
full-string-matching model. None of them contains an anchor, a word
boundary, a backreference, lookaround, or a POSIX class, so every row
passes the frontend without a stripping step.

The 113 patterns are grouped into 12 categories
(Table~\ref{tab:patho-categories}). Each category isolates one
complexity mechanism and carries its own calibrated sweep, chosen so
that a routine, un-overridden pass crosses from all parsers measuring
in microseconds to the standard derivative parser timing out, within
the category's own default points.

\section{Parser Agreement}
\label{sec:eval-agreement}

Every case in the prepared corpus carries a verified outcome, so
membership is a precondition, not something this section establishes.
The question here is parse-tree shape. On a matching case, the POSIX
parsers and the non-POSIX parsers may build different trees, since the
same input can admit several valid decompositions. Some inputs force
both policies onto the same structure. This section measures how often.

%
%
%

\subsection{Method}

The check is implemented in \texttt{demo\_parser\_agreement}. For every
prepared case, all five parsers run on the same (pattern, input) pair.
Two preconditions are checked. First, every parser returns the case's
verified membership outcome. Second, within each family the parsers
agree with each other. The three POSIX variants build the same tree,
and the two non-POSIX variants build the same tree. Agreement 
on the parse tree shape in between them is possible. 
The measured quantity is cross-family tree agreement. Of the cases
where both families matched and were internally consistent, how many
produced the same tree. 
Each parser call runs in a subprocess with a 2-second wall-clock
timeout. Timeouts and crashes are counted separately from tree-shape
outcomes.

The two datasets are not pooled, and each runs through its own binary.

\begin{itemize}
  \item \texttt{demo\_parser\_agreement} on the 463
        full-match-stripped S2ELab patterns.
  \item \texttt{demo\_parser\_agreement\_pathological} on the
        113-row pathological set.
\end{itemize}

%
%
%

\subsection{Discussion}

Both preconditions hold throughout: every parser matches the verified
outcome (100\% on both datasets), and no within-family shape violation
was printed by either run.

Cross-family disagreement concentrates sharply. S2ELab's 17
disagreements are 0.3\% of 6544 compared. The pathological set's are
10.4\% of 202, and within that set category B alone accounts for 18 of
the 21 (64.3\% of its own 28 compared). Category B is exactly the
category built around alternatives sharing a prefix under a quantifier,
the most reliable way to construct genuine ambiguity on purpose.
Categories E and F, also alternation-heavy by design, show smaller but
nonzero disagreement (12.5\% and 8.3\%). Every other category shows
zero. Disagreement reflects the POSIX-versus-non-POSIX policy
difference visible exactly on the ambiguous cases the pathological set
was built to contain, and absent everywhere a pattern leaves only one
decomposition.

The agreement check is what surfaced one dataset defect. Categories A,
B, and C of an early pathological pass all reported 100\% match
agreement. Category H reported 75\%, with two rows, \texttt{P29}
(\verb|(.+){10}|) and \texttt{P31} (\verb|(.*){10}|), where all five
parsers returned match against an input the dataset labeled a
non-match. Both patterns' non-match inputs had been built by appending
a trailing character to a matching string, which only forces a
non-match when the pattern bounds the total input length. Neither
pattern does. \texttt{P31} has no genuine non-match at any length,
since ten \texttt{.*} groups accept the empty string. \texttt{P29}'s
non-match input was replaced with a fixed 9-character string, one
short of the ten-group minimum the pattern needs. \texttt{P31}'s was
removed. Category H now reports 100\%.

\section{Performance Analysis}
\label{sec:eval-performance}

The four parsers are compared on execution time and memory.

%
%
%

\subsection{Cost drivers}
\label{sec:eval-cost-drivers}

Three properties of a corpus make the four parsers cost something.

\textbf{Input length.} The two standard derivative parsers retain
every intermediate expression until the backward pass, so their live
state grows with the number of characters consumed. The bit-coded and
partial-derivative parsers do not carry that history.

\textbf{Pattern structure.} Translation size and derivative cost scale
with the pattern's own node count. This splits into two phases the
evaluation measures separately. \emph{Translation} (PCRE string to
\texttt{Regex}, measured once per distinct pattern by
\texttt{bench\_corpus\_translate} and
\texttt{bench\_pathological\_translate}) and the \emph{derivative
loop} (measured per pattern-input pair by the timing and memory
benches below). A pattern can be cheap to translate and expensive to
derive, or the reverse. Categories C, D, J, K stress the first phase.
Categories A, B, E, F, H stress the second.

\textbf{Ambiguity.} When a single input admits several valid
decompositions, the parsers keep more state alive and must choose
among the surviving trees. Categories B, E, F isolate this at a
controlled scale.

A fixed per-call cost is paid once per pattern-input pair regardless
of length, structure, or ambiguity. It is why the four parsers differ
even on the corpus's shortest entries.

S2ELab's patterns are short, human-authored rules with modest
structural complexity and short given inputs, so it exercises all
three drivers mildly. This is why a second, deliberately extreme
dataset exists.

%

Three observations. Categories A, B, and E confirm the design intent:
both standard variants time out on 60--71\% of entries while
\texttt{deriv\_bc} and both partial-derivative variants stay near 0\%.
Category F is the routine category where \texttt{deriv\_bc} itself
times out at a real rate (40\%, against under 4\% for the
partial-derivative pair), by design: F is calibrated to show the
F-family mechanism defeating bit-coding too. Category C's timeout rate
is close to uniform across all five parsers (57\% for both standard
variants, 18--25\% for the other three) rather than concentrated on the
standard pair, consistent with C's cost being dominated by
\texttt{core\_regex}'s own bound-unrolling at translation time, a cost
every parser pays identically before its derivative loop runs.

Category H is the one category where the ranking inverts:
\texttt{deriv\_bc} times out less often (7\%) than either
partial-derivative variant (both 18\%). H's mechanism, several
unbounded groups placed adjacently rather than nested, is the
frontier-of-residuals shape the partial-derivative construction is
usually best at.

for a dedicated sweep that pushes past the routine default, using
\texttt{PATHO\_ROW\_ID} and \texttt{PATHO\_N}:

\begin{itemize}
  \item \textbf{P60}/\textbf{P61}: the pattern,
        \texttt{(a|b|ab)*}, swept into the millions.
  \item \textbf{P20}: the same family's \texttt{+} variant, pushed to
        the same scale.
  \item \textbf{P01}: the single most-cited ReDoS example,
        \texttt{(a+)+}.
  \item \textbf{P09}: the same nested-quantifier family, swept
        further.
  \item \textbf{P25}, \textbf{P27}, \textbf{P28}: the
        alternation-star-then-literal family, where \texttt{deriv\_bc}
        itself eventually times out.
\end{itemize}

Categories C, D, and H have no row singled out, since their calibrated
default sweep already reaches each category's interesting regime
within the routine pass.

The FLOPS'14 paper benchmarks two implementations, built around two
different derivative constructions. \texttt{parseBC} (its Figures~5
and~6) is the general, DFA-compiled bit-coded algorithm that builds
the full ambiguous POSIX parse tree from the standard (non-partial)
derivative -- the algorithm \texttt{deriv\_bc} implements here.
\texttt{DERIV} is a separate, narrower implementation built for POSIX
submatching, which records only the last iteration of each Kleene
star, a strictly easier problem than full parse-tree construction; the
paper does not describe \texttt{DERIV}'s own construction beyond that
one detail. Only \texttt{DERIV} appears in their Figure~7.
\texttt{pderiv\_bc} and \texttt{pderiv\_std} are this project's own
bit-coded and non-bit-coded constructions over \emph{partial}
derivatives, a separate idea from \citet{sulzmannlu2012}'s own earlier
work and not something FLOPS'14 benchmarks at all. Figure~\ref{fig:patho-fig7}
therefore uses the same pattern and scale as Figure~7, with
\texttt{deriv\_bc} as the one line directly comparable to
\texttt{parseBC}'s prose description, alongside the project's other
parsers for context.

Both standard variants crash rather than time out at every point
tested, including the smallest (500\,K for P61). Crashed entries

itself says something: a crash that takes the same time at every scale
is one that happens early relative to the input.

The two variants fail by two independent mechanisms. The recursive
variant recurses once per character before injecting, so its stack
depth equals characters consumed, and at 500\,K to 10\,M characters
this exceeds the worker's per-call stack budget. The loop variant has
no per-character recursion, yet crashes on the same inputs. Its
forward loop pushes every intermediate derivative onto a single
\texttt{Vec<Regex>} and keeps them alive until the backward pass, and
\texttt{deriv} runs with no simplification step in between, so nothing
bounds the stored sequence's growth on a genuinely ambiguous pattern.
Table~\ref{tab:growth}'s smaller example already shows
\texttt{deriv\_std} reaching 9179 nodes at $n=16$ characters, and at
500\,K+ characters the stored sequence exhausts memory well inside the
120-second cap. The two failures are independent: fixing the stack
overflow alone would not rescue the loop variant.

alternation branch once \texttt{simp}'s dedup ignores bit history. This
is the same fix responsible for \texttt{deriv\_bc}'s bounded growth
above.

\subsubsection{Peak memory in the large}

The max-peak column of Table~\ref{tab:memory} answers whether any
S2ELab pattern causes a peak infeasible on a production machine. At
full corpus scale the answer is no. The highest single-entry peak is
556.8\,MB, for \texttt{deriv\_std\_loop} (\texttt{deriv\_std\_rec}
peaks at 514.8\,MB); the other three peak in single-digit megabytes.

That is a property of S2ELab's input lengths, not a general bound.
Figure~\ref{fig:patho-fig7}, on inputs several orders of
magnitude longer, shows the same two-pass retention pushing both
standard variants to crash at one million characters, while the
bit-coded and partial-derivative variants keep growing smoothly into
the low gigabytes out to ten million, a controlled, roughly linear
growth rather than an outright failure.

\section{Discussion of Results}
\label{sec:eval-discussion}

%
%
%

\subsection{Cost of the standard construction}

The two standard derivative parsers are consistently the slowest and
memory-heaviest. This follows directly from the two-pass structure of
Chapter~\ref{sec:derivative-parser}: every intermediate expression is
stored until the backward pass completes. On \texttt{a*} input of
length $n$, state size grows linearly in $n$, while the bit-coded and
partial-derivative parsers stay constant.

On the full corpus the two standard variants are close in mean time
(7.650\,ms against 7.323\,ms) but the outcome split shows where the
difference lives. On matching entries, \texttt{deriv\_std\_loop}'s
total (66.323\,s) is measurably below \texttt{deriv\_std\_rec}'s
(69.633\,s), while their non-match totals are almost the same. The
recursion-versus-iteration difference is specifically a cost of the
matching path.

%
%
%

\subsection{Cost of bit-coding}
\label{sec:eval-cost-bit-coding}

For the standard-derivative family, bit-coding wins unconditionally.
\texttt{deriv\_bc}'s mean time (1.808\,ms) is roughly $4$--$4.25\times$
below either standard variant's, and its peak allocation (5.1\,MB) is
about $100$--$109\times$ below theirs. The trade-off is that the forward pass
cannot simplify away redundant branches without losing reconstruction
information. The retention is not wasted: it is exactly what makes
single-pass reconstruction possible, and \texttt{deriv\_bc}'s decode
step is close to free (0.005\,ms mean).

%
%

\subsection{Cost of partial derivatives}
\label{sec:eval-cost-partial-derivatives}


%

\subsection{Threats to validity}

\textbf{Corpus scope.} S2ELab is one dataset's own domain and
convention. A corpus from a different domain might exhibit different
acceptance rates and timing profiles. The default scope measures only
the 463 stripped patterns (Section~\ref{sec:eval-anchors}). 

(\texttt{BENCH\_MATCH\_INTENT=both}) with 115 patterns.

\textbf{The pathological set.} Each of its 113 rows isolates one
complexity mechanism at a controlled scale. It does not represent the
distribution of pattern shapes a real author would write. Most
categories sweep one parameter in isolation, so a pattern combining
two stress mechanisms at once is not directly represented.

\textbf{Measurement model.} Memory benches measure allocation counts,
not wall-clock memory pressure. The evaluator runs on a single
machine, so the wall-clock figures are CPU- and cache-specific.
