\chapter{Evaluation}
\label{sec:evaluation}

This chapter evaluates five parser candidates implemented in
Chapters~\ref{sec:derivative-parser} and
\ref{sec:partial-derivative-parser}:

\begin{itemize}
  \item \texttt{deriv\_std\_rec}, the standard derivative parser in
        its recursive form.
  \item \texttt{deriv\_std\_loop}, the standard derivative parser in
        its iterative form.
  \item \texttt{deriv\_bc}, the bit-coded derivative parser.
  \item \texttt{pderiv\_std}, the standard partial-derivative parser.
  \item \texttt{pderiv\_bc}, the bit-coded partial-derivative parser.
\end{itemize}

Section~\ref{sec:eval-criteria} states what is measured and how.
Section~\ref{sec:eval-dataset} describes the two data sources.
Section~\ref{sec:eval-performance} compares the five candidates on
stack depth, execution time, memory, and translation cost, and
reports how often the POSIX and non-POSIX parser families agree on
parse-tree shape. Section~\ref{sec:eval-discussion} interprets the
results.

All measurements were taken on an AMD Ryzen~5~5600
six-core processor with 16\,GB of RAM, running Pop!\_OS 24.04 LTS on
an AMD B550 chipset.

\section{Evaluation Criteria}
\label{sec:eval-criteria}

Three properties of a corpus make the five parsers cost something.

\textbf{Input length.} The two standard derivative parsers retain
every intermediate expression until the backward pass, so their live
state grows with the number of characters consumed. The bit-coded and
partial-derivative parsers do not carry that history.

\textbf{Pattern structure.} Translation size and derivative cost scale
with the pattern's own node count. This splits into two phases the
evaluation measures separately. \emph{Translation} (PCRE string to
\texttt{Regex}, measured once per distinct pattern) and the
\emph{derivative loop} (measured per pattern-input pair). A pattern
can be cheap to translate and expensive to derive, or the reverse.

\textbf{Ambiguity.} When a single input admits several valid
decompositions, the parsers keep more state alive and must choose
among the surviving trees.

A fixed per-call cost is paid once per pattern-input pair regardless
of length, structure, or ambiguity. It is why the five parsers differ
even on the corpus's shortest entries.

S2ELab's patterns are short, human-authored rules with modest
structural complexity and short given inputs, so it exercises all
three drivers mildly. This is why a second, deliberately extreme
dataset exists (Section~\ref{sec:eval-pathological}).

\subsection{What is measured}
\label{sec:eval-criteria-what}

Four quantities are measured, each by its own bench or demo, each
against both datasets.

\begin{itemize}
  \item \textbf{Stack depth.} How deep an input can push
        \texttt{deriv\_std\_rec}'s call stack and
        \texttt{deriv\_std\_loop}'s accumulated state before either
        one fails, isolated from every other cost
        (Section~\ref{sec:eval-stack-depth}).
  \item \textbf{Timing.} Wall-clock time per (pattern, input) pair,
        run once per entry, with no warm-up and no repetition
        (Section~\ref{sec:eval-timing}).
  \item \textbf{Memory.} Heap allocation per (pattern, input) pair,
        measured by a custom global-allocator wrapper
        (Section~\ref{sec:eval-memory}).
  \item \textbf{Translate.} The cost of turning a pattern string into
        a \texttt{Regex}, measured once per distinct pattern, separate
        from the derivative loop that then runs on it
        (Section~\ref{sec:eval-translate}).
\end{itemize}

Timing and memory each report mean, median, 99th percentile, and
maximum. Timing additionally splits its mean into three phases:
\emph{encode} (building the initial bit-coded or partial-derivative
state before any character is consumed), \emph{derive} (the
character-by-character loop itself), and \emph{decode} (reconstructing
a parse tree from the final state, where one is built at all).
\texttt{deriv\_std\_rec} and \texttt{deriv\_std\_loop} report their
entire cost under \emph{derive}, since neither has a separate encode
or decode step. Memory reports total bytes (every allocation,
including churn later freed), average bytes per entry, and max peak
(the highest live-byte high-water mark on any single entry, flat, not
averaged). The two are deliberately different: total bytes measures
allocator pressure, max peak measures the actual memory footprint a
production deployment would see. A parser can have a far higher total
than another while peaking lower, if it allocates and discards many
small objects rather than holding one large one.

\subsection{How it is measured}
\label{sec:eval-criteria-how}

Every timing and memory bench runs each (pattern, input) pair in its
own worker subprocess, isolated from the bench harness and from every
other entry. Two independent limits apply per entry.
\texttt{BENCH\_ENTRY\_TIMEOUT\_MS} is a wall-clock deadline; exceeding
it is recorded as \emph{timed out}, not a crash. A separate memory
ceiling (\texttt{BENCH\_MEM\_CAP\_MB}), enforced via a
\texttt{setrlimit(RLIMIT\_AS, ...)} call on the worker, bounds how much
address space a single entry may claim; exceeding it kills the worker
and is recorded as \emph{crashed}. Without this cap, an unbounded
entry risks the OS out-of-memory killer picking an arbitrary victim
process rather than the one actually responsible. A crashed worker's
exit is detected as a signal-terminated process with no exit code;
the harness does not yet distinguish a genuine stack overflow from a
worker killed by the memory cap, so a \emph{crashed} entry's recorded
reason should be read as ``the worker was killed by a signal,'' not
necessarily ``the worker overflowed its stack''
(Section~\ref{sec:eval-stack-depth} isolates the one measurement where
that distinction is made directly, by removing the memory cap
entirely).

\textbf{Macro-averaging.} Matches and non-matches are not balanced,
within a pattern or across patterns (Section~\ref{sec:eval-s2elab}): a
pattern with 40 matches and 2 non-matches contributes all 42, and a
pattern with 50 surviving examples contributes all 50, even when
another pattern in the same corpus contributes only one. The
resulting cross-pattern imbalance is corrected at averaging time.
Every S2ELab mean in this chapter is a macro-average, not a flat
average over every measured entry: each pattern's own mean is
computed first, then those per-pattern means are averaged together,
unweighted, so every pattern contributes once regardless of its own
example count. Median, 99th percentile, and maximum remain computed
over individual inputs, since they describe the cost of the single
worst input rather than of a typical pattern. The pathological set's
own tables need no such correction, since each of its categories is
already a small, individually-authored set of rows rather than a
corpus with a long tail.

\section{Dataset Preparation}
\label{sec:eval-dataset}

The evaluation uses two pattern sources, chosen for complementary
roles.

\textbf{S2ELab} \citep{s2elab-regexeval-dataset} comprises 762
patterns, each accompanied by a natural-language description and the
author's labeled \texttt{matches} and \texttt{non\_matches}. It
provides measurements on human-authored regular expressions with
author-supplied positive and negative examples, reflecting the kinds
of patterns encountered in practice. A benchmark corpus for a
membership-deciding parser needs, for each pattern, both a matching
string and a non-matching string; a source that does not ship such
pairs forces the corpus builder to manufacture them, and a manufactured
input reflects the sampler's bias. S2ELab ships both lists with every
pattern, so no generation step is needed.

\textbf{The pathological stress set} contains 113 hand-curated
patterns, grouped by the specific complexity mechanism each one
triggers. Within a category, each row defines a pattern and an input
as functions of one or both of two sweep parameters, the input length
$n$ and the pattern size $p$. A category's sweep is a set of values
for these parameters, applied uniformly across its rows and chosen so
that the measured cost moves from microseconds to failure as the
sweep progresses.

\subsubsection{Anchor stripping and corpus acceptance}
\label{sec:eval-anchors}

The frontend of Chapter~\ref{sec:frontend} rejects every anchor,
since \texttt{translate} has no \texttt{Regex} construct for a
position-dependent condition (Table~\ref{tab:surface-syntax}).
Before calling the frontend, the pipeline applies one exception of
its own: a pattern whose top level is a single
\texttt{\textasciicircum...\textdollar} wrap around the whole pattern
has that wrap stripped by \texttt{strip\_full\_anchors} in
\texttt{src/data/prepare.rs}, before \texttt{translate} runs. This is
safe precisely because the engine is full-string-matching only
(Section~\ref{sec:frontend-overview}): consuming the whole input
already requires both endpoints, so a top-level
\texttt{\textasciicircum...\textdollar} wrap is provably redundant
and can be removed without changing what the pattern denotes. Every
other anchor placement (start-only, end-only, nested, or more than one
pair) still reaches \texttt{translate} and is rejected there, for the
same reason the frontend rejects anchors generally: it cannot
translate them. The pipeline records the strip as part of the
pattern's \texttt{MatchIntent} tag (\texttt{ExplicitFullMatch}).

\textbf{Match intent groups.} Every accepted S2ELab pattern falls into
one of two groups. 463 carry the top-level wrap and have it stripped,
landing on the engine's native full-match reading. 115 carry no anchor
and are translated unchanged, still matched under full-string
semantics but with no way to tell whether the author meant a full
match or a search this project does not implement. Both groups are
written to the corpus, but every benchmark in this chapter defaults to
the 463 stripped patterns only: reporting a number for the remaining
115 would assume a reading of the pattern its own author never
committed to. Both groups remain available on opt-in via
\texttt{BENCH\_MATCH\_INTENT=both}.

\subsubsection{The pipeline}
\label{sec:eval-pipeline}

\texttt{run\_pipeline} turns the raw S2ELab JSON into the benchmark
corpus in six steps.

\begin{enumerate}
  \item \textbf{Extract.} Each entry's pattern and its author's own
        \texttt{matches}/\texttt{non\_matches} become one
        \texttt{ExtractedRule}.
  \item \textbf{Deduplicate.} A pattern byte-identical to one already
        seen this run is skipped.
  \item \textbf{Translate.} \texttt{core\_regex\_tagged} parses and
        translates, applying the anchor strip of
        Section~\ref{sec:eval-anchors}. A rejected pattern stops here.
  \item \textbf{Deduplicate examples.} A string appearing in both
        \texttt{matches} and \texttt{non\_matches} is kept once, as a
        positive.
  \item \textbf{Check labels.} Every surviving example is re-checked
        against the translated \texttt{Regex}. A disagreement is
        dropped, not corrected.
  \item \textbf{Write.} Each surviving pair becomes one line of
        \texttt{prepared.jsonl}, tagged with its \texttt{MatchIntent}.
\end{enumerate}

\label{sec:eval-worked-pipeline}

  "matches": ["12/31/2003", "01/01/1900", "11/31/2002", ...],
  "non_matches": ["1/1/2002", "01/01/02", "01/01/2004",

\caption{S2ELab entry 100, fields trimmed.}
\label{fig:s2elab-entry-100}
\end{figure}

\paragraph{Extract.} One \texttt{ExtractedRule} carrying the raw
expression and the two input lists.

\paragraph{Translate.} The top level is a single \texttt{Concat}
opening with \texttt{\textasciicircum} and closing with
\texttt{\textdollar}, so the strip of Section~\ref{sec:eval-anchors}
applies. Both anchors are removed before translation, and the entry is
tagged as a full-match pattern.

\paragraph{Check labels.} Every given example is run through the
translated \texttt{Regex}. The check is against the pattern's own
semantics, not real-world correctness. The given string
\texttt{"11/31/2002"} is listed as a match and is one under the
translated pattern, since the day group accepts \texttt{31} regardless
of month. The pattern silently accepts a November 31st the calendar
does not have, and the check keeps it because the author's claim and
the pattern's own language agree. Whether the pattern encodes a real
calendar is a question the check does not answer.

\paragraph{Write.} The surviving pairs are appended to
\texttt{prepared.jsonl}.

\subsection{The pathological stress set}
\label{sec:eval-pathological}

The pathological stress set is a second, hand-curated dataset whose
purpose is controlled measurement of asymptotic behaviour. S2ELab
supplies realistic patterns and realistic inputs, but its entries do
not stress any single cost mechanism at scale. The pathological set
does.

Each row specifies one regular expression plus a substitution rule
that maps a swept parameter (input length $n$, pattern size $p$, or
both) to a concrete (pattern, input) pair. Most rows hold the pattern
fixed and sweep $n$ as repeated characters. A smaller number sweep
$p$ by substituting a parameter into the pattern template before
parsing.

Every pattern in the set is authored directly against the engine's
full-string-matching model. None of them contains an anchor, a word
boundary, a backreference, lookaround, or a POSIX class, so every row
passes the frontend without a stripping step.

The 113 patterns are grouped into 12 categories
(Table~\ref{tab:patho-categories}). Each category isolates one
complexity mechanism and carries its own calibrated sweep, chosen so
that a routine, un-overridden pass crosses from all parsers measuring
in microseconds to the standard derivative parser timing out, within
the category's own default points.

\subsection{Stack depth}
\label{sec:eval-stack-depth}

\texttt{deriv\_std\_rec} and \texttt{deriv\_std\_loop} compute the
same values by two different control-flow shapes
(Section~\ref{sec:derivative-parser}): one recursive call per
character consumed, or one iteration of a loop. Every other bench in
this chapter runs on a 256\,MiB custom worker stack, generous enough
that call-stack depth is never the limiting factor. \texttt{bench\_stack\_depth}
deliberately runs on the OS's plain default thread stack instead, with
no memory cap, specifically so a doubling search over input length can
isolate stack depth from every other cost and distinguish a genuine
stack overflow (a signal with the Rust runtime's own
\texttt{"thread 'main' has overflowed its stack"} message) from
anything else.

\begin{table}[H]
\centering
\small
\begin{tabular}{llrll}
\hline
Row & Parser & Last $n$ reached & Outcome & Elapsed \\
\hline
P01 & \texttt{deriv\_std\_rec}  & 16        & timed out (15\,s cap) & 15.709\,s \\
P01 & \texttt{deriv\_std\_loop} & 16        & timed out (15\,s cap) & 15.799\,s \\
P30 & \texttt{deriv\_std\_rec}  & 64        & timed out (15\,s cap) & 21.237\,s \\
P30 & \texttt{deriv\_std\_loop} & 64        & timed out (15\,s cap) & 20.345\,s \\
E51 & \texttt{deriv\_std\_rec}  & 32{,}768  & crashed (stack overflow) & 1.234\,s \\
E51 & \texttt{deriv\_std\_loop} & 1{,}048{,}576 & reached sweep cap (2{,}000{,}000) & 0.160\,s \\
\hline
\end{tabular}
\caption{Doubling-search stack-depth results. P01/P30 time out on
derivation cost before stack depth becomes the limiting factor, a

\label{tab:stack-depth}

P01 (\texttt{(a+)+}) and P30 (a many-adjacent-groups pattern) both
exhaust their 15-second per-probe timeout at a tiny $n$, before either
parser's call stack is anywhere near its limit. These two rows measure
derivation cost, not stack depth, and are a negative control: they
confirm that a row needs a cheap, non-exploding derivative step before
a stack-depth sweep can say anything about stack depth specifically.

E51 is such a row: \texttt{a} repeated under \texttt{a*}, a pattern
with no ambiguity and a derivative step cheap enough that the doubling
search can push $n$ far before either timing out. On it,
\texttt{deriv\_std\_rec} crashes with a genuine stack overflow between
32{,}768 and 65{,}536 characters, consistent with one recursive call
per character against the OS's default stack size.
\texttt{deriv\_std\_loop} has no per-character recursion and survives
every $n$ up to the sweep's own cap of 2{,}000{,}000 characters,
over sixty times further than where the recursive variant dies. This
is the only place in the evaluation where the two standard-derivative
variants are compared on stack depth specifically, isolated from
every other cost; everywhere else in this chapter, both variants are
measured together on the same 256\,MiB custom stack, where neither one
runs out of stack before something else fails first.

Three observations. Categories A, B, and E confirm the design intent:
both standard variants time out on 56--70\% of entries while
\texttt{deriv\_bc} and both partial-derivative variants stay under
5\%. Category F is the routine category where \texttt{deriv\_bc}
itself times out at a real rate (40\%, against under 4\% for the
partial-derivative pair), by design: F is calibrated to show the
F-family mechanism defeating bit-coding too. Category C's timeout rate
is close to uniform across all five parsers (57\% for both standard
variants, 18--25\% for the other three) rather than concentrated on the
standard pair, consistent with C's cost being dominated by
\texttt{core\_regex}'s own bound-unrolling at translation time, a cost
every parser pays identically before its derivative loop runs.

Category H is the one category where the ranking inverts:
\texttt{deriv\_bc} times out less often (7\%) than either
partial-derivative variant (both 14\%). H's mechanism, several
unbounded groups placed adjacently rather than nested, is the
frontier-of-residuals shape the partial-derivative construction is
usually best at.

\subsubsection{Pathological (individual representatives)}
\label{sec:eval-timing-patho-representatives}

\textbf{Individually swept representatives.} Eight rows are singled
out for a dedicated sweep that pushes past the routine default, using
\texttt{PATHO\_ROW\_ID} and \texttt{PATHO\_N}:

\begin{itemize}
  \item \textbf{P60}/\textbf{P61}: the pattern,
        \texttt{(a|b|ab)*}, swept into the millions.
  \item \textbf{P20}: the same family's \texttt{+} variant, pushed to
        the same scale.
  \item \textbf{P01}: the single most-cited ReDoS example,
        \texttt{(a+)+}.
  \item \textbf{P09}: the same nested-quantifier family, swept
        further.
  \item \textbf{P25}, \textbf{P27}, \textbf{P28}: the
        alternation-star-then-literal family, where \texttt{deriv\_bc}
        itself eventually times out.
\end{itemize}

Categories C, D, and H have no row singled out, since their calibrated
default sweep already reaches each category's interesting regime
within the routine pass.

The FLOPS'14 paper benchmarks two implementations, built around two
different derivative constructions. \texttt{parseBC} (its Figures~5
and~6) is the general, DFA-compiled bit-coded algorithm that builds
the full ambiguous POSIX parse tree from the standard (non-partial)
derivative -- the algorithm \texttt{deriv\_bc} implements here.
\texttt{DERIV} is a separate, narrower implementation built for POSIX
submatching, which records only the last iteration of each Kleene
star, a strictly easier problem than full parse-tree construction; the
paper does not describe \texttt{DERIV}'s own construction beyond that
one detail. Only \texttt{DERIV} appears in their Figure~7.
\texttt{pderiv\_bc} and \texttt{pderiv\_std} are this project's own
bit-coded and non-bit-coded constructions over \emph{partial}
derivatives, a separate idea from \citet{sulzmannlu2012}'s own earlier
work and not something FLOPS'14 benchmarks at all. Figure~\ref{fig:patho-fig7}
therefore uses the same pattern and scale as Figure~7, with
\texttt{deriv\_bc} as the one line directly comparable to
\texttt{parseBC}'s prose description, alongside the project's other
parsers for context.

\texttt{deriv\_std\_rec}. If these crashes were about call-stack depth,
the two variants would not die at the same input length. They do,
which means it is the shared, two-pass retention of every intermediate
derivative -- not which control-flow shape walks the input -- that
exhausts the memory cap here.

the pattern: P60 survives to 5{,}000 characters before crashing, while
P27 and P28 (nested-class-under-double-star patterns) crash already at

too, between one and two orders of magnitude past where the standard
variants already crashed -- consistent with
Section~\ref{sec:eval-timing-pathological}'s routine-sweep finding
that category F is the one category where bit-coding alone is not
enough.

\subsection{Memory}
\label{sec:eval-memory}

\texttt{bench\_corpus\_memory} and \texttt{bench\_pathological\_memory}
replace the system allocator with a wrapper that counts allocated
bytes and reports three figures per parser: total bytes (every
allocation including churn), average bytes per entry (macro-average
for S2ELab, same as the timing mean), and max peak (highest live-byte
high-water mark on any single entry, flat). Like their timing
counterparts, they read \texttt{BENCH\_PATTERN\_LIMIT} and
\texttt{BENCH\_MATCH\_INTENT} (S2ELab) or the \texttt{PATHO\_*}
variables (pathological).

Heap-only accounting: each worker's call-thread stack is invisible to
it, so a pattern dominated by recursion depth would under-report here
-- Section~\ref{sec:eval-stack-depth} measures that separately, with
the memory cap removed entirely.

factor of about $114$--$144\times$. The standard parser retains its
full derivation sequence for the backward pass; \texttt{deriv\_bc}
carries only a flat bit vector. The same pattern holds in total and
average bytes, though less sharply (roughly $1.9\times$ and
$2\times$).

The partial-derivative pair behaves differently from what the growth
curves alone suggest. \texttt{pderiv\_std} is lower than
\texttt{pderiv\_bc} on every column here (average bytes 0.403 against
0.412\,MB, peak 2.5 against 3.8\,MB), the reverse of the timing gap on
the same corpus. At S2ELab's short input lengths the partial-derivative
frontier is already small regardless of construction, so
\texttt{pderiv\_bc}'s extra bit-tracking machinery is pure overhead.
The asymptotic bound-state argument is about how the two scale as
input grows, not which is smaller at S2ELab's input lengths.

On \texttt{(a+(b+ab))*}, \texttt{deriv\_std} reaches 9179 nodes at

nodes forever. \texttt{simp} dedups branches by structural shape
alone, ignoring bit history, so the same-shape branches this pattern
produces at every step collapse into one. The gap is therefore not a
fixed cost of carrying reconstruction information, as for \texttt{a*},
but the difference between a construction whose branches merge and one
whose branches do not.

(2048 nodes at $n=16$), now that \texttt{pderiv\_std} builds its
residuals with the same \texttt{smart\_seq} construction
\texttt{pderiv\_bc} already used. Their live state is the frontier of
residuals, not a single expression, and the accumulation is bounded by
the pattern's own size, well above \texttt{deriv\_bc}'s fully-collapsed
total but far below \texttt{deriv\_std}'s.

\texttt{(a+(b+ab))*}'s derivative collapses to a single top-level
alternation branch once \texttt{simp}'s dedup ignores bit history. This
is the same fix responsible for \texttt{deriv\_bc}'s bounded growth
above.

answer is no: the highest single-entry peak is 737.6\,MB, for
\texttt{deriv\_std\_loop} (\texttt{deriv\_std\_rec} peaks at
582.4\,MB); the other three peak in single-digit megabytes. That is a
property of S2ELab's input lengths, not a general bound. The
representative sweeps below, on inputs several orders of magnitude
longer, show the same two-pass retention pushing both standard
variants to crash well before a million characters on most rows,
while the bit-coded and partial-derivative variants keep growing
smoothly into the low gigabytes, a controlled, roughly linear growth
rather than an outright failure.

alternation-heavy family, and its forced single bit-vector
representation never has to track more than a handful of live
candidates at once there.

\subsection{Translation depth caps}
\label{sec:eval-translate-depth}

Section~\ref{sec:frontend-bounds} named three fixed limits without
justifying them: \texttt{translate} refuses any \texttt{\{m,n\}} bound
whose \texttt{m} or \texttt{n} exceeds 1{,}000 (\texttt{MAX\_BOUND}),
and \texttt{core\_regex\_tagged} separately refuses a pattern whose
translated \texttt{Regex} exceeds 20{,}000 nodes
(\texttt{MAX\_CORE\_NODES}) or whose estimated nesting depth exceeds
2{,}000 (\texttt{MAX\_CORE\_DEPTH}). This section measures what the
first and third of those guard against directly, the same way
Section~\ref{sec:eval-stack-depth} measured \texttt{deriv\_std\_rec}'s
crash point rather than asserting one.

\texttt{translate} is a plain recursive function (one call per
\texttt{ExtPat} level), and \texttt{desugar\_bound}'s private
\texttt{optional\_extra} recurses once per unit of a bound's open part
(\texttt{n\,-\,m}): an unrolling deep enough risks overflowing
\texttt{translate}'s own call stack, independent of how the resulting
pattern is later matched. Unlike every other bench in this chapter,
which runs on a 256\,MiB custom worker stack
(Section~\ref{sec:eval-stack-depth}), \texttt{core\_regex\_tagged} runs
on whatever stack its caller gives it, and
\texttt{examples/dataset\_prepare.rs} never spawns a custom one -- in
practice the OS's plain default main-thread stack, 8\,MiB on this
machine (\texttt{ulimit -s}). \texttt{bench\_translate\_depth} measures
two mechanisms directly on that same 8\,MiB stack, with the same
process-isolated doubling sweep as Section~\ref{sec:eval-stack-depth}:
\texttt{bound\_unroll} reproduces \texttt{optional\_extra}'s exact
recursive shape (the real, public \texttt{translate} cannot be swept
past its own \texttt{MAX\_BOUND}, so the identical algorithm is
reproduced in the worker instead -- see its module doc); \texttt{syntactic\_nesting}
calls the real, uncapped \texttt{parse\_ext\_pattern}/\texttt{translate}
pipeline on a pattern with \texttt{n} nested non-capturing groups,
\texttt{(?:(?:...(?:a)...))}.

Both caps sit comfortably below where their own mechanism actually
breaks. A single bound's open part is capped at 1{,}000, roughly
$51\times$ below where \texttt{optional\_extra}'s own recursion starts
crashing; the estimated nesting depth is capped at 2{,}000, roughly
$3.2\times$ below where the real, uncapped pipeline crashes on
deeply-nested syntax. \texttt{prepare.rs}'s own depth estimate for a
bound (\texttt{estimated\_translated\_depth}) uses \texttt{hi} rather
than the smaller \texttt{hi\,-\,lo} that \texttt{optional\_extra}
actually recurses to, so the pre-translation check is itself
conservative on top of that margin, never under-estimating the real
risk. (These margins hold for a release build, the only way this
pipeline is run in practice; a debug build's larger per-call frames
would crash sooner, at a smaller $N$, in both mechanisms.)

\texttt{MAX\_BOUND} also comfortably covers real use, not just real
risk: \texttt{demo\_bound\_usage} walks every S2ELab pattern's
\texttt{ExtPat} and collects every \texttt{Bound} node's own
\texttt{hi} (or \texttt{lo} if unbounded above) anywhere in it, not
just at the top level. Of 762 raw patterns (714 parse), 442 contain at
least one bound, 1{,}769 bound occurrences in total; the largest single
value found anywhere in the corpus is 67 (median 2, 99th percentile
16). No S2ELab rule asks for anything within two orders of magnitude of
the 1{,}000 cap.

\texttt{MAX\_CORE\_NODES} is a different kind of limit: node count has
no comparable crash cliff the way recursion depth does (cost grows
smoothly, not in a single catastrophic step), so it is sized by
coverage instead. Section~\ref{sec:eval-translate-s2elab} already
reports the figure this leans on: the largest pattern anywhere in
S2ELab translates to 18{,}707 nodes, so 20{,}000 covers every pattern
this evaluation needed to represent with headroom to spare, while
still bounding how much a single malformed or adversarial pattern can
cost to store and translate.

\texttt{bench\_translate\_depth} and \texttt{demo\_bound\_usage} are
both runnable directly, the same as every other bench and demo in this
chapter.

\subsection{Parse Tree Shape Agreement}
\label{sec:eval-agreement}

\subsubsection{Method}
\label{sec:eval-agreement-method}

Every case in the prepared corpus carries a verified outcome, so
membership is a precondition, not something this section establishes.
The question here is parse-tree shape. On a matching case, the POSIX
parsers and the non-POSIX parsers may build different trees, since the
same input can admit several valid decompositions. Some inputs force
both policies onto the same structure. This section measures how
often.

The check is implemented in \texttt{demo\_parser\_agreement}. For every
prepared case, all five parsers run on the same (pattern, input) pair.
Two preconditions are checked. First, every parser returns the case's
verified membership outcome. Second, within each family the parsers
agree with each other. The three POSIX variants build the same tree,
and the two non-POSIX variants build the same tree. Agreement
on the parse tree shape in between them is possible.
The measured quantity is cross-family tree agreement. Of the cases
where both families matched and were internally consistent, how many
produced the same tree.
Each parser call runs in a subprocess with a 2-second wall-clock
timeout. Timeouts and crashes are counted separately from tree-shape
outcomes.

The two datasets are not pooled, and each runs through its own binary.

\begin{itemize}
  \item \texttt{demo\_parser\_agreement} on the 572 usable S2ELab
        patterns, both match-intent groups.
  \item \texttt{demo\_parser\_agreement\_pathological} on the
        113-row pathological set.
\end{itemize}

\subsubsection{Discussion}
\label{sec:eval-agreement-discussion}

Both preconditions hold throughout: every parser matches the verified
outcome (100\% on both datasets), and no within-family shape violation
was printed by either run.

Cross-family disagreement concentrates sharply. S2ELab's 21
disagreements are 0.3\% of 7041 compared. The pathological set's are
10.1\% of 207, and within that set category B alone accounts for 18 of
the 21 (64.3\% of its own 28 compared). Category B is exactly the
category built around alternatives sharing a prefix under a quantifier,
the most reliable way to construct genuine ambiguity on purpose.
Categories E and F, also alternation-heavy by design, show smaller but
nonzero disagreement (12.5\% and 8.3\%). Every other category shows
zero. Disagreement reflects the POSIX-versus-non-POSIX policy
difference visible exactly on the ambiguous cases the pathological set
was built to contain, and absent everywhere a pattern leaves only one
decomposition.

The agreement check is what surfaced one dataset defect. Categories A,
B, and C of an early pathological pass all reported 100\% match
agreement. Category H reported 75\%, with two rows, \texttt{P29}
(\verb|(.+){10}|) and \texttt{P31} (\verb|(.*){10}|), where all five
parsers returned match against an input the dataset labeled a
non-match. Both patterns' non-match inputs had been built by appending
a trailing character to a matching string, which only forces a
non-match when the pattern bounds the total input length. Neither
pattern does. \texttt{P31} has no genuine non-match at any length,
since ten \texttt{.*} groups accept the empty string. \texttt{P29}'s
non-match input was replaced with a fixed 9-character string, one
short of the ten-group minimum the pattern needs. \texttt{P31}'s was
removed. Category H now reports 100\%.

\textbf{A concrete S2ELab disagreement.} Table~\ref{tab:agreement}'s
21 S2ELab disagreements are real patterns, not synthetic ones. The
shortest to typeset is S2ELab's loosely-formatted-number pattern,
\verb|^[-+]?([0-9]{1,3}[,]?)?([0-9]{3}[,]?)*[.]?[0-9]*$|, on the input
\texttt{"9000"}. Figure~\ref{fig:agreement-sample} gives both parsers'
raw output. Both trees flatten (Section~\ref{sec:eval-translate}'s
sibling function, \texttt{flatten}, concatenates every \texttt{Char}
leaf left to right) to the same string, \texttt{"9000"}, confirming
both really did match the same input -- the disagreement is purely
about tree shape. The two outputs share an 80-character common prefix
through the point where the first digit, \texttt{'9'}, is matched by
\verb|[0-9]{1,3}|'s single mandatory copy; they diverge at that
group's first \emph{optional} copy. \texttt{posix (bc)} takes
\texttt{Left(Empty)} there -- declining the two optional copies
entirely, so the mandatory-copy group matches only \texttt{"9"} -- and
its one \texttt{Star} with a non-empty list (one element) then
accounts for \verb|([0-9]{3}[,]?)*| matching exactly one iteration,
\texttt{"000"}. \texttt{non-posix (pbc)} instead takes both optional
copies (\texttt{Right(Pair(...))} twice), so the mandatory-copy group
matches \texttt{"900"}; its corresponding \texttt{Star} is then empty,
and the one remaining digit, \texttt{"0"}, is caught by the trailing
\verb|[0-9]*| instead. Same four characters, same pattern, two
different ways to apportion them across three overlapping quantified
groups -- exactly the shape ambiguity Section~\ref{sec:eval-agreement}
measures, now visible on a real corpus entry rather than a
purpose-built pathological row.

\section{Discussion of Results}
\label{sec:eval-discussion}

%
%
%

\subsection{Cost of the standard construction}

The two standard derivative parsers are consistently the slowest and
memory-heaviest. This follows directly from the two-pass structure of
Chapter~\ref{sec:derivative-parser}: every intermediate expression is
stored until the backward pass completes. On \texttt{a*} input of
length $n$, state size grows linearly in $n$, while the bit-coded and
partial-derivative parsers stay constant.

On the full corpus the two standard variants are close in mean time
(7.718\,ms against 7.430\,ms) but the outcome split shows where the
difference lives. On matching entries, \texttt{deriv\_std\_loop}'s
total (70.782\,s) is measurably below \texttt{deriv\_std\_rec}'s
(74.725\,s), while their non-match totals are almost the same. The
recursion-versus-iteration difference is specifically a cost of the
matching path, confirmed directly at Figure~7 scale and beyond
(Table~\ref{tab:patho-crash-thresholds}): the two variants crash at
identical input lengths and near-identical memory figures on every
representative row, which rules out recursion depth as the mechanism
there and leaves the two-pass retention both variants share as the
only remaining explanation. Stack depth specifically is where the two
variants do diverge sharply (Section~\ref{sec:eval-stack-depth}):
\texttt{deriv\_std\_loop} survives over sixty times further than
\texttt{deriv\_std\_rec} on a pattern engineered to isolate that one
cost alone, with the memory cap removed. The two findings are not in
tension. They describe two different failure modes, and which one a
given pattern hits first depends on whether its derivative sequence or
its character count is the thing actually growing.

%
%
%

\subsection{Cost of bit-coding}
\label{sec:eval-cost-bit-coding}

For the standard-derivative family, bit-coding wins unconditionally.
\texttt{deriv\_bc}'s mean time (1.699\,ms) is roughly $4$--$4.5\times$
below either standard variant's, and its peak allocation (5.1\,MB) is
about $114$--$144\times$ below theirs. The trade-off is that the forward pass
cannot simplify away redundant branches without losing reconstruction
information. The retention is not wasted: it is exactly what makes
single-pass reconstruction possible, and \texttt{deriv\_bc}'s decode
step is close to free (well under a tenth of a millisecond mean).

The representative sweeps push this further: \texttt{deriv\_bc}
survives every swept input length on six of the eight representative
rows where both standard variants crash outright, at scales ranging
from thousands of characters past the crash point (P27/P28) to ten
million (P60, P20). Section~\ref{sec:eval-memory-patho-representatives}'s
caveat applies directly here: \texttt{deriv\_bc}'s cumulative
allocation at that scale is large (up to 271\,GB of total churn on
P20's full sweep), but its peak live footprint stays in the low
gigabytes throughout, the distinction between allocator pressure and
actual memory held that motivates reporting both figures separately
(Section~\ref{sec:eval-criteria-what}).

%
%
%

\subsection{Cost of partial derivatives}
\label{sec:eval-cost-partial-derivatives}

The two partial-derivative parsers are the fastest and most
memory-light on the full S2ELab corpus, clearly ahead of either
derivative-based variant. They split the residual into a set of states
rather than combining into one expression, which keeps each state
small and avoids the alternation growth the standard derivative
parser suffers.

Within the pair, bit-coding's advantage is not unconditional the way
it is for the standard-derivative family, and which variant wins
depends on more than scale. On the full corpus, \texttt{pderiv\_std}
is marginally ahead on every figure: mean time (0.616 against
0.625\,ms), average bytes (0.403 against 0.412\,MB), and peak bytes
(2.5 against 3.8\,MB). At Figure~7 scale, the ranking splits by row.
On P60 (\texttt{(a|b|ab)*} over `a'-repeated input),
\texttt{pderiv\_std} stays faster at every point, with a stable
gap that does not narrow with input length. On P61 (the same
pattern over `ab'-repeated input) the ranking flips:
\texttt{pderiv\_bc} is faster at every point, with a smaller but
equally consistent gap. On P20 (\texttt{(a|b|ab)+}),
\texttt{pderiv\_bc} is both faster and lower-peak than
\texttt{pderiv\_std} (3.27 against 4.97\,GB peak over the full sweep).
The finding is that the input shape changes which variant wins, not
just how large the gap is. Bit-coding's cost for the
partial-derivative construction is a fixed per-step overhead, and
whether it pays for itself depends on the pattern and input together,
not on scale alone.

The price of partial derivatives, independent of which variant, is
that they produce a non-POSIX tree. This is a specification
difference, not a deficiency, and it is why the two families are
compared separately in Section~\ref{sec:eval-agreement}.

%
%

\subsection{Threats to validity}

\textbf{Corpus scope.} S2ELab is one dataset's own domain and
convention. A corpus from a different domain might exhibit different
acceptance rates and timing profiles. The default scope measures only
the 463 stripped patterns (Section~\ref{sec:eval-anchors}). A
different, defensible choice (\texttt{BENCH\_MATCH\_INTENT=both}) would
fold in the remaining 115 patterns and could shift absolute numbers,
though not the ordering among parsers, which does not depend on which
patterns are included.

\textbf{The pathological set.} Each of its 113 rows isolates one
complexity mechanism at a controlled scale. It does not represent the
distribution of pattern shapes a real author would write. Most
categories sweep one parameter in isolation, so a pattern combining
two stress mechanisms at once is not directly represented.

\textbf{Measurement model.} Memory benches measure allocation counts,
not wall-clock memory pressure. The evaluator runs on a single
machine, so the wall-clock figures are CPU- and cache-specific. A
\emph{crashed} entry's recorded reason is ``killed by signal,'' not a
confirmed diagnosis of stack overflow specifically
(Section~\ref{sec:eval-criteria-how}); Section~\ref{sec:eval-stack-depth}
is the one measurement in this chapter that removes the memory cap and
so can attribute a crash to stack overflow directly, and it is the
basis for the claim, elsewhere in this chapter, that the
representative-row crashes are a shared-retention effect rather than a
recursion-depth one.
