\chapter{Evaluation}
\label{sec:evaluation}

This chapter evaluates the derivative and partial-derivative parsers developed in
Chapters~\ref{sec:derivative-parser} and~\ref{sec:partial-derivative-parser}.
Using two datasets and a common set of measurement criteria, it compares the
candidate parsers in terms of stack depth, execution time, memory consumption,
and translation cost, and assesses how far they agree on membership decisions
and parse-tree shape. The resulting findings are then interpreted and discussed.

All measurements were taken on an AMD Ryzen~5~5600 six-core processor with
16\,GB of RAM, running Pop!\_OS 24.04 LTS on an AMD B550 chipset.

%
%
%


\section{Candidates}
\label{sec:eval-candidates}

All five candidates share the same interface. Each takes an input
string and a translated \texttt{Regex} and returns either a parse
tree or no match:
\[
p :: (\mathit{String}, \mathit{Regex}) \to
     \mathit{Option\langle ParseTree\rangle}.
\]

The input $(w, r)$ is called an \emph{entry}, where $w$
is an input string and $r$ is a translated \texttt{Regex}.
The candidates fall into two families according to their parse-tree
selection strategy.

\textbf{POSIX family.} These three parsers select the POSIX parse tree.
\begin{itemize}
  \item \texttt{deriv\_std\_rec}, the standard derivative parser in recursive
        form (Section~\ref{sec:deriv-std-parser}).
  \item \texttt{deriv\_std\_loop}, the standard derivative parser in iterative
        form, holding the residual sequence in a \texttt{Vec} rather than a call stack.
  \item \texttt{deriv\_bc}, the bit-coded derivative parser
        (Section~\ref{sec:deriv-bc-driver}).
\end{itemize}

\textbf{Non-POSIX family.} These two parsers select the leftmost parse tree.
\begin{itemize}
  \item \texttt{pderiv\_std}, the standard partial-derivative parser
        (Section~\ref{sec:pderiv-std-parser}).
  \item \texttt{pderiv\_bc}, the bit-coded partial-derivative parser
        (Section~\ref{sec:pderiv-bc-parser}).
\end{itemize}

All five parsers are expected to agree on membership. An entry must
either be accepted or rejected by every candidate. Their parse trees,
however, need not have the same shape. Within each family, the
parsers are expected to agree on both membership and tree shape,
since they implement the same parse-tree selection strategy.
Across families, the selected trees may differ for ambiguous patterns.

%
%

\section{Evaluation Criteria}
\label{sec:eval-criteria}

The evaluation addresses \emph{performance}, the time, memory, and translation
cost of each candidate, and \emph{correctness}, whether the five candidates
agree on membership and parse-tree shape. First, a stack-depth comparison of
the two forms of the standard derivative parser determines whether the
iterative optimization is worth adopting.

%
%
%

\subsection{Measurement Setup}
\label{sec:eval-criteria-setup}

Each entry runs in its own worker subprocess for timing, memory,
stack-depth, and parse-agreement measurements. This allows hung or
crashed calls to be terminated and their memory reclaimed; stable Rust
does not support terminating individual threads.

\begin{itemize}
  \item \emph{Measured}: the worker exited zero and reported a result line.
  \item \emph{Timed out}: the worker exceeded the per-entry wall-clock
        deadline, two seconds by default, and was killed by the parent.
  \item \emph{Crashed}: the worker exited non-zero or was killed by a signal,
        covering both a stack overflow and an out-of-memory kill when the
        optional memory ceiling is set.
\end{itemize}

Timing, memory, and parse-agreement workers run the parser call on a custom
256\,MiB stack. All candidates recurse over the pattern structure, so the
default stack overflows on deeply nested patterns before the measured input
sizes are reached. 
The larger stack is intended to prevent failures that reflect stack space
rather than the parser.

Each timing and memory run produces two putputs. A summary table of aggregate
candidate measurements and a per-entry file for comparing candidates
on individual entries.

%
%
%

\subsection{Timing}
\label{sec:eval-criteria-timing}

Each entry $(r, w)$ is timed once, without warm-up or repetition.
Translation is measured separately, 
and the worker's wall clock covers only the parser call $p(r, w)$.

For \texttt{deriv\_std\_rec}, \texttt{deriv\_std\_loop}, and
\texttt{pderiv\_std}, the entire call is reported as \emph{derive}. For
\texttt{deriv\_bc} and \texttt{pderiv\_bc}, the call is divided into
\emph{encode}, constructing the initial annotated state before any character of
$w$ is consumed; \emph{derive}, processing the input character by character;
and \emph{decode}, converting the final bit-string into a \texttt{ParseTree}.

Timing results use four statistics, aggregated differently for the two datasets:

\begin{itemize}
  \item \emph{Mean} is a macro-average over patterns of the real corpus, so
        a pattern with 200 entries and one with 2 contribute equally,
        and a flat mean for the synthetic set.
  \item \emph{Median}, \emph{99th percentile}, and \emph{maximum} are pooled
        over individual entries and describe the single worst entry rather
        than a typical pattern.
\end{itemize}

All four statistics represent lower bounds on the corresponding
execution times, since timed-out and crashed entries are excluded
rather than counted at their timeout values.

A separate \emph{wall} column measures the benchmark's entire loop over one
source pattern. It therefore exceeds $\mathit{entries} \times \mathit{mean}$ by
the per-entry process-spawn and pipe-round-trip overhead excluded from the
individual timings. It captures the total cost of reproducing a pattern's
results, harness included, but is not suitable for comparisons between
candidates.

%
%

\subsection{Memory}
\label{sec:eval-criteria-memory}

Memory is measured by a counting allocator inside the worker.
The baseline is recorded immediately before the parser call, 
so only allocations made during
$p(r, w)$ are counted. Three measures are distinguished:

\begin{itemize}
    \item \emph{Total bytes}: all memory allocated during the call, including
          allocations later freed.
    \item \emph{Average bytes}: total bytes divided by the number of
          completed entries.
    \item \emph{Max peak}: the highest byte count within a single call,
          measuring peak consumption.
\end{itemize}

Total and peak can differ substantially. Many small, short-lived allocations
give a high total but a low peak, while a single large, long-lived allocation
gives a moderate total but a high peak. Reporting both therefore separates
allocation activity from the memory footprint of a call. The average uses the
same averaging bases as the timing measurements. Total and peak are pooled
directly over entries.

The counting allocator sees heap allocations only, not the 256\,MiB worker
stack, so parsers dominated by recursion rather than allocation may appear
inexpensive here. 
Stack depth is evaluated separately for the two forms 
of the standard derivative parser

%
%

\subsection{Translation}
\label{sec:eval-criteria-translation}

Translation cost depends only on the source pattern, so each distinct pattern is
translated once rather than once per entry. It runs in the main process without
a worker subprocess, because the frontend enforces three resource limits:

\begin{itemize}
  \item \emph{Bound cap}: bounds the numeric value of any repetition bound.
  \item \emph{Depth cap}: bounds the estimated depth of the translated
        pattern.
  \item \emph{Node cap}: bounds the node count of the result.
\end{itemize}

Together the three ensure a translation measurement cannot hang or allocate
unboundedly the way a parser call can. The node cap is set empirically, large
enough to cover the node counts exercised by the benchmark suite.

Translation cost is characterised by four measurements:

\begin{itemize}
  \item \emph{Time}: the wall-clock duration of the translation call.
  \item \emph{Total bytes}: every allocation made during translation.
  \item \emph{Peak bytes}: the highest live-byte high-water mark during the
        call.
  \item \emph{Nodes}: the node count of the resulting \texttt{Regex}.
\end{itemize}

The counting allocator is reset before each pattern is translated and read
immediately after the call returns, so subsequent node counting and debug
rendering are excluded. Mean, median, 99th percentile, and maximum are pooled
directly over patterns. Since each pattern contributes exactly one measurement,
no macro-averaging is required. Rejected and panicked patterns produce no
measurement, so all four are lower bounds.

%
%

\subsection{Stack Depth}
\label{sec:eval-criteria-stack-depth}

\texttt{deriv\_std\_rec} and \texttt{deriv\_std\_loop} compute identical results
but maintain the residual sequence differently. The recursive implementation
stores it on the call stack, one frame per input character, whereas the
iterative implementation stores it in an explicit \texttt{Vec}. 
To compare their stack requirements, 
both run with the operating system's default thread stack with no memory cap.

The maximum surviving input length is found by a doubling search. Starting from
a small input length, the size is doubled after each successful probe until the
worker no longer completes. Each probe runs in its own worker subprocess, so a
stack overflow terminates only that process. The per-probe timeout is raised
from the default two seconds to fifteen, so slow derivatives have time to
exhaust the stack. With no memory cap, a signal-killed worker almost always
indicates stack overflow rather than an out-of-memory kill.

The result is a bracket between the last length that completed and the first
that did not, with the outcome of the latter probe. A survived-to-crash bracket
means stack exhaustion limited the input length, whereas a survived-to-timeout
bracket means derivation cost limited it first. The latter are kept as negative
controls, identifying patterns whose derivation becomes prohibitively expensive
before their stack does.

The same doubling search also sets the other two translation caps, the
\emph{bound cap} and the \emph{depth cap}, on an explicit 8\,MiB stack matching
the Linux default. Bound unrolling recurses once per unit of a bound's open
part, syntactic nesting once per level of \texttt{(?:...)} grouping, so each cap
is placed where its mechanism exhausts that stack.

%
%

\subsection{Parse Agreement}
\label{sec:eval-criteria-agreement}

Parse agreement is evaluated on entries with a known expected membership
result, written $(r, w, e)$, where $r$ is the translated \texttt{Regex}, $w$
the input string, and $e \in \{\mathit{true}, \mathit{false}\}$ the expected
result. 

Each candidate processes the same entry in a separate worker
subprocess, and the results are evaluated along three dimensions:

\begin{itemize}
    \item \emph{Timeout or crash}: recorded if a candidate exceeds the default
          2\,s deadline or its worker is killed by a signal.
    \item \emph{Membership}: each candidate's result against $e$. Any
          disagreement is a bug.
    \item \emph{Shape}: compared only when $e = \mathit{true}$ and all
          candidates return a parse tree. The three POSIX parsers must agree
          with one another, as must the two non-POSIX parsers. Agreement
          across the two families is assessed separately but not required.
\end{itemize}

The results summarise how many entries were evaluated and how the
candidates performed on membership and parse-tree agreement.

For each dataset, the summary separates entries that timed out or crashed from
those that could be compared, and reports \emph{match agreement}, the number of
entries on which all candidates returned the expected result. Among successful
matches, \emph{shape agree} counts entries where the two families select the
same tree and \emph{shape disagree} those where their trees differ.

\subsection{S2ELab}
\label{sec:eval-s2elab}

\citet{s2elab-regexeval-dataset} contains 762 human-authored patterns,
each with a natural-language description and labeled matching and
non-matching inputs.

The source patterns follow the usual convention for
\texttt{\textasciicircum} and \texttt{\textdollar}. 
A top-level anchor around
the whole pattern marks a full-string match, and no anchor leaves the pattern
open for substring search.  
Anchors are not supported, as
described in Section~\ref{sec:frontend-rejected}, 
but a fully anchored pattern can still be used by stripping them.
Under full-string matching the pattern already
consumes the entire input, so the anchors add nothing, and the stripped pattern
matches exactly the language the anchored pattern intended.

The benchmarks use the 463 anchor-stripped patterns. The 115 unanchored
patterns are parseable but excluded because they denote substring searches,
whereas the parsers match full strings only. The remaining 177 patterns
are rejected by the frontend. Table~\ref{tab:corpus-rejection-causes}
summarises the rejection causes.

\paragraph{Pipeline.} A date pattern like
\texttt{\textasciicircum(0[1-9]|1[0-2])\textbackslash/...\textdollar} is
processed the following:
\begin{enumerate}
  \item \textbf{Extract.} The pattern is kept with the match
        and non-match lists.
  \item \textbf{Deduplicate.} The pattern is byte-distinct and no input string
        appears double.
  \item \textbf{Translate.} The anchors are stripped and the remainder is
        checked to translate.
  \item \textbf{Check labels.} Each input string is checked against the translated
        pattern. The input string \texttt{"11/31/2002"} is accepted because the day group allows
        \texttt{31} regardless of month, validating the pattern's semantics,
        not real-world correctness.
  \item \textbf{Write.} The surviving pairs are written to the corpus.
\end{enumerate}

\label{sec:eval-stack-depth}

P01, beside E51, is a second negative control. Its nested quantifier makes the
derivative step expensive, so both forms hit the 15\,s cap at $n=16$ before

derivation stays cheap.

E51 is such a row. Every entry mismatches on the first character, so the
derivative collapses to a tiny fixed residual that never grows. The recursive
form crashes with a genuine stack overflow, its bracket $[32\,768;\,65\,536]$.
The iterative form completes every probe up to the $2\,000\,000$ sweep cap, its
bracket $[1\,048\,576;\,2\,000\,000]$ bounded by the sweep length, not by a
failure.

The iterative form is therefore worth adopting. Even on a pattern with a
trivially cheap derivative step, the recursive form fails at tens of thousands
of characters, whereas the iterative form handles every length this sweep
reaches.

adjacently rather than nested, which is the frontier-of-residuals shape the
partial-derivative construction is usually best at, and bit-coding does not
suffer from that shape as much as the standard partial derivative does.

\subsection{Memory}
\label{sec:eval-memory}

\texttt{bench\_corpus\_memory} and \texttt{bench\_pathological\_memory}
replace the system allocator with a wrapper that counts allocated
bytes and reports three figures per parser: total bytes (every
allocation including churn), average bytes per entry (macro-average
for S2ELab, same as the timing mean), and max peak (highest live-byte
high-water mark on any single entry, flat). Like their timing
counterparts, they read \texttt{BENCH\_PATTERN\_LIMIT} and
\texttt{BENCH\_MATCH\_INTENT} (S2ELab) or the \texttt{PATHO\_*}
variables (pathological).

Heap-only accounting: each worker's call-thread stack is invisible to
it, so a pattern dominated by recursion depth would under-report here
-- Section~\ref{sec:eval-stack-depth} measures that separately, with
the memory cap removed entirely.

On \texttt{a*}, the \texttt{deriv\_std} column grows linearly in $n$
while the other three stay bounded. The two-pass structure keeps every
intermediate expression alive until the backward pass, so its state is
a function of input length. Bit-coded and partial-derivative variants
do not carry a history.

On \texttt{(a+(b+ab))*}, \texttt{deriv\_std} reaches 9179 nodes at
$n=16$ and keeps growing. \texttt{deriv\_bc} stays between 8 and 12
nodes forever. \texttt{simp} dedups branches by structural shape
alone, ignoring bit history, so the same-shape branches this pattern
produces at every step collapse into one. The gap is therefore not a
fixed cost of carrying reconstruction information, as for \texttt{a*},
but the difference between a construction whose branches merge and one
whose branches do not.

The two partial-derivative variants are identical at every step
(2048 nodes at $n=16$), now that \texttt{pderiv\_std} builds its
residuals with the same \texttt{smart\_seq} construction
\texttt{pderiv\_bc} already used. Their live state is the frontier of
residuals, not a single expression, and the accumulation is bounded by
the pattern's own size, well above \texttt{deriv\_bc}'s fully-collapsed
total but far below \texttt{deriv\_std}'s.

\texttt{demo\_simp\_branches} confirms this directly: at every step,
\texttt{(a+(b+ab))*}'s derivative collapses to a single top-level
alternation branch once \texttt{simp}'s dedup ignores bit history. This
is the same fix responsible for \texttt{deriv\_bc}'s bounded growth
above.

\textbf{Peak memory in the large.} The max-peak column of
Table~\ref{tab:memory} answers whether any S2ELab pattern causes a
peak infeasible on a production machine. At full corpus scale the
answer is no: the highest single-entry peak is 737.6\,MB, for
\texttt{deriv\_std\_loop} (\texttt{deriv\_std\_rec} peaks at
582.4\,MB); the other three peak in single-digit megabytes. That is a
property of S2ELab's input lengths, not a general bound. The
representative sweeps below, on inputs several orders of magnitude
longer, show the same two-pass retention pushing both standard
variants to crash well before a million characters on most rows,
while the bit-coded and partial-derivative variants keep growing
smoothly into the low gigabytes, a controlled, roughly linear growth
rather than an outright failure.

\subsection{Translation depth caps}
\label{sec:eval-translate-depth}

Section~\ref{sec:frontend-bounds} named three fixed limits without
justifying them: \texttt{translate} refuses any \texttt{\{m,n\}} bound
whose \texttt{m} or \texttt{n} exceeds 1{,}000 (\texttt{MAX\_BOUND}),
and \texttt{core\_regex\_tagged} separately refuses a pattern whose
translated \texttt{Regex} exceeds 20{,}000 nodes
(\texttt{MAX\_CORE\_NODES}) or whose estimated nesting depth exceeds
2{,}000 (\texttt{MAX\_CORE\_DEPTH}). This section measures what the
first and third of those guard against directly, the same way
Section~\ref{sec:eval-stack-depth} measured \texttt{deriv\_std\_rec}'s
crash point rather than asserting one.

\texttt{translate} is a plain recursive function (one call per
\texttt{ExtPat} level), and \texttt{desugar\_bound}'s private
\texttt{optional\_extra} recurses once per unit of a bound's open part
(\texttt{n\,-\,m}): an unrolling deep enough risks overflowing
\texttt{translate}'s own call stack, independent of how the resulting
pattern is later matched. Unlike every other bench in this chapter,
which runs on a 256\,MiB custom worker stack
(Section~\ref{sec:eval-stack-depth}), \texttt{core\_regex\_tagged} runs
on whatever stack its caller gives it, and
\texttt{examples/dataset\_prepare.rs} never spawns a custom one -- in
practice the OS's plain default main-thread stack, 8\,MiB on this
machine (\texttt{ulimit -s}). \texttt{bench\_translate\_depth} measures
two mechanisms directly on that same 8\,MiB stack, with the same
process-isolated doubling sweep as Section~\ref{sec:eval-stack-depth}:
\texttt{bound\_unroll} reproduces \texttt{optional\_extra}'s exact
recursive shape (the real, public \texttt{translate} cannot be swept
past its own \texttt{MAX\_BOUND}, so the identical algorithm is
reproduced in the worker instead -- see its module doc); \texttt{syntactic\_nesting}
calls the real, uncapped \texttt{parse\_ext\_pattern}/\texttt{translate}
pipeline on a pattern with \texttt{n} nested non-capturing groups,
\texttt{(?:(?:...(?:a)...))}.

\centering
\small

\hline

\hline

Syntactic nesting (\texttt{(?:...)}) & 8\,MiB & $N=6{,}400$ & $6{,}400$--$12{,}800$ \\

Both caps sit comfortably below where their own mechanism actually
breaks. A single bound's open part is capped at 1{,}000, roughly
$51\times$ below where \texttt{optional\_extra}'s own recursion starts
crashing; the estimated nesting depth is capped at 2{,}000, roughly
$3.2\times$ below where the real, uncapped pipeline crashes on
deeply-nested syntax. \texttt{prepare.rs}'s own depth estimate for a
bound (\texttt{estimated\_translated\_depth}) uses \texttt{hi} rather
than the smaller \texttt{hi\,-\,lo} that \texttt{optional\_extra}
actually recurses to, so the pre-translation check is itself
conservative on top of that margin, never under-estimating the real
risk. (These margins hold for a release build, the only way this
pipeline is run in practice; a debug build's larger per-call frames
would crash sooner, at a smaller $N$, in both mechanisms.)

\texttt{MAX\_BOUND} also comfortably covers real use, not just real
risk: \texttt{demo\_bound\_usage} walks every S2ELab pattern's
\texttt{ExtPat} and collects every \texttt{Bound} node's own
\texttt{hi} (or \texttt{lo} if unbounded above) anywhere in it, not
just at the top level. Of 762 raw patterns (714 parse), 442 contain at
least one bound, 1{,}769 bound occurrences in total; the largest single
value found anywhere in the corpus is 67 (median 2, 99th percentile
16). No S2ELab rule asks for anything within two orders of magnitude of
the 1{,}000 cap.

\texttt{MAX\_CORE\_NODES} is a different kind of limit: node count has
no comparable crash cliff the way recursion depth does (cost grows
smoothly, not in a single catastrophic step), so it is sized by
coverage instead. Section~\ref{sec:eval-translate-s2elab} already
reports the figure this leans on: the largest pattern anywhere in
S2ELab translates to 18{,}707 nodes, so 20{,}000 covers every pattern
this evaluation needed to represent with headroom to spare, while
still bounding how much a single malformed or adversarial pattern can
cost to store and translate.

\texttt{bench\_translate\_depth} and \texttt{demo\_bound\_usage} are
both runnable directly, the same as every other bench and demo in this
chapter.

\subsection{Parse Tree Shape Agreement}
\label{sec:eval-agreement}

\subsubsection{Method}
\label{sec:eval-agreement-method}

Every case in the prepared corpus carries a verified outcome, so
membership is a precondition, not something this section establishes.
The question here is parse-tree shape. On a matching case, the POSIX
parsers and the non-POSIX parsers may build different trees, since the
same input can admit several valid decompositions. Some inputs force
both policies onto the same structure. This section measures how
often.

The check is implemented in \texttt{demo\_parser\_agreement}. For every
prepared case, all five parsers run on the same (pattern, input) pair.
Two preconditions are checked. First, every parser returns the case's
verified membership outcome. Second, within each family the parsers
agree with each other. The three POSIX variants build the same tree,
and the two non-POSIX variants build the same tree. Agreement
on the parse tree shape in between them is possible.
The measured quantity is cross-family tree agreement. Of the cases
where both families matched and were internally consistent, how many
produced the same tree.
Each parser call runs in a subprocess with a 2-second wall-clock
timeout. Timeouts and crashes are counted separately from tree-shape
outcomes.

The two datasets are not pooled, and each runs through its own binary.

\begin{itemize}
  \item \texttt{demo\_parser\_agreement} on the 572 usable S2ELab
        patterns, both match-intent groups.
  \item \texttt{demo\_parser\_agreement\_pathological} on the
        113-row pathological set.
\end{itemize}

\subsubsection{Discussion}
\label{sec:eval-agreement-discussion}

Both preconditions hold throughout: every parser matches the verified
outcome (100\% on both datasets), and no within-family shape violation
was printed by either run.

Cross-family disagreement concentrates sharply. S2ELab's 21
disagreements are 0.3\% of 7041 compared. The pathological set's are
10.1\% of 207, and within that set category B alone accounts for 18 of
the 21 (64.3\% of its own 28 compared). Category B is exactly the
category built around alternatives sharing a prefix under a quantifier,
the most reliable way to construct genuine ambiguity on purpose.
Categories E and F, also alternation-heavy by design, show smaller but
nonzero disagreement (12.5\% and 8.3\%). Every other category shows
zero. Disagreement reflects the POSIX-versus-non-POSIX policy
difference visible exactly on the ambiguous cases the pathological set
was built to contain, and absent everywhere a pattern leaves only one
decomposition.

The agreement check is what surfaced one dataset defect. Categories A,
B, and C of an early pathological pass all reported 100\% match
agreement. Category H reported 75\%, with two rows, \texttt{P29}
(\verb|(.+){10}|) and \texttt{P31} (\verb|(.*){10}|), where all five
parsers returned match against an input the dataset labeled a
non-match. Both patterns' non-match inputs had been built by appending
a trailing character to a matching string, which only forces a
non-match when the pattern bounds the total input length. Neither
pattern does. \texttt{P31} has no genuine non-match at any length,
since ten \texttt{.*} groups accept the empty string. \texttt{P29}'s
non-match input was replaced with a fixed 9-character string, one
short of the ten-group minimum the pattern needs. \texttt{P31}'s was
removed. Category H now reports 100\%.

\textbf{A concrete S2ELab disagreement.} Table~\ref{tab:agreement}'s
21 S2ELab disagreements are real patterns, not synthetic ones. The
shortest to typeset is S2ELab's loosely-formatted-number pattern,
\verb|^[-+]?([0-9]{1,3}[,]?)?([0-9]{3}[,]?)*[.]?[0-9]*$|, on the input
\texttt{"9000"}. Figure~\ref{fig:agreement-sample} gives both parsers'
raw output. Both trees flatten (Section~\ref{sec:eval-translate}'s
sibling function, \texttt{flatten}, concatenates every \texttt{Char}
leaf left to right) to the same string, \texttt{"9000"}, confirming
both really did match the same input -- the disagreement is purely
about tree shape. The two outputs share an 80-character common prefix
through the point where the first digit, \texttt{'9'}, is matched by
\verb|[0-9]{1,3}|'s single mandatory copy; they diverge at that
group's first \emph{optional} copy. \texttt{posix (bc)} takes
\texttt{Left(Empty)} there -- declining the two optional copies
entirely, so the mandatory-copy group matches only \texttt{"9"} -- and
its one \texttt{Star} with a non-empty list (one element) then
accounts for \verb|([0-9]{3}[,]?)*| matching exactly one iteration,
\texttt{"000"}. \texttt{non-posix (pbc)} instead takes both optional
copies (\texttt{Right(Pair(...))} twice), so the mandatory-copy group
matches \texttt{"900"}; its corresponding \texttt{Star} is then empty,
and the one remaining digit, \texttt{"0"}, is caught by the trailing
\verb|[0-9]*| instead. Same four characters, same pattern, two
different ways to apportion them across three overlapping quantified
groups -- exactly the shape ambiguity Section~\ref{sec:eval-agreement}
measures, now visible on a real corpus entry rather than a
purpose-built pathological row.

\begin{figure}[H]
\centering
\scriptsize
\begin{verbatim}
posix (bc) =
  Pair(Pair(Pair(Pair(Right(Empty),
    Left(Pair(Pair(Pair(Empty, Right(Char('9'))),
               Left(Empty)), Right(Empty)))),

\section{Discussion of Results}
\label{sec:eval-discussion}

%
%
%

\subsection{Cost of the standard construction}

The two standard derivative parsers are consistently the slowest and
memory-heaviest. This follows directly from the two-pass structure of
Chapter~\ref{sec:derivative-parser}: every intermediate expression is
stored until the backward pass completes. On \texttt{a*} input of
length $n$, state size grows linearly in $n$, while the bit-coded and
partial-derivative parsers stay constant.

On the full corpus the two standard variants are close in mean time
(7.718\,ms against 7.430\,ms) but the outcome split shows where the
difference lives. On matching entries, \texttt{deriv\_std\_loop}'s
total (70.782\,s) is measurably below \texttt{deriv\_std\_rec}'s
(74.725\,s), while their non-match totals are almost the same. The
recursion-versus-iteration difference is specifically a cost of the
matching path, confirmed directly at Figure~7 scale and beyond
(Table~\ref{tab:patho-crash-thresholds}): the two variants crash at
identical input lengths and near-identical memory figures on every
representative row, which rules out recursion depth as the mechanism
there and leaves the two-pass retention both variants share as the
only remaining explanation. Stack depth specifically is where the two
variants do diverge sharply (Section~\ref{sec:eval-stack-depth}):
\texttt{deriv\_std\_loop} survives over sixty times further than
\texttt{deriv\_std\_rec} on a pattern engineered to isolate that one
cost alone, with the memory cap removed. The two findings are not in
tension. They describe two different failure modes, and which one a
given pattern hits first depends on whether its derivative sequence or
its character count is the thing actually growing.

%
%
%

\subsection{Cost of bit-coding}
\label{sec:eval-cost-bit-coding}

For the standard-derivative family, bit-coding wins unconditionally.
\texttt{deriv\_bc}'s mean time (1.699\,ms) is roughly $4$--$4.5\times$
below either standard variant's, and its peak allocation (5.1\,MB) is
about $114$--$144\times$ below theirs. The trade-off is that the forward pass
cannot simplify away redundant branches without losing reconstruction
information. The retention is not wasted: it is exactly what makes
single-pass reconstruction possible, and \texttt{deriv\_bc}'s decode
step is close to free (well under a tenth of a millisecond mean).

The representative sweeps push this further: \texttt{deriv\_bc}
survives every swept input length on six of the eight representative
rows where both standard variants crash outright, at scales ranging
from thousands of characters past the crash point (P27/P28) to ten
million (P60, P20). Section~\ref{sec:eval-memory-patho-representatives}'s
caveat applies directly here: \texttt{deriv\_bc}'s cumulative
allocation at that scale is large (up to 271\,GB of total churn on
P20's full sweep), but its peak live footprint stays in the low
gigabytes throughout, the distinction between allocator pressure and
actual memory held that motivates reporting both figures separately
(Section~\ref{sec:eval-criteria-what}).

%
%
%

\subsection{Cost of partial derivatives}
\label{sec:eval-cost-partial-derivatives}

The two partial-derivative parsers are the fastest and most
memory-light on the full S2ELab corpus, clearly ahead of either
derivative-based variant. They split the residual into a set of states
rather than combining into one expression, which keeps each state
small and avoids the alternation growth the standard derivative
parser suffers.

Within the pair, bit-coding's advantage is not unconditional the way
it is for the standard-derivative family, and which variant wins
depends on more than scale. On the full corpus, \texttt{pderiv\_std}
is marginally ahead on every figure: mean time (0.616 against
0.625\,ms), average bytes (0.403 against 0.412\,MB), and peak bytes
(2.5 against 3.8\,MB). At Figure~7 scale, the ranking splits by row.
On P60 (\texttt{(a|b|ab)*} over `a'-repeated input),
\texttt{pderiv\_std} stays faster at every point, with a stable
gap that does not narrow with input length. On P61 (the same
pattern over `ab'-repeated input) the ranking flips:
\texttt{pderiv\_bc} is faster at every point, with a smaller but
equally consistent gap. On P20 (\texttt{(a|b|ab)+}),
\texttt{pderiv\_bc} is both faster and lower-peak than
\texttt{pderiv\_std} (3.27 against 4.97\,GB peak over the full sweep).
The finding is that the input shape changes which variant wins, not
just how large the gap is. Bit-coding's cost for the
partial-derivative construction is a fixed per-step overhead, and
whether it pays for itself depends on the pattern and input together,
not on scale alone.

The price of partial derivatives, independent of which variant, is
that they produce a non-POSIX tree. This is a specification
difference, not a deficiency, and it is why the two families are
compared separately in Section~\ref{sec:eval-agreement}.

\subsection{Threats to validity}

\textbf{Corpus scope.} S2ELab is one dataset's own domain and
convention. A corpus from a different domain might exhibit different
acceptance rates and timing profiles. The default scope measures only
the 463 stripped patterns (Section~\ref{sec:eval-anchors}). A
different, defensible choice (\texttt{BENCH\_MATCH\_INTENT=both}) would
fold in the remaining 115 patterns and could shift absolute numbers,
though not the ordering among parsers, which does not depend on which
patterns are included.

\textbf{The pathological set.} Each of its 113 rows isolates one
complexity mechanism at a controlled scale. It does not represent the
distribution of pattern shapes a real author would write. Most
categories sweep one parameter in isolation, so a pattern combining
two stress mechanisms at once is not directly represented.

\textbf{Measurement model.} Memory benches measure allocation counts,
not wall-clock memory pressure. The evaluator runs on a single
machine, so the wall-clock figures are CPU- and cache-specific. A
\emph{crashed} entry's recorded reason is ``killed by signal,'' not a
confirmed diagnosis of stack overflow specifically
(Section~\ref{sec:eval-criteria-how}); Section~\ref{sec:eval-stack-depth}
is the one measurement in this chapter that removes the memory cap and
so can attribute a crash to stack overflow directly, and it is the
basis for the claim, elsewhere in this chapter, that the
representative-row crashes are a shared-retention effect rather than a
recursion-depth one.
