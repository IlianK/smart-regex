\chapter{Evaluation}
\label{sec:evaluation}

This chapter evaluates the derivative and partial-derivative parsers developed in
Chapters~\ref{sec:derivative-parser} and~\ref{sec:partial-derivative-parser}.
Using two datasets and a common set of criteria, it compares the candidates in
terms of execution time, memory consumption, and translation cost.
It also assesses their agreement on membership decisions and parse-tree shape.

All measurements were taken on an AMD Ryzen~5~5600 six-core processor with
16\,GB of RAM, running Pop!\_OS 24.04 LTS on an AMD B550 chipset.

%
%
%


\section{Candidates}
\label{sec:eval-candidates}

A candidate is a parser $p$ that takes a translated \texttt{Regex} $r$
and an input \texttt{String} $w$, 
and returns either a \texttt{ParseTree} $pt$ or no match.
Such an input pair $(r, w)$ is called an \emph{entry}.
All candidates share the same interface:
\[
p :: (\mathit{Regex}, \mathit{String}) \to
     \mathit{Option\langle ParseTree\rangle}.
\]

Candidates are classified into
two families by their disambiguation strategy.


\textbf{POSIX family.}
\begin{itemize}
  \item \texttt{deriv\_std\_rec}, the recursive standard derivative parser
        (Section~\ref{sec:deriv-std-parser}).
  \item \texttt{deriv\_std\_loop}, the iterative standard derivative parser
  \item \texttt{deriv\_bc}, the bit-coded derivative parser
        (Section~\ref{sec:deriv-bc-driver}).
\end{itemize}

\textbf{Non-POSIX family.} 
\begin{itemize}
  \item \texttt{pderiv\_std}, the standard partial-derivative parser
        (Section~\ref{sec:pderiv-std-parser}).
  \item \texttt{pderiv\_bc}, the bit-coded partial-derivative parser
        (Section~\ref{sec:pderiv-bc-parser}).
\end{itemize}

All five parsers are expected to agree on membership,
so given an entry, they must either all accept it or all reject it.
They are also expected to agree on parse-tree shape \emph{within}
each family, because the parsers of one family share the same
disambiguation policy and differ only in how they compute and
reconstruct the tree. 

For the POSIX family this means the parsers must return the same POSIX parse tree
and the non-POSIX family parsers must return the same leftmost parse tree. 

Across families, agreement is
not required. Since the two families implement different
disambiguation policies, they may select different parse trees for
the same entry even when they agree on membership, as
Chapter~\ref{sec:matching-vs-parsing} shows.

\section{Evaluation Criteria}
\label{sec:eval-criteria}

The evaluation considers two aspects of the candidates. The first is
\emph{performance}, measured in terms of execution time, memory consumption,
and translation cost. The second is \emph{correctness}, assessed by comparing
membership and parse-tree selection.

%
%
%

\subsection{Measurement Setup}
\label{sec:eval-criteria-setup}

Each entry runs in its own worker subprocess for timing, memory,
stack-depth, and parse-agreement measurements. Stable Rust has no safe
way to forcibly terminate a thread~\citep{rust-thread-joinhandle}, so one
that has not returned, e.g. from exponential derivation or from
allocating towards the memory cap, cannot be stopped. A
subprocess, by contrast, can be killed unconditionally, and the operating
system reclaims its memory.

\begin{itemize}
  \item \emph{Measured}: the worker exited zero and reported a result line.
  \item \emph{Timed out}: the worker exceeded the default per-entry timeout
        (2\,s) and was killed.
  \item \emph{Crashed}: the worker exited non-zero or was killed by a
        signal, including stack overflows and out-of-memory kills
        when the memory ceiling is enabled.
\end{itemize}

For timing, memory, and parse-agreement measurements, each worker runs on
a custom 256\,MiB stack: all candidates recurse over the pattern
structure, and on deeply nested patterns the default stack would overflow
before the measured input sizes are reached. This stack is a fixed
allowance and not part of the measured footprint.

A timing and memory run produces two outputs per candidate and dataset: (1) a summary
table of aggregate measurements; (2) a per-entry file
to compare individual entries.

%
%
%

\subsection{Timing}
\label{sec:eval-criteria-timing}

Each entry $(r, w)$ is timed once, without warm-up run or repeated
measurements. Translation is measured separately, so the wall-clock
time covers only the parser call $p(r, w)$.
For \texttt{deriv\_std\_rec}, \texttt{deriv\_std\_loop}, and
\texttt{pderiv\_std}, the entire parser call is reported as \emph{mean}.
For \texttt{deriv\_bc} and \texttt{pderiv\_bc}, the call is split into
three: \emph{Encode} constructs the initial annotated state before
any character of $w$ is consumed, \emph{Derive} processes the input one
character at a time and \emph{Decode} converts the final bit-string into a
parse tree.

Timing results show four statistics, aggregated differently for the two datasets:

\begin{itemize}
  \item \emph{Mean} is a macro-average over patterns of the real corpus, so
        a pattern with 10 entries and one with 2 contribute equally,
        a flat mean is used for the synthetic set.
\item \emph{Median}, \emph{99th percentile}, and \emph{maximum} are pooled
      over individual entries rather than averaged per pattern. The median
      describes a typical entry, the 99th percentile the tail of the entry
      distribution, and the maximum the single worst entry.
\end{itemize}

All four statistics represent lower bounds on the corresponding
execution times, since timed-out and crashed entries are excluded
rather than counted at their timeout values.
A separate \emph{wall} column measures the benchmark's entire loop over one
source pattern. It therefore exceeds $\mathit{entries} \times \mathit{mean}$ by
the per-entry process-spawn and pipe-round-trip overhead excluded from the
individual timings. It captures the total cost of reproducing a pattern's
results, harness included, but is not suitable for comparisons between
candidates.

%
%

\subsection{Memory}
\label{sec:eval-criteria-memory}

Memory is measured with a counting allocator in each worker, baselined
immediately before the parser call so that only allocations made during
$p(r, w)$ are counted. The allocator tracks a running sum of requested
bytes and a running count of live bytes:

\begin{itemize}
  \item \emph{Max live peak}: the highest value of the live-byte counter
        within a call. It bounds the heap a single call requires, and is
        the measure that determines whether a parser can run at a given
        input length within a fixed memory budget.
  \item \emph{Total allocated}: the sum of requested bytes over the call,
        including memory later freed. It is not a footprint, but a proxy
        for allocator pressure and a secondary explanation of timing, since
        a parser that allocates and frees frequently pays a cost even when
        its peak stays low.
\end{itemize}

Total allocation counts memory freed during the call, so it is always at
least as large as peak. Because peak grows with
the input a run processes and total with the work it performs, each is
compared only where those are comparable: peak across rows that reached
comparable input lengths, 
total across rows that completed comparable work.

The allocator sees heap allocations only, not the worker stack
(Section~\ref{sec:eval-criteria-setup}), so a parser that uses substantial
stack but few heap allocations may appear inexpensive in these
measurements. Stack depth is evaluated separately for the two standard
derivative parsers.

%
%
%

\subsection{Translation}
\label{sec:eval-criteria-translation}

Translation depends only on the source pattern and is independent of the
input, so each distinct pattern is translated once rather than once per
entry. Translation runs in the main process because the frontend enforces
the three following resource limits:

\begin{itemize}
  \item \emph{Bound cap}: bounds the numeric value of any repetition bound.
  \item \emph{Depth cap}: bounds the estimated depth of the translated
        pattern.
  \item \emph{Node cap}: bounds the node count of the result.
\end{itemize}

The caps reject a pattern before translation would recurse too deeply or
unroll too large a result, so translation itself is always bounded in
time and memory. A parser call has no such protection. It can run until
the timeout or the memory cap kills it, which is why the caps are checked
at translation and the timeout is enforced per entry.

Translation cost is measured using four quantities:

\begin{itemize}
  \item \emph{Time}: the wall-clock duration of the translation call.
  \item \emph{Total bytes}: the total amount of memory allocated during
        translation.
  \item \emph{Peak bytes}: the highest number of live allocated bytes during
        the call.
  \item \emph{Nodes}: the number of nodes in the resulting \texttt{Regex}.
\end{itemize}

The counting allocator is reset before each translation and read immediately
after the call returns. This excludes subsequent node counting and debug
rendering from the measurement. Mean, median, 99th percentile, and maximum
are calculated directly over patterns. Since each pattern contributes one
measurement, no macro-averaging is needed. Rejected patterns
produce no measurement, so the reported statistics are lower bounds.

%
%
%

\subsection{Stack Depth}
\label{sec:eval-criteria-stack-depth}

\texttt{deriv\_std\_rec} and \texttt{deriv\_std\_loop} compute identical
results but store the residual sequence differently. The recursive
implementation uses one call-stack frame per input character, the
iterative one a \texttt{Vec}. Stack depth is measured to establish which
of the two exhausts the stack first, and at what input length. Both use
the operating system's default thread stack, which is 8\,MiB on Linux.

The maximum surviving input length is estimated using a doubling search.
Starting from a small input, the length is doubled after each successful
probe until the worker fails to complete. The timeout for each probe is
increased from the default $2\,\mathrm{s}$ to $15\,\mathrm{s}$, to give
slow derivatives time to exhaust the stack and cause a stack overflow.
A worker can also be killed by an
out-of-memory condition when a heap cap is set, as described in
Section~\ref{sec:eval-criteria-setup},
but for this measurement no heap cap is applied, so a
signal kill is more likely to be a stack overflow than an out-of-memory
kill.

The search brackets the last length that completed against the first
that did not. A crash means stack exhaustion limited the input, a timeout
means derivation became too expensive first. The timeouts are kept as
negative controls for patterns where derivation cost, not stack depth,
is limiting.

The same doubling search is used to check the two translation caps, the
\emph{bound cap} and the \emph{depth cap}. For the bound cap, the bound
value is doubled until translation of the bound exhausts the stack. 
For the depth cap, the nesting depth of \texttt{(?:...)} groups is doubled
until translation exhausts the stack. Bound unrolling recurses once for
each unit in a bound's open part, while syntactic nesting recurses once
for each level of grouping.

%
%

\subsection{Parse Agreement}
\label{sec:eval-criteria-agreement}

Parse agreement is evaluated on entries with a known expected membership
result. Each entry is written as $(r, w, e)$, where $r$ is the translated
\texttt{Regex}, $w$ is the input string, and
$e \in \{\mathit{true}, \mathit{false}\}$ is the expected match result.
No expected parse tree is provided.

Each candidate processes the same entry, and records:
\begin{itemize}
  \item \emph{Timeout or crash}: if the candidate exceeded the timeout
         or was killed by a signal.
  \item \emph{Membership}: a candidate's decision on ($e = \mathit{true}$)  
        or no-match ($e = \mathit{false}$)
  \item \emph{Parse tree}: the parse tree a candidate returned, when $e = \mathit{true}$.
\end{itemize}

A timeout or crash removes the candidate from the comparison for that
entry. Membership is compared across all candidates. 
Any disagreement with $e$ is a bug. 
Parse trees are compared only when $e = \mathit{true}$
and all candidates returned one. 
Agreement is required within each family, 
whose parsers share a disambiguation policy.
Across families it
is reported but not required, since the two policies may differ.

Thus the summary reports how many entries were evaluated and, for each
dataset, how many timed out or crashed, how many every candidate
classified correctly (\emph{match agreement}), and of those, how many
the two families parsed to the same tree (\emph{shape agree}) or to
different trees (\emph{shape disagree}).

\subsection{S2ELab}
\label{sec:eval-s2elab}

The dataset by \citet{s2elab-regexeval-dataset} contains 762 human-authored
patterns. Each pattern has a natural-language description and lists of labeled
matching and non-matching inputs. The number of each varies per pattern,
so the corpus is not balanced between the two.
The source patterns conventionally use \texttt{\textasciicircum} and
\texttt{\textdollar} as beginning- and end-of-input anchors. A pattern
surrounded by these anchors requires a full-string match, whereas a pattern
without them can match a substring. As described in
Section~\ref{sec:frontend-rejected}, the frontend does not support anchors.
However, fully anchored patterns can still be used by stripping them.
Since the parsers perform full-string matching, the stripped pattern accepts
exactly the inputs intended by the original anchored pattern.

\subsection{Synthetic Stress Set}
\label{sec:eval-pathological}

investigate how parser costs grow with input length and pattern size.
It complements the real corpus, which does not exercise these cost
mechanisms at comparable scales. All patterns are intended for full-string
matching. Each row defines a base pattern and a base input in terms of the
input length $n$, the pattern size $p$, or both, and a \emph{sweep} varies
one of these parameters over a range of values, recording a measurement at
each.

\subsection{Stack Depth}
\label{sec:eval-stack-depth}

The recursive and iterative forms run on the operating system's default
stack of 8\,MB, without a memory cap, using the doubling search described in
Section~\ref{sec:eval-criteria-stack-depth}. Both rows use \texttt{a}
repeated $n$ times as the input, with $n$ increasing across the sweep.

\begin{table}[H]
\centering
\small
\setlength{\tabcolsep}{4pt}
\begin{tabular*}{\textwidth}{@{\extracolsep{\fill}} llllrrl}
\hline
Row & Pattern & Derivative step & Parser & Last $n$ & Outcome & Elapsed \\
\hline
P01 & \texttt{(a+)+} & expensive (nested quantifier)
    & \texttt{rec}  & 16          & timeout & 15.808\,s \\
    & & & \texttt{loop} & 16          & timeout & 15.893\,s \\
\hline
P30 & \texttt{(\textbackslash w+)(\textbackslash w+)}\ldots & moderate (product of stars)
    & \texttt{rec}  & 64          & timeout & 21.217\,s \\
    & & & \texttt{loop} & 64          & timeout & 20.453\,s \\
\hline
E51 & \texttt{x} & cheap (fixed residual)
    & \texttt{rec}  & 32\,768     & crash   & 1.298\,s \\
    & & & \texttt{loop} & 268\,435\,456 & timeout & 32.973\,s \\
\hline
\end{tabular*}
\caption{Doubling-search stack-depth results, one group per pattern with
the recursive (\texttt{rec}) and iterative (\texttt{loop}) parsers.
\emph{Derivative step} categorizes the pattern's derivative cost. P30 is
ten adjacent \texttt{(\textbackslash w+)} groups. \emph{Outcome} reports
what stopped the sweep: \emph{timeout} at the 15\,s per-probe cap, or
\emph{crash} on a stack overflow. \emph{Elapsed} is the cumulative time
taken for the whole sweep.}
\label{tab:stack-depth}
\end{table}

P01 and P30 are negative controls. On both, the derivative step is
expensive enough that the 15\,s timeout fires before either form reaches
its limit, at $n=16$ and $n=64$ respectively. P01 fails first because
its nested quantifier makes each derivative step near-exponential. P30
fails later because ten adjacent \texttt{(\textbackslash w+)} groups
produce a product of stars whose cost grows polynomially. 
In both cases the timeout, not the stack, ends
the sweep, so the input never grows far enough to expose a stack
ceiling. Their role is to rule out the reading that a stack limit would
have been reached at small $n$ on any pattern.

E51 isolates the stack. The pattern is the single literal \texttt{x},
which cannot match an input of \texttt{a}s, so every entry mismatches on
its first character and the residual stays tiny.
The derivative step therefore does not grow with the input. 
Both forms must keep all $n$
intermediate derivatives alive between the forward and backward passes
and differ only in where that sequence lives. The recursive parser keeps
it implicitly, one derivative per stack frame, so the call stack grows
with the input until it crashes between $32\,768$ and $65\,536$
characters. The iterative form keeps the same sequence explicitly, in a
heap-allocated \texttt{Vec}. It reaches $268\,435\,456$ characters and
stops only by the 15\,s timeout ending the sweep.

The comparison is therefore not a contest the iterative form wins on
stack usage, since it has no stack growth to measure, by construction.
This measurement establishes the input length at which the stack becomes
the binding constraint for the recursive form. On crash resistance the
iterative form is therefore preferable even where the derivative step is
cheap, since it has no stack-depth limit within the sweep range.
Whether it is preferable overall depends on which cost matters more 
for a given input, 
which will be examined further through the memory measurements 
presented later in Section~\ref{sec:eval-memory}

\paragraph{Categories A, B, E} show the expected behavior.
The partial-derivative variants are faster
than the derivative variants, though within their own family they are
nearly tied on median (0.24--0.26, 1.98--2.00, and 3.23--3.42\,ms in A, B, and E).
\texttt{deriv\_bc} follows behind (0.30, 2.69, 4.71\,ms).
All three categories let the same input be consumed by many decompositions,
so their residual expressions grow with each step and their size drives the cost.
While \texttt{deriv\_bc} simplifies after each step and keeps a single
expression, the partial-derivative parsers keep a deduplicated set
instead.
The standard derivative parsers are much slower throughout
and timeout against 111 of A's 160, 95 of B's 150, and 42--45 of E's 80 entries.


\paragraph{Category C} has high timeout counts across all five parsers, from 10 to 32
of its 56 entries. Its patterns wrap a star body in a bounded repetition,
so unrolling produces up to ten copies of an already ambiguous
subexpression that every parser must then process within the measured call.
Here the partial-derivative pair overtakes \texttt{deriv\_bc} on both
counts, with 10 timeouts against 14 and medians of 31.03 and 33.55\,ms
against 48.56, while \texttt{deriv\_bc} still beats the standard derivative
parsers on robustness, 14 timeouts against 32. The lower medians (3.67
and 3.80\,ms) come from the 24 entries they complete and describe the
easiest subset rather than a faster parser.

\paragraph{Category F} is where \texttt{deriv\_bc} loses most ground to the
partial-derivative variants, timing out on 28 of its 70 entries against 2
and 3 for the two partial-derivative variants. Its patterns end in a literal that fails late, so every entry
must consume the whole input before that literal is checked and no parser
can reject early. On completed entries \texttt{deriv\_bc} appears faster
than both variants, 41.65 against 88.56 and 113.18\,ms on the mean and
2.39 against 3.32 and 8.13\,ms on the median, but as in C these figures
cover only the 42 entries it completed against 67 and 68 for the two variants, so they
describe the easier subset and the partial-derivative pair remains the more
robust choice.

\paragraph{Category D} is where \texttt{deriv\_bc} regains the lead it lost
on F, timing out on none of its 40 entries against 6 for each
partial-derivative variant. Since the measured counts are close, the means
compare directly, and the fewest timeouts and the lowest mean fall on the
same parser, \texttt{deriv\_bc}, at 137.87 against 193.93--221.25\,ms.
D's patterns are unrolled bounded repetitions, so consuming a prefix
leaves a suffix of the unrolled chain, and different prefix lengths leave
suffixes of different lengths. \texttt{deriv\_bc} simplifies after each
step, which rewrites equivalent residuals into a common form so that
identical ones merge and the expression stays small. But the
partial-derivative parsers only drop residuals that are already equal, so
suffixes of different lengths remain separate elements, each stepped at
every character, and the set grows with the pattern. The advantage of
\texttt{deriv\_bc} therefore comes from the simplification its encoding
uses, not from the encoding itself.

\paragraph{Category H} is a weaker version of D's outcome.
\texttt{deriv\_bc} again times out on fewer entries, 2 of its 28 against 5
and 4 for the two partial-derivative variants, but here the timeouts and the median
disagree. H's patterns are chains of adjacent unbounded groups, such as
\texttt{(.+)(.+)}\(\ldots\), so the split points multiply across the group
boundaries. The residual set the partial-derivative parsers carry grows
with the number of groups. Each element is stepped at every character, but
\texttt{deriv\_bc} only carries a single simplified expression. On
completed entries, however, the partial-derivative parsers are faster
on both mean (167.23 and 213.98 against 253.72\,ms) and median (49.95 and
53.42 against 74.75\,ms).

\subsubsection{Representative Patterns}
\label{sec:eval-timing-representative}

Six representative rows are drawn from the categories above.
Four are swept past their baseline values in input length $n$,
reaching millions of characters or thousands of repetitions,
so that each row crosses from measured to failing within its own range.
The other two, E37 and E38,
instead sweep the pattern's own alternation width $p$ at fixed input length,
isolating compile-size cost from input length.
Row selection and sweep points were set empirically as each row’s cost became clear.
Since the four $n$-sweep rows’ inputs exceed the default 2 s budget,
each uses a fixed 120 s deadline and an 8 GiB memory cap,
so that its largest point can finish.
E37 and E38 stay within the default budget and need neither override.
Table~\ref{tab:patho-crash-thresholds} summarises how far each parser gets on them, 
in terms of the largest $n$ or $p$ it completes and the first value at which it fails.

The standard pair fails earliest on every row, by crashing rather than timing out. 
Since both run on the 256\,MiB worker stack with the 8\,GiB heap cap enabled, 
they have more stack headroom than in the bench of \ref{sec:eval-stack-depth}.
They still reach the cap at the same $n$ with nearly identical allocation.
Recursion depth is therefore not the cause, but the heap is.
Both keep the derivation sequence for the backward pass 
and its size grows with the input. 
With the standard pair ruled out, 
the remaining question is how \texttt{deriv\_bc} and the partial-derivative pair compare. 
On P01 the pair outlasts \texttt{deriv\_bc},

P61 is the exception: \texttt{deriv\_bc} and \texttt{pderiv\_bc} both
still reach the maximum, but \texttt{pderiv\_std} now crashes there
instead, the only failure among these three parsers on any of the six
rows.

edge on either row: \texttt{pderiv\_bc} is faster at 7 of P60's 12

different points along each sweep rather than showing P60's older

\texttt{pderiv\_std} value to compare against, since it crashes there
instead of completing (Table~\ref{tab:patho-crash-thresholds}). At the
largest input both still complete, \texttt{pderiv\_bc} is a little
ahead on each row: 0.685 against \texttt{pderiv\_std}'s 0.722 of
\texttt{deriv\_bc}'s time at $n=10\,000\,000$ on P60, and 0.831 against
0.901 at $n=5\,000\,000$ on P61.
This leans the same way as the dataset-wide result rather than against
it: \texttt{pderiv\_bc} was shown to be faster on mean in nine
categories and median in six. \texttt{pderiv\_bc} and
\texttt{pderiv\_std} step the same residuals and differ only in how
they tag them, so a lead this narrow and this inconsistent from one
swept point to the next is better explained by ordinary run-to-run
variation than by a mechanism tied to tagging.

Let $B$ denote the pattern \texttt{a|b|ab}, so the whole
pattern is $B^{*}$, and let a \emph{state} be the set of residuals that
remain after a prefix of the input has been consumed. Moving to the next
character means taking each residual's derivative and then dropping
duplicates, keeping the first copy of any residual reached twice
(\ref{sec:pderiv-state-set}
and~\ref{sec:pderiv-bc-state-set}), starting with $S_0 = \{B^{*}\}$.
\[
\begin{aligned}
\mathit{step}(S_0, \mathtt{a}) &= \{\,B^*,\ \ \mathtt{b}\cdot B^*\,\} =: S_1, \\
\mathit{step}(S_1, \mathtt{a}) &= S_1, \\
\mathit{step}(S_1, \mathtt{b}) &= \{\,B^*\,\} = S_0.
\end{aligned}
\]

The second residual in $S_1$ is $b\cdot B^{*}$. Here the \texttt{ab} branch
has already used its \texttt{a} and is waiting for a \texttt{b}. When the
next character is \texttt{a}, this residual cannot move, so it disappears.
Meanwhile $B^{*}$ produces the same two residuals again, and $S_1$ reproduces
itself. Repeated \texttt{a}s give $S_1 \to S_1 \to S_1$, with two residuals
on every step. When the next character is \texttt{b}, the waiting residual
completes, both residuals become $B^{*}$, and the one copy that remains is
$S_0$. So \texttt{ab}-repeated input alternates
$S_0 \to S_1 \to S_0 \to S_1 \to \cdots$, with two residuals on every
\texttt{a} and one on every \texttt{b}.

Each new residual carries a tag recording which branch produced it.
\texttt{pderiv\_bc} extends a bit string by one node per residual, while
\texttt{pderiv\_std} wraps the previous closure in another. Both allocate
a small node, but the bit version also materialises the new bit slice, so
\texttt{pderiv\_bc} pays a real, if small, extra cost on every residual it
tags. \texttt{a}-repeated input carries two residuals at every step, so
that cost is paid twice per character. \texttt{ab}-repeated input drops to
one on every other step, so it is paid 1.5 times on average and the gap
narrows between the two partial-derivative parsers.

The difference is what each pattern's ambiguity costs per character. P01
nests a \texttt{+} inside another \texttt{+}, so each additional
\texttt{a} multiplies the number of ways the outer repetition could have
been split into iterations, making every derivative step
near-exponential. \texttt{deriv\_bc} keeps all of these live splits in one
expression and compares every pair of them after each character, so the
cost grows with $n$, and the ratio collapses from near parity to under
0.01 before \texttt{deriv\_bc} times out. P09's ambiguity is shallower,
since category B's shared-prefix alternatives under one flat quantifier
leave only a couple of live readings at any position, not a count tied to
how many iterations have passed. The same pairwise cleanup therefore costs
a bounded amount per character, holding the ratio in the 0.37--0.67
band out to ten million characters.

\texttt{pderiv\_bc} is faster at 9 of the 15 swept points here,

\texttt{deriv\_bc}'s time at ten million characters) -- the same
modest, inconsistent lean seen on P60 and P61 above, not a clean win
for either variant.

An \texttt{E}-row instead sweeps the pattern itself,
isolating how \texttt{deriv\_bc} and \texttt{pderiv\_bc}'s three phases
(Section~\ref{sec:eval-criteria-timing})
scale with pattern size rather than input length, 
on the matching side only. 
Both are drawn from category J (``large pattern, short input''),
whose mechanism is the per-node cost of a very large pattern.
Alternation was chosen to grow a pattern's node count by a
single parameter $p$ while leaving the input trivial.
Table~\ref{tab:patho-phases-e37} reports E37, 
a $p$-way alternation of distinct four-letter words.
Table~\ref{tab:patho-phases-e38} shows E38,

(Section~\ref{sec:eval-criteria-translation})
raised from 20\,000 to 200\,000 for this test.
The cap was sized for the real corpus, but within
a $p$-way alternation it is too small once $p$ gets this large.

almost seven times the default cap.

\textbf{\texttt{deriv\_bc}, not the partial-derivative pair, is the one that blows up.}
Table~\ref{tab:patho-e38-all-parsers} shows the mean time of all parsers
on E38.
Past a few thousand alternatives, \texttt{deriv\_bc} is the only parser
whose cost explodes: by $p=10\,000$ it is roughly $18\times$ slower than
the standard pair, while the partial-derivative pair (\texttt{pderiv\_std}
and \texttt{pderiv\_bc}) stays cheapest of all five parsers throughout the
sweep.
The standard pair's own advantage has one cause.
Unlike the other three, it does not attempt to simplify the alternation at all,
so it never pays for an attempt that could not have paid off anyway,
since every one of the $p$ alternatives stays genuinely distinct by construction.
Of those other three, only \texttt{deriv\_bc} pays dearly for its attempt.
\texttt{pderiv\_std} and \texttt{pderiv\_bc} simplify just as genuinely,
through \texttt{nub\_tree} and \texttt{nub2},
but cheaply enough for the cost not to show, for reasons given below.
\texttt{deriv\_bc} also pays more for the same attempt on E38 than on E37:
comparing two Cat-chains for \texttt{same\_shape} means walking them node
by node, and E38's words share a five-character prefix (\texttt{w0000})
that E37's four-letter words do not, so each comparison walks further
before reaching the difference that makes it fail.
That is why \texttt{deriv\_bc} diverges from \texttt{pderiv\_bc} more
sharply on E38 (Table~\ref{tab:patho-phases-e38}) than on E37
(Table~\ref{tab:patho-phases-e37}).

\small

fn dedup_first(branches: &mut Vec<ARegex>) {
    let mut i = 0;
    while i < branches.len() {
        let mut j = i + 1;
        while j < branches.len() {
            if same_shape(&branches[i], &branches[j]) {
                branches.remove(j);
            } else {
                j += 1;
            }
        }
        i += 1;
    }
}
\end{verbatim}
\caption{\texttt{dedup\_first}: the nested loop behind Figure~\ref{fig:simp-rust}'s 
own \texttt{dedup\_first} call. 
Every branch is compared against every later branch via \texttt{same\_shape}, 
removing a match in place.}
\label{fig:dedup-first-rust}
\end{figure}

Figure~\ref{fig:dedup-first-rust}'s nested loop compares branch $i$
against every later branch $j$.
With $p$ branches, that is roughly $p^2/2$ calls to \texttt{same\_shape}, 
every single character. 
For $p$ genuinely distinct words, 
\texttt{same\_shape} is essentially always false, 
so nothing is ever removed.
The full $O(p^2)$ cost is paid every character for zero branches removed.
This directly implements the \texttt{nub} call in the choice case of
\citet[sect.~3, Fig.~6]{sulzmannlu2014}'s simplification:
\[
simp\ (bs@{\oplus}(ri : rsi)) = bs@{\oplus}\bigl(\mathit{nub}\
(\mathit{filter}\ (\neg\,\mathit{isPhi})\ ((simp\ ri) : \mathit{map}\
simp\ rsi))\bigr),
\]
Haskell's \texttt{nub} is quadratic for the same reason.
With only an \texttt{Eq} instance available, 
it keeps the first occurrence of each element 
by comparing it against every element already kept.
\texttt{same\_shape} is this same equality test, 
made insensitive to bit-code history 
so that identical branches merge regardless of parse path. 
The paper's complexity claim covers input length rather than pattern width, 
so this result does not contradict it.

%

The partial-derivative pair deduplicates differently, and more cheaply: 
\texttt{nub2} and \texttt{nub\_tree} are both hash-based and $O(p)$.
The two differ only in what carries along with each residual, 
a bit vector in \texttt{pderiv\_bc} and an injection closure in \texttt{pderiv\_std}.
Since the mechanism is otherwise the same, 
only \texttt{pderiv\_bc}'s is shown (Figure~\ref{fig:nub2-rust}). 

\begin{figure}[H]
\small
\begin{verbatim}
pub(super) fn step_frontier(frontier: &[(Regex, AppendBits)], x: char) 
-> Vec<(Regex, AppendBits)> {
    let mut out = Vec::new();
    for (r, bits) in frontier {
        for (r_next, extra) in pderiv_bc(r, x) {
            out.push((r_next, bits.append(&extra)));
        }
    }
    nub2(out)
}

pub(super) fn nub2<B>(pairs: Vec<(Regex, B)>) -> Vec<(Regex, B)> {
    let mut seen: HashSet<Regex> = HashSet::with_capacity(pairs.len());
    let mut out = Vec::with_capacity(pairs.len());
    for (r, bs) in pairs {
        if seen.insert(r.clone()) {
            out.push((r, bs));
        }
    }
    out
}
\end{verbatim}
\caption{\texttt{pderiv\_bc}'s own \texttt{step\_frontier} and
\texttt{nub2}: each live residual steps through its own
\texttt{pderiv\_bc} call, then the combined results are deduplicated
once via a \texttt{HashSet} keyed on the residual alone,
implementing the rule of \citet{sulzmannlu2012}, Definition~8: keep
only the first occurrence of each residual across the whole combined
result.}
\label{fig:nub2-rust}
\end{figure}

The real bottleneck used to be a single call, not \texttt{step\_frontier}'s loop.
Before the pattern's $p$-way alternation has split into separate live
residuals, the very first call to \texttt{pderiv\_bc} must itself descend
through the whole $p$-deep nested \texttt{Alt}, since at that point the
pattern is still one combined tree rather than $p$ separate alternatives.
An earlier version of \texttt{pderiv\_bc} called \texttt{nub2} once per
nesting level during that descent -- $p$ calls whose combined cost was
quadratic in $p$ -- instead of flattening the alternation into its $p$
leaves first and deduplicating them once, the fix described in
Section~\ref{sec:pderiv-tree-impl}.
Measured directly, essentially all of that old cost sat in the single
first call, not spread across later characters.
\texttt{step\_frontier}'s own loop, run once the alternation has already
split into separate residuals, calls \texttt{pderiv\_bc} and then
\texttt{nub2} exactly once per character, each call linear in the number
of live residuals.
On E38, the shared prefix \texttt{w0000\dots} keeps more residuals alive
and undistinguished for longer, so this linear cost repeats over more
characters than it does on E37 -- but a linear cost repeated a few extra
times is nowhere near the quadratic cost the old nesting paid once, which
is why the partial-derivative pair stays cheap on both.
The standard pair pays neither cost.
No cross-branch comparison and no per-residual call.

The improvement for \texttt{deriv\_bc} would be
replacing the pairwise \texttt{same\_shape} scan
with a hash keyed on bit-code-independent structure,
which is the same approach \texttt{nub2} and \texttt{nub\_tree} already take.
This would make this dedup $O(p)$ without changing what it computes.
A fix of the same shape was available for the partial-derivative pair's
own former bottleneck too, and has already been applied: flattening the
nested \texttt{Alt} before deduplicating once, rather than once per
nesting level (Section~\ref{sec:pderiv-tree-impl}).
\texttt{deriv\_bc}'s own fix above is the one that remains outstanding.
Batching that loop's work across all live residuals in one pass 
would require restructuring how they are stored, not just replacing a comparison.

choice when $p$ is bounded, as it is on the real corpus
(Section~\ref{sec:eval-s2elab}), but the two synthetic rows show
that choice does not hold unconditionally as $p$ grows without bound.

a 99th percentile of 16.

The largest real-corpus pattern translates to 18\,707 nodes, so the
20\,000-node cap covers every pattern in this evaluation.

\textbf{S2ELab.} The loosely-formatted-number pattern
\begin{center}

\end{center}

\section{Discussion of Results}
\label{sec:eval-discussion}

%
%
%

\subsection{Cost of the standard construction}

The two standard derivative parsers are consistently the slowest and
use the most memory. Their two-pass structure stores every intermediate
expression until the backward pass completes. On \texttt{a\*} input,
their state grows linearly with $n$, while the other three variants
remain bounded in the measured range.

On the full corpus, the standard variants have similar mean times
(7.605\,ms and 7.371\,ms), but their matching totals differ.
\texttt{deriv\_std\_loop} takes 70.321\,s, compared with 73.493\,s
for \texttt{deriv\_std\_rec}. Their non-match totals are almost
identical, suggesting that iteration mainly reduces the cost of
matching. On the representative rows, both variants reach the
memory cap at the same input lengths and have similar allocation
figures. This points to their shared retention of intermediate
derivatives rather than recursion depth. The separate stack-depth
test isolates the other failure mode. Without a memory cap,
\texttt{deriv\_std\_loop} survives roughly 25 times longer in wall
time before the doubling search's own per-probe cap ends it. Thus, the limiting factor depends on whether
derivation cost or stack depth grows first.

%
%
%

\subsection{Cost of bit-coding}
\label{sec:eval-cost-bit-coding}

For the standard-derivative family, bit-coding performs better on
the measured corpus. \texttt{deriv\_bc} has a mean time of
1.646\,ms, roughly $4.5\times$ below the standard variants,
and a peak allocation of 5.1\,MB, about $114$--$144\times$ lower.
Its forward pass retains information needed for single-pass
reconstruction rather than simplifying every redundant branch.
The decode step adds little time, staying under 0.1\,ms even at
$p=2\,000$ swept alternatives, while encode grows with pattern size
alone, from 0.65\,ms at $p=500$ to 2.97\,ms at $p=2\,000$
(Table~\ref{tab:patho-phases-e37}). At far larger $p$, this same row
is also where \texttt{deriv\_bc} stops being faster than the standard
pair at all, discussed below.

The representative sweeps extend this result. \texttt{deriv\_bc}
completes three of the four rows (P60, P61, P09), while both standard
variants crash on all four. It reaches the full ten-million-character
range on all three. Cumulative allocation can still be high, reaching
169.26\,GB on P60, although peak allocation is 2.64\,GB. This distinction between
cumulative allocation and peak live bytes is why both are reported
(Section~\ref{sec:eval-criteria-memory}).

%
%
%

\subsection{Cost of partial derivatives}
\label{sec:eval-cost-partial-derivatives}

The partial-derivative parsers are the fastest and use the least
memory on the S2ELab corpus. They represent the residual as a set
of states rather than one combined expression, limiting the
alternation growth seen in the standard derivative parser.

Within the pair, bit-coding does not consistently help or hurt.
On the full corpus, \texttt{pderiv\_bc} is marginally faster
(0.664 against \texttt{pderiv\_std}'s 0.759\,ms mean) and has
lower total allocation (4.70 against \texttt{pderiv\_std}'s
5.68\,GB), though \texttt{pderiv\_std} still has the lower peak
(2.5 against 3.8\,MB). This asymmetry follows from how the two
parsers apply the same collapse (Section~\ref{sec:pderiv-tree-impl}):
\texttt{pderiv\_std}'s nullable-\texttt{Seq} branch builds a
differently-shaped injection closure on every step where $r_1$'s own
derivative is \texttt{Eps}, regardless of whether a duplicate
residual was actually waiting to be caught, while \texttt{pderiv\_bc}'s
side of the same collapse only removes a wrapper, with no added cost
on a step where nothing needed collapsing. On the real corpus, where
that collision is rare, this shows up as a small net loss for
\texttt{pderiv\_std} and a small net gain for \texttt{pderiv\_bc}.
The ranking on the representative rows is less clean than the
corpus-wide one, and in a different way than it first appeared. At
the largest input each parser reaches, the two trade narrow leads
rather than either holding a stable one: \texttt{pderiv\_bc} is a
little ahead on P60 (0.685 against \texttt{pderiv\_std}'s 0.722 of
\texttt{deriv\_bc}'s time), on P61 (0.831 against 0.901, at the
five-million-character point both still reach there before
\texttt{pderiv\_std} crashes), and on P09 (0.520 against 0.529),
while \texttt{pderiv\_std} is the more consistent winner on P01,
increasingly so from $n=1\,000$ onward. Three of the four rows
therefore lean the same way as the full corpus; P01, not P61, is the
one that does not. The peak-memory ranking generalizes more cleanly:
\texttt{pderiv\_bc} has the lower peak on every one of the four rows
without exception, compared at the largest input length both reach --
1.14 against 1.68\,GB on P01; 1.40 against 2.56\,GB on P09; 1.64
against 3.12\,GB on P60; and 1.64 against 3.12\,GB on P61 at the
five-million-character point, the largest \texttt{pderiv\_std} still
reaches there before it crashes. \texttt{pderiv\_std}'s own peak also
rose from the previous measurement on exactly the three rows built
around an alternation -- P60, P61, and P09 -- enough on P61 to newly
cross the memory cap at the input length where it previously
completed; \texttt{pderiv\_bc} shows no such rise on any row
(Section~\ref{sec:eval-memory-representative} discusses this
further). The results suggest that the relative cost of bit-coding
depends on the pattern and input, not only on input length --
consistently so for peak memory, where \texttt{pderiv\_bc} always
helps, but less so for speed, where the margin between the two is
narrow enough on three of the four representative rows that it reads
as noise rather than a stable effect, leaving P01 as the only row
with a clear, consistent winner.

The two bit-coded parsers' phase costs diverge sharply once the
pattern itself grows wide, but in the opposite direction from before
the \texttt{Alt}-flattening fix described in
Section~\ref{sec:pderiv-tree-impl}: it is now \texttt{deriv\_bc}, not
\texttt{pderiv\_bc}, that falls behind. On a $p$-way alternation of
equal-length words (Table~\ref{tab:patho-phases-e37}),
\texttt{deriv\_bc}'s derive time grows from $2.1\times$
\texttt{pderiv\_bc}'s at $p=100$ to $13.3\times$ at $p=10\,000$ on
matching input, since \texttt{deriv\_bc}'s own branch-deduplication
(Figure~\ref{fig:dedup-first-rust}) is still the pairwise $O(p^2)$ scan
it always was, where \texttt{pderiv\_bc}'s is now a single $O(p)$
hashed pass over the flattened alternatives. \texttt{deriv\_bc} also
now loses badly to the standard pair at this scale
(Section~\ref{sec:eval-timing-representative}), where previously it
was the other bit-coded parser's own bug that lost there instead;
\texttt{pderiv\_bc} itself stays well ahead of the standard pair
throughout.
Non-matching input tells the opposite story. Rejecting
\texttt{"zzzz"} still means deriving every one of the $p$ alternatives
once, but none of them survive, so there is nothing left to
deduplicate either way -- and here \texttt{pderiv\_bc} is the slower
parser, not the faster one: 39.51\,ms against \texttt{deriv\_bc}'s
30.58\,ms at $p=10\,000$. Flattening itself is not free: it builds one
prefix per leaf before any of them are derived, and a right-nested
chain gives the $k$-th leaf a prefix of length $k$, so flattening alone
costs $O(p^2)$ bit-vector copies regardless of whether a single leaf
survives (the same cost behind the memory rows in
Section~\ref{sec:eval-memory-representative}). On matching input that
cost is paid once and is dwarfed by the $O(p^2)$ dedup it replaces; on
input every alternative rejects immediately, the dedup it replaces was
already cheap, so flattening has nothing left to offset it against.
\texttt{pderiv\_bc}'s own encode step remains consistently cheaper
than \texttt{deriv\_bc}'s regardless of outcome, since cloning the
pattern tree does less work per node than building \texttt{deriv\_bc}'s
annotated state.

Both partial-derivative variants produce non-POSIX trees. This is
a difference in parsing policy, not a correctness defect, and is
why the two families are compared separately in
Section~\ref{sec:eval-agreement}.

\subsection{Threats to validity}

\textbf{Corpus scope.} S2ELab represents one domain and its
conventions. Other corpora may have different acceptance rates and
timing profiles. Timing, Memory, and Parse Agreement use the
463-pattern default scope (Section~\ref{sec:eval-s2elab}).
Including the remaining 115 patterns with
\texttt{BENCH\_MATCH\_INTENT=both} could change the absolute
results and potentially the ranking of candidates.

\textbf{The synthetic set.} Its 112 rows isolate individual
complexity mechanisms at controlled scales rather than representing
patterns written by typical users. Most categories vary one parameter
at a time, so combinations of stress mechanisms are not directly tested.

\textbf{Agreement subset.} The \emph{Compared} subset includes
expected matches completed by every candidate, with both families
internally consistent. It excludes 71 of 5\,869 S2ELab matches
(about 1\%) and 236 of 443 synthetic matches (about 53\%).
The synthetic result is therefore based on a much smaller subset.
For alternation-heavy categories, the excluded cases may also contain
more ambiguity because shared prefixes can increase both derivation
cost and the number of possible parses. This need not apply to
categories such as I, where timeouts arise from input length alone.

\textbf{Measurement model.} The memory benchmarks measure heap
allocations, not total process memory. Timing results are specific
to the machine used and may vary with its CPU and cache. A recorded
\emph{crash} means that the process was killed by a signal, not
that stack overflow was confirmed
(Section~\ref{sec:eval-criteria-setup}). The separate stack-depth
test removes the memory cap and provides direct evidence of stack
overflow. The representative-row crashes are instead consistent
with the memory costs of retaining intermediate derivatives.
