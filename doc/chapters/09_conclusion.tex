\subsection{Space-Efficient Parsing}
\label{sec:space-efficient-parsing}

\texttt{deriv\_bc} (Section~\ref{sec:derivative-parser-bitcoded-rust}) already
avoids materializing a full \texttt{ParseTree} at every step by carrying
a bit-string instead, but the bit-string itself is still rebuilt from
scratch by \texttt{internalize} and grows with the regular expression's
own size, not with the input consumed so far -- space use is bounded by
$|r|$ per step, not by $|w|$ overall, but it is not asymptotically
smaller than building a tree directly. \citet{sulzmannlu2014} point to
exactly this as future work, citing \citet{grathwohl2013}'s two-pass
approach: a first, forward pass over the input computes only enough --
a sequence of automaton states, not full derivatives or bit-strings --
to determine \emph{whether} the input matches and, if so, the length of
each top-level split the POSIX ordering settled on; a second, backward
pass then replays that information to construct the actual parse tree,
without needing to keep every intermediate derivative alive at once.
The two-pass structure trades one full left-to-right scan for a
guarantee that neither pass carries the accumulated state proportional
to $|r| \times |w|$ that a naive one-pass tree-building approach would
in the worst case. Nothing in this thesis's own four parsers implements
this: \texttt{deriv\_std}/\texttt{deriv\_bc} are already effectively
one-pass-forward-then-one-pass-backward (Section~\ref{sec:mk-eps-impl}'s
$\mathit{mkEps}$ plus injection, or $\mathit{mkEpsBC}$ plus
\texttt{decode}), but neither pass is restricted to the reduced
state Grathwohl et al.\ describe -- both still carry a full
(bit-annotated) regular expression forward at every step, which is
exactly the space cost their two-pass method is designed to cut.

\subsection{DFA/NFA Hybrid Abstraction}
\label{sec:dfa-nfa-hybrid}

Section~\ref{sec:performance-comparison} traced this thesis's
five-to-six order of magnitude gap against Rust's \texttt{regex}
crate/RE2 to a difference in kind: those engines compile an automaton
once and then only walk it, while every parser here recomputes
derivative structure on every character of every match.
\citet{sulzmannlu2014} name a concrete middle ground between "no
automaton at all" and "compile the full POSIX DFA," directly in their
own related-work discussion: \emph{"a surprisingly simple and efficient
method to improve the performance of our approach is to apply some form
of abstraction. Instead of trying to find matches for all subpattern
locations, we may only be interested in certain locations. \ldots For
subparts we don't care about, rely on an NFA"} -- using the (potentially
exponentially larger) POSIX-respecting DFA construction only for the
subexpressions whose exact parse-tree shape a caller actually needs, and
falling back to a plain NFA, which needs no disambiguation bookkeeping
at all, for the rest. This is a different lever than
Section~\ref{sec:derivative-automaton-caching}'s automaton caching: caching
answers \emph{how} to avoid rebuilding the same automaton on every
match, whereas this abstraction answers \emph{how much} automaton needs
building in the first place, by admitting that most callers of a parser
do not need a fully disambiguated tree for every subexpression, only for
the ones a capture group or downstream consumer actually reads. Neither
this thesis's derivative-based parsers nor its partial-derivative-based
ones currently distinguish "subpatterns I need a tree for" from
"subpatterns I only need to know matched" -- every subexpression is
carried through derivation and disambiguated with the same POSIX
machinery regardless of whether anything downstream inspects its shape,
which is exactly the cost this abstraction is designed to let a caller
opt out of.



\section{Further Performance Optimizations}
\label{sec:further-performance-optimizations}

Section~\ref{sec:performance-comparison} measured a five-to-six order of
magnitude gap between this thesis's parsers and Rust's \texttt{regex}
crate/RE2 on the real-world corpus, and argued that the gap is a
difference in kind -- recomputing structure on every character of every
match, against compiling once and walking a table -- rather than a
shortfall to be closed outright. This section is about what is
realistically achievable within that same "recompute per match" model,
and, separately, what would step outside it.

\subsection{Character Classes in Place of Literal Alternation}
\label{sec:char-class-optimization}

The single largest inefficiency specific to the real-world corpus
workload is not in the parsers themselves but in what they are asked to
parse: every unanchored dataset pattern is padded with one or two copies
of \texttt{wildcard\_run()}, a 98-way \texttt{Alt} of individual literal
characters (\texttt{docs/SUBSTRING\_SEARCH.md}). Deriving through this
padding costs a walk over up to 98 alternatives per character, for
padding that is syntactically identical across every one of the sixty
sampled patterns. A dedicated \texttt{Regex} variant representing a
character class as a range set or bitset, rather than as a literal tree
of \texttt{Lit}/\texttt{Alt} nodes, would turn nullability and
derivative computation on the padding into an $O(1)$ set-membership test
in place of an $O(98)$ tree walk -- plausibly the single highest-leverage
change available without altering the parsing algorithm itself, since it
is exactly the kind of workload Section~\ref{sec:performance-comparison}'s
real-world benchmark exercises most.

\subsection{Structural Sharing via \texttt{Rc}}
\label{sec:rc-sharing-optimization}

Every \texttt{Regex}/\texttt{ARegex} subexpression left untouched by a
derivative step -- for instance \texttt{Seq}'s right operand when the
left was not nullable -- is still deep-cloned into the freshly
constructed parent node, since \texttt{Box} implies exclusive ownership.
Replacing \texttt{Box} with \texttt{Rc} throughout the core types would
turn every such "subexpression is unchanged this step" case into an
$O(1)$ reference-count increment instead of an $O(\text{subtree size})$
clone, at the cost of the types no longer being trivially
\texttt{Send}/\texttt{Sync} without further work -- not a concern for
this project's single-threaded parsers and benchmarks, but worth noting
as a real trade-off, not a free change.

\subsection{Memoizing \texttt{deriv}/\texttt{nullable}}
\label{sec:memoization-optimization}

Real corpus patterns, and in particular the wildcard padding shared
across nearly all of them, cause the same \texttt{(Regex, char)} pairs
to be derived repeatedly across the sample. A cache keyed on that pair
-- practical once structural sharing (Section~\ref{sec:rc-sharing-optimization})
makes cache keys cheap to compare and hash -- would turn repeated
derivations into cache hits. This is a direct application of the same
principle Section~\ref{sec:bitcoded-optimization-theory}'s bit-coded
construction already uses \emph{within} a single parse (never repeating
work \texttt{mkEpsBC} needs by fusing it forward); a cache would extend
the same idea \emph{across} parses of different patterns against
overlapping padding.

\subsection{Benchmarking the Matcher, Not the Parser, for Membership}
\label{sec:matcher-benchmark-fairness}

This one is a benchmarking-methodology correction rather than an
implementation change. \texttt{bench\_dataset.rs} and
\texttt{bench\_external.rs} both call the full parsers
(\texttt{parse\_loop}, \texttt{parse\_bitcoded}, \texttt{parse\_pderiv\_bc},
\texttt{parse\_pderiv\_std}) even though the corpus sweep only ever
checks \texttt{Option::is\_some()} -- Chapter~\ref{sec:derivatives}'s
Boolean matchers (\texttt{match\_deriv}/\texttt{match\_pderiv}), which
build no parse tree or bit-vector at all, answer the identical question
more cheaply and would be the fairer comparison against
\texttt{regex}/RE2's own \texttt{is\_match}, which likewise builds
nothing beyond a Boolean. Re-pointing the corpus benchmarks at the
matchers rather than the parsers for membership-only measurements is a
benchmark change, not a code change, and has not been done here.

\subsection{A Different Project: Caching the Derivative Automaton}
\label{sec:derivative-automaton-caching}

All four optimizations above stay within the model
Section~\ref{sec:performance-comparison} described: every match still
recomputes its own derivative sequence from scratch. Closing the
remaining gap to \texttt{regex}/RE2 would mean stepping outside that
model entirely -- caching the states a pattern's derivatives reach, and
the transitions between them, \emph{once}, then reusing that cache
across every subsequent match the way a compiled automaton engine
already does. This is not a novel idea original to this thesis: it is,
in essence, Brzozowski's own original construction, since a regular
expression's derivatives were introduced specifically to build a DFA
(each distinct derivative is a state, each character a transition)
\citep{brzozowski1964} -- Section~\ref{sec:brzozowski-derivatives}'s
$r \backslash x$ already computes exactly this, just without memoizing
the states reached. Owens, Reppy, and Turon reexamine this construction
in a modern functional setting, showing it practical for engines
handling large character sets and producing smaller state machines than
the classical McNaughton--Yamada construction \citep{owens2009}.

Doing this for the parsers in this thesis, not just the Boolean matchers
the classical construction targets, would mean caching not bare
\texttt{Regex} states but enough annotation at each cached state to
still recover a POSIX or Greedy parse tree on a later match reusing it
-- an open question this thesis does not attempt to answer, since it
changes what is being built: a compiled, reusable automaton with
derivative-based \emph{construction}, rather than a derivative-based
\emph{parser} run directly against each input as this thesis's four
constructions are. It is named here as the concrete, literature-grounded
direction that would actually close most of Section~\ref{sec:performance-comparison}'s
gap, rather than as a plan this thesis attempts to execute.
