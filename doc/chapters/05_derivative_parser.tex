\chapter{Derivative-Based Parser}
\label{sec:derivative-parser}
Chapter~\ref{sec:derivatives} showed how a Brzozowski-derivative matcher
determines whether $w \in L(r)$ and Chapter~
\ref{sec:matching-vs-parsing} showed that a matching word may admit multiple
valid parse trees. A parser must therefore select a single parse tree
according to a disambiguation policy.

Following Sulzmann and Lu \citep{sulzmannlu2014}, this chapter presents two
methods for constructing POSIX parse trees from regular expression
derivatives. The direct construction performs a forward derivative pass
followed by backward tree reconstruction, while the bit-coded construction
records parse-tree information during the forward pass and reconstructs the
tree without a separate backward pass. Both methods produce identical POSIX
trees, and each algorithmic step is accompanied by its Rust implementation.

%
%
%

\section{The Two-Pass Approach}
\label{sec:deriv-parser-motivation}
Consider $r = a\cdot b$ with input $w = \mathtt{ab}$. This expression is unambigious 
and has exactly one parse tree, so the question is 
whether it can be recovered from the derivation sequence:

\begin{equation}\label{eq:deriv-std-example}
\begin{aligned}
a\cdot b &\xrightarrow{\ a\ } \varepsilon\cdot b \\
\varepsilon\cdot b &\xrightarrow{\ b\ } \phi\cdot b+\varepsilon.
\end{aligned}
\end{equation}

The final expression is nullable, confirming $w \in L(r)$, as
established by the derivative construction in Chapter~\ref{sec:derivatives}.
However, no consumed character survives in the final expression, so the parse
tree $(a,b)$ cannot be recovered directly from $\phi\cdot b+\varepsilon$.

The derivation sequence itself already contains the information needed to reconstruct
the tree. Each step transforms the expression by consuming one character.
Reversing these steps reinserts the characters into a parse tree, so it can be
recovered by walking the same sequence backward. Figure~\ref{fig:two-pass}
shows this process, with the forward pass showing the derivation
sequence and the backward pass showing the corresponding tree reconstruction.

\label{fig:two-pass}

The backward pass reconstructs the parse tree by walking the derivation
sequence in reverse. $\mathit{mkEps}$ builds a parse tree for the empty word
from the final nullable expression. Each injection step $\mathit{inj}$ then reinserts
one character, moving right to left. After the first injection, the tree is
$((\,),b)$, where $(\,)$ holds the position for $a$. After the second
injection, that position receives $a$ and the tree $(a,b)$ is complete.

The example above is unambiguous and therefore does not address the
disambiguation problem. The following section presents the standard
derivative-based parser with its reconstruction operations,
including $\mathit{mkEps}$ and $\mathit{inj}$, while showing how
ambiguity is resolved using the POSIX disambiguation policy.

\section{The Direct Construction}
\label{sec:core-algorithm}

The direct construction uses two passes. The forward pass applies
\texttt{deriv} ~\ref{fig:deriv-rust} and \texttt{nullable} ~\ref{fig:nullable-rust} 
from Chapter~\ref{sec:derivatives} to process the input. 
The backward pass applies two new functions,
$\mathit{mkEps}$ and $\mathit{inj}$, 
to reconstruct a parse tree ~\ref{fig:parsetree-enum} 
from the derivation sequence. 

Unlike the matcher from Section~\ref{sec:derivative-matcher}, the direct
construction does not simplify expressions during the forward pass.
Simplification is deliberately omitted because the backward reconstruction
depends on the explicit structure of the expressions. Removing nodes during
simplification would discard information required for tree reconstruction.

%

\subsection{Building the Empty-Word Tree}
\label{sec:mkeps-theory}

The function $\mathit{mkEps}$ takes a nullable expression and constructs a
parse tree for the empty word by recursively traversing the expression's
structure. This function serves as the base case for the backward pass. Once
all input has been consumed and the final expression is known to be nullable,
$\mathit{mkEps}$ produces the initial parse tree that subsequent injection
steps will extend and refine.

\begin{equation}\label{eq:mkeps}
\begin{aligned}
\mathit{mkEps}_{\varepsilon} &= () &&(\mathsf{E}_{\varepsilon}) \\
\mathit{mkEps}_{r^{*}} &= [\,] &&(\mathsf{E}_{*}) \\
\mathit{mkEps}_{r_1 r_2} &= (\mathit{mkEps}_{r_1}, \mathit{mkEps}_{r_2})
  &&(\mathsf{E}_{\mathrm{seq}}) \\
\mathit{mkEps}_{r_1+r_2} &=
  \begin{cases}
    \mathit{Left}\ \mathit{mkEps}_{r_1} & \varepsilon \in L(r_1) \\
    \mathit{Right}\ \mathit{mkEps}_{r_2} & \text{otherwise}
  \end{cases}
  &&\begin{array}{l}(\mathsf{E}_{+}^{L}) \\ (\mathsf{E}_{+}^{R})\end{array}
\end{aligned}
\end{equation}

The first three rules follow directly from the structure of the expression.
The expression $\varepsilon$ has a single parse tree, a star matching the
empty word represents zero iterations, and a concatenation matches
$\varepsilon$ only when both factors do. No rules are required for
$\emptyset$ or literals, since neither can match the empty word.

The alternation rule incorporates the POSIX disambiguation policy. If both
$r_1$ and $r_2$ are nullable, both alternatives match the empty word, so the
longest-match criterion does not distinguish them. The left alternative is
therefore selected by the guard $\varepsilon \in L(r_1)$. This corresponds to
the left-to-right priority required by the POSIX policy when the alternatives
have equal match length. Sulzmann and Lu show that this local choice leads to
the POSIX parse tree globally \citep{sulzmannlu2014}.

%

\paragraph{In Rust.}
\label{sec:mk-eps-impl}

The recursive definition of $\mathit{mkEps}$ ~\eqref{eq:mkeps} is implemented directly in
Rust, as shown in Figure~\ref{fig:mkeps-rust} 
and follows the same cases for each expression form.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn mk_eps(r: &Regex) -> ParseTree {
    match r {
        Regex::Eps => ParseTree::Empty,
        Regex::Star(_) => ParseTree::Star(Vec::new()),
        Regex::Seq(r1, r2) => ParseTree::Pair(
            Box::new(mk_eps(r1)), Box::new(mk_eps(r2))),
        Regex::Alt(r1, r2) => if nullable(r1) {
            ParseTree::Left(Box::new(mk_eps(r1)))
        } else {
            ParseTree::Right(Box::new(mk_eps(r2)))
        },
        Regex::Lit(c) => panic!("mk_eps called on Lit('{}')", c),
        Regex::Phi => panic!("mk_eps called on Phi"),
    }
}
\end{verbatim}
\caption{\texttt{mk\_eps}: construct a parse tree for the empty word.}
\label{fig:mkeps-rust}
\end{figure}

The expression $r$ is borrowed rather than consumed because the backward pass
reads it again during injection. The alternation arm encodes the POSIX
decision as a conditional. \texttt{r2} is examined only when
\texttt{nullable(r1)} is false. Since the input is the empty word, there are
no lengths to compare, so the longest-match criterion does not apply.
The final two arms panic rather than return arbitrary trees, encoding the
precondition that neither $\phi$ nor a literal is nullable.

\subsection{Reinserting Characters}
\label{sec:inj-theory}

The function $\mathit{inj}$ reverses a single derivation step. Given a parse
tree for $r\backslash x$, it reconstructs a parse tree for $r$ by reinserting
the consumed character $x$.

\begin{equation}\label{eq:inj}
\begin{aligned}
\mathit{inj}_{x \backslash x}() &= x &&(\mathsf{I}_{\mathrm{lit}}) \\
\mathit{inj}_{(r_1+r_2) \backslash x}(\mathit{Left}\ v_1)
  &= \mathit{Left}\ (\mathit{inj}_{r_1 \backslash x}\ v_1)
  &&(\mathsf{I}_{+}^{L}) \\
\mathit{inj}_{(r_1+r_2) \backslash x}(\mathit{Right}\ v_2)
  &= \mathit{Right}\ (\mathit{inj}_{r_2 \backslash x}\ v_2)
  &&(\mathsf{I}_{+}^{R}) \\
\mathit{inj}_{r^{*} \backslash x}(v, vs)
  &= (\mathit{inj}_{r \backslash x}\ v) : vs
  &&(\mathsf{I}_{*}) \\
\mathit{inj}_{(r_1 r_2) \backslash x}(v_1, v_2)
  &= (\mathit{inj}_{r_1 \backslash x}\ v_1,\ v_2)
  &&(\mathsf{I}_{\mathrm{seq}}),\ n(r_1) = \mathrm{false} \\
\mathit{inj}_{(r_1 r_2) \backslash x}(\mathit{Left}(v_1, v_2))
  &= (\mathit{inj}_{r_1 \backslash x}\ v_1,\ v_2)
  &&(\mathsf{I}_{\mathrm{seq}}^{L}),\ n(r_1) = \mathrm{true} \\
\mathit{inj}_{(r_1 r_2) \backslash x}(\mathit{Right}\ v_2)
  &= (\mathit{mkEps}_{r_1},\ \mathit{inj}_{r_2 \backslash x}\ v_2)
  &&(\mathsf{I}_{\mathrm{seq}}^{R}),\ n(r_1) = \mathrm{true}
\end{aligned}
\end{equation}

The first four rules follow directly from the corresponding expression
constructors. A literal derived to $\varepsilon$ is reconstructed as its
consumed character. For an alternation, the incoming tag identifies the
branch containing the derived expression. For a star, the first component of
the incoming tree represents the current iteration, which is reconstructed
and prepended to the remaining iterations.

The concatenation rules cover the two cases of $\mathsf{D}_{\mathrm{seq}}$.
When $r_1$ is not nullable, no alternation is introduced, and the character
is reconstructed within the left component. When $r_1$ is nullable, the
derivative introduces an alternation whose tag records whether the character
was consumed by $r_1$ or passed to $r_2$. In the latter case, $r_1$ is absent
from the derivation sequence, so its parse tree is reconstructed using
$\mathit{mkEps}_{r_1}$.

\paragraph{In Rust.}
\label{sec:inject-impl}

\begin{figure}[H]
\small
\begin{verbatim}
pub fn inject(r: &Regex, l: char, v: ParseTree) -> ParseTree {
    match r {
        Regex::Lit(c) => { assert!(*c == l);
            ParseTree::Char(l) }
        Regex::Alt(r1, r2) => match v {
            ParseTree::Left(v1) =>
                ParseTree::Left(Box::new(inject(r1, l, *v1))),
            ParseTree::Right(v2) =>
                ParseTree::Right(Box::new(inject(r2, l, *v2))),
            _ => panic!("inject/Alt: want Left|Right"),
        },
        Regex::Star(r1) => match v {
            ParseTree::Pair(v1, vs) => {
                let mut it = vec![inject(r1, l, *v1)];
                if let ParseTree::Star(rest) = *vs { it.extend(rest); }
                ParseTree::Star(it)
            }
            _ => panic!("inject/Star: want Pair"),
        },
        Regex::Seq(r1, r2) => if !nullable(r1) {
            match v {
                ParseTree::Pair(v1, v2) => ParseTree::Pair(
                    Box::new(inject(r1, l, *v1)), v2),
                _ => panic!("inject/Seq: want Pair"),
            }
        } else {
            match v {
                ParseTree::Left(vp) => match *vp {
                    ParseTree::Pair(v1, v2) => ParseTree::Pair(
                        Box::new(inject(r1, l, *v1)), v2),
                    o => panic!("inject/SeqL: want Pair, got {:?}", o),
                },
                ParseTree::Right(v2) => ParseTree::Pair(
                    Box::new(mk_eps(r1)),
                    Box::new(inject(r2, l, *v2))),
                _ => panic!("inject/Seq: want Left|Right"),
            }
        },
        Regex::Eps | Regex::Phi => panic!("inject called on Eps/Phi"),
    }
}
\end{verbatim}
\caption{\texttt{inject}: reinsert a character into a parse tree.}
\label{fig:inject-rust}
\end{figure}

\texttt{inject(r, l, v)} takes three arguments because $\mathit{inj}$ is 
indexed by both an expression and a character. Figure~\ref{fig:inject-rust} 
shows the complete implementation.

The function matches on \texttt{r} first, then \texttt{v}, because 
~\eqref{eq:inj} indexes every rule by expression first. A tag like 
\texttt{Left} means different things depending on context. Under an alternation, 
it selects the left disjunct. Under a nullable concatenation, it indicates that 
the derivative continued inside the left operand rather than skipping to the right. 
Matching \texttt{v} before \texttt{r} would lose this context.

The expression \texttt{r} is borrowed 
and read only, as the tree \texttt{v} is consumed and decomposed. In the 
concatenation arms where the right operand was not derived, \texttt{v2} moves 
directly into the new pair with no copy, since ~\eqref{eq:inj} leaves 
$v_2$ unchanged. Only the \texttt{Right} arm of concatenation builds new content: 
the derivative skipped $r_1$ entirely, so nothing from the forward pass exists 
for its half of the pair. Therefore, \texttt{mk\_eps(r1)} synthesizes it.

Calling \texttt{nullable(r1)} here recomputes what the forward pass already 
decided when choosing between $\mathsf{D}_{\mathrm{seq}}$ and 
$\mathsf{D}_{\mathrm{seq}}^{\,n}$. Caching this information would require 
storing a separate data structure alongside the expression sequence, adding 
overhead that the bit-coded construction of 
~\ref{sec:bitcoded-optimization-theory} avoids by eliminating the 
backward pass entirely.

\subsection{The Standard Derivative-Based Parser }
\label{sec:deriv-std-parser}
The parser composes \texttt{mkEps} and \texttt{inject} by storing all 
expressions from the forward pass, then reconstructing the tree by walking 
backward. Figure~\ref{fig:deriv-std-drivers-rust} implements this 
loop-based. A recursive implementation would use the call stack to 
hold the expression sequence, but stacks have fixed size while a \texttt{Vec} 
grows dynamically on the heap, allowing the loop form to handle longer inputs 
without overflow.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn parse_deriv_std_loop(input: &str, r: &Regex)
    -> Option<ParseTree>
{
    let chars: Vec<char> = input.chars().collect();
    let mut expressions = Vec::with_capacity(chars.len() + 1);
    expressions.push(r.clone());
    for &c in &chars {
        expressions.push(deriv(expressions.last().unwrap(), c));
    }
    if !nullable(expressions.last().unwrap()) { return None; }
    let mut tree = mk_eps(expressions.last().unwrap());
    for i in (0..chars.len()).rev() {
        tree = inject(&expressions[i], chars[i], tree);
    }
    Some(tree)
}
\end{verbatim}
\caption{Standard derivative-based parser. Forward pass builds the expression sequence; 
Backward pass reconstructs the parse tree via \texttt{mkEps} and \texttt{inject}.}
\label{fig:deriv-std-drivers-rust}
\end{figure}

Every parser presented returns \texttt{Option<ParseTree>}, which allows direct 
comparison of outputs. The \texttt{flatten} function ~\ref{fig:flatten-rust}, 
is kept separate from tree construction and provides an independent correctness check: a successful parse of 
$w$ must satisfy $\mathit{flatten}(v) = w$.

\subsection{Worked Example}
\label{sec:deriv-std-worked}

This section traces the direct construction on the running example 
$r_1=(a+ab)(b+\varepsilon)$ against input $\mathtt{ab}$, as verified by 
running the tool with \texttt{--parser deriv\_std\_rec --diag 3} 
(Appendix~\ref{app:report-deriv-std-match}).

The forward pass derives twice to consume the input:

\begin{equation}\label{eq:dp-4}
r_1 \xrightarrow{\ a\ } (\varepsilon+\varepsilon b)(b+\varepsilon)
    \xrightarrow{\ b\ } \underbrace{(\phi+(\phi b+\varepsilon))(b+\varepsilon)}_{X}
       + \underbrace{(\varepsilon+\phi)}_{Y}.
\end{equation}

The first step applies $\mathsf{D}_{\mathrm{seq}}$ because $a+ab$ is not 
nullable. The second applies $\mathsf{D}_{\mathrm{seq}}^{\,n}$ because 
$\varepsilon+\varepsilon b$ now is, introducing summand $Y$. The entire 
expression becomes nullable due to $Y$. The \texttt{Eps} inside $\varepsilon b$, 
printed as \texttt{Seq(Eps, Lit('b'))}, is the node that simplification rule 
$\mathsf{S}_2$ would delete. It survives here because simplification is 
forbidden, and the backward pass requires it.

Both disjuncts $X$ and $Y$ of the final expression are nullable. Applying 
$\mathit{mkEps}$ makes the POSIX choice via rule $\mathsf{E}_{+}^{L}$, 
descending through $\mathsf{E}_{\mathrm{seq}}$ and two applications of 
$\mathsf{E}_{+}^{R}$ to reach the tree 
$v_2=\mathit{Left}(\mathit{Right}\,\mathit{Right}\,(), \mathit{Right}\,())$. 
The tool confirms this as \texttt{mkEps: nullable(r1)=true -> Left(mkEps(r1))}.

The backward pass undoes both derivatives. Undoing the second character 
applies rules $\mathsf{I}_{\mathrm{seq}}^{L}$, $\mathsf{I}_{+}^{R}$, and 
$\mathsf{I}_{\mathrm{seq}}^{R}$ in sequence. Rule $\mathsf{I}_{\mathrm{seq}}^{R}$ 
requires $\mathit{mkEps}$ to synthesize the left half of the pair, yielding 
$v_1=(\mathit{Right}((\,),b), \mathit{Right}(\,))$. Undoing the first character 
applies $\mathsf{I}_{\mathrm{seq}}$, $\mathsf{I}_{+}^{R}$, and 
$\mathsf{I}_{\mathrm{lit}}$ to produce the final tree

\[
v_0=(\mathit{Right}(a,b),\mathit{Right}(\,)),
\]

which matches the POSIX tree from Section~\ref{sec:posix-longest-leftmost}. 
The tool output records that three expressions were stored: \texttt{r0 -> r1 
-> r2}. Each is retained until its backward pass step completes. The next 
section shows how the bit-coded construction eliminates this storage 
requirement entirely.

\section{The Bit-Coded Construction}
\label{sec:bitcoded-optimization-theory}

The direct construction cannot start building the tree until the input
is exhausted, because $\mathit{inj}$ needs each $r_{i-1}$ to reconstruct
against. Sulzmann and Lu's bit-coded construction (their
Section~3.2) \citep{sulzmannlu2014} removes that dependency by building
the tree during the forward pass. Figure~\ref{fig:single-pass} shows the
result on $a^{*}$ against \texttt{"aaa"}, the bit-coded analogue of
Figure~\ref{fig:two-pass}: no bottom row, and the expression stays two
nodes wide while a bit-prefix carries the tree.

\paragraph{Bits, and annotated expressions.}
\label{sec:bitcodes}
\label{sec:annotated-expressions}
A parse tree becomes a flat bit-sequence: at an alternation, $0$ marks
$\mathit{Left}$ and $1$ marks $\mathit{Right}$; inside a star, $0$
marks "one more iteration" and $1$ marks "stop", so $\mathtt{aaa}$
under $a^{*}$ encodes as $[0,0,0,1]$ and $\varepsilon$ as $[1]$. The
bits alone are not a tree, only which branch was taken, so reading them
back needs $r$. The construction gets there by annotating the
derivative's \emph{input}: an annotated expression $\mathit{ri}$ extends
$r$ with a bit-list $bs$ at every node except $\emptyset$, which has no
parse tree to annotate,
\[
\mathit{ri} ::= \emptyset \mid (bs@\varepsilon) \mid (bs@x) \mid
(bs@\mathit{ri}_1 \oplus \mathit{ri}_2) \mid (bs@\mathit{ri}_1\, \mathit{ri}_2)
\mid (bs@\mathit{ri}^{*}),
\]
so that by the time a subexpression has become $\varepsilon$, its
accumulated annotation already is the relevant slice of the bit-string.
$\mathit{internalize}$ converts $r$ into $\mathit{ri}$ with every
bit-list empty except at an alternation, where the left operand is
tagged with a leading $0$ and the right with a leading $1$;
$\mathit{fuse}(bs,\mathit{ri})$ prepends a bit-list onto whatever
annotation $\mathit{ri}$'s top node already carries, and every other
operation here is built from it.

\paragraph{In Rust.}
\label{sec:aregex-type}
\label{sec:internalize-fuse}
Figure~\ref{fig:aregex-enum} is a second enum alongside \texttt{Regex}.

\begin{figure}[H]
\small
\begin{verbatim}
pub enum ARegex {
    Phi,                     // no annotation slot
    Eps(Vec<bool>), Lit(Vec<bool>, char),
    Alt(Vec<bool>, Box<ARegex>, Box<ARegex>),
    Seq(Vec<bool>, Box<ARegex>, Box<ARegex>),
    Star(Vec<bool>, Box<ARegex>),
}
\end{verbatim}
\caption{The annotated-expression type. \texttt{Phi} is the one variant
with no \texttt{Vec<bool>}, matching the grammar's omission.}
\label{fig:aregex-enum}
\end{figure}

Comparing this with Figure~\ref{fig:regex-enum} shows the one place a
plain \texttt{Regex} will not do: threading parse-tree information
through the expression needs somewhere on every node to put it.
\texttt{fuse} and \texttt{internalize} (Figure~\ref{fig:internalize-rust})
implement the two operations above; \texttt{fuse} rebuilds a node one
arm per variant since no field is common to all of them, with an early
return that makes the (very common) empty-prefix case a move and not a
rebuild, and \texttt{internalize}'s \texttt{Alt} arm is the only place
in the whole construction that introduces a bit from nothing, tagging
each side exactly once.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn fuse(bs: &[bool], ri: ARegex) -> ARegex {
    if bs.is_empty() { return ri; }
    match ri {
        ARegex::Phi => ARegex::Phi,
        ARegex::Eps(p) => ARegex::Eps(combine(bs, p)),
        ARegex::Lit(p, c) => ARegex::Lit(combine(bs, p), c),
        ARegex::Alt(p, r1, r2) => ARegex::Alt(combine(bs, p), r1, r2),
        ARegex::Seq(p, r1, r2) => ARegex::Seq(combine(bs, p), r1, r2),
        ARegex::Star(p, r) => ARegex::Star(combine(bs, p), r),
    }
}
pub fn internalize(r: &Regex) -> ARegex {
    match r {
        Regex::Phi => ARegex::Phi,
        Regex::Eps => ARegex::Eps(vec![]),
        Regex::Lit(c) => ARegex::Lit(vec![], *c),
        Regex::Alt(r1, r2) => ARegex::Alt(vec![],
            Box::new(fuse(&[false], internalize(r1))),
            Box::new(fuse(&[true], internalize(r2)))),
        Regex::Seq(r1, r2) => ARegex::Seq(vec![],
            Box::new(internalize(r1)), Box::new(internalize(r2))),
        Regex::Star(r1) => ARegex::Star(vec![], Box::new(internalize(r1))),
    }
}
\end{verbatim}
\caption{\texttt{fuse} prepends a bit-prefix; \texttt{internalize}
converts a \texttt{Regex}, tagging the two sides of every alternation.
\texttt{combine} concatenates two bit-lists.}
\label{fig:internalize-rust}
\end{figure}

\paragraph{The annotated derivative, in Rust.}
\label{sec:bderiv-theory}
\label{sec:deriv-bc}
$\mathit{ri}\backslash_b l$ has the case structure of
Equation~\eqref{eq:derivative}, bits threaded through instead of
discarded:
\begin{equation}\label{eq:bderiv}
\begin{aligned}
(bs@\mathit{ri}_1 \oplus \mathit{ri}_2) \backslash_b l &=
  (bs@(\mathit{ri}_1 \backslash_b l) \oplus (\mathit{ri}_2 \backslash_b l))
  &&(\mathsf{B}_{+}) \\
(bs@\mathit{ri}_1\, \mathit{ri}_2) \backslash_b l &=
  (bs@(\mathit{ri}_1 \backslash_b l)\, \mathit{ri}_2)
  &&(\mathsf{B}_{\mathrm{seq}}),\ \varepsilon \notin L(\mathit{ri}_1) \\
(bs@\mathit{ri}_1\, \mathit{ri}_2) \backslash_b l &=
  (bs@(\mathit{ri}_1 \backslash_b l)\, \mathit{ri}_2) \oplus
  \mathit{fuse}(\mathit{mkEpsBC}_{\mathit{ri}_1}, \mathit{ri}_2 \backslash_b l)
  &&(\mathsf{B}_{\mathrm{seq}}^{\,n}),\ \varepsilon \in L(\mathit{ri}_1) \\
(bs@\mathit{ri}^{*}) \backslash_b l &=
  (bs@\mathit{fuse}([0], \mathit{ri} \backslash_b l)\; ([\,]@\mathit{ri}^{*}))
  &&(\mathsf{B}_{*})
\end{aligned}
\end{equation}
On the branch where the derivative abandons $\mathit{ri}_1$ and jumps
into $\mathit{ri}_2$, the bits $\mathit{ri}_1$ would contribute to an
empty match are fused onto $\mathit{ri}_2$'s derivative: this is the
entire optimization, doing during the forward pass what
$\mathsf{I}_{\mathrm{seq}}^{R}$ postponed into $\mathit{inj}$.

\paragraph{Extracting the bits, and simplification.}
\label{sec:mkepsbc-theory}
\label{sec:simplification-rules-theory}
\label{sec:mk-eps-bc}
\label{sec:decode}
$\mathit{mkEpsBC}$ mirrors $\mathit{mkEps}$ but returns bits, with the
same left-preference guard at an alternation and a closing $1$ at a
star:
\begin{equation}\label{eq:mkepsbc}
\begin{aligned}
\mathit{mkEpsBC}_{(bs@\varepsilon)} &= bs,
\qquad
\mathit{mkEpsBC}_{(bs@\mathit{ri}^{*})} = bs \mathbin{+\!\!+} [1], \\
\mathit{mkEpsBC}_{(bs@\mathit{ri}_1\, \mathit{ri}_2)} &=
  bs \mathbin{+\!\!+} \mathit{mkEpsBC}_{\mathit{ri}_1} \mathbin{+\!\!+} \mathit{mkEpsBC}_{\mathit{ri}_2}, \\
\mathit{mkEpsBC}_{(bs@\mathit{ri}_1\oplus\mathit{ri}_2)} &=
  bs \mathbin{+\!\!+}
  \begin{cases}
    \mathit{mkEpsBC}_{\mathit{ri}_1} & \varepsilon \in L(\mathit{ri}_1) \\
    \mathit{mkEpsBC}_{\mathit{ri}_2} & \text{otherwise.}
  \end{cases}
\end{aligned}
\end{equation}
$\mathit{decode}_r$ then turns the bit-string into an ordinary parse
tree, using slice patterns on the conventions above: \texttt{[false,
rest @ ..]} means \texttt{Left} at an alternation and one more
iteration at a star, \texttt{[true, ..]} the opposite. It takes the
\emph{original}, un-annotated $r$, since $\mathit{ri}$ no longer
describes the shape once its own annotations are consumed, the dashed
arrow in Figure~\ref{fig:single-pass}. \texttt{decode} is the one
function this chapter shares with Chapter~\ref{sec:partial-derivative-parser}'s
\texttt{pderiv\_bc}, which reaches an identical \texttt{(Regex, bits)}
pair by an entirely different route.

Section~\ref{sec:deriv-no-simp} forbade simplification in the direct
construction; the bit-coded one is free to simplify, since the
information a backward pass would need is already carried on the
expression as bits, and it needs to: \citet{sulzmannlu2014} show
$a^{*}$ doubling in size at every step without it,
$a^{*}\to\varepsilon a^{*}\to\phi a^{*}+\varepsilon a^{*}\to\cdots$. A
function $\mathit{simp}$, applied after every step, propagates $\phi$
through $\mathit{Seq}$/$\mathit{Alt}$, deduplicates nested alternations
keeping the first syntactic duplicate, and folds an eliminated
$\varepsilon$'s bits forward with \texttt{fuse} rather than dropping
them; an explicit \emph{isPhi} test recognizes an empty-language
expression built up from these rules, not only the literal $\emptyset$.
Figure~\ref{fig:simp-growth} shows where the bound this buys holds and
where it does not.

The bits are not redundant duplicates to be pruned on shape alone:
each branch's annotation is a different candidate parse tree, and
dropping duplicates that ignore bits would change which tree
$\mathit{mkEpsBC}$'s left-preference selects, not merely shrink the
expression. Sulzmann and Lu claim, without fully proving, that the
construction runs in time linear in the input, on the premise that
\emph{simp} keeps the expression small; Figure~\ref{fig:simp-growth} is
one concrete case where that premise holds ($a^{*}$) and one where it
fails ($(a+(b+ab))^{*}$). Chapter~\ref{sec:evaluation} measures the
wall-clock consequence.

The driver is four lines of loop and three of finish:
\begin{verbatim}
pub fn parse_bitcoded_loop(input: &str, r: &Regex) -> Option<ParseTree> {
    let mut ri = internalize(r);
    for l in input.chars() { ri = simp(deriv_bc(ri, l)); }
    if !nullable_bc(&ri) { return None; }
    Some(decode(r, &mk_eps_bc(&ri)))
}
\end{verbatim}
Compare with Figure~\ref{fig:deriv-std-drivers-rust}: no
\texttt{Vec<Regex>} and no backward loop, \texttt{ri} reassigned in
place so only one annotated expression is ever live, and \texttt{r}
itself still borrowed at the last line, the dashed dependency of
Figure~\ref{fig:single-pass} made visible in the signature.
\label{sec:deriv-bc-driver}

\paragraph{Worked example.}
\label{sec:deriv-bc-worked}
\label{sec:deriv-worked-example}
The same $r_1$ against $\mathtt{ab}$, checked against
\texttt{--parser deriv\_bc --diag 3}
(Appendix~\ref{app:report-deriv-bc-match}). \texttt{internalize} tags
the two alternatives of $a+ab$ with
$[\mathrm{false}]$/$[\mathrm{true}]$ and likewise for $b+\varepsilon$;
those four tags are the only bits this run will ever produce, since
\texttt{internalize} is the only source of new bits. The first
character takes $\mathsf{B}_{\mathrm{seq}}$ and moves no bit, only
turning \texttt{'a'} to \texttt{epsilon}. The second takes
$\mathsf{B}_{\mathrm{seq}}^{\,n}$: two bits move, and both are traceable.
A \texttt{[false, false]} prefix appears on the right disjunct, which is
\texttt{fuse(mkEpsBC ri1)}, $a+ab$'s own left-alternative bit followed by
$(b+\varepsilon)$'s; and a \texttt{[true]} tags the left disjunct,
recording that the derivative continued into it, the same tagging
$\mathit{inj}$ discovered on the way back in
Section~\ref{sec:deriv-std-worked} but here committed immediately.
Both disjuncts are now nullable, and $\mathit{mkEpsBC}$ faces the same
choice $\mathit{mkEps}$ faced above: $\mathsf{EB}_{+}^{L}$ then
$\mathsf{EB}_{+}^{R}$ give $[1,1]$, and the report confirms
\texttt{decode((a|ab)(b|), [11]): = (Right (a, b), Right ())}, the same
$v_1$ Section~\ref{sec:deriv-std-worked} reached through an explicit
backward pass, read here off the forward pass alone.

$r_1$ has no star; running $a^{*}$ against \texttt{"aaa"} exercises
$\mathsf{B}_{*}$ instead, and is exactly Figure~\ref{fig:single-pass}:
the expression stays $([\,]@\mathtt{a})^{*}$ at every step while the
prefix grows by one \texttt{false} per character, and
\texttt{mkEpsBC(ri3) = [0001]} decodes to \texttt{[a, a, a]}, three
iterations and a stop.

\paragraph{Comparison, and where this leaves the next chapter.}
\begin{center}
\begin{tabular}{@{}l>{\raggedright\arraybackslash}p{3.7cm}%
                  >{\raggedright\arraybackslash}p{4.1cm}@{}}
\hline
& \texttt{deriv\_std} & \texttt{deriv\_bc} \\
\hline
Named intermediates & \texttt{r0 -> r1 -> r2} & \texttt{ri0 -> ri1 -> ri2} \\
Retained at the end & all three & the last one only \\
Tree-building calls & 1 \texttt{mkEps} + 2 \texttt{inject} & 1 \texttt{mkEpsBC} + 1 \texttt{decode} \\
Simplification & none, by necessity & \texttt{simp} after every step \\
\hline
\end{tabular}

\texttt{deriv\_std} needs one \texttt{inject} per character;
\texttt{deriv\_bc} needs exactly one \texttt{mkEpsBC} and one
\texttt{decode}, however long the input is: the whole content of the
optimization. Against $\mathtt{b}$, neither parser reaches a
tree-building phase; \texttt{deriv\_std} holds a \texttt{Seq} whose
left operand has both alternatives dead, while \texttt{deriv\_bc}'s
\texttt{simp} collapses the same expression to \texttt{phi} outright,
the clearest illustration of what \emph{isPhi} adds over plain
\texttt{simplify}. Both then report the identical failure, character
for character (Appendices~\ref{app:report-deriv-std-nomatch},
\ref{app:report-deriv-bc-nomatch}), since the diagnostics layer reads
its expected set off the expression at the point of failure regardless
of which construction produced it. Running both parsers, plus
\texttt{deriv\_std}'s loop driver, over 300 generated expressions
against 39 inputs each, 11\,700 cases total
(Section~\ref{sec:cross-implementation-equivalence}), all three agree
on every one, on membership and on the exact tree, despite the
bit-coded and inject routes sharing no code beyond \texttt{Regex} and
\texttt{nullable}.

Both constructions compute the POSIX tree by the same move: consume the
input with $r\backslash x$, then resolve the one remaining choice, an
alternation whose two sides both match the empty word, by preferring
the left. $\mathit{mkEps}$ makes that choice on the way back;
$\mathit{mkEpsBC}$ makes it at the end of the way out.
Chapter~\ref{sec:partial-derivative-parser} keeps this shape and
replaces $r\backslash x$ with Antimirov's $pd(r,x)$, which returns a
\emph{set}. With a set there is no single expression to be nullable and
no single alternation to prefer the left of, which changes not only the
machinery but the answer.
