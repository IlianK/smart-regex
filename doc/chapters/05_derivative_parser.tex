\chapter{Derivative-Based Parser}
\label{sec:derivative-parser}

Chapter~\ref{sec:derivatives} showed how a Brzozowski-derivative matcher
determines whether $w \in L(r)$ and Chapter~
\ref{sec:matching-vs-parsing} showed that a matching word may admit multiple
valid parse trees. A parser must therefore select a single parse tree
according to a disambiguation policy.

Following Sulzmann and Lu \citep{sulzmannlu2014}, this chapter presents two
derivative-based methods for constructing POSIX parse trees. The direct
method performs a forward derivative pass followed by a backward pass for tree
reconstruction. The bit-coded method records parse-tree information during
the forward pass, avoiding a separate backward pass.

%
%

\section{The Standard Derivative-Based Parser}
\label{sec:core-algorithm}
Consider the example $r = (a + ab)(b + \varepsilon)$ with input
$w = \mathtt{ab}$. Chapter~\ref{sec:matching-vs-parsing} showed that it
is ambiguous, as the word admits two parse trees. The question here is
whether a parse tree can be recovered from the final derivative:
\begin{equation}\label{eq:deriv-std-example}
\begin{aligned}
r
  &\xrightarrow{\ a\ }
    (\varepsilon + \varepsilon b)(b + \varepsilon) \\[2pt]
  &\xrightarrow{\ b\ }
    (\phi + (\phi b + \varepsilon))(b + \varepsilon) + (\varepsilon + \phi).
\end{aligned}
\end{equation}

The derivation was already computed in
Section~\ref{sec:deriv-worked-example}, shown here unsimplified. The
final derivative is nullable, so \(w \in L(r)\) and both disjuncts
accept the empty word. Its first disjunct,
\((\phi+(\phi b+\varepsilon))(b+\varepsilon)\), reflects
\(ab\cdot\varepsilon\), and its second,
\((\varepsilon+\phi)\), reflects \(a\cdot b\).

Since a derivative step only records the remaining input language and
not how consumed characters were matched, the final derivative alone does
not show which decomposition was selected, and cannot be
used to recover the parse tree.
However, the derivation sequence itself contains this information. Each
step consumed one character and is invertible given that character, so
reversing the steps recovers the tree, as shown in
Figure~\ref{fig:two-pass}:

\paragraph{The two-pass pipeline.}
The direct construction uses two passes. The forward pass applies
\texttt{deriv} (Figure~\ref{fig:deriv-rust}) and \texttt{nullable}
(Figure~\ref{fig:nullable-rust}) to process the input.

The backward pass applies two new functions to walk the derivation
sequence in reverse and reconstruct the parse tree. 
First $\mathit{mkEps}$ builds a parse tree for the empty word
from the final nullable expression. 
Then injection steps are applied, 
with $\mathit{inj}$ reinserting one consumed character into the parse tree, 
moving in $w$ from right to left.
Each injection step takes the current parse tree, the corresponding
derivative step, and its consumed character, 
and returns the parse tree for the preceding expression.

As shown in Figure~\ref{fig:two-pass} after the first injection of $b$, the tree is
\((\mathit{Right}((),b),\mathit{Right}())\), where \(()\) marks the
position still to be filled. After the second injection of $a$, that position is
replaced by the subtree \(\mathit{Right}(a,b)\), giving the complete parse
tree \((\mathit{Right}(a,b),\mathit{Right}())\). 

In the following the operations for the standard
derivative parser are shown in more detail.

%

\subsection{Building the Empty-Word Tree}
\label{sec:mkeps-theory}

The backward pass begins with $\mathit{mkEps}$, which reads a parse tree
for the empty word off the final nullable expression. The function
follows \citep[Fig.~3]{sulzmannlu2014} and is defined recursively:
\begin{equation}\label{eq:mkeps}
\begin{aligned}
\mathit{mkEps}_{\varepsilon} &= () &&(\mathsf{E}_{\varepsilon}) \\
\mathit{mkEps}_{r^{*}} &= [\,] &&(\mathsf{E}_{*}) \\
\mathit{mkEps}_{r_1 r_2} &= (\mathit{mkEps}_{r_1}, \mathit{mkEps}_{r_2})
  &&(\mathsf{E}_{\mathrm{seq}}) \\
\mathit{mkEps}_{r_1+r_2} &=
  \begin{cases}
    \mathit{Left}\ \mathit{mkEps}_{r_1} & \text{if } n(r_1) \\
    \mathit{Right}\ \mathit{mkEps}_{r_2} & \text{otherwise}
  \end{cases}
  &&\begin{array}{l}(\mathsf{E}_{+}^{L}) \\ (\mathsf{E}_{+}^{R})\end{array}
\end{aligned}
\end{equation}

The first three rules follow from the structure of the expression:
$(\mathsf{E}_{\varepsilon})$ gives $\varepsilon$ an empty parse tree,
$(\mathsf{E}_{*})$ treats a star matching the empty word as zero
iterations, and $(\mathsf{E}_{\mathrm{seq}})$ matches a concatenation
against $\varepsilon$ only when both factors do. No rules are needed for
$\emptyset$ or literals, since neither can match the empty word.
The alternation rule is where disambiguation occurs. If exactly one of
\(r_1\) and \(r_2\) is nullable, that branch is the only possible witness.
If both are, $(\mathsf{E}_{+}^{L})$ breaks the
tie by preferring the left one, following POSIX's leftmost-longest policy
\citep{sulzmannlu2014}.
In the example, the final expression is:
\[
(\phi + (\phi b + \varepsilon))(b + \varepsilon) + (\varepsilon + \phi).
\]
At top-level \(+\), both summands are nullable, so
$(\mathsf{E}_{+}^{L})$ applies and picks the left one. Within the left
summand's first factor \(\phi + (\phi b + \varepsilon)\), only the right
alternative is nullable, so $(\mathsf{E}_{+}^{R})$ applies, and within it
only the right sub-alternative \(\varepsilon\) is nullable, so
$(\mathsf{E}_{+}^{R})$ applies again, contributing
\(\mathit{RightRight}()\). The second factor \(b + \varepsilon\)
contributes \(\mathit{Right}()\) via $(\mathsf{E}_{+}^{R})$, giving:
\[
\mathit{Left}(\mathit{RightRight}(),\mathit{Right}()).
\]

Because disambiguation is deferred to $\mathit{mkEps}$, the forward pass
cannot simplify. The second injection recovers $\mathit{Right}(a,b)$
only because the forward pass preserved the branch that consumed $a$.
Simplified at each step, the derivation collapses to:
\[
r \xrightarrow{\ a\ } (\varepsilon + b)(b + \varepsilon)
  \xrightarrow{\ b\ } \varepsilon,
\]
This still witnesses \(w \in L(r)\) but keeps no record of which alternative
consumed \(a\) or \(b\): the matcher accepts, but a parser cannot
recover $\mathit{Right}(a,b)$ from $\varepsilon$.

%

\paragraph{In Rust.}
\label{sec:mk-eps-impl}

The recursive definition of $\mathit{mkEps}$~\eqref{eq:mkeps} is implemented directly in
Rust, as shown in Figure~\ref{fig:mkeps-rust}, following the same cases for each expression form.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn mk_eps(r: &Regex) -> ParseTree {
    match r {
        Regex::Eps         => ParseTree::Empty,
        Regex::Star(_)     => ParseTree::Star(Vec::new()),
        Regex::Seq(r1, r2) => ParseTree::Pair(
                              Box::new(mk_eps(r1)), Box::new(mk_eps(r2))),
        Regex::Alt(r1, r2) => 
            if nullable(r1)   {ParseTree::Left(Box::new(mk_eps(r1)))} 
            else              {ParseTree::Right(Box::new(mk_eps(r2)))},
        Regex::Lit(c)      => panic!("mk_eps called on Lit('{}')", c),
        Regex::Phi         => panic!("mk_eps called on Phi"),
    }
}
\end{verbatim}
\caption{\texttt{mk\_eps}: construct a parse tree for the empty word.}
\label{fig:mkeps-rust}
\end{figure}

The expression $r$ is borrowed rather than consumed because the backward
pass needs it again during injection. 
The alternation arm encodes disambiguation as a conditional,
examining \texttt{r2} only when \texttt{nullable(r1)} is false. The panic
arms enforce the precondition that $\mathit{mkEps}$ applies only to
nullable expressions, rejecting the non-nullable $\phi$ and literals.

\subsection{Reinserting Characters via Injection}
\label{sec:inj-theory}

After $\mathit{mkEps}$ constructed the parse tree $v$ for the empty input, 
the reconstruction starts
from this initial tree and proceeds backwards through the derivation sequence.
Each application of $\mathit{inj}$ takes the current tree, the corresponding
derivative step, and its consumed character, returning a tree for the
preceding expression.
$\mathit{inj}$ recursively follows the structure of
the residual until it reaches the subexpression containing the literal that
consumed the character. It reinserts the character there and then unwinds to
rebuild the surrounding tree. After all characters have been reinserted, 
the parse tree for the original expression and input is recovered. 
The injection function is defined by the following rules \citep[Fig.~3]{sulzmannlu2014}:
\begin{equation}\label{eq:inj}
\begin{aligned}
\mathit{inj}_{x \backslash x}() &= x
  &&(\mathsf{I}_{\mathrm{lit}}) \\
\mathit{inj}_{(r_1+r_2) \backslash x}(\mathit{Left}\ v_1)
  &= \mathit{Left}\ (\mathit{inj}_{r_1 \backslash x}\ v_1)
  &&(\mathsf{I}_{+}^{L}) \\
\mathit{inj}_{(r_1+r_2) \backslash x}(\mathit{Right}\ v_2)
  &= \mathit{Right}\ (\mathit{inj}_{r_2 \backslash x}\ v_2)
  &&(\mathsf{I}_{+}^{R}) \\
\mathit{inj}_{r^{*} \backslash x}(v, vs)
  &= (\mathit{inj}_{r \backslash x}\ v) : vs
  &&(\mathsf{I}_{*}) \\
\mathit{inj}_{(r_1 r_2) \backslash x}(v_1, v_2)
  &= (\mathit{inj}_{r_1 \backslash x}\ v_1,\ v_2)
  &&(\mathsf{I}_{\mathrm{seq}}),\ n(r_1) = \mathrm{false} \\
\mathit{inj}_{(r_1 r_2) \backslash x}(\mathit{Left}(v_1, v_2))
  &= (\mathit{inj}_{r_1 \backslash x}\ v_1,\ v_2)
  &&(\mathsf{I}_{\mathrm{seq}}^{L}),\ n(r_1) = \mathrm{true} \\
\mathit{inj}_{(r_1 r_2) \backslash x}(\mathit{Right}\ v_2)
  &= (\mathit{mkEps}_{r_1},\ \mathit{inj}_{r_2 \backslash x}\ v_2)
  &&(\mathsf{I}_{\mathrm{seq}}^{R}),\ n(r_1) = \mathrm{true}
\end{aligned}
\end{equation}

Rules $(\mathsf{I}_{\mathrm{lit}})$ and $(\mathsf{I}_{*})$ invert their
derivative rules directly, reconstructing the consumed character and the
current iteration, the latter prepended to the remaining ones.
Since the consumed character lies in exactly one branch of an
alternation, the incoming tree is either $\mathit{Left}\ v_1$ or
$\mathit{Right}\ v_2$. Rule $(\mathsf{I}_{+}^{L})$ recurses into $v_1$
and rebuilds the $\mathit{Left}$ node, and $(\mathsf{I}_{+}^{R})$
recurses into $v_2$ and rebuilds the $\mathit{Right}$ node.
The concatenation rules cover the three cases of the sequence derivative. If
$n(r_1) = \mathrm{false}$, $r_1$ cannot match $\varepsilon$ and must consume
$x$, so $(\mathsf{I}_{\mathrm{seq}})$ recurses into $v_1$. If
$n(r_1) = \mathrm{true}$, the derivative recorded which component consumed
$x$ as a tag: $(\mathsf{I}_{\mathrm{seq}}^{L})$ handles an incoming
$\mathit{Left}(v_1, v_2)$ tag and recurses into $v_1$, while
$(\mathsf{I}_{\mathrm{seq}}^{R})$ handles a $\mathit{Right}\ v_2$ tag by
reconstructing $r_1$'s empty match with $\mathit{mkEps}_{r_1}$ and recursing
into $v_2$. Since $\phi$ consumes no characters, $\mathit{inj}$ is never applied with
$\phi$ as the residual.

\paragraph{In Rust.}
\label{sec:inject-impl}

\begin{figure}[H]
\small
\begin{verbatim}
pub fn inject(r: &Regex, l: char, v: ParseTree) -> ParseTree {
    match r {
        Regex::Lit(c) => { assert!(*c == l);
            ParseTree::Char(l) }
        Regex::Alt(r1, r2) => match v {
            ParseTree::Left(v1) =>
                ParseTree::Left(Box::new(inject(r1, l, *v1))),
            ParseTree::Right(v2) =>
                ParseTree::Right(Box::new(inject(r2, l, *v2))),
            _ => panic!("inject/Alt: want Left|Right"),
        },
        Regex::Star(r1) => match v {
            ParseTree::Pair(v1, vs) => {
                let mut it = vec![inject(r1, l, *v1)];
                if let ParseTree::Star(rest) = *vs { it.extend(rest); }
                ParseTree::Star(it)
            }
            _ => panic!("inject/Star: want Pair"),
        },
        Regex::Seq(r1, r2) => if !nullable(r1) {
            match v {
                ParseTree::Pair(v1, v2) => ParseTree::Pair(
                    Box::new(inject(r1, l, *v1)), v2),
                _ => panic!("inject/Seq: want Pair"),
            }
        } else {
            match v {
                ParseTree::Left(vp) => match *vp {
                    ParseTree::Pair(v1, v2) => ParseTree::Pair(
                        Box::new(inject(r1, l, *v1)), v2),
                    o => panic!("inject/SeqL: want Pair, got {:?}", o),
                },
                ParseTree::Right(v2) => ParseTree::Pair(
                    Box::new(mk_eps(r1)),
                    Box::new(inject(r2, l, *v2))),
                _ => panic!("inject/Seq: want Left|Right"),
            }
        },
        Regex::Eps | Regex::Phi => panic!("inject called on Eps/Phi"),
    }
}
\end{verbatim}
\caption{\texttt{inject}: reinsert a character into a parse tree.}
\label{fig:inject-rust}
\end{figure}

\texttt{inject(r, l, v)} takes three arguments because $\mathit{inj}$ is
indexed by both an expression and a character. Figure~\ref{fig:inject-rust}
shows the complete implementation.

The function matches on the expression \texttt{r} first and on the tree
\texttt{v} second, following the order in which \eqref{eq:inj} indexes its
rules. This order matters because a tree tag is interpreted relative to the
expression that produced it. Under an alternation, \texttt{Left} selects the
left disjunct, while under a nullable concatenation it indicates that the
derivative continued inside the left operand. The \texttt{Lit} arm
reconstructs a leaf after asserting that the consumed character matches,
and the \texttt{Star} arm inverts $(\mathsf{I}_{*})$, reinserting the
character into the current iteration and prepending it to the remaining
ones.

The expression \texttt{r} is borrowed and read only, while the tree
\texttt{v} is consumed and decomposed. In the concatenation arms where the
right operand was not derived, \texttt{v2} moves directly into the new pair,
since \eqref{eq:inj} leaves it unchanged. The \texttt{Right} arm of
concatenation is the only concatenation case that synthesizes content,
calling \texttt{mk\_eps(r1)} because the derivative skipped \texttt{r1} and
the forward pass produced no tree for that half of the pair.

Calling \texttt{nullable(r1)} in the \texttt{Seq} arm recomputes a decision
the forward pass already made when it chose between
$\mathsf{D}_{\mathrm{seq}}$ and $\mathsf{D}_{\mathrm{seq}}^{\,n}$. However, carrying
this as a flag at every step would require additional storage, 
while \texttt{nullable} is cheap to evaluate on demand.

\subsection{Parser}
\label{sec:deriv-std-parser}
The parser composes \texttt{mkEps} and \texttt{inject} by storing every
forward-pass expression and reconstructing the tree in reverse. Since
\texttt{inject} takes the preceding expression as an explicit argument,
each call needs $r_{i-1}$. Re-deriving it from $r$ through the same prefix
would duplicate the forward pass, so storing it avoids computing the derivation again.

Figure~\ref{fig:deriv-std-drivers-rust} implements this iteratively,
using a \texttt{Vec} that grows dynamically on the heap. 
\begin{figure}[H]
\small
\begin{verbatim}
pub fn parse_deriv_std_loop(input: &str, r: &Regex) -> Option<ParseTree>
{
    let chars: Vec<char> = input.chars().collect();
    let mut expressions = Vec::with_capacity(chars.len() + 1);
    expressions.push(r.clone());
    for &c in &chars {
        expressions.push(deriv(expressions.last().unwrap(), c));
    }
    if !nullable(expressions.last().unwrap()) { 
      return None; 
      }
    let mut tree = mk_eps(expressions.last().unwrap());
    for i in (0..chars.len()).rev() {
        tree = inject(&expressions[i], chars[i], tree);
    }
    Some(tree)
}
\end{verbatim}
\caption{The standard derivative-based parser. The forward pass stores the
residual after each character in \texttt{expressions}, entry $i$ being the
residual after $i$ characters, and returns \texttt{None} if the final entry
is not nullable. The backward pass starts from \texttt{mk\_eps} of the
final entry and applies \texttt{inject} to the preceding entries in
reverse, yielding the parse tree for $r$.}
\label{fig:deriv-std-drivers-rust}
\end{figure}

\subsection{Worked Example: Ambiguous Expression}
\label{sec:worked-example}
Recall the ambiguous example of Section~\ref{par:ambiguous-example},
$r_0=(a\mid ab)(b\mid\varepsilon)$ on input $\texttt{ab}$.

%

\paragraph{Forward pass.}
There are two derivative steps, one per input symbol. After
deriving \texttt{a}, the left factor $\varepsilon+\varepsilon b$
is nullable, so the second derivation on \texttt{b} uses
$\mathsf{D}_{\mathrm{seq}}^{\,n}$ rather than $\mathsf{D}_{\mathrm{seq}}$:
\[
\begin{aligned}
r_0 = (a+ab)(b+\varepsilon)
  &\xrightarrow[\mathsf{D}_{\mathrm{seq}}]{a}
    r_1 = (\varepsilon+\varepsilon b)(b+\varepsilon) \\
  &\xrightarrow[\mathsf{D}_{\mathrm{seq}}^{\,n}]{b}
    r_2 = \underbrace{(\phi+(\phi b+\varepsilon))(b+\varepsilon)}_{X}
       + \underbrace{(\varepsilon+\phi)}_{Y}.
\end{aligned}
\]
The resulting final expression is $r_2$, both $X$ and $Y$ are nullable. 
The disjunct $X$ is the residual of the
$ab$ alternative in the first factor, and $Y$ is the residual of the $a$
alternative. 

%

\paragraph{Backward pass: mkEps.}
The backward pass starts by building the parse tree for the empty word: $\mathit{mkEps}(r_2)$. 
Since $r_2 = X + Y$ and both disjuncts are nullable,
$\mathsf{E}_{+}^{L}$ selects $X$.
As $X$ is a concatenation, $\mathsf{E}_{\mathrm{seq}}$ combines
the trees for its two factors:
\[
\begin{aligned}
\mathit{mkEps}(r_2)
  &= \mathit{mkEps}(X+Y)
     \xrightarrow{\ \mathsf{E}_{+}^{L}\ }
     \mathit{Left}\,\mathit{mkEps}(X)
\\[0.8em]
  \mathit{mkEps}(X)
  &\xrightarrow{\ \mathsf{E}_{\mathrm{seq}}\ }
     \bigl(
       \mathit{mkEps}(\phi+(\phi b+\varepsilon)),
       \mathit{mkEps}(b+\varepsilon)
     \bigr).
\end{aligned}
\]
Since $\phi$ and $\phi b$ are not nullable, the first factor
selects $\varepsilon$ by applying the rule $\mathsf{E}_{+}^{R}$ twice, 
while the second factor selects
$\varepsilon$ through $\mathsf{E}_{+}^{R}$ since $b$ is not
nullable, giving $v_2$:
\[
\begin{array}{@{}c@{\hspace{1em}}c@{}}
\begin{aligned}
\mathit{mkEps}(\phi+(\phi b+\varepsilon))
  &\xrightarrow{\ \mathsf{E}_{+}^{R}\ }
    \mathit{Right}\,\mathit{mkEps}(\phi b+\varepsilon)\\
  &\xrightarrow{\ \mathsf{E}_{+}^{R}\ }
    \mathit{Right}\,\mathit{Right}\,
    \mathit{mkEps}(\varepsilon)\\
  &\xrightarrow{\ \mathsf{E}_{\varepsilon}\ }
    \mathit{Right}\,\mathit{Right}\,()
\end{aligned}
&
\begin{aligned}
\mathit{mkEps}(b+\varepsilon)
  &\xrightarrow{\ \mathsf{E}_{+}^{R}\ }
    \mathit{Right}\,\mathit{mkEps}(\varepsilon)\\
  &\xrightarrow{\ \mathsf{E}_{\varepsilon}\ }
    \mathit{Right}\,()
\end{aligned}
\end{array}
\]
\[
v_2 = \mathit{mkEps}(r_2)
    = \mathit{Left}\bigl(
        \mathit{Right}\,\mathit{Right}\,(),
        \mathit{Right}\,()
      \bigr).
\]

\paragraph{Backward pass: Inj.}
Reinsertion begins with $\mathtt{b}$ and maps $v_2$ to a tree for
$r_1=(\varepsilon+\varepsilon b)(b+\varepsilon)$. Since $v_2$
carries a $\mathit{Left}$ tag, $\mathsf{I}_{\mathrm{seq}}^{L}$
recurses into $\varepsilon+\varepsilon b$, leaving the second
factor's tree $\mathit{Right}\,()$ unchanged, as all input
characters belong to the first factor under the
$ab\cdot\varepsilon$ decomposition. Inside $\varepsilon+\varepsilon b$,
$\mathsf{I}_{+}^{R}$ selects $\varepsilon b$, the residual of the
$ab$ alternative. Since $\varepsilon$ is nullable,
$\mathsf{I}_{\mathrm{seq}}^{R}$ supplies
$\mathit{mkEps}(\varepsilon)=()$ and recurses into $b$, where
$\mathsf{I}_{\mathrm{lit}}$ reinserts $\mathtt{b}$.
\[
\begin{aligned}
\mathit{inj}_{r_1 \backslash \mathtt{b}}(v_2)
  &= \mathit{inj}_{r_1 \backslash \mathtt{b}}\Bigl(
       \underbrace{\mathit{Left}(\mathit{Right}\,\mathit{Right}\,(),\;
                    \mathit{Right}\,())}_{v_2}\Bigr)\\
  &\xrightarrow{\ \mathsf{I}_{\mathrm{seq}}^{L}\ }
    \bigl(\mathit{inj}_{(\varepsilon+\varepsilon b)
          \backslash \mathtt{b}}(\mathit{Right}\,\mathit{Right}\,()),\;
          \mathit{Right}\,()\bigr)\\
  &\xrightarrow{\ \mathsf{I}_{+}^{R}\ }
    \bigl(\mathit{Right}\,
          \mathit{inj}_{\varepsilon b \backslash \mathtt{b}}
          (\mathit{Right}\,()),\;
          \mathit{Right}\,()\bigr)\\
  &\xrightarrow{\ \mathsf{I}_{\mathrm{seq}}^{R}\ }
    \bigl(\mathit{Right}\,
          (\mathit{mkEps}(\varepsilon),\;
           \mathit{inj}_{b \backslash \mathtt{b}}()),\;
          \mathit{Right}\,()\bigr)\\
  &\xrightarrow{\ \mathsf{E}_{\varepsilon},\ \mathsf{I}_{\mathrm{lit}}\ }
    \underbrace{\bigl(\mathit{Right}((), b),\;
          \mathit{Right}\,()\bigr)}_{v_1}
\end{aligned}
\]

Reinsertion of $\mathtt{a}$ maps $v_1$ to a parse tree for
$r_0=(a+ab)(b+\varepsilon)$. The outer sequence's first factor $a+ab$ is
not nullable, so $\mathsf{I}_{\mathrm{seq}}$ fires directly on $v_1$'s
first component, again leaving the second component $\mathit{Right}\,()$
untouched. That first component, $\mathit{Right}((),b)$, carries a
$\mathit{Right}$ tag, so $\mathsf{I}_{+}^{R}$ selects $ab$. Inside
$ab=\mathit{Seq}(a,b)$ the first factor $a$ is again not nullable, so
$\mathsf{I}_{\mathrm{seq}}$ fires once more and recurses into $a$, where
$\mathsf{I}_{\mathrm{lit}}$ reinserts the character:
\[
\begin{aligned}
\mathit{inj}_{r_0 \backslash \mathtt{a}}(v_1)
  &= \mathit{inj}_{r_0 \backslash \mathtt{a}}\Bigl(
       \underbrace{(\mathit{Right}((), b),\;
                    \mathit{Right}\,())}_{v_1}
     \Bigr)\\
  &\xrightarrow{\ \mathsf{I}_{\mathrm{seq}}\ }
    \bigl(\mathit{inj}_{(a+ab) \backslash \mathtt{a}}
          (\mathit{Right}((), b)),\;
          \mathit{Right}\,()\bigr)\\
  &\xrightarrow{\ \mathsf{I}_{+}^{R}\ }
    \bigl(\mathit{Right}\,
          \mathit{inj}_{ab \backslash \mathtt{a}}
          (((), b)),\;
          \mathit{Right}\,()\bigr)\\
  &\xrightarrow{\ \mathsf{I}_{\mathrm{seq}}\ }
    \bigl(\mathit{Right}\,
          (\mathit{inj}_{a \backslash \mathtt{a}}(()),\;
           b),\;
          \mathit{Right}\,()\bigr)\\
  &\xrightarrow{\ \mathsf{I}_{\mathrm{lit}}\ }
    \underbrace{\bigl(\mathit{Right}(a, b),\;
          \mathit{Right}\,()\bigr)}_{v_0}
\end{aligned}
\]

This implementation stores three intermediate expressions, $r_0$, $r_1$,
and $r_2$, one per input character plus the initial expression, for the
backward pass to reconstruct from.

\section{The Bit-Coded Derivative-Based Parser}
\label{sec:bitcoded-construction-formal}

The direct construction of Sulzmann and Lu \citep{sulzmannlu2014}
reconstructs the tree only after the full input, since each injection
step needs the preceding expression. Their bit-coded optimization records
this information during a single pass instead.

Each subexpression carries the bit-sequence it has committed to so far,
written $bs@r$. $P$ and $Q$ denote
the annotated factors for $r_0=(a+ab)(b+\varepsilon)$. Deriving  $w = \mathtt{ab}$ gives:
\begin{equation}\label{eq:bitcoded-overview-example}
\begin{aligned}
\mathit{ri}_0 &= [\,]@\Big(\underbrace{[0]@a \oplus [1]@(a\,b)}_{P}
                 \,\cdot\, \underbrace{[0]@b \oplus [1]@\varepsilon}_{Q}\Big) \\[2pt]
  &\xrightarrow{\ a\ }
    \mathit{ri}_1 = [\,]@\big(\underbrace{[0]@\varepsilon \oplus [1]@b}_{P'} \cdot\, Q\big) \\[2pt]
  &\xrightarrow{\ b\ }
    \mathit{ri}_2 = [\,]@\big([1]@Q \,\oplus\, [0,0]@\varepsilon\big).
\end{aligned}
\end{equation}

\paragraph{The bit-coded pipeline.}
$\mathit{internalize}$ tags each alternation branch with a bit that
records its preference, producing $\mathit{ri}_0=[\,]@(P\cdot Q)$ with
$P=[0]@a\oplus[1]@(a\,b)$ and
$Q=[0]@b\oplus[1]@\varepsilon$, where $0$ selects the left branch and
$1$ the right.

Deriving by $\mathtt{a}$ consumes $P$'s leading $a$, giving $P'$, while $Q$ remains
untouched. Deriving by $\mathtt{b}$ consumes the rest. Since $P'$'s
$\varepsilon$ branch is nullable, both decompositions survive. 
In the first, the derivative continues
inside $P'$, which finishes and folds its bit $1$ onto $Q$. In the
second, $Q$ matches $\mathtt{b}$ instead, and $P'$'s completion bit fuses
with $Q$'s match into $[0,0]@\varepsilon$. This yields
$\mathit{ri}_2=[\,]@([1]@Q \oplus [0,0]@\varepsilon)$. 
The helper $\mathit{fuse}$ performs this folding and fusing of bits onto surviving
nodes, prepending a bit-sequence to a node's annotation without
descending into its children. Both $\mathit{deriv}_{\mathit{bc}}$ and
$\mathit{simp}$ rely on it. 

Unlike the direct construction, the bit-coded construction requires
simplification to prevent unbounded growth of annotated expressions.
The function $\mathit{simp}$ discards dead branches and collapses
finished subexpressions, while $\mathit{fuse}$ preserves their bits
on surviving nodes, as when $P$ collapses into $P'$ and then onto $Q$.

Once $\mathtt{ab}$ is exhausted, $\mathit{mkEpsBC}$ walks $\mathit{ri}_2$
the way $\mathit{mkEps}$ walks a plain expression, taking the leftmost
nullable branch at each remaining choice: $[1]@Q$ is nullable, so it
contributes its $1$, and inside $Q$ the $\varepsilon$ branch is nullable,
contributing a second $1$, giving $\mathit{bits}=[1,1]$.
$\mathit{decode}_{r_0}$ then replays these two bits against the original
$r_0$. The first $1$ selects $a+ab$'s right branch and the second selects
$b+\varepsilon$'s right branch, giving the tree
$(\mathit{Right}(a,b),\mathit{Right}\,())$.

This shows that the bit-coded construction reconstructs the parse tree
in a single step, while the direct construction reverses residuals step by step.

\subsection{Annotated Expressions}
\label{sec:annotated-expressions}

Building parse-tree information during the forward pass extends the
derivative computation with bit-sequence annotations, propagated by the
bit-threaded derivative $\mathit{ri}\backslash_b l$.
An annotated expression $\mathit{ri}$ extends $r$ by associating each
non-$\emptyset$ node with a bit-sequence $bs$ recording the reconstruction
choices made during the forward pass.
\begin{equation}\label{eq:aregex-grammar}
\mathit{ri} ::= \emptyset \mid (bs@\varepsilon) \mid (bs@x) \mid
(bs@\mathit{ri}_1 \oplus \mathit{ri}_2) \mid
(bs@\mathit{ri}_1\,\mathit{ri}_2) \mid
(bs@\mathit{ri}^{*}).
\end{equation}

%

\paragraph{In Rust.}
\label{sec:aregex-type}
Figure~\ref{fig:aregex-enum} defines \texttt{ARegex} as the annotated
counterpart of \texttt{Regex}. Every variant except \texttt{Phi} carries a
leading \texttt{Vec<bool>} corresponding to ~\eqref{eq:aregex-grammar},
with one \texttt{bool} per bit. \texttt{Phi}
has no annotation, since it cannot contribute to a successful parse.

\begin{figure}[H]
\small
\begin{verbatim}
pub enum ARegex {
    Phi,                     // no annotation slot
    Eps(Vec<bool>), Lit(Vec<bool>, char),
    Alt(Vec<bool>, Box<ARegex>, Box<ARegex>),
    Seq(Vec<bool>, Box<ARegex>, Box<ARegex>),
    Star(Vec<bool>, Box<ARegex>),
}
\end{verbatim}
\caption{The annotated-expression type extends \texttt{Regex} with a leading
bit-list.}
\label{fig:aregex-enum}
\end{figure}

All following operations act on this \texttt{ARegex}. Since derivative and
simplification steps remove nodes while the bits attached to them must
survive, each operation needs a way to transfer those bits onto the node
that remains. The helper $\mathit{fuse}$ provides this transfer.

\subsection{Fusing Bit-Lists}
\label{sec:fuse}
$\mathit{fuse}$, defined in \citep[Fig.~5]{sulzmannlu2014}, transfers
bits from a node that is about to be removed onto the node that survives
in its place. It prepends $bs$ to the top node's annotation $bs'$ without
descending into its children, so outer reconstruction choices precede
those already recorded in the subtree.
\begin{equation}\label{eq:fuse}
\begin{aligned}
\mathit{fuse}(bs, \emptyset) &= \emptyset \\
\mathit{fuse}(bs, (bs'@\varepsilon)) &= (bs \mathbin{+\!\!+} bs')@\varepsilon \\
\mathit{fuse}(bs, (bs'@x)) &= (bs \mathbin{+\!\!+} bs')@x \\
\mathit{fuse}(bs, (bs'@\mathit{ri}_1 \oplus \mathit{ri}_2))
  &= (bs \mathbin{+\!\!+} bs')@(\mathit{ri}_1 \oplus \mathit{ri}_2) \\
\mathit{fuse}(bs, (bs'@\mathit{ri}_1\,\mathit{ri}_2))
  &= (bs \mathbin{+\!\!+} bs')@(\mathit{ri}_1\,\mathit{ri}_2) \\
\mathit{fuse}(bs, (bs'@\mathit{ri}^{*}))
  &= (bs \mathbin{+\!\!+} bs')@\mathit{ri}^{*}.
\end{aligned}
\end{equation}

%

\paragraph{In Rust.}
\label{sec:fuse-impl}

Figure~\ref{fig:fuse-rust} implements the six rules of~\eqref{eq:fuse},
one per variant. The helper \texttt{combine} corresponds to the
concatenation $\mathbin{+\!\!+}$ and places \texttt{bs} before \texttt{p},
so the newly prepended bits precede those already recorded:
\begin{figure}[H]
\small
\begin{verbatim}
pub fn fuse(bs: &[bool], ri: ARegex) -> ARegex {
    if bs.is_empty() { return ri; }
    match ri {
        ARegex::Phi => ARegex::Phi,
        ARegex::Eps(p) => ARegex::Eps(combine(bs, p)),
        ARegex::Lit(p, c) => ARegex::Lit(combine(bs, p), c),
        ARegex::Alt(p, r1, r2) => ARegex::Alt(combine(bs, p), r1, r2),
        ARegex::Seq(p, r1, r2) => ARegex::Seq(combine(bs, p), r1, r2),
        ARegex::Star(p, r) => ARegex::Star(combine(bs, p), r),
    }
}

fn combine(bs: &[bool], p: Vec<bool>) -> Vec<bool> {
    let mut new = bs.to_vec();
    new.extend(p);
    new
}
\end{verbatim}
\caption{\texttt{fuse}: prepend a bit-list to the annotation of the
top node.}
\label{fig:fuse-rust}
\end{figure}

The \texttt{Phi} arm is the only case that returns without calling
\texttt{combine}, because \texttt{Phi} represents the empty language and
carries no annotation slot, so there is no bit-list for \texttt{fuse} to
prepend to. Every other arm rebuilds the top node with a combined
annotation and moves its two children, or single child in the star case,
unchanged. Since \texttt{fuse} prepends \texttt{bs} only to the top node's
annotation, the bits carried by its children are not touched, and the
operation rewrites exactly one node regardless of how large the subtree
below it is. 

The function is therefore non-recursive, and no subtree needs to be
copied. The implementation realizes this directly, since \texttt{ri} is
consumed by value and its untouched children move into the rebuilt node
without a clone. The helper \texttt{combine} allocates a fresh
\texttt{Vec}, at a cost proportional to the combined length of the two
bit-lists rather than to the size of the subtree below. This allocation
happens on every call with a non-empty \texttt{bs}. An empty \texttt{bs}
is the one case that skips it, since combining an empty prefix with
\texttt{p} gives \texttt{p} and the rebuilt node would be identical to
the input.

\subsection{Internalizing Expressions}
\label{sec:internalize}

The forward pass operates on annotated expressions, but the input is a
plain expression, so $r$ must first be converted into its annotated
counterpart $\mathit{ri}$. The function $\mathit{internalize}$, following
\citep[Fig.~5]{sulzmannlu2014}, performs this conversion recursively, and
it is the only step that introduces new bits:
\begin{equation}\label{eq:internalize}
\begin{aligned}
\mathit{internalize}(\emptyset) &= \emptyset \\
\mathit{internalize}(\varepsilon) &= [\,]@\varepsilon \\
\mathit{internalize}(x) &= [\,]@x \\
\mathit{internalize}(r_1+r_2) &=
  [\,]@\big(\mathit{fuse}([0],\mathit{internalize}(r_1))
  \oplus \mathit{fuse}([1],\mathit{internalize}(r_2))\big) \\
\mathit{internalize}(r_1\,r_2) &=
  [\,]@\big(\mathit{internalize}(r_1)\,\mathit{internalize}(r_2)\big) \\
\mathit{internalize}(r^{*}) &= [\,]@\mathit{internalize}(r)^{*}.
\end{aligned}
\end{equation}

The tags $[0]$ and $[1]$ on the two branches of $r_1+r_2$ mark the left and
right branch respectively, so the decoder can later recover which one was
taken. Every other case
introduces no new bit and uses only the empty list $[\,]$. The two
calls to $\mathit{fuse}$ in ~\eqref{eq:internalize} are the only
points in the construction where new bits are introduced.

%

\paragraph{In Rust.}
\label{sec:internalize-impl}

Figure~\ref{fig:internalize-rust} directly maps the constructors of
\texttt{Regex} to their annotated counterparts.
Each recursive call applies \texttt{internalize} to the corresponding
subexpression, preserving the structure of the original expression in
the annotated representation.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn internalize(r: &Regex) -> ARegex {
    match r {
        Regex::Phi => ARegex::Phi,
        Regex::Eps => ARegex::Eps(vec![]),
        Regex::Lit(c) => ARegex::Lit(vec![], *c),
        Regex::Alt(r1, r2) => {
            let ri1 = fuse(&[false], internalize(r1));
            let ri2 = fuse(&[true], internalize(r2));
            ARegex::Alt(vec![], Box::new(ri1), Box::new(ri2))
        }
        Regex::Seq(r1, r2) => ARegex::Seq(vec![],
            Box::new(internalize(r1)), Box::new(internalize(r2))),
        Regex::Star(r1) => ARegex::Star(vec![], Box::new(internalize(r1))),
    }
}
\end{verbatim}
\caption{\texttt{internalize} converts a \texttt{Regex} into an \texttt{ARegex}.
Each alternation branch receives a tag recording its side, and the two
\texttt{fuse} calls are the only points where new bits are introduced.}
\label{fig:internalize-rust}
\end{figure}

The \texttt{Alt} case calls \texttt{fuse} with a non-empty bit-list,
tagging the left operand with \texttt{[false]} and the right with
\texttt{[true]} before wrapping them in a \texttt{Alt} with an empty
outer bit-list. Every later bit originates from one of these two tags and
is propagated during derivation.

The \texttt{Phi}, \texttt{Eps}, \texttt{Lit}, \texttt{Seq}, and
\texttt{Star} cases use an empty bit-list, since they introduce no
disambiguation choice at this stage. Star iteration choices are instead
determined during derivative computation.

\subsection{Extracting Bits}
\label{sec:mkepsbc-theory}

$\mathit{mkEpsBC}$, from \citep[Fig.~5]{sulzmannlu2014}, mirrors
$\mathit{mkEps}$ but extracts the corresponding bit-list, using the same
left preference at alternation and a closing $1$ for a star. Unlike
$\mathit{mkEps}$, it constructs no parse-tree nodes. Each rule prepends
the current node's bits to those returned recursively.
\begin{equation}\label{eq:mkepsbc}
\begin{aligned}
\mathit{mkEpsBC}_{(bs@\varepsilon)} &= bs \\[2pt]
\mathit{mkEpsBC}_{(bs@\mathit{ri}^{*})} &= bs \mathbin{+\!\!+} [1] \\[2pt]
\mathit{mkEpsBC}_{(bs@\mathit{ri}_1\, \mathit{ri}_2)} &=
  bs \mathbin{+\!\!+} \mathit{mkEpsBC}_{\mathit{ri}_1}
  \mathbin{+\!\!+} \mathit{mkEpsBC}_{\mathit{ri}_2} \\[2pt]
\mathit{mkEpsBC}_{(bs@\mathit{ri}_1\oplus\mathit{ri}_2)} &=
  bs \mathbin{+\!\!+}
  \begin{cases}
    \mathit{mkEpsBC}_{\mathit{ri}_1} & \varepsilon \in L(\mathit{ri}_1) \\
    \mathit{mkEpsBC}_{\mathit{ri}_2} & \text{otherwise.}
  \end{cases}
\end{aligned}
\end{equation}

The rules cover the four expression forms that can be nullable, as in
$\mathit{mkEps}$. No rules are needed for $\emptyset$ or literals, since
neither can match the empty word, and $\mathit{mkEpsBC}$ is called only on
nullable expressions, so both are handled as preconditions.

%

\paragraph{In Rust.}
Figure~\ref{fig:mkepsbc-rust} mirrors \texttt{mk\_eps}
(Figure~\ref{fig:mkeps-rust}), with one difference. Where \texttt{mk\_eps}
builds a \texttt{ParseTree}, \texttt{mk\_eps\_bc} concatenates bit-lists.
The \texttt{Star} arm also does not recurse, since a star matching the
empty word uses zero iterations, so it only appends the closing
\texttt{true} and never examines the child expression:
\begin{figure}[H]
\small
\begin{verbatim}
pub fn mk_eps_bc(ri: &ARegex) -> Vec<bool> {
    match ri {
        ARegex::Phi => panic!("mk_eps_bc called on Phi"),
        ARegex::Lit(_, c) => panic!("mk_eps_bc called on Lit('{}')", c),
        ARegex::Eps(bs) => bs.clone(),
        ARegex::Alt(bs, r1, r2) => {
            let mut result = bs.clone();
            if nullable_bc(r1) {
                result.extend(mk_eps_bc(r1));
            } else {
                result.extend(mk_eps_bc(r2));
            }
            result
        }
        ARegex::Seq(bs, r1, r2) => {
            let mut result = bs.clone();
            result.extend(mk_eps_bc(r1));
            result.extend(mk_eps_bc(r2));
            result
        }
        ARegex::Star(bs, _) => {
            let mut result = bs.clone();
            result.push(true);                     
            result                                
        }
    }
}
\end{verbatim}
\caption{\texttt{mk\_eps\_bc} implements \eqref{eq:mkepsbc}. \texttt{Phi}
and \texttt{Lit} panic, since neither can be nullable.}
\label{fig:mkepsbc-rust}
\end{figure}

\subsection{Annotated Derivatives}
\label{sec:deriv-bc-theory}

$\mathit{ri}\backslash_b l$ has the same case structure as the plain
derivative~\eqref{eq:derivative}, but extended with bits threaded through
the rules. Each rule corresponds to its unannotated
counterpart:
\begin{equation}\label{eq:bderiv}
\begin{aligned}
\emptyset \backslash_b x &= \emptyset
  &&\hspace{-1em}(\mathsf{B}_{\emptyset}) \\
(bs@\varepsilon) \backslash_b x &= \emptyset
  &&\hspace{-1em}(\mathsf{B}_{\varepsilon}) \\
(bs@c) \backslash_b x &=
  \begin{cases}
    bs@\varepsilon & c = x \\
    \emptyset & \text{otherwise}
  \end{cases}
  &&\hspace{-1em}(\mathsf{B}_{\mathrm{lit}}) \\
(bs@\mathit{ri}_1 \oplus \mathit{ri}_2) \backslash_b x &=
  (bs@(\mathit{ri}_1 \backslash_b x) \oplus (\mathit{ri}_2 \backslash_b x))
  &&\hspace{-1em}(\mathsf{B}_{+}) \\
(bs@\mathit{ri}_1\,\mathit{ri}_2) \backslash_b x &=
  (bs@(\mathit{ri}_1 \backslash_b x)\,\mathit{ri}_2)
  &&\hspace{-1em}(\mathsf{B}_{\mathrm{seq}}),\ \varepsilon \notin L(\mathit{ri}_1) \\
(bs@\mathit{ri}_1\,\mathit{ri}_2) \backslash_b x &=
  bs@\Big(
    ([\,]@(\mathit{ri}_1 \backslash_b x)\,\mathit{ri}_2)
    \oplus
    \mathit{fuse}(\mathit{mkEpsBC}_{\mathit{ri}_1},
                   \mathit{ri}_2 \backslash_b x)
  \Big)
  &&\hspace{-1em}(\mathsf{B}_{\mathrm{seq}}^{\,n}),\ \varepsilon \in L(\mathit{ri}_1) \\
(bs@\mathit{ri}^{*}) \backslash_b x &=
  (bs@\mathit{fuse}([0],\mathit{ri} \backslash_b x)\,
  ([\,]@\mathit{ri}^{*}))
  &&\hspace{-1em}(\mathsf{B}_{*}).
\end{aligned}
\end{equation}

The rules $\mathsf{B}_{+}$, $\mathsf{B}_{\mathrm{seq}}$, and
$\mathsf{B}_{*}$ preserve the outer $bs$, since derivation changes the
residual but not the choices already recorded above it. 

The nullable
sequence case $\mathsf{B}_{\mathrm{seq}}^{\,n}$ is the exception. Since
$\mathit{ri}_1$ is nullable, $x$ may be matched by either factor, so the
rule introduces a new alternation. Its left branch continues into
$\mathit{ri}_1$, while its right branch recurses into $\mathit{ri}_2$,
with the empty match's bits extracted by $\mathit{mkEpsBC}$ and fused onto
$\mathit{ri}_2$'s derivative, so the choice inside $\mathit{ri}_1$
survives. This performs during the forward pass what
$\mathsf{I}_{\mathrm{seq}}^{R}$ performs during injection. The outer $bs$
attaches to the new alternation, since the alternation as a whole is what
$\mathit{ri}_1\,\mathit{ri}_2$ derived into.

%

\paragraph{In Rust.}
\label{sec:deriv-bc-impl}

Figure~\ref{fig:derivbc-rust} implements~\eqref{eq:bderiv}, following the
case structure of plain \texttt{deriv} with bits threaded through the
constructors. The base cases \texttt{Phi}, \texttt{Eps}, and \texttt{Lit}
match plain \texttt{deriv}, except that \texttt{Lit} carries its bit-list
onto the resulting \texttt{Eps}.

The \texttt{Alt} arm derives both operands and rebuilds the alternation
with the outer \texttt{bs} on the wrapper, not pushed into either branch.
This matches $\mathsf{B}_{+}$, where the recorded choice belongs to the
alternation itself and derivation does not change it, so the bit stays on
the outer constructor until the decoder reads it.

The \texttt{Seq} arm reflects $\mathsf{B}_{\mathrm{seq}}$ and
$\mathsf{B}_{\mathrm{seq}}^{\,n}$. In the non-nullable case, \texttt{r1}
must consume the character, so only its derivative is needed and
\texttt{r2} moves directly into the rebuilt sequence. In the nullable
case, both alternatives are possible. The bits of \texttt{r1}'s empty
match are extracted by \texttt{mk\_eps\_bc} \emph{before} \texttt{r1} is
consumed by \texttt{deriv\_bc}, since after that call the original
\texttt{r1} is gone. Those bits are then fused onto the derivative of
\texttt{r2}, so the choice made inside \texttt{r1} reaches the surviving
branch. The left branch is wrapped in a fresh \texttt{Seq} with an empty
bit-list, since the outer \texttt{bs} moves to the new \texttt{Alt}
wrapper, matching $\mathsf{B}_{\mathrm{seq}}^{\,n}$. Two clones are
therefore needed. \texttt{r2.clone()} provides one copy for the left
branch and one for its own derivative, and \texttt{nullable\_bc} borrows
\texttt{r1} before \texttt{deriv\_bc} consumes it.

The \texttt{Star} arm follows the same pattern as the nullable case of
\texttt{Seq}. The body is needed both for its derivative and for the
reconstructed star, so \texttt{r.clone()} provides the second copy, and
the reconstructed star is wrapped in a fresh \texttt{Star} with an empty
bit-list for the same reason as the left branch above. The leading
\texttt{[false]} prepended to the derivative marks one more iteration,
matching the outermost bit in $\mathsf{B}_{*}$

\begin{figure}[H]
\small
\begin{verbatim}
pub fn deriv_bc(ri: ARegex, l: char) -> ARegex {
    match ri {
        // ...
        ARegex::Alt(bs, r1, r2) => {
            let d1 = deriv_bc(*r1, l);
            let d2 = deriv_bc(*r2, l);
            ARegex::Alt(bs, Box::new(d1), Box::new(d2))
        }
        ARegex::Seq(bs, r1, r2) => {
            if nullable_bc(&r1) {
                let eps_bits = mk_eps_bc(&r1);
                let d1 = deriv_bc(*r1, l);
                let d2 = deriv_bc(*r2.clone(), l);
                let left_branch = ARegex::Seq(vec![], Box::new(d1), r2);
                let right_branch = fuse(&eps_bits, d2);
                ARegex::Alt(bs, Box::new(left_branch), Box::new(right_branch))
            } else {
                let d1 = deriv_bc(*r1, l);
                ARegex::Seq(bs, Box::new(d1), r2)
            }
        }
        ARegex::Star(bs, r) => {
            let d = deriv_bc(*r.clone(), l);
            let fused = fuse(&[false], d);
            let new_star = ARegex::Star(vec![], r);
            ARegex::Seq(bs, Box::new(fused), Box::new(new_star))
        }
    }
}
\end{verbatim}

$\mathsf{B}_{\emptyset}$, $\mathsf{B}_{\varepsilon}$,
$\mathsf{B}_{\mathrm{lit}}$, $\mathsf{B}_{+}$,
$\mathsf{B}_{\mathrm{seq}}/\mathsf{B}_{\mathrm{seq}}^{\,n}$,
$\mathsf{B}_{*}$.}
\label{fig:derivbc-rust}
\end{figure}

\subsection{Decoding Bits}
\label{sec:decode}

$\mathit{decode}_r$ reconstructs a \texttt{ParseTree} from the bit
sequence produced by $\mathit{mkEpsBC}$. It walks the original,
unannotated $r$ and uses one bit per alternation to choose a branch:
{\small
\begin{equation}\label{eq:decode}
\begin{aligned}
\mathit{decode}_r(bs) &= v \quad\text{if } \mathit{decodeInner}_r(bs)=(v,[\,]) \\[0.8em]
\mathit{decodeInner}_{\varepsilon}(bs)
  &= (\mathit{Empty},\ bs) \\
\mathit{decodeInner}_{x}(bs)
  &= (\mathit{Char}(x),\ bs) \\
\mathit{decodeInner}_{r_1+r_2}(0{:}bs)
  &= \bigl(\mathit{Left}(v),\ bs_1\bigr)
  \quad\text{if } \mathit{decodeInner}_{r_1}(bs)=(v,bs_1) \\
\mathit{decodeInner}_{r_1+r_2}(1{:}bs)
  &= \bigl(\mathit{Right}(v),\ bs_1\bigr)
  \quad\text{if } \mathit{decodeInner}_{r_2}(bs)=(v,bs_1) \\[4pt]
\mathit{decodeInner}_{r_1r_2}(bs)
  &= \bigl(\mathit{Pair}(v_1,v_2),\ bs_2\bigr) \\
  &\quad\text{if } \mathit{decodeInner}_{r_1}(bs)=(v_1,bs_1)
    \text{ and } \mathit{decodeInner}_{r_2}(bs_1)=(v_2,bs_2) \\[4pt]
\mathit{decodeInner}_{r^{*}}(1{:}bs)
  &= (\mathit{Star}([\,]),\ bs) \\
\mathit{decodeInner}_{r^{*}}(0{:}bs)
  &= \bigl(\mathit{Star}(v{:}vs),\ bs_2\bigr) \\
  &\quad\text{if } \mathit{decodeInner}_{r}(bs)=(v,bs_1)
    \text{ and } \mathit{decodeInner}_{r^{*}}(bs_1)=(\mathit{Star}(vs),bs_2)
\end{aligned}
\end{equation}
}

The annotated expression has been reduced to a bare bit sequence, so
$\mathit{decode}_r$ walks the original $r$ and uses the bits only to
choose between alternation branches. Its worker $\mathit{decodeInner}$
returns both the tree for the current subexpression and the unconsumed
bits, so the recursion can continue at the correct position.

%

\paragraph{In Rust.}
Figure~\ref{fig:decode-rust} shows \texttt{decode} and the compound
arms of its worker \texttt{decode\_inner}. The worker returns a pair,
\texttt{(ParseTree, \&[bool])}, holding the tree for the current
subexpression together with whatever bits remain, which is what lets the
recursion continue at the correct position in the bit-string. Rust's slice
patterns make the leading-bit test direct, since \texttt{[false, rest @ ..]}
and \texttt{[true, rest @ ..]} both check the bit and name the remainder in
one pattern.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn decode(r: &Regex, bs: &[bool]) -> ParseTree {
    let (v, rest) = decode_inner(r, bs);
    assert!(rest.is_empty(),
        "decode: {} leftover bit(s) after decoding {:?}", rest.len(), r);
    v
}

fn decode_inner<'a>(r: &Regex, bs: &'a [bool]) -> (ParseTree, &'a [bool]) {
    match r {
        // ...
        Regex::Alt(r1, r2) => match bs {
            [false, rest @ ..] => {
                let (v, remaining) = decode_inner(r1, rest);
                (ParseTree::Left(Box::new(v)), remaining)
            }
            [true, rest @ ..] => {
                let (v, remaining) = decode_inner(r2, rest);
                (ParseTree::Right(Box::new(v)), remaining)
            }
            // ...
        },
        Regex::Seq(r1, r2) => {
            let (v1, after_r1) = decode_inner(r1, bs);
            let (v2, after_r2) = decode_inner(r2, after_r1);
            (ParseTree::Pair(Box::new(v1), Box::new(v2)), after_r2)
        }
        Regex::Star(r1) => {
            let mut items = Vec::new();
            let mut remaining = bs;
            loop {
                match remaining {
                    [true, rest @ ..] => { remaining = rest; break; }
                    [false, rest @ ..] => {
                        let (v, after) = decode_inner(r1, rest);
                        items.push(v);
                        remaining = after;
                    }
                    // ...
                }
            }
            (ParseTree::Star(items), remaining)
        }
    }
}
\end{verbatim}
\caption{\texttt{decode} and the \texttt{Alt}, \texttt{Seq}, and
\texttt{Star} arms of \texttt{decode\_inner}.}
\label{fig:decode-rust}
\end{figure}

\texttt{decode} calls the worker and asserts that no bits remain, which is
exactly the side condition that $\mathit{decode}_r$ be defined only when
the worker consumes the entire bit-string. The \texttt{Alt} arm tests the
leading bit with a slice pattern and recurses into the branch it names,
returning the remaining bits unchanged, since only the leading bit belongs
to the alternation.

The \texttt{Seq} arm shows why the worker returns a pair. It recurses into
the first factor, receives both a tree and the bits the first factor left
unconsumed, and passes those bits to the second factor. The second factor
then returns its own tree and the bits that follow it, which are the bits
for any enclosing expression. Returning only the tree would leave the
second recursion with no way to know where to start.

The \texttt{Star} arm loops, since the number of iterations is not known
in advance and is itself encoded in the bits. Each leading \texttt{false}
corresponds to one iteration, so the arm recurses into the body and then
continues the loop from whatever bits the body left behind. The loop ends
at the leading \texttt{true} that \texttt{mk\_eps\_bc} appended. The
\texttt{Eps}, \texttt{Lit}, and \texttt{Phi} arms are elided, since the
first two consume no bits and the third is unreachable.

\subsection{Parser}
\label{sec:deriv-bc-driver}

Figure~\ref{fig:deriv-bc-loop-rust} implements the bit-coded driver.
It internalizes $r$, applies \texttt{deriv\_bc} and \texttt{simp} to each
input character, checks nullability and, if successful, calls
\texttt{mk\_eps\_bc} and \texttt{decode}.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn parse_bitcoded_loop(input: &str, r: &Regex) -> Option<ParseTree> {
    let mut ri = internalize(r);
    for l in input.chars() { ri = simp(deriv_bc(ri, l)); }
    if !nullable_bc(&ri) { return None; }
    Some(decode(r, &mk_eps_bc(&ri)))
}
\end{verbatim}
\caption{\texttt{parse\_bitcoded\_loop}: the bit-coded parser implementation.}
\label{fig:deriv-bc-loop-rust}
\end{figure}

Unlike the direct implementation, which has a growing
\texttt{Vec<Regex>} for backward reconstruction, the bit-coded implementation
needs only the current \texttt{ri}. The recursive entry point has the same
three-step computation but differs only in how intermediate expressions
are stored.

\subsection{Worked Example: Ambigious Expression}
\label{sec:deriv-bc-worked}

Consider the same input $\texttt{ab}$ and regular expression $r_0=(a\mid ab)(b\mid\varepsilon)$.

%

\paragraph{Internalize.}
Before consuming input, $\mathit{internalize}$ tags each alternative with $[0]$ for the left 
branch and $[1]$ for the right branch:

\begin{equation}\label{eq:dpbc-internalize}
\mathit{internalize}(r_0) = \mathit{ri}_0 =
[\,]@\big(
  [\,]@([0]@a \oplus [1]@(a\,b))
  \cdot
  [\,]@([0]@b \oplus [1]@\varepsilon)
\big).
\end{equation}

%

\paragraph{Forward pass.}
The two input symbols are consumed by successive bit-threaded derivatives with $\mathit{simp}$ 
applied after each step. The first derivative uses $\mathsf{B}_{\mathrm{seq}}$. After consuming $\mathtt{a}$, 
the first factor becomes nullable, so the second derivative uses $\mathsf{B}_{\mathrm{seq}}^{\,n}$, 
which propagates bits from the empty match of the first factor into the derivative of the second:

\begin{equation}\label{eq:dpbc-forward}
\begin{aligned}
\mathit{ri}_0
  &\xrightarrow[\mathsf{B}_{\mathrm{seq}}]{\ a\ }
  \mathit{ri}_1 =
  [\,]@\big(
    [\,]@([0]@\varepsilon \oplus [1]@b)
    \cdot
    [\,]@([0]@b \oplus [1]@\varepsilon)
  \big) \\
\mathit{ri}_1
  &\xrightarrow[\mathsf{B}_{\mathrm{seq}}^{\,n}]{\ b\ }
  \mathit{ri}_2 =
  [\,]@\big(
    [1]@([0]@b \oplus [1]@\varepsilon)
    \oplus
    [0,0]@\varepsilon
  \big).
\end{aligned}
\end{equation}

The $[1]$ records the right alternative $ab$ of the first factor. The $[0,0]$ on the second 
branch results from fusing bits during the derivative. Unlike the direct construction, where 
$\mathit{inj}$ recovers this information later, the bit-coded method propagates it during 
the forward pass.

%

\paragraph{Extracting and decoding the bits.}
Both disjuncts of $\mathit{ri}_2$ are nullable, so $\mathit{mkEpsBC}$ applies the left-preference 
rule and selects the left disjunct. Inside, $b$ is not nullable while $\varepsilon$ is, so 
$\mathsf{EB}_{+}^{R}$ contributes its $[1]$ tag:

\begin{equation}\label{eq:dpbc-mkepsbc}
\mathit{mkEpsBC}(\mathit{ri}_2)
  \xrightarrow{\mathsf{EB}_{+}^{L}}
  \mathit{mkEpsBC}\big(
    [1]@([0]@b \oplus [1]@\varepsilon)
  \big)
  \xrightarrow{\mathsf{EB}_{+}^{R}}
  [1,1].
\end{equation}

Unlike $\mathit{mkEps}$, which constructs a partial parse tree, $\mathit{mkEpsBC}$ extracts 
only the committed choices as a bit-string. The decoder then interprets $[1,1]$ against the 
original $r_0$: the first bit selects the right branch of $a+ab$ (producing $ab$), and the 
second selects the right branch of $b+\varepsilon$:

\begin{equation}\label{eq:dpbc-decode}
\mathit{decode}_{r_0}([1,1])
  = \big(
      \mathit{Right}(a,b),
      \mathit{Right}(\,)
    \big)
  = v_0.
\end{equation}

Flattening validates the result:
\begin{equation}\label{eq:dpbc-flatten}
\mathit{flatten}(v_0) = a \cdot b \cdot \varepsilon = \mathtt{ab}.
\end{equation}

The bit-coded construction produces the same parse tree as the direct construction but stores 
only the final annotated expression $\mathit{ri}_2$, not the intermediate expressions $r_0$ 
and $r_1$.
