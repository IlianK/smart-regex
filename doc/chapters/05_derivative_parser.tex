\chapter{Derivative-Based Parser}
\label{sec:derivative-parser}
Chapter~\ref{sec:derivatives} showed how a Brzozowski-derivative matcher
determines whether $w \in L(r)$ and Chapter~
\ref{sec:matching-vs-parsing} showed that a matching word may admit multiple
valid parse trees. A parser must therefore select a single parse tree
according to a disambiguation policy.

Following Sulzmann and Lu \citep{sulzmannlu2014}, this chapter shows two
methods for constructing POSIX parse trees using derivatives. 
The direct construction performs a forward derivative pass
followed by backward tree reconstruction. Meanwhile, the bit-coded construction
records parse-tree information during the forward pass and can reconstruct the
tree without a separate backward pass. Both methods produce identical POSIX
trees, and each algorithmic step is accompanied by its Rust implementation.

%
%
%

\section{The Two-Pass Approach}
\label{sec:deriv-std-overview}
Consider $r = a\cdot b$ with input $w = \mathtt{ab}$. This expression is unambiguous 
and has exactly one parse tree, so the question is 
whether it can be recovered from the derivation sequence:

\begin{equation}\label{eq:deriv-std-example}
\begin{aligned}
a\cdot b &\xrightarrow{\ a\ } \varepsilon\cdot b \\
\varepsilon\cdot b &\xrightarrow{\ b\ } \phi\cdot b+\varepsilon.
\end{aligned}
\end{equation}

The final expression is nullable, confirming $w \in L(r)$, as
established by the derivative construction in Chapter~\ref{sec:derivatives}.
However, no consumed character survives in the final expression, so the parse
tree $(a,b)$ cannot be recovered directly from $\phi\cdot b+\varepsilon$.

The derivation sequence itself already contains the information needed to reconstruct
the tree. Each step transforms the expression by consuming one character.
Reversing these steps reinserts the characters into a parse tree, so it can be
recovered by walking the same sequence backward. Figure~\ref{fig:two-pass}
shows this process, with the forward pass showing the derivation
sequence and the backward pass showing the corresponding tree reconstruction.

\paragraph{The two-pass pipeline.}
The backward pass reconstructs the parse tree by walking the derivation
sequence in reverse. $\mathit{mkEps}$ builds a parse tree for the empty word
from the final nullable expression. Each injection step $\mathit{inj}$ then reinserts
one character, moving right to left. After the first injection, the tree is
$((\,),b)$, where $(\,)$ holds the position for $a$. After the second
injection, that position receives $a$ and the tree $(a,b)$ is complete.

The example above is unambiguous and therefore does not address the
disambiguation problem. The following section presents the standard
derivative-based parser with its reconstruction operations,
including $\mathit{mkEps}$ and $\mathit{inj}$, while showing how
ambiguity is resolved using the POSIX disambiguation policy.

\section{The Standard Derivative-Based Parser}
\label{sec:core-algorithm}

The direct construction uses two passes. The forward pass applies
\texttt{deriv} ~\ref{fig:deriv-rust} and \texttt{nullable} ~\ref{fig:nullable-rust} 
from Chapter~\ref{sec:derivatives} to process the input. 
The backward pass applies two new functions,
$\mathit{mkEps}$ and $\mathit{inj}$, 
to reconstruct a parse tree ~\ref{fig:parsetree-enum} 
from the derivation sequence. 

Unlike the matcher from Section~\ref{sec:derivative-matcher}, the direct
construction does not simplify expressions during the forward pass.
Simplification is deliberately omitted because the backward reconstruction
depends on the explicit structure of the expressions. Removing nodes during
simplification would discard information required for tree reconstruction.

%

\subsection{Building the Empty-Word Tree}
\label{sec:mkeps-theory}

The function $\mathit{mkEps}$ takes a nullable expression and constructs a
parse tree for the empty word by recursively traversing the expression's
structure. This function serves as the base case for the backward pass. Once
all input has been consumed and the final expression is known to be nullable,
$\mathit{mkEps}$ produces the initial parse tree that subsequent injection
steps will extend and refine.

\begin{equation}\label{eq:mkeps}
\begin{aligned}
\mathit{mkEps}_{\varepsilon} &= () &&(\mathsf{E}_{\varepsilon}) \\
\mathit{mkEps}_{r^{*}} &= [\,] &&(\mathsf{E}_{*}) \\
\mathit{mkEps}_{r_1 r_2} &= (\mathit{mkEps}_{r_1}, \mathit{mkEps}_{r_2})
  &&(\mathsf{E}_{\mathrm{seq}}) \\
\mathit{mkEps}_{r_1+r_2} &=
  \begin{cases}
    \mathit{Left}\ \mathit{mkEps}_{r_1} & \varepsilon \in L(r_1) \\
    \mathit{Right}\ \mathit{mkEps}_{r_2} & \text{otherwise}
  \end{cases}
  &&\begin{array}{l}(\mathsf{E}_{+}^{L}) \\ (\mathsf{E}_{+}^{R})\end{array}
\end{aligned}
\end{equation}

The first three rules follow directly from the structure of the expression.
The expression $\varepsilon$ has a single parse tree, a star matching the
empty word represents zero iterations, and a concatenation matches
$\varepsilon$ only when both factors do. No rules are required for
$\emptyset$ or literals, since neither can match the empty word.

The alternation rule incorporates the POSIX disambiguation policy. If both
$r_1$ and $r_2$ are nullable, both alternatives match the empty word, so the
longest-match criterion does not distinguish them. The left alternative is
therefore selected by the guard $\varepsilon \in L(r_1)$. This corresponds to
the left-to-right priority required by the POSIX policy when the alternatives
have equal match length. Sulzmann and Lu show that this local choice leads to
the POSIX parse tree globally \citep{sulzmannlu2014}.

%

\paragraph{In Rust.}
\label{sec:mk-eps-impl}

The recursive definition of $\mathit{mkEps}$ ~\eqref{eq:mkeps} is implemented directly in
Rust, as shown in Figure~\ref{fig:mkeps-rust} 
and follows the same cases for each expression form.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn mk_eps(r: &Regex) -> ParseTree {
    match r {
        Regex::Eps => ParseTree::Empty,
        Regex::Star(_) => ParseTree::Star(Vec::new()),
        Regex::Seq(r1, r2) => ParseTree::Pair(
            Box::new(mk_eps(r1)), Box::new(mk_eps(r2))),
        Regex::Alt(r1, r2) => if nullable(r1) {
            ParseTree::Left(Box::new(mk_eps(r1)))
        } else {
            ParseTree::Right(Box::new(mk_eps(r2)))
        },
        Regex::Lit(c) => panic!("mk_eps called on Lit('{}')", c),
        Regex::Phi => panic!("mk_eps called on Phi"),
    }
}
\end{verbatim}
\caption{\texttt{mk\_eps}: construct a parse tree for the empty word.}
\label{fig:mkeps-rust}
\end{figure}

The expression $r$ is borrowed rather than consumed because the backward pass
reads it again during injection. The alternation arm encodes the POSIX
decision as a conditional. \texttt{r2} is examined only when
\texttt{nullable(r1)} is false. Since the input is the empty word, there are
no lengths to compare, so the longest-match criterion does not apply.
The final two arms panic rather than return arbitrary trees, encoding the
precondition that neither $\phi$ nor a literal is nullable.

\subsection{Reinserting Characters via Injection}
\label{sec:inj-theory}

The function $\mathit{inj}$ reverses a single derivation step. Given a parse
tree for $r\backslash x$, it reconstructs a parse tree for $r$ by reinserting
the consumed character $x$.

\begin{equation}\label{eq:inj}
\begin{aligned}
\mathit{inj}_{x \backslash x}() &= x &&(\mathsf{I}_{\mathrm{lit}}) \\
\mathit{inj}_{(r_1+r_2) \backslash x}(\mathit{Left}\ v_1)
  &= \mathit{Left}\ (\mathit{inj}_{r_1 \backslash x}\ v_1)
  &&(\mathsf{I}_{+}^{L}) \\
\mathit{inj}_{(r_1+r_2) \backslash x}(\mathit{Right}\ v_2)
  &= \mathit{Right}\ (\mathit{inj}_{r_2 \backslash x}\ v_2)
  &&(\mathsf{I}_{+}^{R}) \\
\mathit{inj}_{r^{*} \backslash x}(v, vs)
  &= (\mathit{inj}_{r \backslash x}\ v) : vs
  &&(\mathsf{I}_{*}) \\
\mathit{inj}_{(r_1 r_2) \backslash x}(v_1, v_2)
  &= (\mathit{inj}_{r_1 \backslash x}\ v_1,\ v_2)
  &&(\mathsf{I}_{\mathrm{seq}}),\ n(r_1) = \mathrm{false} \\
\mathit{inj}_{(r_1 r_2) \backslash x}(\mathit{Left}(v_1, v_2))
  &= (\mathit{inj}_{r_1 \backslash x}\ v_1,\ v_2)
  &&(\mathsf{I}_{\mathrm{seq}}^{L}),\ n(r_1) = \mathrm{true} \\
\mathit{inj}_{(r_1 r_2) \backslash x}(\mathit{Right}\ v_2)
  &= (\mathit{mkEps}_{r_1},\ \mathit{inj}_{r_2 \backslash x}\ v_2)
  &&(\mathsf{I}_{\mathrm{seq}}^{R}),\ n(r_1) = \mathrm{true}
\end{aligned}
\end{equation}

The first four rules follow directly from the corresponding expression
constructors. A literal derived to $\varepsilon$ is reconstructed as its
consumed character. For an alternation, the incoming tag identifies the
branch containing the derived expression. For a star, the first component of
the incoming tree represents the current iteration, which is reconstructed
and prepended to the remaining iterations.

The concatenation rules cover the two cases of $\mathsf{D}_{\mathrm{seq}}$.
When $r_1$ is not nullable, no alternation is introduced, and the character
is reconstructed within the left component. When $r_1$ is nullable, the
derivative introduces an alternation whose tag records whether the character
was consumed by $r_1$ or passed to $r_2$. In the latter case, $r_1$ is absent
from the derivation sequence, so its parse tree is reconstructed using
$\mathit{mkEps}_{r_1}$.

%

\paragraph{In Rust.}
\label{sec:inject-impl}

\begin{figure}[H]
\small
\begin{verbatim}
pub fn inject(r: &Regex, l: char, v: ParseTree) -> ParseTree {
    match r {
        Regex::Lit(c) => { assert!(*c == l);
            ParseTree::Char(l) }
        Regex::Alt(r1, r2) => match v {
            ParseTree::Left(v1) =>
                ParseTree::Left(Box::new(inject(r1, l, *v1))),
            ParseTree::Right(v2) =>
                ParseTree::Right(Box::new(inject(r2, l, *v2))),
            _ => panic!("inject/Alt: want Left|Right"),
        },
        Regex::Star(r1) => match v {
            ParseTree::Pair(v1, vs) => {
                let mut it = vec![inject(r1, l, *v1)];
                if let ParseTree::Star(rest) = *vs { it.extend(rest); }
                ParseTree::Star(it)
            }
            _ => panic!("inject/Star: want Pair"),
        },
        Regex::Seq(r1, r2) => if !nullable(r1) {
            match v {
                ParseTree::Pair(v1, v2) => ParseTree::Pair(
                    Box::new(inject(r1, l, *v1)), v2),
                _ => panic!("inject/Seq: want Pair"),
            }
        } else {
            match v {
                ParseTree::Left(vp) => match *vp {
                    ParseTree::Pair(v1, v2) => ParseTree::Pair(
                        Box::new(inject(r1, l, *v1)), v2),
                    o => panic!("inject/SeqL: want Pair, got {:?}", o),
                },
                ParseTree::Right(v2) => ParseTree::Pair(
                    Box::new(mk_eps(r1)),
                    Box::new(inject(r2, l, *v2))),
                _ => panic!("inject/Seq: want Left|Right"),
            }
        },
        Regex::Eps | Regex::Phi => panic!("inject called on Eps/Phi"),
    }
}
\end{verbatim}
\caption{\texttt{inject}: reinsert a character into a parse tree.}
\label{fig:inject-rust}
\end{figure}

\texttt{inject(r, l, v)} takes three arguments because $\mathit{inj}$ is 
indexed by both an expression and a character. Figure~\ref{fig:inject-rust} 
shows the complete implementation.

The function matches on \texttt{r} first, then \texttt{v}, because 
~\eqref{eq:inj} indexes every rule by expression first. A tag like 
\texttt{Left} means different things depending on context. Under an alternation, 
it selects the left disjunct. Under a nullable concatenation, it indicates that 
the derivative continued inside the left operand rather than skipping to the right. 
Matching \texttt{v} before \texttt{r} would lose this context.

The expression \texttt{r} is borrowed 
and read only, as the tree \texttt{v} is consumed and decomposed. In the 
concatenation arms where the right operand was not derived, \texttt{v2} moves 
directly into the new pair with no copy, since ~\eqref{eq:inj} leaves 
$v_2$ unchanged. Only the \texttt{Right} arm of concatenation builds new content: 
the derivative skipped $r_1$ entirely, so nothing from the forward pass exists 
for its half of the pair. Therefore, \texttt{mk\_eps(r1)} synthesizes it.

Calling \texttt{nullable(r1)} here recomputes what the forward pass already 
decided when choosing between $\mathsf{D}_{\mathrm{seq}}$ and 
$\mathsf{D}_{\mathrm{seq}}^{\,n}$. Caching this information would require 
storing a separate data structure alongside the expression sequence, adding 
overhead.

\subsection{Parser}
\label{sec:deriv-std-parser}
The parser composes \texttt{mkEps} and \texttt{inject} by storing all 
expressions from the forward pass, then reconstructing the tree by walking 
backward. Figure~\ref{fig:deriv-std-drivers-rust} implements this 
in a loop. A recursive implementation would use the call stack to 
hold the expression sequence, but stacks have fixed size while a \texttt{Vec} 
grows dynamically on the heap, allowing the loop form to handle longer inputs 
without overflow.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn parse_deriv_std_loop(input: &str, r: &Regex)
    -> Option<ParseTree>
{
    let chars: Vec<char> = input.chars().collect();
    let mut expressions = Vec::with_capacity(chars.len() + 1);
    expressions.push(r.clone());
    for &c in &chars {
        expressions.push(deriv(expressions.last().unwrap(), c));
    }
    if !nullable(expressions.last().unwrap()) { return None; }
    let mut tree = mk_eps(expressions.last().unwrap());
    for i in (0..chars.len()).rev() {
        tree = inject(&expressions[i], chars[i], tree);
    }
    Some(tree)
}
\end{verbatim}
\caption{Standard derivative-based parser. Forward pass builds the expression sequence; 
Backward pass reconstructs the parse tree via \texttt{mkEps} and \texttt{inject}.}
\label{fig:deriv-std-drivers-rust}
\end{figure}

Every parser presented returns \texttt{Option<ParseTree>}, which allows direct 
comparison of outputs. The \texttt{flatten} function ~\ref{fig:flatten-rust} 
provides an independent correctness check. As shown in 
Section~\ref{sec:parse-trees-as-evidence}, a parse tree is a valid witness for 
membership only if $\mathit{flatten}(v) = w$.

\subsection{Worked Example}
\label{sec:worked-example}
Consider input $\texttt{ab}$ and the regular expression $r_0=(a\mid ab)(b\mid\varepsilon)$.

%

\paragraph{Forward pass.}
The two input symbols are consumed by successive derivatives:
\begin{equation}\label{eq:dp-4}
\begin{aligned}
r_0 = (a+ab)(b+\varepsilon)
  &\xrightarrow[\mathsf{D}_{\mathrm{seq}}]{a}
    r_1 = (\varepsilon+\varepsilon b)(b+\varepsilon) \\
  &\xrightarrow[\mathsf{D}_{\mathrm{seq}}^{\,n}]{b}
    r_2 = \underbrace{(\phi+(\phi b+\varepsilon))(b+\varepsilon)}_{X}
       + \underbrace{(\varepsilon+\phi)}_{Y}.
\end{aligned}
\end{equation}

Both $X$ and $Y$ are nullable. So $\mathit{mkEps}$ chooses the left
disjunct by $\mathsf{E}_{+}^{L}$, which 
causes the first factor to match $\mathtt{ab}$ rather than
$\mathtt{a}$, implementing POSIX's leftmost-longest rule:
\begin{equation}\label{eq:dp-mkeps}
\mathit{mkEps}(r_2) = \mathit{mkEps}(X+Y)
  \xrightarrow{\mathsf{E}_{+}^{L}} \mathit{Left}\ \mathit{mkEps}(X).
\end{equation}

%

\paragraph{Backward pass.}
Injection reverses both derivatives. Starting from
$\mathit{mkEps}(r_2)$, undoing $\mathtt{b}$ applies
$\mathsf{I}_{\mathrm{seq}}^{L}$, $\mathsf{I}_{+}^{R}$, and
$\mathsf{I}_{\mathrm{seq}}^{R}$; undoing $\mathtt{a}$ then applies
$\mathsf{I}_{\mathrm{seq}}$ twice:
\begin{equation}\label{eq:dp-backward}
\begin{aligned}
v_2 &= \mathit{mkEps}(r_2)
     = \mathit{Left}(\mathit{Right}\,\mathit{Right}\,(),\mathit{Right}\,()) \\
v_1 &= \mathit{inj}_{r_1\backslash b}(v_2)
     = (\mathit{Right}((),b),\mathit{Right}\,()) \\
v_0 &= \mathit{inj}_{r_0\backslash a}(v_1)
     = (\mathit{Right}(a,b),\mathit{Right}\,()).
\end{aligned}
\end{equation}

\section{The Bit-Coded Approach}
\label{sec:deriv-bitcoded-overview}

The direct construction cannot reconstruct the parse tree until the input
has been exhausted, because $\mathit{inj}$ requires each preceding
expression $r_{i-1}$. Sulzmann and Lu's bit-coded construction
\citep{sulzmannlu2014} removes this dependency by recording the information
needed for reconstruction during the forward pass. Figure~\ref{fig:single-pass}
shows this on pattern $a^{*}$ and input \texttt{"aaa"}. Unlike
Figure~\ref{fig:two-pass}, the derivation remains a single forward sequence,
while a growing bit-prefix records the choices needed to reconstruct the
parse tree.

  lbl/.style={font=\scriptsize, inner sep=1.5pt},

\paragraph{The bit-coded pipeline.}
Figure~\ref{fig:single-pass} shows the four main operations of the bit-coded
method. $\mathit{internalize}$ converts the input pattern $r$
into an annotated expression, tagging each alternation branch with an initial
bit. $\mathit{fuse}$ prepends the bit-lists to the annotations of
existing nodes, to allow this information to be carried between subexpressions.
At each character, the annotated expression is derived using a bit-threaded
derivative operation, then simplified by $\mathit{simp}$.

Unlike the direct construction, which forbids simplification to preserve
nodes that backward reconstruction requires, the bit-coded method allows it
because the bits carry the information a backward pass would need. It is
applied after each derivative step to control expression growth.

Once the input is consumed, $\mathit{mkEpsBC}$ extracts the accumulated bits
from the final expression, using the same left-preference rule at alternations
as $\mathit{mkEps}$ does in the direct construction. The function
$\mathit{decode}_r$ then interprets these bits using the original pattern $r$
to reconstruct the parse tree, reading off which branch was taken at each
choice point.

\section{The Bit-Coded Derivative-Based Parser}
\label{sec:bitcoded-construction-formal}

Building the parse tree information during the forward pass extends the
derivative computation with annotations that carry bit-lists through each
derivation step. The bit-threaded derivative
$\mathit{ri}\backslash_b l$ propagates these annotations, while
$\mathit{mkEpsBC}$ and $\mathit{decode}_r$ use the final bit-list to
reconstruct the \texttt{ParseTree}.

%

\subsection{Annotated Expressions}
\label{sec:annotated-expressions}

An annotated expression $\mathit{ri}$ extends $r$ by associating a bit-list
$bs$ with every node except $\emptyset$. The bit-list records the
reconstruction choices made during the forward pass, such as which branch
of an alternation or which iteration of a star is selected.

\[
\mathit{ri} ::= \emptyset \mid (bs@\varepsilon) \mid (bs@x) \mid
(bs@\mathit{ri}_1 \oplus \mathit{ri}_2) \mid
(bs@\mathit{ri}_1\,\mathit{ri}_2) \mid
(bs@\mathit{ri}^{*}).
\]

%

\subsection{Annotated Derivatives}
\label{sec:deriv-bc-theory}

$\mathit{ri}\backslash_b l$ has the same case structure of
~\eqref{eq:derivative}, with bits threaded through instead of
discarded:
\begin{equation}\label{eq:bderiv}
\begin{aligned}
(bs@\mathit{ri}_1 \oplus \mathit{ri}_2) \backslash_b l &=
  (bs@(\mathit{ri}_1 \backslash_b l) \oplus (\mathit{ri}_2 \backslash_b l))
  &&(\mathsf{B}_{+}) \\
(bs@\mathit{ri}_1\,\mathit{ri}_2) \backslash_b l &=
  (bs@(\mathit{ri}_1 \backslash_b l)\,\mathit{ri}_2)
  &&(\mathsf{B}_{\mathrm{seq}}),\ \varepsilon \notin L(\mathit{ri}_1) \\
(bs@\mathit{ri}_1\,\mathit{ri}_2) \backslash_b l &=
  (bs@(\mathit{ri}_1 \backslash_b l)\,\mathit{ri}_2)
  \oplus
  \mathit{fuse}(\mathit{mkEpsBC}_{\mathit{ri}_1},
                 \mathit{ri}_2 \backslash_b l)
  &&(\mathsf{B}_{\mathrm{seq}}^{\,n}),\ \varepsilon \in L(\mathit{ri}_1) \\
(bs@\mathit{ri}^{*}) \backslash_b l &=
  (bs@\mathit{fuse}([0],\mathit{ri} \backslash_b l)\,
  ([\,]@\mathit{ri}^{*}))
  &&(\mathsf{B}_{*}).
\end{aligned}
\end{equation}

The $\mathsf{B}_{\mathrm{seq}}^{\,n}$ branch proceeds directly into
$\mathit{ri}_2$, so the bits produced by the empty match of
$\mathit{ri}_1$ are fused into the derivative of $\mathit{ri}_2$. This
performs during the forward pass the reconstruction step that
$\mathsf{I}_{\mathrm{seq}}^{R}$ would otherwise perform during
$\mathit{inj}$.

%

\paragraph{In Rust.}
\label{sec:deriv-bc-impl}

Figure~\ref{fig:derivbc-rust} implements the rules in
~\eqref{eq:bderiv}. The base cases follow the ordinary derivative,
while the nullable \texttt{Seq} and \texttt{Star} cases additionally use
\texttt{mk\_eps\_bc} and \texttt{fuse} to preserve reconstruction
information:

\begin{figure}[H]
\small
\begin{verbatim}
pub fn deriv_bc(ri: ARegex, l: char) -> ARegex {
    match ri {
        ARegex::Phi => ARegex::Phi,
        ARegex::Eps(_) => ARegex::Phi,
        ARegex::Lit(bs, c) => {
            if c == l {
                ARegex::Eps(bs)
            } else {
                ARegex::Phi
            }
        }
        ARegex::Alt(bs, r1, r2) => {
            let d1 = deriv_bc(*r1, l);
            let d2 = deriv_bc(*r2, l);
            ARegex::Alt(bs, Box::new(d1), Box::new(d2))
        }
        ARegex::Seq(bs, r1, r2) => {
            if nullable_bc(&r1) {
                let eps_bits = mk_eps_bc(&r1);
                let d1 = deriv_bc(*r1, l);
                let d2 = deriv_bc(*r2.clone(), l);
                let left_branch = ARegex::Seq(vec![], Box::new(d1), r2);
                let right_branch = fuse(&eps_bits, d2);
                ARegex::Alt(bs, Box::new(left_branch), Box::new(right_branch))
            } else {
                let d1 = deriv_bc(*r1, l);
                ARegex::Seq(bs, Box::new(d1), r2)
            }
        }
        ARegex::Star(bs, r) => {
            let d = deriv_bc(*r.clone(), l);
            let fused = fuse(&[false], d);
            let new_star = ARegex::Star(vec![], r);
            ARegex::Seq(bs, Box::new(fused), Box::new(new_star))
        }
    }
}
\end{verbatim}
\caption{\texttt{deriv\_bc}: annotated derivative.}
\label{fig:derivbc-rust}
\end{figure}

Each arm follows the same case structure as the plain \texttt{deriv}
(Figure~\ref{fig:deriv-rust}), with annotations threaded through the
constructors and modified only where required by ~\eqref{eq:bderiv}.

The \texttt{Phi}, \texttt{Eps}, and \texttt{Lit} arms retain the behaviour
of plain \texttt{deriv}. \texttt{Phi} and \texttt{Eps} derive to
\texttt{Phi}, while \texttt{Lit} compares its character with
\texttt{l}. On a match, its \texttt{bs} is transferred to the resulting
\texttt{Eps} and on a mismatch, the annotation is discarded with the
non-contributing branch. The \texttt{Alt} arm derives both operands and
preserves the outer \texttt{bs}, since deriving does not change the
choice already recorded for that alternation.

The \texttt{Seq} arm reflects $\mathsf{B}_{\mathrm{seq}}$ and
$\mathsf{B}_{\mathrm{seq}}^{\,n}$. In the non-nullable case, \texttt{r2}
is moved directly into the rebuilt sequence. In the nullable case,
\texttt{r2} is needed both unchanged in \texttt{left\_branch} and for its
derivative, so \texttt{r2.clone()} provides the second copy. Similarly,
\texttt{r1} is borrowed by \texttt{nullable\_bc} before being consumed.

The \texttt{Star} arm follows the same pattern. Its body is needed both for
the derivative and the reconstructed star, so \texttt{r.clone()} provides
the second copy. So both clones correspond to duplicated subexpressions
in the corresponding derivative rules.

\subsection{Internalizing Expressions}
\label{sec:internalize}

$\mathit{internalize}$ recursively converts a plain expression $r$ into an
annotated expression $\mathit{ri}$. All nodes receive an empty bit-list
except the two branches of an alternation, which are tagged with
$0{=}\mathit{Left}$ and $1{=}\mathit{Right}$:
\begin{equation}\label{eq:internalize}
\begin{aligned}
\mathit{internalize}(\emptyset) &= \emptyset \\
\mathit{internalize}(\varepsilon) &= [\,]@\varepsilon \\
\mathit{internalize}(x) &= [\,]@x \\
\mathit{internalize}(r_1+r_2) &=
  [\,]@\big(\mathit{fuse}([0],\mathit{internalize}(r_1))
  \oplus \mathit{fuse}([1],\mathit{internalize}(r_2))\big) \\
\mathit{internalize}(r_1\,r_2) &=
  [\,]@\big(\mathit{internalize}(r_1)\,\mathit{internalize}(r_2)\big) \\
\mathit{internalize}(r^{*}) &= [\,]@\mathit{internalize}(r)^{*}.
\end{aligned}
\end{equation}

The $[0]$/$[1]$ tags on the two sides of $r_1+r_2$ follow the
$0{=}\mathit{Left}/1{=}\mathit{Right}$ convention. Every other case
introduces no new bit and uses only the empty list $[\,]$. The two
calls to $\mathit{fuse}$ in ~\eqref{eq:internalize} are the only
points in the construction where new bits are introduced.

%

\paragraph{In Rust.}
\label{sec:internalize-impl}

Figure~\ref{fig:internalize-rust} directly maps the constructors of
\texttt{Regex} to their annotated counterparts, showing only the \texttt{Alt} case
introduces non-empty annotations.

\begin{figure}[H]
\small

        Regex::Eps => ARegex::Eps(vec![]),
        Regex::Lit(c) => ARegex::Lit(vec![], *c),
        Regex::Alt(r1, r2) => {
            let ri1 = fuse(&[false], internalize(r1));
            let ri2 = fuse(&[true], internalize(r2));
            ARegex::Alt(vec![], Box::new(ri1), Box::new(ri2))
        }
        Regex::Seq(r1, r2) => ARegex::Seq(vec![],
            Box::new(internalize(r1)), Box::new(internalize(r2))),
        Regex::Star(r1) => ARegex::Star(vec![], Box::new(internalize(r1))),
    }

\label{fig:internalize-rust}

The structure directly mirrors the six constructors of \texttt{Regex}, with
one match arm for each constructor and each recursive call wrapped in the
corresponding \texttt{ARegex} constructor.

The \texttt{Phi}, \texttt{Eps}, \texttt{Lit}, \texttt{Seq}, and
\texttt{Star} cases use an empty bit-list, since they introduce no
disambiguation choice at this stage. Star iteration choices are instead
determined during derivative computation by $\mathsf{B}_{*}$.

Only the \texttt{Alt} case calls \texttt{fuse} with a non-empty bit-list,
tagging the left operand with \texttt{[false]} and the right with
\texttt{[true]} before wrapping them in a fresh \texttt{Alt} with an empty
outer bit-list. These are the only points where new bits are introduced;
all later bits originate from these two tags and are propagated during
derivation.

\subsection{Fusing Bit-Lists}
\label{sec:fuse}

$\mathit{fuse}$ modifies only the top node's bit-list and prepends $bs$ to
its existing list $bs'$. It does not descend into the children, leaving the
recursively constructed subexpressions unchanged.

\begin{equation}\label{eq:fuse}
\begin{aligned}
\mathit{fuse}(bs, \emptyset) &= \emptyset \\
\mathit{fuse}(bs, (bs'@\varepsilon)) &= (bs \mathbin{+\!\!+} bs')@\varepsilon \\
\mathit{fuse}(bs, (bs'@x)) &= (bs \mathbin{+\!\!+} bs')@x \\
\mathit{fuse}(bs, (bs'@\mathit{ri}_1 \oplus \mathit{ri}_2))
  &= (bs \mathbin{+\!\!+} bs')@(\mathit{ri}_1 \oplus \mathit{ri}_2) \\
\mathit{fuse}(bs, (bs'@\mathit{ri}_1\,\mathit{ri}_2))
  &= (bs \mathbin{+\!\!+} bs')@(\mathit{ri}_1\,\mathit{ri}_2) \\
\mathit{fuse}(bs, (bs'@\mathit{ri}^{*}))
  &= (bs \mathbin{+\!\!+} bs')@\mathit{ri}^{*}.
\end{aligned}
\end{equation}

The $\emptyset$ case is unchanged, while all other cases prepend $bs$,
which allows $\mathit{fuse}$ to add branch information without inspecting the
subexpression below the annotated node.

%

\paragraph{In Rust.}
\label{sec:fuse-impl}

Figure~\ref{fig:fuse-rust} implements this operation. The helper
\texttt{combine} concatenates the bit-lists, while \texttt{fuse} preserves
the structure below the top node. An empty \texttt{bs} returns the node
unchanged, avoiding unnecessary rebuilding; otherwise only the top node is
rebuilt. The \texttt{Phi} case is unchanged because it carries no annotation.
The same operation later propagates bits from sub-derivations in
$\mathsf{B}_{\mathrm{seq}}^{\,n}$ and $\mathsf{B}_{*}$.
\begin{figure}[H]
\small
\begin{verbatim}
pub fn fuse(bs: &[bool], ri: ARegex) -> ARegex {
    if bs.is_empty() { return ri; }
    match ri {
        ARegex::Phi => ARegex::Phi,
        ARegex::Eps(p) => ARegex::Eps(combine(bs, p)),
        ARegex::Lit(p, c) => ARegex::Lit(combine(bs, p), c),
        ARegex::Alt(p, r1, r2) => ARegex::Alt(combine(bs, p), r1, r2),
        ARegex::Seq(p, r1, r2) => ARegex::Seq(combine(bs, p), r1, r2),
        ARegex::Star(p, r) => ARegex::Star(combine(bs, p), r),
    }
}

fn combine(bs: &[bool], p: Vec<bool>) -> Vec<bool> {
    let mut new = bs.to_vec();
    new.extend(p);
    new
}
\end{verbatim}

top node.}

\subsection{Extracting Bits}
\label{sec:mkepsbc-theory}

$\mathit{mkEpsBC}$ mirrors $\mathit{mkEps}$ but returns bits, with the
same left-preference guard at an alternation and a closing $1$ at a
star:

\begin{equation}\label{eq:mkepsbc}
\begin{aligned}
\mathit{mkEpsBC}_{(bs@\varepsilon)} &= bs,
\qquad
\mathit{mkEpsBC}_{(bs@\mathit{ri}^{*})} = bs \mathbin{+\!\!+} [1], \\
\mathit{mkEpsBC}_{(bs@\mathit{ri}_1\, \mathit{ri}_2)} &=
  bs \mathbin{+\!\!+} \mathit{mkEpsBC}_{\mathit{ri}_1} \mathbin{+\!\!+} \mathit{mkEpsBC}_{\mathit{ri}_2}, \\
\mathit{mkEpsBC}_{(bs@\mathit{ri}_1\oplus\mathit{ri}_2)} &=
  bs \mathbin{+\!\!+}
  \begin{cases}
    \mathit{mkEpsBC}_{\mathit{ri}_1} & \varepsilon \in L(\mathit{ri}_1) \\
    \mathit{mkEpsBC}_{\mathit{ri}_2} & \text{otherwise.}
  \end{cases}
\end{aligned}
\end{equation}

Where $\mathit{mkEps}$ builds a \texttt{ParseTree} node by node,
$\mathit{mkEpsBC}$ only concatenates bit-lists. Each rule prepends the
bits already present to those produced by the corresponding recursive call,
without constructing a parse-tree node of its own.

%

\paragraph{In Rust.}
Compared with \texttt{mk\_eps} (Figure~\ref{fig:mkeps-rust}), the case
structure is unchanged; only the result differs, with \texttt{ParseTree}
construction replaced by bit-list concatenation. The \texttt{Star} case
does not recurse because a star is always nullable, so only the closing
\texttt{true} is appended. The \texttt{Phi} and \texttt{Lit} cases panic
because neither is nullable; \texttt{mk\_eps\_bc} is called only after
\texttt{nullable\_bc(\&ri)} establishes this precondition.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn mk_eps_bc(ri: &ARegex) -> Vec<bool> {
    match ri {
        ARegex::Phi => panic!("mk_eps_bc called on Phi"),
        ARegex::Lit(_, c) => panic!("mk_eps_bc called on Lit('{}')", c),
        ARegex::Eps(bs) => bs.clone(),
        ARegex::Alt(bs, r1, r2) => {
            let mut result = bs.clone();
            if nullable_bc(r1) {
                result.extend(mk_eps_bc(r1));
            } else {
                result.extend(mk_eps_bc(r2));
            }
            result
        }
        ARegex::Seq(bs, r1, r2) => {
            let mut result = bs.clone();
            result.extend(mk_eps_bc(r1));
            result.extend(mk_eps_bc(r2));
            result
        }
        ARegex::Star(bs, _) => {
            let mut result = bs.clone();
            result.push(true);
            result
        }
    }
}
\end{verbatim}

\texttt{ARegex} has already committed to.}
\label{fig:mkepsbc-rust}
\end{figure}

\subsection{Decoding Bits}
\label{sec:decode}

$\mathit{decode}_r$ reconstructs a \texttt{ParseTree} from the bit-string
produced by $\mathit{mkEpsBC}$. It traverses the original, unannotated $r$,
since the annotated expression has been now reduced to bits.
The recursive worker threads the remaining bit-list through the structure
of $r$:
\begin{equation}\label{eq:decode}
\begin{aligned}
\mathit{decodeInner}_{\varepsilon}(bs)
  &= (\mathit{Empty}, bs) \\
\mathit{decodeInner}_{x}(bs)
  &= (\mathit{Char}(x), bs) \\
\mathit{decodeInner}_{r_1+r_2}(0{:}bs)
  &= (\mathit{Left}(v), bs_1),
  & (v,bs_1) &= \mathit{decodeInner}_{r_1}(bs) \\
\mathit{decodeInner}_{r_1+r_2}(1{:}bs)
  &= (\mathit{Right}(v), bs_1),
  & (v,bs_1) &= \mathit{decodeInner}_{r_2}(bs) \\
\mathit{decodeInner}_{r_1r_2}(bs)
  &= (\mathit{Pair}(v_1,v_2), bs_2), \\
  && (v_1,bs_1) &= \mathit{decodeInner}_{r_1}(bs), \\
  && (v_2,bs_2) &= \mathit{decodeInner}_{r_2}(bs_1) \\
\mathit{decodeInner}_{r^{*}}(1{:}bs)
  &= (\mathit{Star}([\,]), bs) \\
\mathit{decodeInner}_{r^{*}}(0{:}bs)
  &= (\mathit{Star}(v{:}vs), bs_2), \\
  && (v,bs_1) &= \mathit{decodeInner}_{r}(bs), \\
  && (\mathit{Star}(vs),bs_2)
     &= \mathit{decodeInner}_{r^{*}}(bs_1).
\end{aligned}
\end{equation}

The outer function is
$\mathit{decode}_r(bs)=v$ where
$(v,[\,])=\mathit{decodeInner}_r(bs)$, and is undefined if bits remain.
The $\mathit{Alt}$ case reads the $0{=}\mathit{Left}/1{=}\mathit{Right}$
tags introduced by $\mathit{internalize}$. The $\mathit{Star}$ case consumes
one $0$ per iteration until the trailing $1$ inserted by
$\mathit{mkEpsBC}$ terminates the sequence.

%

\paragraph{In Rust.}

Figure~\ref{fig:decode-rust} implements ~\eqref{eq:decode}
directly, with \texttt{decode\_inner} matching its rules and
\texttt{decode} providing the top-level wrapper.

Where \texttt{mk\_eps\_bc} creates bits by concatenation, \texttt{decode}
consumes the flat bit-string from left to right while recursively
traversing the tree-shaped $r$. The function \texttt{decode\_inner} returns
\texttt{(ParseTree, \&[bool])}, producing the tree for the current
subexpression together with the remaining bits. Rust's slice patterns make
the leading-bit cases direct, with \texttt{[false, rest @ ..]} and
\texttt{[true, rest @ ..]} selecting an \texttt{Alt} branch or terminating
a \texttt{Star}. \texttt{Seq} recurses once per factor, while \texttt{Star}
uses a loop because its number of iterations is determined by the bits.

The outer \texttt{decode} asserts that no bits remain after decoding,
enforcing the side condition in ~\eqref{eq:decode} and preventing
leftover bits from being silently discarded.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn decode(r: &Regex, bs: &[bool]) -> ParseTree {
    let (v, rest) = decode_inner(r, bs);
    assert!(rest.is_empty(),
        "decode: {} leftover bit(s) after decoding {:?}", rest.len(), r);
    v
}

fn decode_inner<'a>(r: &Regex, bs: &'a [bool]) -> (ParseTree, &'a [bool]) {
    match r {
        Regex::Eps => (ParseTree::Empty, bs),
        Regex::Lit(c) => (ParseTree::Char(*c), bs),
        Regex::Alt(r1, r2) => match bs {
            [false, rest @ ..] => {
                let (v, remaining) = decode_inner(r1, rest);
                (ParseTree::Left(Box::new(v)), remaining)
            }
            [true, rest @ ..] => {
                let (v, remaining) = decode_inner(r2, rest);
                (ParseTree::Right(Box::new(v)), remaining)
            }
            [] => panic!("decode: unexpected end of bits at Alt"),
        },
        Regex::Seq(r1, r2) => {
            let (v1, after_r1) = decode_inner(r1, bs);
            let (v2, after_r2) = decode_inner(r2, after_r1);
            (ParseTree::Pair(Box::new(v1), Box::new(v2)), after_r2)
        }
        Regex::Star(r1) => {
            let mut iterations = Vec::new();
            let mut remaining = bs;
            loop {
                match remaining {
                    [true, rest @ ..] => { remaining = rest; break; }
                    [false, rest @ ..] => {
                        let (v, after) = decode_inner(r1, rest);
                        iterations.push(v);
                        remaining = after;
                    }
                    [] => panic!("decode: unexpected end of bits inside Star"),
                }
            }
            (ParseTree::Star(iterations), remaining)
        }
        Regex::Phi => panic!("decode: called on Phi"),
    }
}
\end{verbatim}

\texttt{decode\_inner}.}
\label{fig:decode-rust}
\end{figure}

\subsection{Simplification}
\label{sec:simplification-rules-theory}

Unlike the direct construction the
bit-coded method must simplify: Sulzmann and Lu show that $a^{*}$ doubles
in size at every derivative step without simplification. Simplification is
safe here because the information required for reconstruction is encoded in
the bits rather than in the unsimplified expression. The function
$\mathit{simp}$ is applied after every derivative step.

\paragraph{Sequence and star.}
The local simplification rules handle sequences and stars. A sequence
propagates $\emptyset$, eliminates a leading $\varepsilon$ while preserving
its bits with $\mathit{fuse}$, and otherwise retains its structure. A star
simplifies only its body:


{\small
\begin{equation}\label{eq:simp}
\begin{aligned}
\mathit{simp}(\emptyset) &= \emptyset \\
\mathit{simp}((bs@\varepsilon)) &= (bs@\varepsilon) \\
\mathit{simp}((bs@x)) &= (bs@x) \\[2pt]
\mathit{simp}((bs@\mathit{ri}_1\,\mathit{ri}_2)) &=
  \begin{cases}
    \emptyset
      & \mathit{isPhi}(\mathit{simp}(\mathit{ri}_1)) \lor \mathit{isPhi}(\mathit{simp}(\mathit{ri}_2)) \\
    \mathit{fuse}(bs\mathbin{+\!\!+} bs_1,\mathit{simp}(\mathit{ri}_2))
      & \mathit{simp}(\mathit{ri}_1) = (bs_1@\varepsilon) \\
    (bs@\mathit{simp}(\mathit{ri}_1)\,\mathit{simp}(\mathit{ri}_2)) & \text{otherwise}
  \end{cases}\\[4pt]
\mathit{simp}((bs@\mathit{ri}_1\oplus\mathit{ri}_2)) &=
  \mathit{fuse}(bs,\ \mathit{prune}(\mathit{flatten}(\mathit{ri}_1,\mathit{ri}_2)))\\[2pt]
\mathit{simp}((bs@\mathit{ri}^{*})) &= (bs@\mathit{simp}(\mathit{ri})^{*})
\end{aligned}
\end{equation}
}

The first case propagates the empty language through a sequence, while the
second removes a leading $\varepsilon$ and transfers its bits to the
remaining expression. The $\mathit{isPhi}$ test also recognizes expressions
equivalent to $\emptyset$ beyond the literal $\emptyset$.

\paragraph{Alternation.}
Alternation requires additional restructuring. $\mathit{flatten}$ collects
nested alternatives that carry no bit-tag of their own into a single branch
list. When descending through a tagged alternative, it first fuses its bits
into both branches so that no recorded choice is lost. $\mathit{prune}$
then simplifies each branch, removes branches equivalent to $\emptyset$,
and removes duplicate annotated expressions while retaining the first
occurrence. Finally, $\mathit{collapse}$ rebuilds the remaining branches
and applies the outer $bs$ once:

\begin{equation}\label{eq:simp-alt}
\mathit{simp}(bs@(r_1\oplus r_2))
  =
  \mathit{fuse}\bigl(bs,\,
    \mathit{prune}(\mathit{flatten}(r_1,r_2))\bigr).
\end{equation}

The pruning step compares complete annotated expressions, including their
bit-lists. Thus, branches with identical underlying expressions but
different annotations remain distinct because they represent different
reconstruction choices. If no branch survives, $\mathit{collapse}$ produces
$\emptyset$; with one survivor it returns that expression, and otherwise it
rebuilds an alternation.

%

\paragraph{In Rust.}
Figure~\ref{fig:simp-rust} implements $\mathit{simp}$ together with the
helpers for flattening and rebuilding alternatives. The \texttt{Seq} and
\texttt{Star} arms implement the local rules, while the \texttt{Alt} arm
collects nested branches, simplifies them, removes $\texttt{Phi}$ branches
and duplicates, and rebuilds the result according to the number of
surviving branches.


\begin{figure}[H]
\scriptsize
\begin{verbatim}
fn simp_once(ri: ARegex) -> ARegex {
    match ri {
        ARegex::Phi => ARegex::Phi,
        ARegex::Eps(_) => ri,
        ARegex::Lit(_, _) => ri,

        ARegex::Seq(bs, r1, r2) => {
            let r1s = simp_once(*r1);
            let r2s = simp_once(*r2);

            if is_phi(&r1s) || is_phi(&r2s) {
                return ARegex::Phi;
            }

            if let ARegex::Eps(bs2) = r1s {
                let mut combined = bs;
                combined.extend(bs2);
                return fuse(&combined, r2s);
            }

            ARegex::Seq(bs, Box::new(r1s), Box::new(r2s))
        }

        ARegex::Alt(bs, r1, r2) => {
            let branches_raw = collect_alt_branches(*r1, *r2);
            let branches_simped: Vec<ARegex> = branches_raw
                .into_iter()
                .map(simp_once)
                .collect();

            let mut branches: Vec<ARegex> = branches_simped
                .into_iter()
                .filter(|b| !is_phi(b))
                .collect();

            dedup_first(&mut branches);

            match branches.len() {
                0 => ARegex::Phi,
                1 => fuse(&bs, branches.remove(0)),
                _ => {
                    let folded = fold_alt(branches);
                    fuse(&bs, folded)
                }
            }
        }

        ARegex::Star(bs, r) => {
            ARegex::Star(bs, Box::new(simp_once(*r)))
        }
    }
}

fn push_branches(ri: ARegex, out: &mut Vec<ARegex>) {
    match ri {
        ARegex::Alt(bs, r1, r2) => {
            if bs.is_empty() {
                push_branches(*r1, out);
                push_branches(*r2, out);
            } else {
                let r1f = fuse(&bs, *r1);
                let r2f = fuse(&bs, *r2);
                push_branches(r1f, out);
                push_branches(r2f, out);
            }
        }
        other => out.push(other),
    }
}
\end{verbatim}
\caption{\texttt{simp\_once} and \texttt{push\_branches}, the helper
doing $\mathit{flatten}$'s bit-fusing work.}
\label{fig:simp-rust}
\end{figure}

The \texttt{Seq} arm checks the $\mathsf{S}_1$ condition before
$\mathsf{S}_2$, matching the rule order. The \texttt{Alt} arm first
collects and simplifies the branches, then filters $\texttt{Phi}$,
deduplicates complete annotated expressions, and uses the number of
survivors to implement $\mathit{collapse}$. The outer annotation is fused
only after rebuilding the result.

Because annotations are part of the expression, simplification does not
merge branches solely on their underlying regex structure. Distinct bits
can therefore keep branches separate even when their shapes coincide.
This preserves the parse-tree choices encoded by the derivative, but also
means that simplification does not guarantee bounded expression growth in
every case.

\subsection{Parser}
\label{sec:deriv-bc-driver}

Figure~\ref{fig:deriv-bc-loop-rust} implements the bit-coded driver.
It internalizes $r$, applies \texttt{deriv\_bc} and \texttt{simp} to each
input character, checks nullability and, if successful, calls
\texttt{mk\_eps\_bc} and \texttt{decode}.

\begin{figure}[H]
\small
\begin{verbatim}
pub fn parse_bitcoded_loop(input: &str, r: &Regex) -> Option<ParseTree> {
    let mut ri = internalize(r);
    for l in input.chars() { ri = simp(deriv_bc(ri, l)); }
    if !nullable_bc(&ri) { return None; }
    Some(decode(r, &mk_eps_bc(&ri)))
}
\end{verbatim}
\caption{\texttt{parse\_bitcoded\_loop}: the bit-coded parser implementation.}
\label{fig:deriv-bc-loop-rust}
\end{figure}

Unlike the direct implementation, which has a growing
\texttt{Vec<Regex>} for backward reconstruction, the bit-coded implementation
needs only the current \texttt{ri}. The recursive entry point has the same
three-step computation but differs only in how intermediate expressions
are stored.

\subsection{Worked Example}
\label{sec:deriv-bc-worked}
\label{sec:deriv-worked-example}

Consider the same input $\texttt{ab}$ and regular expression
$r_0=(a\mid ab)(b\mid\varepsilon)$.

%

\paragraph{Internalize.}
Before consuming any input, \texttt{internalize} tags each alternative with
$[0]$ for the left branch and $[1]$ for the right branch. These initial tags
record the disambiguation choices that can later be propagated by
$\mathit{fuse}$:

\begin{equation}\label{eq:dpbc-internalize}
\mathit{internalize}(r_0) = \mathit{ri}_0 =
[\,]@\big(
  [\,]@([0]@a \oplus [1]@(a\,b))
  \cdot
  [\,]@([0]@b \oplus [1]@\varepsilon)
\big).
\end{equation}

%

\paragraph{Forward pass.}
The two input symbols are consumed by successive bit-threaded derivatives,
with $\mathit{simp}$ applied after each step. The first derivative uses
$\mathsf{B}_{\mathrm{seq}}$. After consuming $\mathtt{a}$, the first factor
becomes nullable. The second derivative therefore uses
$\mathsf{B}_{\mathrm{seq}}^{\,n}$, which propagates the bits of the empty
match of the first factor into the derivative of the second factor:

\begin{equation}\label{eq:dpbc-forward}
\begin{aligned}
\mathit{ri}_0
  &\xrightarrow[\mathsf{B}_{\mathrm{seq}}]{\ a\ }
  \mathit{ri}_1 =
  [\,]@\big(
    [\,]@([0]@\varepsilon \oplus [1]@b)
    \cdot
    [\,]@([0]@b \oplus [1]@\varepsilon)
  \big) \\
\mathit{ri}_1
  &\xrightarrow[\mathsf{B}_{\mathrm{seq}}^{\,n}]{\ b\ }
  \mathit{ri}_2 =
  [\,]@\big(
    [1]@([0]@b \oplus [1]@\varepsilon)
    \oplus
    [0,0]@\varepsilon
  \big).
\end{aligned}
\end{equation}

The $[1]$ on the first surviving branch records the right alternative
$ab$ of the first factor. The $[0,0]$ on the second branch results from
fusing the bits of the empty match of the first factor into the derivative
of $b+\varepsilon$. Thus, the information that would be recovered later by
$\mathit{inj}$ in the direct construction has already been propagated
during the forward pass.

\paragraph{Extracting the bits.}
Both disjuncts of $\mathit{ri}_2$ are nullable, so
$\mathit{mkEpsBC}$ applies $\mathsf{EB}_{+}^{L}$ and selects the left
disjunct. Its outer annotation is empty, so no bit is emitted at that
level. Inside the surviving alternative, $b$ is not nullable while
$\varepsilon$ is, so $\mathsf{EB}_{+}^{R}$ selects the right branch and
contributes its $[1]$ tag:

\begin{equation}\label{eq:dpbc-mkepsbc}
\mathit{mkEpsBC}(\mathit{ri}_2)
  \xrightarrow{\mathsf{EB}_{+}^{L}}
  \mathit{mkEpsBC}\big(
    [1]@([0]@b \oplus [1]@\varepsilon)
  \big)
  \xrightarrow{\mathsf{EB}_{+}^{R}}
  [1]\mathbin{+\!\!+}[1]
  = [1,1].
\end{equation}

Unlike $\mathit{mkEps}$, which constructs a partial parse tree,
$\mathit{mkEpsBC}$ only extracts the committed choices as a flat
bit-string. The tree structure is reconstructed by $\mathit{decode}$.

\paragraph{Result.}
The decoder reads $[1,1]$ against the original, unannotated $r_0$. The
first bit selects the right branch of $a+ab$, producing the $ab$ factor,
while the second selects the right branch of $b+\varepsilon$:

\begin{equation}\label{eq:dpbc-decode}
\mathit{decode}_{r_0}([1,1])
  = \big(
      \mathit{Right}(a,b),
      \mathit{Right}(\,)
    \big)
  = v_0.
\end{equation}

Thus, the bit-coded construction produces the same POSIX parse tree as the
direct construction, but without retaining the intermediate expressions
$r_0$, $r_1$, and $r_2$:

  = \mathtt{ab}.
