\chapter{Derivative-Based Parser}
\label{sec:derivative-parser}

Chapter~\ref{sec:matching-vs-parsing} fixed what is being computed, the
$\geq_r$-maximal parse tree of Section~\ref{sec:posix-longest-leftmost},
without saying how. This chapter presents Sulzmann and Lu's answer
\citep{sulzmannlu2014}: a parser built directly on the Brzozowski
derivative of Section~\ref{sec:brzozowski-derivatives}, in two forms.
The first, direct construction computes a derivative sequence and then
explicitly rebuilds a parse tree from it in a second, backward pass. The
second, bit-coded construction fuses parse-tree bookkeeping into the
derivative step itself, needing only one forward pass. Both are POSIX,
computing the identical $\geq_r$-maximal tree, and differ only in how
that tree is produced.

Both are developed here as theory first
(Sections~\ref{sec:core-algorithm} to
\ref{sec:simplification-rules-theory}), then as the two Rust
implementations that realize them, \texttt{deriv\_std}
(Section~\ref{sec:derivative-parser-inj-rust}) and \texttt{deriv\_bc}
(Section~\ref{sec:derivative-parser-bitcoded-rust}), and are finally
set against each other in Section~\ref{sec:deriv-worked-example}.
Throughout, the implementation's own execution traces are used as the
primary evidence for what each construction does, so
Section~\ref{sec:deriv-tracing} introduces the tracing facility first.
Chapter~\ref{sec:partial-derivative-parser} then repeats the exercise
once more, replacing the Brzozowski derivative throughout with
Antimirov's partial derivative from
Section~\ref{sec:antimirov-partial-derivatives}, and, as that chapter
shows, changing more than just which derivative operator is used.



\section{Reading the Implementation's Traces}
\label{sec:deriv-tracing}

Each of the four parsers in this thesis exists in two forms: a plain one
and a \emph{traced} one that records every step it takes. The traced
form is not a debugging afterthought bolted on afterwards. It computes
the same result by the same code path and additionally emits, at each
step, the rule it applied and the intermediate value it produced, which
makes it possible to check a construction against its defining equations
by running it rather than by reading it.

The facility is exposed through \texttt{--diag}, which selects one of
four verbosity levels:

\begin{center}
\begin{tabular}{lll}
\hline
Level & Adds & Destination \\
\hline
\texttt{--diag 0} & \texttt{true}/\texttt{false} only & stdout \\
\texttt{--diag 1} & regex, input, tree, error caret & stdout \\
\texttt{--diag 2} & timing, step count, construction steps & stdout \\
\texttt{--diag 3} & full derivation trace & \texttt{reports/report.txt} \\
\hline
\end{tabular}
\end{center}

Level 3 writes to a file rather than the terminal because its output
grows with both the input length and the size of the intermediate
expressions, and Section~\ref{sec:simplification-rules-theory} shows how
quickly the latter can grow. \texttt{--diag-report} overrides the
destination; the environment variables \texttt{REGEX\_DIAG} and
\texttt{REGEX\_DIAG\_REPORT} set the same two values for library use.

\paragraph{How traces are used in this chapter.} Rather than reproducing
whole reports, the sections that follow quote \emph{excerpts}, each
placed next to the construction step it illustrates. A level-3 report is
organized into labelled sections, and those sections map onto the
algorithm's own phases closely enough that individual fragments stand on
their own:

\begin{center}
\begin{tabular}{ll}
\hline
Report section & Construction phase \\
\hline
\texttt{FORWARD PASS} & the derivative sequence \\
\texttt{NULLABILITY CHECK} & the accept/reject decision \\
\texttt{BACKWARD PASS} & $\mathit{mkEps}$ and $\mathit{inj}$, direct construction \\
\texttt{INTERNALIZE}, \texttt{MKEEPSBC + DECODE} & the bit-coded construction's ends \\
\texttt{PARTIAL RECOVERY}, \texttt{ERROR SUMMARY} & failure diagnostics \\
\hline
\end{tabular}
\end{center}

All eight reports quoted from in this chapter and the next are
reproduced in full in Appendix~\ref{app:diagnostic-reports}, so that any
excerpt can be read back in its original context. They all use the same
running example, $r_1 = (a+ab)(b+\varepsilon)$ from
Section~\ref{sec:disambiguation-problem}, against the matching input
\texttt{"ab"} and the non-matching input \texttt{"b"}. In the frontend's
surface syntax (Section~\ref{sec:frontend-parsing}) that expression is
written \texttt{"(a|ab)(b|)"}, with $\varepsilon$ spelled as an empty
right alternative, so the command producing every trace in this chapter
is
\begin{verbatim}
cargo run -- parse "(a|ab)(b|)" "ab" --parser <PARSER> --diag 3
\end{verbatim}
Excerpts are shown exactly as the tool writes them, except that the
tool's Unicode operators are transliterated into ASCII ($\partial$ as
\texttt{d}, $\cdot$ as \texttt{.}, $\oplus$ as \texttt{(+)},
$\varepsilon$ as \texttt{epsilon}, $\phi$ as \texttt{phi}, and
$\checkmark$ as \texttt{[OK]}), and long lines are wrapped.



\section{Core Algorithm}
\label{sec:core-algorithm}

The direct construction follows the same two-phase shape informally
sketched for Brzozowski's derivative in
Section~\ref{sec:brzozowski-derivatives}: consume the input by taking
successive derivatives, then decide whether the result is nullable. What
is new here is what happens \emph{between} those two phases. Instead of
a single Boolean, a parse tree is built. The construction is best
understood in two halves, shown in Figure~\ref{fig:two-pass}: a forward
pass that is nothing more than the derivative sequence already
introduced, and a backward pass that walks that sequence in reverse to
assemble a tree one consumed character at a time.

\paragraph{Forward pass.} For input $x_1 x_2 \cdots x_n$, compute
$r_0 \xrightarrow{x_1} r_1 \xrightarrow{x_2} \cdots \xrightarrow{x_n} r_n$
exactly as before, where $r_0 = r$ and $r_{i} = r_{i-1} \backslash x_i$.
If $r_n$ is not nullable, no parse tree exists and parsing fails. This
half of the construction is identical to \texttt{match\_deriv}
(Section~\ref{sec:brzozowski-derivatives}) with one difference: no
simplification is applied between steps. \texttt{simplify} is safe for a
Boolean matcher, since it only ever normalizes $r_i$ to a
language-equivalent expression, but the backward pass below needs to
walk back through the \emph{exact} sequence of derivative
transformations that produced $r_n$ from $r_0$, and a simplified $r_i$
may no longer be the expression \texttt{inject} expects to see at that
step.

The trace makes both halves of that claim visible at once. Each forward
step names the derivative rule it applied and prints the resulting
expression in full:
\begin{verbatim}
Step 1: d(r0, 'a')
  rule: d(r1.r2, 'a')  [nullable(r1)=false]
       = d(r1, 'a').r2
r1 = Seq(Alt(Eps, Seq(Eps, Lit('b'))), Alt(Lit('b'), Eps))
  nullable(r1) = true  [OK] position 1 matched
\end{verbatim}
The rule line records which branch of the $(r_1 r_2) \backslash x$ case
split was taken and why, and \texttt{r1} is printed unsimplified: the
\texttt{Eps} inside \texttt{Seq(Eps, Lit('b'))} is exactly the kind of
node \texttt{simplify} would have removed, and it is retained because
\texttt{inject} will need it.

\paragraph{Backward pass.} Once $r_n$ is known to be nullable, the parse
tree $v_n$ for the empty remainder is built directly, by the function
$\mathit{mkEps}$ of Equation~\eqref{eq:mkeps}, defined by structural
recursion on a nullable expression:
\begin{equation}\label{eq:mkeps}
\begin{aligned}
\mathit{mkEps}_{\varepsilon} &= () &&(\mathsf{E}_{\varepsilon}) \\
\mathit{mkEps}_{r^{*}} &= [\,] &&(\mathsf{E}_{*}) \\
\mathit{mkEps}_{r_1 r_2} &= (\mathit{mkEps}_{r_1}, \mathit{mkEps}_{r_2})
  &&(\mathsf{E}_{\mathrm{seq}}) \\
\mathit{mkEps}_{r_1+r_2} &=
  \begin{cases}
    \mathit{Left}\ \mathit{mkEps}_{r_1} & \varepsilon \in L(r_1) \\
    \mathit{Right}\ \mathit{mkEps}_{r_2} & \text{otherwise}
  \end{cases}
  &&\begin{array}{l}(\mathsf{E}_{+}^{L}) \\ (\mathsf{E}_{+}^{R})\end{array}
\end{aligned}
\end{equation}

The rule names continue the scheme of
Section~\ref{sec:brzozowski-derivatives}, and derivations below cite
them with the binding of $r_1$ and $r_2$ stated, since which
subexpression each stands for is what decides the case taken.
$\mathit{mkEps}$ has no case for a literal $x$ or for $\emptyset$, since
neither is ever nullable. The function is only ever called on an
expression already known to satisfy $n(r)$. Its only interesting case is
alternation, and exactly one of rules (A1)/(A2) of
Section~\ref{sec:posix-longest-leftmost} is relevant there: both sides
of an empty match have length $0$, so (A2)'s tie-break, "prefer left
when lengths are equal", degenerates at the empty word to "prefer left
whenever left is even possible", which is exactly the
$\varepsilon \in L(r_1)$ guard above.

That guard is the single most consequential line in the whole backward
pass, and the trace prints it firing:
\begin{verbatim}
mkEps(r2):
  mkEps(r1 + r2): nullable(r1)=true -> Left(mkEps(r1))
v2 = Left (Right Right (), Right ())
\end{verbatim}
Matching \texttt{r2} against $\mathit{mkEps}_{r_1+r_2}$ binds $r_1$ to
its long \texttt{Seq(...)} disjunct and $r_2$ to
\texttt{Alt(Eps, Phi)}, and at this point \emph{both} are nullable. $\mathsf{E}_{+}^{L}$ and $\mathsf{E}_{+}^{R}$ are therefore
not both applicable: the case split tests only $\varepsilon \in L(r_1)$,
so $\mathsf{E}_{+}^{L}$ fires and $r_2$ is never examined.
$\mathit{mkEps}$ does not compare the two; it takes the left one because
it is nullable at all. Everything the backward pass produces downstream
follows from that choice, and Sulzmann and Lu prove that making it this
way is the POSIX-correct one \citep{sulzmannlu2014}.

With $v_n$ in hand, the remaining task is to turn it back into a parse
tree of the \emph{original} $r_0$, one derivative step in reverse at a
time. This is the job of $\mathit{inj}$, an injection function that
takes a parse tree of a derivative $r \backslash x$ and re-inserts the
consumed character $x$ to produce a parse tree of $r$ itself,
Equation~\eqref{eq:inj}:
\begin{equation}\label{eq:inj}
\begin{aligned}
\mathit{inj}_{r^{*} \backslash x}(v, vs) &= (\mathit{inj}_{r \backslash x}\ v) : vs
  &&(\mathsf{I}_{*}) \\
\mathit{inj}_{(r_1 r_2) \backslash x}(v) &=
  \begin{cases}
    (\mathit{inj}_{r_1 \backslash x}\ v_1,\ v_2) & v = (v_1, v_2),\ \text{not nullable}(r_1) \\
    (\mathit{inj}_{r_1 \backslash x}\ v_1,\ v_2) & v = \mathit{Left}(v_1, v_2),\ \text{nullable}(r_1) \\
    (\mathit{mkEps}_{r_1},\ \mathit{inj}_{r_2 \backslash x}\ v_2) & v = \mathit{Right}\ v_2,\ \text{nullable}(r_1)
  \end{cases}
  &&\begin{array}{l}(\mathsf{I}_{\mathrm{seq}}) \\ (\mathsf{I}_{\mathrm{seq}}^{L}) \\ (\mathsf{I}_{\mathrm{seq}}^{R})\end{array} \\
\mathit{inj}_{(r_1+r_2) \backslash x}(v) &=
  \begin{cases}
    \mathit{Left}\ (\mathit{inj}_{r_1 \backslash x}\ v_1) & v = \mathit{Left}\ v_1 \\
    \mathit{Right}\ (\mathit{inj}_{r_2 \backslash x}\ v_2) & v = \mathit{Right}\ v_2
  \end{cases}
  &&\begin{array}{l}(\mathsf{I}_{+}^{L}) \\ (\mathsf{I}_{+}^{R})\end{array} \\
\mathit{inj}_{x \backslash x}() &= x &&(\mathsf{I}_{\mathrm{lit}})
\end{aligned}
\end{equation}
The three-way $(r_1 r_2)$ case is worth reading against the derivative
rule it inverts (Section~\ref{sec:brzozowski-derivatives}): $(r_1 r_2)
\backslash x$ produced either $(r_1 \backslash x) r_2$ alone (when $r_1$
is not nullable) or that same term joined with $r_2 \backslash x$ via
$+$ (when it is), tagged $\mathit{Left}$/$\mathit{Right}$ respectively
by the $\mathit{Alt}$ this new $+$ introduces. $\mathit{inj}$ undoes
exactly that tagging. A bare pair means $r_1$ was not nullable and the
derivative went straight into it; a $\mathit{Left}$-tagged pair means it
was nullable but the derivative still chose to continue matching $r_1$;
a $\mathit{Right}$-tagged value means the derivative instead jumped
straight into $r_2$, so $r_1$'s own contribution to the reconstructed
pair has to be synthesized fresh via $\mathit{mkEps}_{r_1}$, since no
part of it was consumed by $x$ at all.

Parsing is then this two-phase process packaged into one function,
applying $\mathit{mkEps}$ once at the end of the forward pass and
$\mathit{inj}$ once per character on the way back:
\begin{equation}\label{eq:parse}
\begin{aligned}
\mathit{parse}(r, \varepsilon) &= \mathit{mkEps}_r
  \qquad (\text{if } \varepsilon \in L(r)) \\
\mathit{parse}(r, xw) &= \mathit{inj}_{r \backslash x}(\mathit{parse}(r \backslash x, w))
\end{aligned}
\end{equation}

\paragraph{The worked example, one step at a time.} Return to
$r_1 = (a+ab)(b+\varepsilon)$ against $\mathtt{ab}$, whose two candidate
parse trees were already established in
Section~\ref{sec:disambiguation-problem}. The forward pass computes
\begin{equation}\label{eq:dp-4}
\begin{aligned}
r_1 &\xrightarrow{\ a\ } (\varepsilon+\varepsilon b)(b+\varepsilon)
    &&\mathsf{D}_{\mathrm{seq}},\ r = a+ab,\ s = b+\varepsilon,\ n(r) = \mathrm{false} \\
    &\xrightarrow{\ b\ } (\phi+(\phi b+\varepsilon))(b+\varepsilon)
       + (\varepsilon+\phi)
    &&\mathsf{D}_{\mathrm{seq}}^{\,n},\ r = \varepsilon+\varepsilon b,\ n(r) = \mathrm{true}
\end{aligned}
\end{equation}
The two steps take different cases of the same rule, and the reason is
the binding: after one character the left operand has become
$\varepsilon+\varepsilon b$, which is nullable by $\mathsf{N}_{+}$ and
$\mathsf{N}_{\varepsilon}$, where the original $a+ab$ was not. That is
what adds the second summand $(\varepsilon+\phi)$, and it is that
summand which makes the whole expression nullable. The trace's second
forward step confirms the rule taken and shows the expression that the
hand derivation abbreviates:
\begin{verbatim}
Step 2: d(r1, 'b')
  rule: d(r1.r2, 'b')  [nullable(r1)=true]
       = d(r1, 'b').r2  +  d(r2, 'b')
r2 = Alt(Seq(Alt(Phi, Alt(Seq(Phi, Lit('b')), Eps)), Alt(Lit('b'),
  Eps)), Alt(Eps, Phi))
  nullable(r2) = true  [OK] position 2 matched
\end{verbatim}
This is the nullable-$r_1$ branch, the one that introduces a fresh
$\mathit{Alt}$, and it is that new $\mathit{Alt}$ whose two branches
$\mathit{mkEps}$ then chooses between. From $v_2$ the backward pass
runs two injections, each printed with the expression it injects into
and the value it produces:
\begin{verbatim}
inject(r1, 'b', v2):
  -> (Right ((), b), Right ())
v1 = (Right ((), b), Right ())

inject(r0, 'a', v1):
  -> (Right (a, b), Right ())
v0 = (Right (a, b), Right ())
\end{verbatim}
Reading the two lines together shows $\mathit{inj}$ doing its
characteristic work. At the first step the tree still contains
\texttt{()}, an empty-word placeholder where the literal $\mathtt{a}$
has not yet been reinserted; at the second, the \texttt{Lit} case
replaces it with \texttt{a}, and the result is a complete tree of
$r_1$ itself. The answer, $(\mathit{Right}(a,b), \mathit{Right}())$,
selects the \emph{longer} $ab$ branch, matching the POSIX result claimed
in Section~\ref{sec:posix-longest-leftmost} rather than Greedy's
$(\mathit{Left}\ a, \mathit{Left}\ b)$.

The report's header quantifies the cost of the two-pass shape in one
line:
\begin{verbatim}
Expressions stored:   3 (r0 -> r1 -> r2)
\end{verbatim}
one expression per input character plus the original, all of them live
until the backward pass has consumed them. That is exactly the
requirement Figure~\ref{fig:two-pass} draws, and exactly the one
Section~\ref{sec:bitcoded-optimization-theory} removes.






\section{Bit-Coded Optimization (Theory)}
\label{sec:bitcoded-optimization-theory}

The direct construction of Section~\ref{sec:core-algorithm} must retain
the whole forward-pass sequence, every $r_i$ from $r_0$ to $r_n$, or in
an implementation an equivalent call stack, so that $\mathit{inj}$ has
each $r_{i-1} \backslash x_i$ available to reconstruct against on the
way back: the backward pass cannot begin until the forward pass has
fully finished. Sulzmann and Lu's bit-coded construction (their
Section~3.2, "Incremental Bit-Coded Forward Parse Tree Construction")
\citep{sulzmannlu2014} removes this requirement by incrementally
building the parse tree \emph{during} the forward pass itself, so that
by the time the last character is consumed, the winning tree's
information is already sitting in the final expression, with no second
pass required. Figure~\ref{fig:single-pass} gives the resulting shape,
which is Figure~\ref{fig:two-pass} with the return journey removed.

\paragraph{Bit-code representation.} Rather than a \texttt{ParseTree}
value, a parse tree is represented as a flat sequence of bits: $0$ marks
a $\mathit{Left}$ choice, $1$ a $\mathit{Right}$ choice, and inside a
Kleene star, $0$ marks "one more iteration" and $1$ marks "stop". A pair
of mutually recursive functions $\mathit{encode}_r$/$\mathit{decode}_r$
convert between a $\vdash v : r$ parse tree and its bit-string
representation, structurally straightforward given the tagging already
present in $v$ itself.

The star convention is worth spelling out on a concrete case, since it
is the one place where a bit does not correspond to an alternation.
Under $r = a^{*}$, the word $\mathtt{aaa}$ encodes as $[0,0,0,1]$: three
$0$s, one per iteration taken, then a final $1$ ending the star. The
empty word under the same $r$ encodes as $[1]$ alone, a star that stops
immediately. So the bit-string length grows with the number of
iterations rather than with the size of $r$, and reading it back
requires knowing $r$, which is what $\mathit{decode}_r$ is given.

\paragraph{Annotated regular expressions.} The construction's core idea
is to annotate the derivative operation's own \emph{input}, not just its
output, with partial bit-code information, so that by the time a
sub-expression becomes $\varepsilon$ its accumulated annotation already
\emph{is} the relevant slice of the final bit-string. An annotated
regular expression $\mathit{ri}$ extends plain $r$ with a bit-list $bs$
attached at every node except $\emptyset$, which denotes no language and
so has no parse tree to annotate:
\begin{equation}\label{eq:aregex-grammar}
\mathit{ri} \;::=\; \emptyset \mid (bs@\varepsilon) \mid (bs@x) \mid
(bs@\mathit{ri}_1 \oplus \mathit{ri}_2) \mid (bs@\mathit{ri}_1\, \mathit{ri}_2)
\mid (bs@\mathit{ri}^{*})
\end{equation}
Two operations connect plain $r$ to this annotated world.
$\mathit{internalize}$ converts $r$ into $\mathit{ri}$ with every
bit-list initially empty, except at $\mathit{Alt}$: the left operand of
$r_1 + r_2$ is tagged with a leading $0$ and the right with a leading
$1$ at construction time, so that which alternative a sub-tree came from
can always be recovered from its own annotation without re-inspecting
the surrounding structure. $\mathit{fuse}(bs, \mathit{ri})$ prepends a
bit-list onto whatever annotation $\mathit{ri}$'s own top-most node
already carries, and is the one primitive every other operation in this
construction is built from.

The trace's \texttt{INTERNALIZE} section shows the result for $r_1$,
with the alternation tags already in place before any input is read:
\begin{verbatim}
ri0 = []@([]@([false]@'a' (+) [true]@([]@'a' . []@'b')) .
  []@([false]@'b' (+) [true]@epsilon))
\end{verbatim}
Reading the four tags off: \texttt{[false]} on $a$ and \texttt{[true]}
on $ab$ record the two alternatives of $a + ab$, and the same pair
appears again on $b$ and $\varepsilon$. Every other bit-list is empty.
Those four tags are the only bits the construction will ever emit for
this expression; everything the derivative does from here is a matter of
moving them, never of inventing new ones.

\paragraph{The refined derivative.} The ordinary derivative operation is
lifted to annotated expressions, written $\mathit{ri} \backslash_b l$,
following the same case structure as
Equation~\eqref{eq:derivative}'s $r \backslash l$ but threading bits
through instead of discarding the annotation:
\begin{equation}\label{eq:bderiv}
\begin{aligned}
(bs@\mathit{ri}_1 \oplus \mathit{ri}_2) \backslash_b l &=
  (bs@(\mathit{ri}_1 \backslash_b l) \oplus (\mathit{ri}_2 \backslash_b l))
  &&(\mathsf{B}_{+}) \\
(bs@\mathit{ri}_1\, \mathit{ri}_2) \backslash_b l &=
  \begin{cases}
    (bs@(\mathit{ri}_1 \backslash_b l)\, \mathit{ri}_2) \oplus
    \mathit{fuse}(\mathit{mkEpsBC}_{\mathit{ri}_1}, \mathit{ri}_2 \backslash_b l)
      & \varepsilon \in L(\mathit{ri}_1) \\
    (bs@(\mathit{ri}_1 \backslash_b l)\, \mathit{ri}_2) & \text{otherwise}
  \end{cases}
  &&\begin{array}{l}(\mathsf{B}_{\mathrm{seq}}^{\,n}) \\ (\mathsf{B}_{\mathrm{seq}})\end{array} \\
(bs@\mathit{ri}^{*}) \backslash_b l &= (bs@\mathit{fuse}([0], \mathit{ri} \backslash_b l)\; ([\,]@\mathit{ri}^{*}))
  &&(\mathsf{B}_{*})
\end{aligned}
\end{equation}
The concatenation case mirrors $(r_1 r_2) \backslash x$'s two-way split
exactly, with one addition: on the branch where $r_1$'s derivative is
abandoned in favor of jumping into $r_2$, the bits $r_1$ would have
contributed to an empty match ($\mathit{mkEpsBC}_{\mathit{ri}_1}$,
below) are fused directly onto $r_2$'s derivative rather than discarded.
This is the incremental step that replaces the direct construction's
\emph{later} call to $\mathit{mkEps}_{r_1}$ inside $\mathit{inj}$
(Section~\ref{sec:core-algorithm}) with work done immediately, during
the forward pass. The star case attaches a leading $0$ bit ("one more
iteration") each time the body is derived once more; the outer $bs$
stays where it is, on the new alternation or concatenation node the
derivative rule produces, exactly as it does for plain $\mathit{Alt}$.

\paragraph{mkEpsBC.} Mirroring Equation~\eqref{eq:mkeps}'s
$\mathit{mkEps}$ but returning accumulated bits instead of a tree:
\begin{equation}\label{eq:mkepsbc}
\begin{aligned}
\mathit{mkEpsBC}_{(bs@\varepsilon)} &= bs &&(\mathsf{EB}_{\varepsilon}) \\
\mathit{mkEpsBC}_{(bs@\mathit{ri}_1 \oplus \mathit{ri}_2)} &=
  bs \mathbin{+\!\!+} \begin{cases}
    \mathit{mkEpsBC}_{\mathit{ri}_1} & \varepsilon \in L(\mathit{ri}_1) \\
    \mathit{mkEpsBC}_{\mathit{ri}_2} & \text{otherwise}
  \end{cases}
  &&\begin{array}{l}(\mathsf{EB}_{+}^{L}) \\ (\mathsf{EB}_{+}^{R})\end{array} \\
\mathit{mkEpsBC}_{(bs@\mathit{ri}_1\, \mathit{ri}_2)} &=
  bs \mathbin{+\!\!+} \mathit{mkEpsBC}_{\mathit{ri}_1} \mathbin{+\!\!+} \mathit{mkEpsBC}_{\mathit{ri}_2}
  &&(\mathsf{EB}_{\mathrm{seq}}) \\
\mathit{mkEpsBC}_{(bs@\mathit{ri}^{*})} &= bs \mathbin{+\!\!+} [1] &&(\mathsf{EB}_{*})
\end{aligned}
\end{equation}
Once the forward pass ends on a nullable annotated expression,
$\mathit{mkEpsBC}$ extracts its complete bit-string directly, and
$\mathit{decode}_r$ turns that bit-string into an ordinary parse tree.
$\mathit{decode}$ uses the \emph{original}, un-annotated $r$, because it
needs to know the shape it is decoding bits \emph{for}, which the
annotated $\mathit{ri}$ alone no longer determines once its own
annotations have been consumed. That is the dashed dependency in
Figure~\ref{fig:single-pass}, and the only thing the construction still
has to remember from before the forward pass began.

\paragraph{The worked example, one step at a time.} Run
Section~\ref{sec:core-algorithm}'s $r_1$ against $\mathtt{ab}$ through
this construction instead, to see the same POSIX answer assembled
incrementally rather than reconstructed afterward. Starting from the
$\mathit{ri}_0$ quoted above, deriving with respect to $\mathtt{a}$
takes the Seq case's second branch, since the left operand
$[\,]@(0@a \oplus 1@ab)$ is not nullable:
\begin{verbatim}
Step 1 (char: 'a', position 1)
  rule: (bs@ri1.ri2) \ 'a'  [nullable_bc(ri1)=false]
       = bs@(ri1\'a'.ri2)
  simp -> []@([]@([false]@epsilon (+) [true]@'b') . []@([false]@'b'
    (+) [true]@epsilon))
\end{verbatim}
Comparing this against $\mathit{ri}_0$, the literal \texttt{'a'} has
become \texttt{epsilon} and \texttt{[]@'a' . []@'b'} has become
\texttt{'b'}, while both alternation tags stay exactly where they were.
Deriving one character has consumed structure and moved no bits.

$\mathit{ri}_1$'s left operand is now nullable, via
\texttt{[false]@epsilon}, so the second character takes the other branch
of the Seq case, and this is where bits finally move:
\begin{verbatim}
Step 2 (char: 'b', position 2)
  rule: (bs@ri1.ri2) \ 'b'  [nullable_bc(ri1)=true]
       = bs@((ri1\'b'.ri2) (+) (fuse (mkEpsBC ri1) (ri2\'b')))
  simp -> []@([true]@([false]@'b' (+) [true]@epsilon) (+) [false,
    false]@epsilon)
\end{verbatim}
Two things happened in that one step. The rule's \texttt{fuse (mkEpsBC
ri1)} produced the \texttt{[false, false]} prefix on the right disjunct:
the first \texttt{false} is $\mathit{ri}_1$'s own empty-match bit, the
second is $(b+\varepsilon)$'s left-alternative tag, fused in front of
it. And a \texttt{[true]} appeared on the left disjunct, tagging
"the derivative continued into the left operand" as the \emph{Right}
alternative of the freshly introduced node. Where $\mathit{inj}$
discovers that tagging only on the way back,
$\backslash_b$ must commit to it immediately, as part of the forward
pass.

Both disjuncts of $\mathit{ri}_2$ are nullable, so $\mathit{mkEpsBC}$
faces the same choice $\mathit{mkEps}$ faced in
Section~\ref{sec:core-algorithm}, and resolves it the same way, by
preferring the left disjunct whenever it is nullable at all:
\begin{equation}\label{eq:dp-7}
\begin{aligned}
\mathit{mkEpsBC}_{\mathit{ri}_2}
&= [\,] \mathbin{+\!\!+} \mathit{mkEpsBC}_{1@([\,]@(0@b\oplus 1@\varepsilon))}
&&\mathsf{EB}_{+}^{L},\ bs = [\,] \\
&= [1] \mathbin{+\!\!+} \big([\,] \mathbin{+\!\!+} \mathit{mkEpsBC}_{1@\varepsilon}\big)
&&\mathsf{EB}_{+}^{R},\ bs = [1] \\
&= [1] \mathbin{+\!\!+} [1] \;=\; [1,1]
&&\mathsf{EB}_{\varepsilon},\ bs = [1]
\end{aligned}
\end{equation}
The outer step takes $\mathsf{EB}_{+}^{L}$ and the inner one
$\mathsf{EB}_{+}^{R}$, for the same reason in both cases: the rule tests
only whether its own $\mathit{ri}_1$ is nullable. At the outer node
$\mathit{ri}_1$ is the $1@(\ldots)$ disjunct, which is; at the inner
node $\mathit{ri}_1$ is $0@b$, a bare literal, which is not, so the
right branch is taken and contributes the second $1$.
which the trace confirms, together with the decode that follows:
\begin{verbatim}
mkEpsBC(ri2) = [11]

decode((a|ab)(b|), [11]):
  = (Right (a, b), Right ())
\end{verbatim}
Both constructions therefore encode "prefer continuing the match already
in progress over falling back to the shorter alternative", just applied
at different points: in $\mathit{inj}$'s backward pass there, and
directly inside $\mathit{mkEpsBC}$'s forward-accumulated bits here. The
two bits select $\mathit{Right}$ at both alternation points of $r_1$,
which is the tree Section~\ref{sec:core-algorithm}'s worked example
reached via its explicit backward pass, read this time straight off the
forward pass alone.

\emph{On simplification between steps.} Section~\ref{sec:core-algorithm}
noted that the plain construction's forward pass must \emph{not}
simplify between steps, since the backward pass needs to walk back
through the exact sequence of derivatives that produced it. The
bit-coded construction has no such restriction, and both entry points in
\texttt{src/parsers/deriv\_bc/parse.rs} do call \texttt{simp} after every
step, which is why every trace excerpt above shows a \texttt{simp ->}
line rather than a raw derivative. This is safe here for the same reason
\texttt{fuse} is: the information a backward pass would otherwise need
to walk back for is already carried \emph{on} the annotated expression
itself, as bits attached to its nodes, so simplifying $\mathit{ri}_i$
down to a smaller but bit-equivalent expression loses nothing
$\mathit{mkEpsBC}$ needs later. In the plain construction, by contrast,
simplifying $r_i$ would destroy the very structure \texttt{inject} needs
to reconstruct against.



\section{Simplification Rules}
\label{sec:simplification-rules-theory}

Section~\ref{sec:brzozowski-derivatives}'s worked example already showed
plain derivatives growing an extra $+$ at every nullable-prefix step
with nothing to bound that growth, and the bit-coded construction
inherits the same problem. \citet{sulzmannlu2014} give the concrete case
\begin{equation}\label{eq:dp-8}
\begin{aligned}
a^{*} &\xrightarrow{\ a\ } \varepsilon a^{*}
      \xrightarrow{\ a\ } \phi a^{*} + \varepsilon a^{*} \\
      &\xrightarrow{\ a\ } (\phi a^{*} + \varepsilon a^{*})
        + (\phi a^{*} + \varepsilon a^{*})
      \xrightarrow{\ a\ } \cdots
\end{aligned}
\end{equation}
where every step after the first is language-equivalent to
$\varepsilon a^{*}$ but syntactically doubles in size. Left unchecked,
this defeats the whole point of the bit-coded construction's
incremental, single-pass promise: an unboundedly growing $\mathit{ri}$
makes each subsequent $\backslash_b$ step correspondingly more
expensive.

A simplification function $\mathit{simp}$, applied after every
derivative step, keeps the annotated expression's size bounded. Its
rules are Phi-propagation through $\mathit{Seq}$ and $\mathit{Alt}$,
epsilon-elimination
($(bs@(bs'@\varepsilon)\, \mathit{ri}) \to
\mathit{fuse}(bs \mathbin{+\!\!+} bs', \mathit{ri})$, folding the
eliminated node's own bits forward rather than discarding them), and
flattening and deduplicating nested alternations, keeping the first
occurrence of a syntactic duplicate. All of these are instances of the
familiar algebraic identities from
Section~\ref{sec:brzozowski-derivatives} ($\emptyset \cdot r =
\emptyset$, $\varepsilon \cdot r = r$, $\emptyset + r = r$, $r + r =
r$), applied here to the annotated grammar and combined with an explicit
\emph{isPhi} test that recognizes "empty language" expressions built up
from these rules rather than only the literal $\emptyset$ constructor.

\paragraph{$\mathit{simp}$ on the paper's own example.} Applied to
$a^{*}$ against $\mathtt{aaa}$, $\mathit{simp}$ collapses every step
back down to a bit-annotated form of $a^{*}$ itself. The trace shows one
\texttt{simp} result per character, each a single star node whose
accumulated bit-prefix has grown by one $0$:
\begin{verbatim}
Step 1 ... simp -> [false]@([]@'a')*
Step 2 ... simp -> [false, false]@([]@'a')*
Step 3 ... simp -> [false, false, false]@([]@'a')*

mkEpsBC(ri3) = [0001]
decode(a*, [0001]):
  = [a, a, a]
\end{verbatim}
The expression stays at two nodes throughout while the bit-prefix grows
linearly, and the three $0$s plus $\mathit{mkEpsBC}$'s closing $1$ are
exactly the $[0,0,0,1]$ encoding of "three iterations, then stop" from
Section~\ref{sec:bitcoded-optimization-theory}. This is the clearest
single illustration of what the bit-coded construction is for: all of
the parse-tree information is in the prefix, and none of it is in the
expression.

\paragraph{Where $\mathit{simp}$ does not bound the growth.} This result
does not generalize to every expression, and it is worth being precise
about that rather than letting the $a^{*}$ case stand for the general
one. Figure~\ref{fig:simp-growth} measures node counts per derivative
step for two patterns, each with and without $\mathit{simp}$.

The two simplified series behave completely differently. For $a^{*}$ the
line is flat. For $(a+(b+ab))^{*}$ it is straight on a logarithmic axis,
which is to say exponential. Every two characters take the size $s$ to
$2s+1$ exactly, so $s+1$ doubles: from $35$ at step 4 the series runs
$71$, $143$, $287$, $575$, $1151$, $2303$ at step 16, and $36\,863$ at
step 24. The growth is therefore $\Theta(2^{n/2})$ in the input length,
not the bounded size the $a^{*}$ case suggests. The figures are unchanged if the
three-way alternation is grouped the other way, as $((a+b)+ab)^{*}$,
which is what the CLI spelling \texttt{"(a|b|ab)*"} parses to
(Section~\ref{sec:regex-syntax}); the growth depends on the pattern's
shape rather than on that grouping. Applying $\mathit{simp}$ repeatedly
to a genuine fixpoint changes nothing either: a single pass already
\emph{is} the fixpoint here, producing byte-identical expressions at
every step, so this is not a case of the implementation stopping too
early.

The mechanism is specific and easy to state. $\mathit{simp}$'s
deduplication rule discards an alternation branch only when it is
\emph{syntactically identical} to an earlier one, and an annotated
branch carries its bit-list as part of its syntax. Counting the
top-level alternation branches of $\mathit{simp}(\mathit{ri}_i)$ at each
step, and counting them again after erasing every annotation, separates
the two:

\begin{center}
\begin{tabular}{lrrrrrr}
\hline
Step & 2 & 4 & 6 & 8 & 10 & 12 \\
\hline
Branches & 2 & 4 & 8 & 16 & 32 & 64 \\
Distinct branches & 2 & 4 & 8 & 16 & 32 & 64 \\
Distinct ignoring bits & 1 & 1 & 1 & 1 & 1 & 1 \\
\hline
\end{tabular}
\end{center}

At every step, all of the branches are structurally the same
expression, differing only in the bits recording which route through the
alternation reached it, so the last row stays at $1$ while the first two
double. The $r + r = r$ rule never fires, because on annotated
expressions the two sides are not equal.

The bits are not redundant: each branch's annotation is a different
candidate parse tree, and $\mathit{mkEpsBC}$'s left-preference is what
eventually selects among them, so dropping duplicates on shape alone
would change which tree the parser returns rather than merely shrinking
the expression. That is why the rule is stated on full syntactic
equality in the first place, and why the growth here is a property of
the construction rather than a defect in this transcription of it.

Sulzmann and Lu claim, but do not fully prove, that the resulting
construction runs in time linear in the input, on the grounds that each
of $\backslash_b$, $\mathit{simp}$, $\mathit{fuse}$, $\mathit{mkEpsBC}$,
and \emph{isPhi} only ever recurses over sub-calls bounded by the
now-simplified expression's size, and they note explicitly that detailed
space-complexity estimates are left as future work
\citep{sulzmannlu2014}. Figure~\ref{fig:simp-growth} is one concrete
reason that gap matters: the argument's premise, that $\mathit{simp}$
keeps the expression small, holds for $a^{*}$ and fails for
$(a+(b+ab))^{*}$, and the linear-time claim rests on it.
Chapter~\ref{sec:evaluation} measures the resulting wall-clock behaviour
on both kinds of pattern, and
Section~\ref{sec:pathological-inputs} returns to this family
specifically.



\section{Rust Implementation}
\label{sec:derivative-parser-inj-rust}

Both parsers of this chapter are transcriptions of the equations above.
Each definition becomes one Rust function over the \texttt{Regex} or
\texttt{ARegex} enum, the case split of the equation becomes the arms of
a \texttt{match}, and the recursion becomes recursion; the mapping is
mechanical enough that reading the code against the equation adds nothing
the equation does not already say. Appendix~\ref{app:src-parsers} gives
the file-by-file correspondence. What is worth setting out here is the
short list of places where Rust forces a decision the specification does
not make.

\paragraph{Partial functions become panics.}
\label{sec:mk-eps-impl}
\label{sec:inject-impl}
$\mathit{mkEps}_r$ is defined only for nullable $r$: Equation~\eqref{eq:mkeps}
has no clause for $\phi$ or for a literal, because neither is ever
reached. Rust has no partial functions, so the transcription has to say
something, and it says this:

\begin{verbatim}
Regex::Lit(c) => panic!("mk_eps called on Lit('{}')", c),
Regex::Phi   => panic!("mk_eps called on Phi"),
\end{verbatim}

The panic is an assertion about the caller, not error handling. Every
call site establishes nullability before calling, so reaching either arm
would mean the invariant the backward pass rests on has already been
broken. \texttt{inject} makes the same move at a finer grain: a bare
\texttt{Pair} arriving where a nullable $r_1$ requires a tagged
\texttt{Left} or \texttt{Right} can only mean the tree handed in did not
come from that expression's own derivative sequence. The alternative in
both cases is to invent a plausible value and return it, and a wrong
parse tree that looks well formed is precisely what the agreement tests
of Chapter~\ref{sec:evaluation} could not detect: they would be comparing
two parsers that had each guessed.

\paragraph{Recursion or an explicit vector.}
\label{sec:recursive-vs-loop}
The two entry points of \texttt{deriv\_std} compute the same tree by
different means. The recursive one descends to
the end of the input and calls \texttt{inject} as the stack unwinds, so
the call stack \emph{is} the derivative sequence of
Figure~\ref{fig:two-pass}'s top row and nothing else stores it. The loop
one builds that sequence as an explicit \texttt{Vec<Regex>} going
forward, then walks it backward. The algorithm is identical; the two
differ only in where the top row is kept while the bottom row consumes
it. That is a resource decision, and in Rust it is a consequential one,
because a thread's stack is a fixed allocation while the heap is not:
the recursive entry point overflows on input the loop entry point
handles without difficulty. Section~\ref{sec:stack-depth} measures where
the difference begins.

\paragraph{Trees and their flattening.}
\label{sec:parsetree-and-flatten}
\texttt{ParseTree} (Section~\ref{sec:parse-trees-as-evidence}) is the one
representation every parser in this thesis produces, which is what lets
the agreement tests compare outputs directly. \texttt{flatten} is kept
separate from tree construction so that it can serve as an independent
check: it discards every tag and pair boundary and returns the
concatenated literals, so a successful parse of $w$ must flatten back to
$w$ whatever the disambiguation policy was. Every diagnostic report
prints the two next to each other for that reason.

\subsection{The Bit-Coded Parser}
\label{sec:derivative-parser-bitcoded-rust}

\paragraph{One extra field, and the traits that come with it.}
\label{sec:aregex-type}
\texttt{ARegex} is \texttt{Regex} with a \texttt{Vec<bool>} added to
every variant but $\phi$, which has no annotation slot. This is the only
point in the implementation where a plain \texttt{Regex} will not do,
since the whole purpose of the construction is to thread partial
parse-tree information through the expression as it is derived, and that
needs somewhere on every node to put it.

The two types then diverge in the traits they derive, and Rust makes
that divergence explicit rather than incidental. \texttt{Regex} derives
\texttt{Hash} because
Chapter~\ref{sec:partial-derivative-parser}'s deduplication uses it as a
\texttt{HashSet} key; \texttt{ARegex} does not, because
\texttt{deriv\_bc} never hashes an annotated expression. Its own
deduplication, inside \texttt{simp}, compares alternation branches
pairwise instead. A language deriving a fixed bundle of instances at once
would leave that difference implicit; here it is a visible fact about
which operations each type is expected to support.

\paragraph{Ownership makes the common case free.}
\label{sec:internalize-fuse}
\label{sec:deriv-bc}
\texttt{fuse(bs, ri)} prepends a bit-prefix to an expression's top-level
annotation, and it opens by handing the expression straight back when
there is nothing to prepend:

\begin{verbatim}
pub fn fuse(bs: &[bool], ri: ARegex) -> ARegex {
    if bs.is_empty() { return ri; }
    // ... otherwise rebuild the node with bs in front of its prefix
}
\end{verbatim}

Because \texttt{fuse} takes \texttt{ri} by value, that early return is a
move and not a copy: the expression is handed on untouched. \texttt{fuse}
runs on every \texttt{Seq} and \texttt{Star} step of every derivative and
the overwhelming majority of those calls carry an empty prefix, so the
check converts the common case from a node rebuild into nothing at all.

\paragraph{Decoding, and where a bad bit-string is caught.}
\label{sec:mk-eps-bc}
\label{sec:decode}
\texttt{decode} turns the original plain \texttt{Regex} plus a flat
\texttt{Vec<bool>} back into a \texttt{ParseTree}, consuming one bit per
alternation and one per star iteration. It takes the un-annotated
expression, not the derived one, which is the dashed dependency in
Figure~\ref{fig:single-pass} and the reason it is shared with
Chapter~\ref{sec:partial-derivative-parser}'s \texttt{pderiv\_bc}: that
parser arrives at a \texttt{(Regex, bits)} pair by an entirely different
route and needs the identical final step. \texttt{decode} asserts that no
bits remain once the expression has been walked, and panics on an
unexpected end of bits, which is the same invariant-assertion discipline
as \texttt{mk\_eps} and \texttt{inject}, applied at the other end of the
construction.


\section{Comparing the Two Constructions}
\label{sec:deriv-worked-example}

Sections~\ref{sec:core-algorithm} and
\ref{sec:bitcoded-optimization-theory} have now run the same expression
against the same input through both constructions, quoting each trace at
the point where it illustrated a rule. Setting the two reports against
each other as wholes makes the structural difference visible in one
view. The full reports are
Appendix~\ref{app:report-deriv-std-match} and
Appendix~\ref{app:report-deriv-bc-match}.

\begin{center}
\begin{tabular}{@{}lp{3.9cm}p{4.3cm}@{}}
\hline
& \texttt{deriv\_std} & \texttt{deriv\_bc} \\
\hline
Report sections & forward, nullability, backward & internalize, forward, nullability, decode \\[2pt]
Named intermediates & \texttt{r0 -> r1 -> r2} & \texttt{ri0 -> ri1 -> ri2} \\[2pt]
Retained at the end & all three & the last one only \\[2pt]
Tree-building calls & 1 \texttt{mkEps} \newline + 2 \texttt{inject} & 1 \texttt{mkEpsBC} \newline + 1 \texttt{decode} \\[2pt]
Simplification & none, by necessity & \texttt{simp} after every step \\[2pt]
Final answer & \multicolumn{2}{@{}l@{}}{\texttt{(Right (a, b), Right ())}} \\
\hline
\end{tabular}
\end{center}

The number of tree-building calls is the row that does not scale with
the input. \texttt{deriv\_std} needs one \texttt{inject} per character
and so grows with the input length; \texttt{deriv\_bc} needs exactly one
\texttt{mkEpsBC} and one \texttt{decode} no matter how long the input
is. That is the whole content of the optimization, and it is visible in
the reports as the difference between a \texttt{BACKWARD PASS} section
whose length depends on the input and a fixed-size \texttt{MKEEPSBC +
DECODE} section.

The final bits \texttt{[11]} and the final tree
\texttt{(Right (a, b), Right ())} encode the same answer in the two
representations, and the correspondence is exact: each \texttt{Right}
in the tree is a \texttt{1} in the bit-string, read in the order
\texttt{decode} walks the expression.

\paragraph{What happens on a failure.} Running the same $r_1$ against
$\mathtt{b}$, a string not in $L(r_1)$ since every derivation of $r_1$
must begin by matching $\mathtt{a}$, both parsers stop after one
derivative step and neither reaches a tree-building phase at all. What
each has in hand at that point differs, and the difference is
instructive:
\begin{verbatim}
deriv_std:  r1 = Seq(Alt(Phi, Seq(Phi, Lit('b'))), Alt(Lit('b'), Eps))
              nullable(r1) = false  [FAIL] position 1

deriv_bc:   simp -> phi
            ri1 = phi
              nullable_bc(ri1) = false  [FAIL]
\end{verbatim}
\texttt{deriv\_std}'s expression denotes the empty language but is not
syntactically \texttt{Phi}; it is a \texttt{Seq} whose left operand has
both alternatives dead. \texttt{deriv\_bc}'s \texttt{simp} collapses
exactly that expression all the way down to \texttt{phi}. This is the
single clearest illustration of what
Section~\ref{sec:simplification-rules-theory}'s \emph{isPhi} test adds
over plain \texttt{simplify}: recognizing an empty-language expression
that is not the literal $\emptyset$ constructor.

Both constructions then report the identical failure, character for
character:
\begin{verbatim}
Failure at position:  1 (1-indexed)
Found:                'b'
Expected:             'a'
  b
  ^
\end{verbatim}
The diagnostics layer's expected set is read directly off the
first-literal set of the expression at the point of failure, so it does
not depend on which construction produced that expression or on how much
simplification was applied to it. This is the general pattern for
failures across all four parsers in this thesis: the constructions
differ in what they build on a successful match, and agree on what they
report when there is nothing to build. The two full failure reports are
Appendix~\ref{app:report-deriv-std-nomatch} and
Appendix~\ref{app:report-deriv-bc-nomatch}.

\paragraph{Agreement between the three POSIX entry points.} The two
parsers of this chapter, together with \texttt{deriv\_std}'s loop
variant, are three separate routes to the same tree, so their outputs are
directly comparable. Running all three over 300
randomly generated expressions against 39 inputs each, 11\,700 cases in
total, they agree on every one, both on whether the input matched and on
the exact \texttt{ParseTree} returned when it did.
Section~\ref{sec:cross-implementation-equivalence} describes the
generator and the full test setup; what matters here is that the
bit-coded route and the inject route, which share no code beyond
\texttt{Regex} itself and \texttt{nullable}, are not observed to diverge
on any of them.
