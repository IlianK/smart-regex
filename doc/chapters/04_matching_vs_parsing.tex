\chapter{Matching versus Parsing}
\label{sec:matching-vs-parsing}

Chapter~\ref{sec:derivatives} established matching with a Boolean
answer: whether $w \in L(r)$. A matcher therefore answers only whether
the input is accepted by the regular expression. Parsing goes beyond
this membership question by identifying the derivation for the match.

This distinction is important because a regular expression can admit
more than one way of matching the same word. A parser must therefore
represent the choices made during a match. These choices can be
represented by \emph{parse trees}, which provide structured witnesses
for membership in the language.

%

\section{Matching Ambiguity}
\label{sec:matching-problem}

Consider the regular expression
\[
r = (a+ab)(b+\varepsilon)
\]
and the input word
\[
w = \mathtt{ab}.
\]

The matcher can establish that $w \in L(r)$ using the matching
procedures of Chapter~\ref{sec:derivatives}. There are, however, two
ways in which the match can be obtained. In the first, the left
subexpression matches $\mathtt{a}$ and the right subexpression matches
$\mathtt{b}$:
\[
\underbrace{a}_{a+ab}\;
\underbrace{b}_{b+\varepsilon}.
\]

In the second, the left subexpression matches the entire input and the
right subexpression matches the empty word:
\[
\underbrace{\mathtt{ab}}_{a+ab}\;
\underbrace{\varepsilon}_{b+\varepsilon},
\]

Both choices therefore establish the same membership result,
\[
\mathtt{ab} \in L\bigl((a+ab)(b+\varepsilon)\bigr),
\]
but assign the input differently to the subexpressions of $r$.
The Boolean result of matching does not distinguish these cases.

Parsing makes this additional structure explicit. A parser must represent
which alternatives were chosen and which parts of the input were
consumed by the corresponding subexpressions.
A \emph{parse tree} provides a structured witness for such a derivation,
recording the choices made by the expression and the corresponding
consumption of the input.

%

\section{Parse Trees as Matching Evidence}
\label{sec:parse-trees-as-evidence}

Sulzmann and Lu view regular expressions as types and parse trees as their
values \citep{sulzmannlu2014}. The judgment $\vdash v : r$ states that
$v$ is a valid parse tree for $r$ and records the structural choices made
when matching $r$:

\begin{equation}
\label{eq:typing-rules}
\begin{aligned}
\begin{aligned}
\vdash () : \varepsilon
&
\quad(\mathsf{T}_{\varepsilon})
\\[1.0em]
\dfrac{l \in \Sigma}{\vdash l : l}
&
\quad(\mathsf{T}_{\mathrm{lit}})
\\[1.4em]
\dfrac{\vdash v_1 : r_1 \qquad \vdash v_2 : r_2}
      {\vdash (v_1,v_2) : r_1 r_2}
&
\quad(\mathsf{T}_{\mathrm{seq}})
\end{aligned}
\qquad\qquad
\begin{aligned}
\dfrac{\vdash v_1 : r_1}
      {\vdash \mathit{Left}\ v_1 : r_1 + r_2}
&
\quad(\mathsf{T}_{+}^{L})
\\[1.4em]
\dfrac{\vdash v_2 : r_2}
      {\vdash \mathit{Right}\ v_2 : r_1 + r_2}
&
\quad(\mathsf{T}_{+}^{R})
\\[1.4em]
\dfrac{}{\vdash [\,] : r^{*}}
&
\quad(\mathsf{T}_{*}^{0})
\\[1.4em]
\dfrac{\vdash v : r \qquad \vdash vs : r^{*}}
      {\vdash (v:vs) : r^{*}}
&
\quad(\mathsf{T}_{*})
\end{aligned}
\end{aligned}
\end{equation}

The rules correspond to the constructors of regular
expressions. A concatenation uses a pair of parse trees, an alternation
records the chosen branch with a tagged injection, and a Kleene star
records its iterations as a list.

%

\paragraph{In Rust.}
The definitions above translate directly to Rust. Figure~\ref{fig:parsetree-enum}
shows the parse-tree type, with one variant for each constructor in
Equation~\eqref{eq:typing-rules}. The two star rules share a single
\texttt{Star} variant, represented by a \texttt{Vec}.

\begin{figure}[H]
\begin{verbatim}
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum ParseTree {
    Empty,                                 // ()
    Char(char),                            // l
    Pair(Box<ParseTree>, Box<ParseTree>),  // (v1, v2)
    Left(Box<ParseTree>),                  // Left v
    Right(Box<ParseTree>),                 // Right v
    Star(Vec<ParseTree>),                  // [v1, ..., vn]
}
\end{verbatim}
\caption{The parse-tree type (\texttt{types/tree.rs}). The variants
correspond to the constructors of Equation~\eqref{eq:typing-rules};
the two star rules share the \texttt{Star} variant.}
\label{fig:parsetree-enum}
\end{figure}

The correspondence is one to one except for the star case:
$\mathsf{T}_{\varepsilon}$, $\mathsf{T}_{\mathrm{lit}}$,
$\mathsf{T}_{\mathrm{seq}}$, $\mathsf{T}_{+}^{L}$, and
$\mathsf{T}_{+}^{R}$ correspond to \texttt{Empty}, \texttt{Char},
\texttt{Pair}, \texttt{Left}, and \texttt{Right}, respectively. The
empty and non-empty star rules are both represented by \texttt{Star},
with $[\,]$ represented by \texttt{Star(vec![])}.

The recursive variants use \texttt{Box<ParseTree>} because Rust requires
recursive types to have a statically known size. \texttt{Star} instead
uses \texttt{Vec<ParseTree>}, which already provides indirection through
a fixed-size vector handle.

\paragraph{Derived traits.}
\texttt{PartialEq} and \texttt{Eq} allow direct comparison of parse
trees, while \texttt{Hash} is omitted because parse trees are not used
as keys for deduplication.

%

The typing judgment describes the structure of a match, but a parse tree
must also be related to the word that it matches. For this purpose, they
define a \emph{flattening} function $\lvert v\rvert$ that maps a parse
tree to the word represented by its structure:

\begin{equation}
\label{eq:flatten}
\begin{aligned}
\begin{aligned}
\lvert ()\rvert
  &= \varepsilon,
\\
\lvert l\rvert
  &= l,
\\
\lvert [\,]\rvert
  &= \varepsilon
\end{aligned}
\qquad\qquad
\begin{aligned}
\lvert (v_1,v_2)\rvert
  &= \lvert v_1\rvert\lvert v_2\rvert,
\\
\lvert \mathit{Left}\ v\rvert
  &= \lvert v\rvert,
\\
\lvert \mathit{Right}\ v\rvert
  &= \lvert v\rvert,
\\
\lvert v:vs\rvert
  &= \lvert v\rvert\lvert vs\rvert.
\end{aligned}
\end{aligned}
\end{equation}

The flattening function connects parse trees to the language of a regular
expression:

\begin{equation}\label{eq:mvp-5}
L(r)
=
\{\,\lvert v\rvert \mid \vdash v : r\,\}.
\end{equation}

Thus, a parse tree $v$ provides a structured \emph{witness} for
membership in $L(r)$, recording both the match and the structural
choices by which $r$ produces the word.

%

\paragraph{In Rust.}
Flattening is implemented directly from Equation~\eqref{eq:flatten}:

\begin{figure}[H]
\begin{verbatim}
pub fn flatten(v: &ParseTree) -> String {
    match v {
        ParseTree::Empty       => String::new(),
        ParseTree::Char(c)     => c.to_string(),
        ParseTree::Pair(v1, v2) =>
            format!("{}{}", flatten(v1), flatten(v2)),
        ParseTree::Left(v)     => flatten(v),
        ParseTree::Right(v)    => flatten(v),
        ParseTree::Star(vs)    => vs.iter().map(flatten).collect(),
    }
}
\end{verbatim}
\caption{Flattening (\texttt{types/tree.rs}), corresponding to
Equation~\eqref{eq:flatten}.}
\label{fig:flatten-rust}
\end{figure}

The function takes \texttt{\&ParseTree} rather than consuming the tree,
so the same parse tree can be inspected, printed, and compared after
flattening. The star case similarly borrows its elements through
\texttt{vs.iter()}.

Keeping flattening separate from tree construction provides an
independent validation of a parse: a tree for $w$ must satisfy
$\lvert v\rvert=w$, as required by Equation~\eqref{eq:mvp-26}.

%

\paragraph{Unambiguous example.}
Consider $r = ab$ and $w = \mathtt{ab}$. The sequence rule requires a
parse tree for $a$ followed by a parse tree for $b$. Since each
subexpression is a literal, the literal rule gives the only possible
derivation:

\begin{equation}\label{eq:mvp-6}
\dfrac{
  \dfrac{a \in \Sigma}{\vdash a : a}\;(\mathsf{T}_{\mathrm{lit}})
  \qquad
  \dfrac{b \in \Sigma}{\vdash b : b}\;(\mathsf{T}_{\mathrm{lit}})
}{
  \vdash (a,b) : ab
}\;(\mathsf{T}_{\mathrm{seq}})
\end{equation}

The parse tree is $v=(a,b)$ and flattening recovers the
input word:
$\lvert (a,b)\rvert = \lvert a\rvert\,\lvert b\rvert
= \mathtt{a}\mathtt{b}$.

\section{Disambiguation Problem}
\label{sec:disambiguation-problem}

The typing judgment identifies all valid parse trees for a given regular
expression, while the flattening function determines which word each
tree represents. So for a regular expression $r$ and word $w$, a parse
result must satisfy:

\begin{equation}
\label{eq:mvp-26}
\vdash v : r
\qquad\text{and}\qquad
\lvert v\rvert = w.
\end{equation}

When several parse trees satisfy these conditions, the typing judgment
does not determine which one should be returned. A \emph{disambiguation
policy} specifies how this choice is made.
Two policies commonly considered in the literature are \emph{Greedy} and
\emph{POSIX}:

\begin{itemize}
  \item \emph{Greedy} resolves choices by the order in which the
  expression offers them, preferring the earlier alternative and
  preferring a further iteration to stopping, whatever each consumes
  \citep{frischcardelli2004}.

  \item \emph{POSIX} resolves choices by subpattern match length from left
  to right, with ties resolved by the expression order \citep{posix_ere}.
\end{itemize}

The precise definitions of these policies are given in the corresponding
literature; see \citet{frischcardelli2004} and \citet{sulzmannlu2014}
for formal treatments. Instead, the examples below
show how the policies distinguish between valid parse trees.

%

\paragraph{Ambiguity in concatenation.}
For
$r_1 = (a + ab)(b + \varepsilon)$ and $w = \mathtt{ab}$, there are two
possible matches, corresponding to two distinct parse trees.

The first consumes $\mathtt{ab}$ with the second alternative of $a+ab$
and then chooses $\varepsilon$:

\begin{equation}
\label{eq:mvp-7}
\dfrac{
  \dfrac{\vdash a : a \quad \vdash b : b}
        {\vdash (a,b) : ab}
}{
  \vdash \mathit{Right}(a,b) : a + ab
}
\quad
\dfrac{
  \vdash () : \varepsilon
}{
  \vdash \mathit{Right}() : b + \varepsilon
}
\quad\Rightarrow\quad
\vdash
\bigl(
  \mathit{Right}(a,b),
  \mathit{Right}()
\bigr)
:
(a+ab)(b+\varepsilon).
\end{equation}

Thus,

\begin{equation}
\label{eq:mvp-8}
v_1 =
\bigl(
  \mathit{Right}(a,b),
  \mathit{Right}()
\bigr),
\qquad
\lvert v_1\rvert = \mathtt{ab}.
\end{equation}

The second matches $\mathtt{a}$ and $\mathtt{b}$ using the first
alternatives of $a+ab$ and $b+\varepsilon$:

\begin{equation}
\label{eq:mvp-9}
\dfrac{\vdash a : a}
      {\vdash \mathit{Left}\ a : a + ab}
\quad
\dfrac{\vdash b : b}
      {\vdash \mathit{Left}\ b : b + \varepsilon}
\quad\Rightarrow\quad
\vdash
\bigl(
  \mathit{Left}\ a,
  \mathit{Left}\ b
\bigr)
:
(a+ab)(b+\varepsilon).
\end{equation}

Thus,

\begin{equation}
\label{eq:mvp-10}
v_1' =
\bigl(
  \mathit{Left}\ a,
  \mathit{Left}\ b
\bigr),
\qquad
\lvert v_1'\rvert = \mathtt{ab}.
\end{equation}

Hence $v_1 \neq v_1'$ are valid parse trees for the same expression and
word. POSIX selects $v_1$ because the leftmost subpattern matches the
longer string $\mathtt{ab}$, while Greedy selects $v_1'$ because its left
alternative comes first.

%

\paragraph{Ambiguity in repetition.}
A similar ambiguity arises from repetition. Consider
$r_2 = (a+b+ab)^{\ast}$ against $w=\mathtt{ab}$, with the alternation
nested as $a+(b+ab)$. The word can either be consumed by one iteration
using the $ab$ alternative or by two iterations consuming $\mathtt{a}$
and $\mathtt{b}$ separately.

The first match is

\begin{equation}
\label{eq:mvp-16}
\dfrac{
  \dfrac{
    \dfrac{\vdash a : a \quad \vdash b : b}
          {\vdash (a,b) : ab}
  }{
    \vdash \mathit{Right}(a,b) : b+ab
  }
}{
  \vdash \mathit{Right}\,\mathit{Right}(a,b) : a+(b+ab)
}
\quad\Rightarrow\quad
\vdash
[
  \mathit{Right}\,\mathit{Right}(a,b)
]
:
(a+(b+ab))^{\ast}.
\end{equation}

Thus,

\begin{equation}
\label{eq:mvp-17}
v_2 =
[
  \mathit{Right}\,\mathit{Right}(a,b)
],
\qquad
\lvert v_2\rvert = \mathtt{ab}.
\end{equation}

The second match uses two iterations:

\begin{equation}
\label{eq:mvp-18}
\begin{aligned}
\dfrac{\vdash a : a}
      {\vdash \mathit{Left}\ a : a+(b+ab)}
&\qquad
\dfrac{
  \dfrac{\vdash b : b}
        {\vdash \mathit{Left}\ b : b+ab}
}{
  \vdash \mathit{Right}\,\mathit{Left}\ b : a+(b+ab)
}
\\[1.2em]
&\qquad\qquad\Rightarrow\qquad
\vdash
[
  \mathit{Left}\ a,
  \mathit{Right}\,\mathit{Left}\ b
]
:
(a+(b+ab))^{\ast}.
\end{aligned}
\end{equation}

Thus,

\begin{equation}
\label{eq:mvp-19}
v_2' =
[
  \mathit{Left}\ a,
  \mathit{Right}\,\mathit{Left}\ b
],
\qquad
\lvert v_2'\rvert = \mathtt{ab}.
\end{equation}

Here POSIX selects the single-iteration tree $v_2$,
since the star's first iteration can match
both characters through the $ab$ alternative. Greedy selects the
two-iteration tree $v_2'$, since the alternative $a$ comes first and
consuming only $\mathtt{a}$ leaves $\mathtt{b}$ for a second iteration.

The examples show that the same regular expression and input can admit
multiple valid parse trees, with the selected tree depending on the
disambiguation policy. The next two chapters apply these ideas to
derivative-based parsing and compare the resulting parser implementations.
